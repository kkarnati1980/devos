# 0019 — Delegated gate rule, final form (gate integrity Part 4)

- **Status:** Accepted (runner A, 13 Nov 2026). The rule itself is KK's (12 Nov 2026, gate-integrity spec §3); this note records how it is applied.
- **Linear:** DEVOS-144 · Contract: `docs/modules/GI-4.md` · Amends ADR-0013 §2.

## Context
ADR-0013 §2 lets runner A approve G2–G4. KK's spec of 12 Nov 2026 requires that the approval rest on stored results the runner did not produce by judgement: the floor guard (Part 1), the pass rule (Part 2) and the merge-gate record (Part 3). Parts 1–3 are merged, so the rule moves from its interim form to its final form.

## Decision
1. Delegated approval of G2, G3 or G4 needs ADR-0013's four conditions plus three stored results: floor guard clean or validly disposed for every merged PR; a passing pass-rule result per module on its merged SHA; green CI and a Codex PASS on the same head SHA for every merged PR.
2. The decision is made by `scripts/gates/evaluate-gate.mjs` from a JSON manifest of those stored results, each with a link. Exit 0 approves, exit 1 pauses, exit 2 is never an approval. Any result without a link counts as missing.
3. A paused gate posts what is missing on the gate issue. Every other lane continues and build-ahead stays allowed. KK gets no card, because a technical gap is not his decision.
4. The approval comment is generated by the evaluator, so it always lists every condition with a link to each stored result.
5. Why a manifest and not a live GitHub/Linear reader: the stored results live in three systems (GitHub statuses, Linear comments, server-check statuses), and a pure evaluator over a manifest is deterministic and testable offline. Automatic manifest compilation is follow-up GI-4b.

## Rollback
Reverting returns the rule to the interim form (ADR-0013 §2, interim text of 12 Nov 2026), never to the form before 12 Nov.

## Proposed Decision Record row (for KK to confirm)

Any missing result pauses only that gate; other lanes continue.
