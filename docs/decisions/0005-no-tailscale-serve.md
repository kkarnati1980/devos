# ADR-0005 — No Tailscale Serve; tailnet reaches Docker ports via a UFW route rule

- **Status:** accepted (31 Oct 2026, Architect, under D10). Refines ADR-0003 (Tailscale stays; Serve is dropped).
- **Context:** M0.2 v1.0.0 fronted Coolify with Tailscale Serve on 443/6001/6002. Coolify's own containers publish the same ports on `0.0.0.0`. On reboot tailscaled bound `100.88.140.76:{443,6001,6002}` first and Docker failed: `failed to bind host port 0.0.0.0:6001/tcp: address already in use` (`coolify`), same for 443 (`coolify-proxy`). The panel was down until a manual `docker start`.
- **Decision:** No Tailscale Serve on the DevOS server. Add `ufw route allow in on tailscale0`. That ACCEPT sits in `ufw-user-forward`, which the M0.1 DOCKER-USER chain calls first, so traffic arriving on `tailscale0` reaches Docker-published ports and public traffic stays dropped. Coolify is used at `http://devos:8000`; realtime (6001) and terminal (6002) connect natively.
- **Consequences:** No port is shared between tailscaled and Docker, so the boot order no longer matters. Transport is plain HTTP inside the WireGuard-encrypted tailnet: confidentiality and peer authentication come from Tailscale, and browsers will label the page "Not secure". If browser-trusted HTTPS is wanted later (e.g. the P1 dashboard), use Serve on a port no container publishes, or `tailscale cert` with Traefik — decided then. Tailnet devices reach every published container port; acceptable because the tailnet contains only KK's devices.
