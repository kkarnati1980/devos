# ADR-0012 — Continuous-run mode for app builds (contract)

- **Linear:** DEVOS-76 · P2 (CR-a, CR-b) and P3–P4 (CR-c … CR-e) · unlaned (runner A) · High · critical-path
- **Source:** KK's requirement of 6 Nov 2026, recorded in DEVOS-76's description; continuous build runbook v1.0.1 §1 ("App builds by DevOS").
- **Applies:** ADR-0012 (`docs/decisions/0012-continuous-run-app-builds.md`), DV-FR-003 and DV-FR-012 (cards; work waits only on the cards it depends on), DV-FR-011 (KK approves `requirements.md` once), ADR-0006 (cards and grants through M2.3/M1.7 only), ADR-0011 §1, §2, §9, §10 (CSRF, escaped output, safe retries, backward-compatible migrations), ADR-0013 (runner decides technical design; one task = one PR), F1 (no secret values in a card), D1, D13.
- **Owned files:** this contract and the ADR. Each task sub-issue below names its own files; no sub-issue edits another lane's owned files, it calls their exported interfaces. CR-a changes M2.2 files (Lane A, same runner).

## Goal
An app DevOS builds runs 24/7 with KK touching it only at the **intake card** (requirements approval and pre-flight answers in one decision), at gates, and for stop-and-ask items. "Done when" (DEVOS-76): a throwaway app goes from intake to preview with KK touching it exactly twice (the intake card and the gate approval); a mid-build question arrives batched in the next report; a forced deadlock does not stop the other lanes; a budget stop pauses only that project; lanes run overnight.

Pure: no I/O, no model call, no change to `route.ts` or the pipeline.
- **CR-a2** (DEVOS-198): the API side: the additive migration, the intake card reason built from `preflightLine`, `preflightOpen`, answers on approval, the mode switch in `route.ts`. Covers AT2, AT3, AT4, AT6 and the card half of AT5 (no secret value in a raised reason).
- **CR-a2 design (runner decisions, 14 Nov 2026; built in DEVOS-198):**
  - **Migration** (additive, `packages/db/prisma/migrations/<ts>_continuous_run`): `project.continuous_run boolean NOT NULL DEFAULT false` then `SET DEFAULT true`, and `project.preflight_state text NOT NULL DEFAULT 'approved'` (CHECK `pending | approved | rejected`) then `SET DEFAULT 'pending'`. Existing rows keep `false` / `approved` (rule 2's backfill); rows inserted later, by old or new code, get `true` / `pending`. `requirements_doc.preflight jsonb NULL` holds that version's `PreflightItem[]`, so approval reads the exact list KK saw. New table `project_decision` (columns as in rule 3, index on `project_id, item_id, created_at`). Why columns and not a new table for the state: one row per project, read on every task start (CR-c), no join.
  - **Pipeline** (`packages/analyst/src/pipeline.ts`, `route.ts`): the store's `project()` row gains `continuousRun` and `capUsd` (read in the same call, so no second read can fail separately; absent = off), and a port `secretNames(projectId)` gives the S5 names (absent = none). In the mode, `submit` builds the items with `buildPreflight`, stores them with the doc, sets `preflight_state` `pending` in the same store call, appends `preflightLine(items, 2000 − base.length − 1)` to the requirements card reason (base = today's lines, so the action and target are unchanged), and calls `raiseQuestionCards` with the technical routing only (non-technical questions are pre-flight items). Off: unchanged.
  - **Approval** (`applyDecision` with KK's comments, passed by `syncApproval` from `ApprovalStore.comments`; `preflightDecisions` lives in `packages/analyst/src/preflight.ts`): on `approved`, in one store transaction: approve the doc, parse KK's decision comment (`^PF-(\d+):\s*(.+)$` per line; unknown ids and `secret` items ignored), write one `project_decision` row per `decision` item (`kk` or `default`), set `preflight_state` `approved`. On `rejected`: `preflight_state` `rejected`. Idempotent: a second sync of the same card writes nothing (rows keyed by `approval_id, item_id`, unique).
  - **Card fallback** (pre-review finding 1): the pre-flight line carries spec-derived question text, which M2.3's `looksSecret` can refuse (`card-contains-secret`) or reject (`invalid-input`). `ensureCardFor` then retries once with `withholdPreflightText`: every spec-derived question text becomes "question text withheld …, see the project page"; the fixed budget and public-URL texts, the defaults and the secret names stay. Same rule as M2.2-c's `fallbackReason` for question cards. Off the mode the card has no spec text, so no retry.
  - **Unattended rejection** (pre-review finding 2): `draftsAwaitingDecision` also lists a newest draft whose intake card (with a pre-flight) was rejected while `preflight_state` is not yet `rejected`, so the sync job closes it without a page read; once `rejected` it drops out.
  - **Deferred** (pre-review findings 4 and 5): re-answers from a later KK comment (rule 3's last sentence) → DEVOS-204; system and probe projects created with the mode off before CR-c reads the state → DEVOS-205. CR-a2's answers are KK's comments read at the approval sync.
  - **DEVOS-205** (runner decision, 14 Nov 2026; built after CR-a2): system projects that never get an intake card are created with `continuous_run` false and `preflight_state` `approved` (today only the G1 probe, `packages/run-engine/src/g1-cli.ts` `PROBE_PROJECT_DATA`; a small change to an M1.x file, Lane A). An existing probe row still `pending` (created between CR-a2's migration and this change) is opened the same way on the next probe start; an `approved` row is not written (pre-review finding 1). Approving a doc without a pre-flight on a `pending` project sets `approved` (the doc approval is the whole intake decision there); the approval leaves `rejected` and `approved` as they are. Tested in memory (`pipeline.test.mjs`), on Postgres (`test-db/preflight.test.mjs`) and in `run-engine/test/g1.test.mjs` AT4. A mode-off project whose earlier intake card was rejected is re-opened by a new spec version → DEVOS-208.
  - **DEVOS-208** (runner decision, 14 Nov 2026): rule 4 also holds with the mode off. A new spec version without a pre-flight moves a `rejected` state to `pending` (conditional update under the same project lock; `approved` is not moved), and the doc approval then opens it as in DEVOS-205. Tested in memory (`pipeline.test.mjs`) and on Postgres (`test-db/preflight.test.mjs`).
  - **`preflightOpen(projectId)`** (`apps/api/src/preflight.ts`): reads `preflight_state` and the newest doc's secret items in one SQL statement (`preflightSnapshot`, one snapshot; Codex PR122-r2: two reads could pair an `approved` state with a newer, unapproved version's list), then `vault.hasProject(projectId, "preview/<NAME>")` for each; any read failure → false (fail closed).
- **DEVOS-204** (runner decisions, 14 Nov 2026): a later KK comment re-answers a pre-flight item (rule 3's last sentence).
  - **Deterministic window.** The approval sync counts only the card's comments created at or before `approval.decided_at` (the decide comment carries that time), whenever the sync runs. Comments after it are re-answers. Bound: a comment whose time is before the decision but which commits after the approval sync is not read (KK would have to post and decide within the same few seconds).
  - **Re-answers** (`preflightReanswers`, pure, `packages/analyst/src/preflight.ts`): start from the rows written with the approval; read the later comments oldest first; a `PF-<n>: <answer>` line for a `decision` item whose answer differs from its current answer gives one `kk` row and becomes the current answer (within one comment the last line for an id wins). Unchanged answers, unknown ids, `secret` items and other text give nothing. The same input always gives the same rows.
  - **Storage** (additive migration `20261114000400_preflight_reanswers`): `project_decision.comment_id uuid NULL` (FK to `approval_comment`, RESTRICT) with a unique (`comment_id`, `item_id`) index; a re-answer row has `comment_id` set and `approval_id` null, so the existing unique (`approval_id`, `item_id`) still guards the approval rows and a re-run of either is a no-op. `requirements_doc.answers_synced_at timestamptz NULL` is the re-answer cursor. Why a comment key and not "compare with the newest row": the rows are a function of the comments alone, so concurrent or repeated syncs cannot write a duplicate or depend on timing.
  - **Job.** `syncApproval` on a project whose newest doc is approved reads the card's comments and writes the re-answers (`RequirementsPipeline.applyReanswers`; store ports `approvalDecisions`, `recordReanswers`). The sync job also lists `reanswersAwaiting` (newest doc approved with a pre-flight, card approved, a comment newer than both the decision and the cursor), in its own batch of 100 so approvals and re-answers never starve each other. Only the settled comments are read: those older than the settle window, so every comment in that prefix has committed and a comment that commits late with an earlier time can never land before rows already written from a later one (Codex PR130-r1). The window is `reanswerSettleMs(bound)`: the approvals store's real write bound (`PrismaApprovalStore.stepBoundMs`, connection wait plus transaction, 2 × `DEVOS_OUTBOUND_TIMEOUT_MS`) plus a 5 s margin, never below 30 s (`REANSWER_SETTLE_MS`); `requirementsServices` builds it from the same bound `runtime.ts` passes for expiry, so at the 30 s timeout maximum it is 65 s (Codex PR130-r2). Younger comments wait for a later tick; the cursor moves forward only, to the newest settled comment.
  - **No pause.** Re-answers never touch `preflight_state`, any task or any card (rule 3).
  - **Project page.** CR-a3's decision log for the card (`decisions(projectId, approvalId)`) also returns the re-answer rows from that card's comments: the approval rows first, then the re-answers in comment order (`created_at`, `id`), so the panel's newest answer per item wins (pre-review finding 1: rows of one pass share `created_at`).
  - **Files** (Lane A): `packages/analyst/src/preflight.ts`, `pipeline.ts`, `memory-store.ts`, `index.ts`; `apps/api/src/requirements.ts`, `requirements-store.ts`, `requirements-sync.ts`; `packages/db/prisma/schema.prisma`, the migration, `packages/db/test-db/catalog.test.mjs`; tests `packages/analyst/test/preflight.test.mjs`, `pipeline.test.mjs`, `apps/api/test/requirements-sync.test.mjs`, `apps/api/test-db/preflight.test.mjs`.
  - **AT-RA (DEVOS-204):** after an approval recorded with `PF-1: yes`, a `PF-1: no` comment adds exactly one `kk` row for PF-1 (`comment_id` set); the earlier rows are unchanged; no other item gets a row; `preflight_state` stays `approved`; a re-run adds nothing; a comment made after the decision but before the approval sync is not counted by the approval. Covered in memory (`pipeline.test.mjs`, `requirements-sync.test.mjs`), pure (`preflight.test.mjs`) and on Postgres (`test-db/preflight.test.mjs`).
- **CR-a3** (DEVOS-199): the read-only pre-flight section on the dashboard project page ("waiting for secrets").
- **CR-a3 design (runner decisions, 14 Nov 2026; DEVOS-199):**
  - **API:** `GET /projects/by-slug/:slug/preflight` (session, read-only, ADR-0011 §1) in `apps/api/src/requirements.ts`, built on `preflightView` in `apps/api/src/preflight.ts`: `{ continuousRun, state, open, items, missingSecrets, secretsUnverified, decisions }`. By slug because the dashboard project page is addressed by slug and has no project id. The vault is asked only `hasProject` for `preview/<NAME>`; no vault or a vault error lists every name as missing with `secretsUnverified` true and `open` false (fail closed). Decision log: oldest first, at most 500 rows. 404 `project-not-found`; store faults → 500 `requirements-store-error`.
  - **Dashboard:** a client section `apps/dashboard/app/projects/[slug]/preflight-panel.tsx` reading that route through `DevosApi` (session like the approvals pages): the state, "waiting for secrets: <names>" when approved with names missing, each item with its default or KK's answer from the log. All text is rendered as React text (escaped, strict CSP unchanged). Signed out → a sign-in line; any error → a fixed message, never the error text.
  - **Answers per card** (Codex PR127-r1): `PF-<n>` numbers restart with every spec version, so the view shows only the decision rows recorded with the newest doc's intake card. `preflightSnapshot` returns that doc's `approvalId` from the same one-statement read, and `decisions(projectId, approvalId)` reads only that card's rows; a doc with no card yet shows no answers.
  - **Page wording:** advisory (pre-review F1 note): question text the intake card withheld as secret-looking is shown here in full, to KK's session only; that is the "see the project page" the card points to.

CR-b2b is the store side only: `apps/api/src/card-batch-store.ts` (`PrismaQueueStore`, `approvalBatchCards`, `prismaTaskProjects`), the migration `20261115000100_card_batch` and `apps/api/test-db/card-batch.test.mjs` (AT8b, the M2.3 half of AT11). `@devos/api` gains the dependencies `@devos/card-batch` and `pg` (8.23.1, MIT, already used by `@devos/provision`).
      - **CR-b2d** (DEVOS-218): `apps/api/src/card-batch-sync.ts` (`CardBatchJob`), wired in `runtime.ts` (`cardBatch`, `cardBatchQueue`) and started by `main.ts`. Unit tests in `apps/api/test/card-batch-sync.test.mjs` (memory stores). Adapted from the CR-b2b WIP branch `kishore/devos-215-cr-b2b-postgres` (runner A, 14 Nov), which the 15 Nov run replaced. Runner decisions:
        - One tick every 5 minutes; ticks never overlap. Each tick first applies the listed batches, at any time of day, then flushes (rule 8). Until CR-e moves the flush into the M4.6 daily report, the day's batches are claimed by **one** pass: the first tick at or after 08:00 IST whose list read (`projectsToFlush(istDay(now))`) succeeds. A question queued later that day waits for the next day's pass. Later ticks only retry batches still `raising`, or refused and not handed off (`projectsWithOpenBatch`). A restart repeats the pass, which claims nothing for a project that already has the day's batch. A project whose claim itself failed during the pass waits for the next day (pre-review CR-b2d r2).
        - The daily pass reads every page of eligible projects (100 a page, at most 50 pages) before the day counts as flushed (Codex PR143-r1). Pages are keyset-paginated: `projectsToFlush(day, limit, after)` orders by (`since`, `project_id`), returns each row's `since` as Postgres timestamp text (full precision), and lists only rows after `after`, the previous page's last row. So open batches still `raising` or refused (which stay eligible) cannot fill every page and hide a later project: 100 stuck batches and a 101st project with a queued question are both reached in one tick. The pass ends only at a short page; a pass cut by the page bound or a failed read stays open, and the next tick lists again from the start (Codex PR143-r2, which replaced the r1 "no project not yet seen" stop).
        - An `approved` or `rejected` apply logs each follow-up (`card-batch-follow-up`, keyed by question id, with the task count) and then calls `settle`. M3 cannot file tasks yet, so the log line is the follow-up for the Architect, and CR-c turns it into a task. A crash before `settle` repeats the log lines on the next tick: they are delivered at least once and never lost. A `not-ready` or `settled` apply does nothing.
        - A `refused` flush raises each member as its own `decision` card (target `question:<id>`). Before each raise the job looks the target up in any status (M2.3 list filter), so a retry never raises a member twice, even after KK decided its card, and never re-blocks tasks KK released (pre-review CR-b2d). Reading KK's answer back from a member card is **CR-b2e** (DEVOS-222, below); before it, a refused batch's questions kept only their `default-provisional` row (pre-review CR-b2d r2). Refusals are rare, because `check` refuses such questions at queue time. The hand-off runs outside the batch lock: with two API processes, a member card decided between their two lookups can be raised once more (the same bound as the CR-b2b lock drop; accepted).
          - **CR-b2e** (DEVOS-222), runner decisions:
            - The member card's reason is the question and its default, clipped so that the instruction always fits in M2.3's 2,000 characters: `To answer, comment "BQ-1: <your answer>", then approve. Approving without that line keeps the default; rejecting keeps the tasks stopped.` (`memberCardReason`).
            - Each tick, after the batch applies, the job applies approved member cards like a one-question batch: only comments up to `decidedAt` count (fail closed on a missing or invalid time, as `applyBatch`), the `BQ-1:` line is KK's answer (`batchAnswers`), else the default. The final row is `Q-<id>` with `approval_id` = the member card, written once (`ON CONFLICT (approval_id, item_id) DO NOTHING`).
            - The store lists the work with one bounded read, `PrismaQueueStore.memberCardsToApply` (members of refused, handed-off batches whose `question:<id>` card in the same project is approved and has no `Q-<id>` row yet, oldest decision first, at most 100). The row's existence is the "applied" marker, so this needs no migration.
            - The follow-up line (`card-batch-follow-up`, an answer differing from the default) is logged before the row is written. A crash in between logs it again on the next tick (at least once, never lost; rule 7), and after the write the member is no longer listed, so a replay writes and logs nothing.
            - A rejected or expired member card writes nothing: M2.3 keeps its tasks blocked, as for a rejected batch card.
            - Pre-review CR-b2e: the final row is once per question, not per card. If two member cards exist for one question (the CR-b2d bound with two processes), only the first applied writes (`NOT EXISTS` on the project's `Q-<id>` final row, under a per-item advisory xact lock); the other is never listed again. Accepted (low): the follow-up line is computed from the comments read on that tick, not the stored row, so a repeat after a lost write could differ; comments after `decidedAt` never count, so it cannot in practice. A card skipped by the read-back checks would stay listed; the SQL filters make that unreachable today.
            - A card the job reads back must still be `approved`, have target `question:<id>` and belong to the question's project; otherwise it is skipped.
            - Tests: `apps/api/test/card-batch-sync.test.mjs` ("CR-b2e job"); the store's SQL was checked against local Postgres 16 (listed once, written once, then no longer listed).
          - A member whose tasks are missing or belong to another project is raised without blockers.
          - A member M2.3 refuses outright is logged (`card-batch-question-refused`).
          - `handOff` runs only when every member has been handled. A transient failure leaves the hand-off open for the next tick.
        - Failures are logged with fixed codes (`card-batch-list-failed`, `card-batch-apply-failed`, `card-batch-flush-failed`), never with the error message. A failed list skips only that half of the tick.
        - The agent-facing entry point is `cardBatchQueue` on the runtime. The first caller is M3.2's Builder (no HTTP route is added now).
        - Accepted (pre-review CR-b2d, low):
          - Before 08:00 IST the flush half does not run at all, so a `raising` batch or an open hand-off also waits until 08:00. Its questions keep their provisional defaults meanwhile (rule 7), so nothing is blocked; CR-e's move into the M4.6 report revisits the timing.
          - A batch whose apply or settle keeps failing is retried, and its follow-ups logged again, every tick. A failure that lasts is a database outage, which the health checks already report.
          - The follow-ups live in the logs until CR-c. They can always be rebuilt from `project_decision` (rows with source `kk` whose answer differs from the question's `default-provisional` row), and CR-c files them from there, not from the logs.
      - Runner decisions (CR-b2b):
        - Tables: `queued_question` (`default_answer` for the default, since `default` is a keyword; `blocks uuid[]`, at most 50; `batch_id` null until claimed) and `card_batch` (unique on `project_id, ist_day`; `state` CHECK `raising` with no card, `raised` with a card, `refused` with no card; `applied_at` only when raised, `settled_at` only after `applied_at`, `handed_off_at` only when refused). ## Interface (CR-a, CR-b)
- `PreflightItem = { id, kind: "decision" | "secret", text, options?: string[], default: string, blocks?: string[] }`. `id` is `PF-<n>` in order. A `secret` item carries the secret's **name** only (pattern `^[A-Z][A-Z0-9_]{1,63}$`), its default is `"enter in setup wizard"`, and it is never answered in the card.
- `buildPreflight(analysis, secretNames, envelope)`: `secretNames` is the list the caller derives from the S5 selection (empty until S5 exists); `envelope` is the project's M1.7 budget envelope. Deterministic for the same input. No model call.

The full list is a new read-only section on the dashboard project page (`apps/dashboard/app/projects/[slug]`), listed in CR-a's files when built.

## Behaviour
1. **One intake decision.** In continuous-run mode (`project.continuous_run` true, the default for app projects created after CR-a), the requirements card is the only intake card; M2.2-c's `raiseQuestionCards` is not called for non-technical questions (technical ones still go to the Architect log). With the mode off, M2.2 behaves exactly as today.
2. **The build waits for the intake card and the secrets.** While `preflightOpen` is false, no task of that project starts; other projects are unaffected. If the card is approved but a secret is missing, the project page shows "waiting for secrets: <names>" and no new card is raised (KK enters them in the setup wizard; the intake card already listed them). Projects that existed before CR-a's migration are backfilled `continuous_run` false and `preflight_state` `approved`, so nothing already running stops.
3. **Defaults.** On approval, every `decision` item KK did not answer takes its default. Each answer or default is one `project_decision` row (`project_id`, `item_id`, `text`, `answer`, `source` `kk` | `default` | `default-provisional`, `approval_id`, `created_at`). A later KK comment can change an answer; that writes a new row and never stops running work.
4. **Rejection.** A rejected intake card keeps `preflight_state` `rejected` and the build closed. The way forward is M2.2's existing one: KK uploads a new spec version, which raises a new requirements card with a fresh pre-flight; `preflight_state` returns to `pending`.
5. **No secret values.** A card reason or comment with a secret-shaped value is refused by M2.3 (`card-contains-secret`); CR-a never puts a value in a card.
6. **Batching is opt-in by allow-list.** `queueQuestion` accepts a question only when its gate is `decision` **and** its text hits none of the stop-and-ask words. Anything else is refused with `not-batchable` and the caller raises the card at once.
   - **One word list, shared with M2.2-c.** CR-b splits M2.2-c's `NON_TECHNICAL` list in `packages/analyst/src/route.ts` into exported groups without changing what it matches (the existing route tests pass unchanged): `MONEY_WORDS` (prices, budgets, costs, payments, billing, fees, charges, plans, tiers, free, revenue, refunds, discounts, and buying, renting or hiring anything: buy … sponsorship), `LEGAL_WORDS` (legal … vendors) and `DELETION_WORDS` (delete … restore), plus the rest. The queue's list is those three groups plus the D11/D13 words `copyright`, `copyleft`, `gpl`, `drm`, `circumvent`, `crack`, `reverse`, `malware`, `exploit`. A word added to a group later reaches both rules at once, so they cannot drift.
   - **Matching covers inflections.** Each listed word gives a stem: the word itself, and the word without a final `e` (`truncate` → `truncat`, `purchase` → `purchas`, `delete` → `delet`). A question hits when any of its words starts with a stem, case-insensitive (`truncating`, `purchasing`, `deletion`, `licensed`, `restoring` all hit). It also hits on `₹` or `$` anywhere.
   - Runner decisions (PR113-r4, r5): the caller cannot mark a question urgent or not; the queue decides, and it fails toward interrupting, because `CardInput` has no category field and no gate covers legal, D11 or D13. Stem matching over-matches (`plan` hits `planet`, `free` hits `frequency`); a false hit only costs an immediate card, while a miss would let a KK decision run on a provisional default.
7. **A queued question blocks only its tasks, and only through M2.3.** The queue never writes task states. Until the flush, the tasks in `blocks` keep running on the question's default (recorded as `source` `default-provisional` in `project_decision`). The batch card is raised with `raiseCard(input, { blocks })`, so M2.3's `task_blocker` rows hold those tasks, and only those, until it is decided (DV-FR-012). If KK's answer differs from the default, CR-b files a follow-up task for the affected work. Runner decision: M2.3 exports no block-without-card call, and the delay is at most one day.
8. **Flush: one batch per project per IST day, with a stable identity and membership.** A batch is a `card_batch` row (unique on `project_id, ist_day`), not M2.3's pending-card dedupe (which keys on the action and only sees pending cards). `flushBatch` runs in two steps:
   1. **Claim (one transaction).** If the project has a `raising` batch from any earlier attempt, it is retried as is (step 2) and nothing new is claimed. Otherwise, when questions with `batchId` null exist and no batch exists for today, it inserts today's row (`state` `raising`) and sets `batchId` on exactly those questions. Membership is now stored before any card exists; a question queued later never joins this batch.
   2. **Raise, serialized per batch.** Lookup, raise and record run as one critical section under a Postgres session advisory lock, `pg_try_advisory_lock(hashtext('devos:card-batch:' || batchId))`, taken on one dedicated connection before the lookup and released only after the record (the M2.4 step-runner pattern). A flush that cannot take the lock does nothing for that batch: the holder finishes it, or leaves it `raising` for the next flush. Inside the lock the flush first re-reads the `card_batch` row; if it is already `raised`, it stops. It then looks up an existing card by the batch's target (M2.3 store listing, with the filter DEVOS-190 adds), so a card created by an attempt that failed before recording it is recorded instead of raised again, even if it was already decided. Only when there is none is `raiseCard(input, { blocks })` called, with the batch's own members, action and target (`batch:<batchId>`), so every retry sends the same card. If it fails, the batch stays `raising` and is retried by the next flush, whatever the day. If it succeeds, the row becomes `raised` with the card id. A holder that crashes drops its connection, which releases the lock, and the next flush's lookup finds any card it created.
   Runner decision (PR113-r7): the claim transaction cannot hold a row lock across `raiseCard`, because M2.3 runs its own bounded transactions; a session advisory lock spans them, and `try` (not wait) means a second flush never queues behind a slow raise. M2.3's dedupe covers pending cards only, so this lock, not the dedupe, is what keeps a decided card from being raised twice.
   A day that already has a batch raises nothing more; its later questions wait for the next day. The queue is empty → nothing is claimed.
9. **Batch answers.** The card says: approve to apply the answers in your comment (`BQ-<n>: <answer>`; unanswered questions take their defaults); reject to stop that work. On approval, `applyBatch` records each answer or default as a `project_decision` row, and M2.3 releases the blocked tasks. On rejection nothing is re-raised: M2.3 keeps the rejected card's blockers (its existing rule), so those tasks stay blocked, the questions are closed with KK's comment, and the project page lists the stopped tasks. Runner decision: M2.3 has no blocker-transfer operation, and adding one would widen the approvals core; a rejection here means "do not do this work as planned", which is what M2.3's rule already does.
10. **Failure.** Covered by rule 8: a batch whose card was not recorded stays `raising` with its members and target fixed, and the next flush retries exactly that card; ADR-0011 §9 holds because the retry is deduped (pending) or looked up (decided).
