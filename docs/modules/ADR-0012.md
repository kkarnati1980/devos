## Goal
An app DevOS builds runs 24/7 with KK touching it only at the **intake card** (requirements approval and pre-flight answers in one decision), at gates, and for stop-and-ask items. "Done when" (DEVOS-76): a throwaway app goes from intake to preview with KK touching it exactly twice (the intake card and the gate approval); a mid-build question arrives batched in the next report; a forced deadlock does not stop the other lanes; a budget stop pauses only that project; lanes run overnight.

## Interface (CR-a, CR-b)
- `PreflightItem = { id, kind: "decision" | "secret", text, options?: string[], default: string, blocks?: string[] }`. `id` is `PF-<n>` in order. A `secret` item carries the secret's **name** only (pattern `^[A-Z][A-Z0-9_]{1,63}$`), its default is `"enter in setup wizard"`, and it is never answered in the card.
- `buildPreflight(analysis, selection, secretNames)`: one `decision` item per open question M2.2-c routes `non-technical` (spec-wide or with an `owner`; an owned item's `blocks` is its requirement key), with default `"build as written; the Architect proposes the criteria"` for a `missing-acceptance` question and the first option, or `"Architect decides"`, otherwise; one item per budget and public-URL choice; one `secret` item per name. Deterministic for the same input. No model call.
- Intake card (M2.2-d's existing `requirements` card, unchanged gate, action and target): its reason gains one line `Pre-flight: <n> questions, <m> secrets — PF-1: … (default: …); …`, cut to M2.3's 2,000-character limit; past the limit it ends with `+<k> more on the project page`. The full list is a new read-only section on the dashboard project page (`apps/dashboard/app/projects/[id]`), listed in CR-a's files when built.
- KK answers items in the card's comment as `PF-<n>: <answer>` lines; any other text in the comment is kept as a note.
- `preflightOpen(projectId)`: true only when `preflight_state` is `approved` **and** `vault.hasProject(projectId, "preview/<NAME>")` is true for every `secret` item.
- `QueuedQuestion = { id, projectId, text, source, default, blocks: string[], queuedAt, cardId: string | null }`. Batch card: gate `decision`, action `Answer <n> build questions for <project name>`, target `batch:<projectId>:<YYYY-MM-DD IST>`, reason one line per question `BQ-<n>: … (default: …)`.

## Behaviour
1. **One intake decision.** In continuous-run mode (`project.continuous_run` true, the default for app projects created after CR-a), the requirements card is the only intake card; M2.2-c's `raiseQuestionCards` is not called for non-technical questions (technical ones still go to the Architect log). With the mode off, M2.2 behaves exactly as today.
2. **The build waits for the intake card and the secrets.** While `preflightOpen` is false, no task of that project starts; other projects are unaffected. If the card is approved but a secret is missing, the project page shows "waiting for secrets: <names>" and no new card is raised (KK enters them in the setup wizard; the intake card already listed them). Projects that existed before CR-a's migration are backfilled `continuous_run` false and `preflight_state` `approved`, so nothing already running stops.
3. **Defaults.** On approval, every `decision` item KK did not answer takes its default. Each answer or default is one `project_decision` row (`project_id`, `item_id`, `text`, `answer`, `source` `kk` | `default`, `approval_id`, `created_at`). A later KK comment can change an answer; that writes a new row and never stops running work.
4. **Rejection.** A rejected intake card keeps `preflight_state` `rejected` and the build closed. The way forward is M2.2's existing one: KK uploads a new spec version, which raises a new requirements card with a fresh pre-flight; `preflight_state` returns to `pending`.
5. **No secret values.** A card reason or comment with a secret-shaped value is refused by M2.3 (`card-contains-secret`); CR-a never puts a value in a card.
6. **Batching is opt-in by allow-list.** `queueQuestion` accepts a question only when its gate is `decision` **and** its text matches none of the stop-and-ask words (legal, law, licen[cs]e, copyright, copyleft, GPL, contract, GDPR, privacy, DRM, reverse engineer, delete, purge, destroy, pay, spend, money, cost, budget, ₹, `$`), case-insensitive. Anything else is refused with `not-batchable` and the caller raises the card at once. Runner decision: the caller cannot mark a question urgent or not; the queue decides, and it fails toward interrupting, because `CardInput` has no category field and no gate covers legal, D11 or D13.
7. **A queued question blocks only its tasks.** `queueQuestion` sets each task in `blocks` to `blocked` at once (M2.3 task states); when the batch card is raised, its `task_blocker` rows hold them until it is decided. A task not named in `blocks` is never touched (DV-FR-012: unrelated work continues).
8. **Flush.** `flushBatch` raises one card per project per IST day from the questions with `cardId` null. If `raiseCard` returns a card that already existed (M2.3 dedupe), no question is marked and they stay for the next day's flush. Only questions listed in a newly created card's reason get its `cardId`. The queue is empty → nothing is raised.
9. **Batch answers.** On approval, `applyBatch` records each `BQ-<n>: <answer>` from KK's comment, or the question's default, as a `project_decision` row, and the blocked tasks become `ready`. On rejection, each question is raised as its own immediate card (KK wants to answer them one by one).
10. **Failure.** A failed `raiseCard` in `flushBatch` leaves the questions queued with `cardId` null (retried on the next flush; ADR-0011 §9: raising a deduped card is safe to retry).
