## Goal
An app DevOS builds runs 24/7 with KK touching it only at the pre-flight card, at gates and for stop-and-ask items. "Done when" (DEVOS-76): a throwaway app goes from intake to preview with KK touching it exactly twice (the pre-flight card and the gate approval); a mid-build question arrives batched in the next report; a forced deadlock does not stop the other lanes; a budget stop pauses only that project; lanes run overnight.

## Interface (CR-a, CR-b)
- `PreflightItem = { id, kind: "decision" | "secret", text, options?: string[], default: string }`. `id` is `PF-<n>` in order. A `secret` item carries the secret's **name** only (pattern `^[A-Z][A-Z0-9_]{1,63}$`), its default is `"enter in setup wizard"`, and it is never answered in the card.
- `buildPreflight(analysis, selection, secretNames)`: one `decision` item per open question M2.2-c routed `non-technical` that is spec-wide (no `owner`); one per budget and public-URL choice; one `secret` item per name. Deterministic for the same input. No model call.
- Card shape (M2.3): gate `decision`, action `Answer the pre-flight questions for <project name>`, target `preflight:<projectId>`, reason = the items as one numbered line each (`PF-1: … (default: …)`), cut to M2.3's 2,000-character limit; past the limit, the reason ends with `+<k> more on the project page` and the full list is on the project page.
- `QueuedQuestion = { id, projectId, text, source, queuedAt }`; `flushBatch` card: gate `decision`, action `Answer <n> build questions for <project name>`, target `batch:<projectId>:<YYYY-MM-DD IST>`.

## Behaviour
1. **One pre-flight card per project.** A second `raisePreflight` for the same project returns the pending card (M2.3 dedupe on `(project, gate, action, target)`); after it is decided, `raisePreflight` is refused with `preflight-decided`.
2. **The queue stays closed until decided.** While `preflight_state` is `pending` (or missing, for a project created after CR-a), `preflightOpen(projectId)` is false; other projects are unaffected. `approved` opens it; `rejected` keeps it closed and the project shows "pre-flight rejected" with KK's comment. The run engine has no task scheduler yet; CR-c makes the M1.5/M3.6 scheduler call `preflightOpen` before it starts any task of an app build (runner decision: the gate lives with the pre-flight state it reads, so the scheduler only reads one boolean). Projects that existed before CR-a's migration are backfilled `approved`, so nothing already running stops.
3. **Defaults.** On approval, every item KK did not answer in the card's comment takes its `default`, and each answer or default is written to the project's decision log with its source (`kk` or `default`).
4. **No secret values.** A card reason or comment with a secret-shaped value is refused by M2.3 (`card-contains-secret`); CR-a never puts a value in a card.
5. **Batching.** `queueQuestion` refuses gates `destructive_or_spend`, `purge`, `first_launch`, and any input tagged `legal`, `d11` or `d13` (`not-batchable`): those go to `raiseCard` at once. `flushBatch` is idempotent per project per IST day (dedupe on the target) and raises nothing when the queue is empty. A flushed question is marked with the card id and never sent twice.
6. **Failure.** A failed `raiseCard` in `flushBatch` leaves the questions queued (retried on the next flush, ADR-0011 §9: raising a deduped card is safe to retry).
