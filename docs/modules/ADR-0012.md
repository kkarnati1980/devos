## Goal
An app DevOS builds runs 24/7 with KK touching it only at the **intake card** (requirements approval and pre-flight answers in one decision), at gates, and for stop-and-ask items. "Done when" (DEVOS-76): a throwaway app goes from intake to preview with KK touching it exactly twice (the intake card and the gate approval); a mid-build question arrives batched in the next report; a forced deadlock does not stop the other lanes; a budget stop pauses only that project; lanes run overnight.

- **CR-a2 design (runner decisions, 14 Nov 2026; built in DEVOS-198):**
  - **Migration** (additive, `packages/db/prisma/migrations/<ts>_continuous_run`): `project.continuous_run boolean NOT NULL DEFAULT false` then `SET DEFAULT true`, and `project.preflight_state text NOT NULL DEFAULT 'approved'` (CHECK `pending | approved | rejected`) then `SET DEFAULT 'pending'`. Existing rows keep `false` / `approved` (rule 2's backfill); rows inserted later, by old or new code, get `true` / `pending`. `requirements_doc.preflight jsonb NULL` holds that version's `PreflightItem[]`, so approval reads the exact list KK saw. New table `project_decision` (columns as in rule 3, index on `project_id, item_id, created_at`).   - **Pipeline** (`packages/analyst/src/pipeline.ts`, `route.ts`): the store's `project()` row gains `continuousRun` and `capUsd` (read in the same call, so no second read can fail separately; absent = off), and a port `secretNames(projectId)` gives the S5 names (absent = none). In the mode, `submit` builds the items with `buildPreflight`, stores them with the doc, sets `preflight_state` `pending` in the same store call, appends `preflightLine(items, 2000 − base.length − 1)` to the requirements card reason (base = today's lines, so the action and target are unchanged), and calls `raiseQuestionCards` with the technical routing only (non-technical questions are pre-flight items). Off: unchanged.
  - **Approval** (`applyDecision` with KK's comments, passed by `syncApproval` from `ApprovalStore.comments`; `preflightDecisions` lives in `packages/analyst/src/preflight.ts`): on `approved`, in one store transaction: approve the doc, parse KK's decision comment (`^PF-(\d+):\s*(.+)$` per line; unknown ids and `secret` items ignored), write one `project_decision` row per `decision` item (`kk` or `default`), set `preflight_state` `approved`. On `rejected`: `preflight_state` `rejected`. Idempotent: a second sync of the same card writes nothing (rows keyed by `approval_id, item_id`, unique).
  - **Card fallback** (pre-review finding 1): the pre-flight line carries spec-derived question text, which M2.3's `looksSecret` can refuse (`card-contains-secret`) or reject (`invalid-input`). `ensureCardFor` then retries once with `withholdPreflightText`: every spec-derived question text becomes "question text withheld …, see the project page"; the fixed budget and public-URL texts, the defaults and the secret names stay. Same rule as M2.2-c's `fallbackReason` for question cards. Off the mode the card has no spec text, so no retry.
  - **Unattended rejection** (pre-review finding 2): `draftsAwaitingDecision` also lists a newest draft whose intake card (with a pre-flight) was rejected while `preflight_state` is not yet `rejected`, so the sync job closes it without a page read; once `rejected` it drops out.
  - **Deferred** (pre-review findings 4 and 5): re-answers from a later KK comment (rule 3's last sentence) → DEVOS-204; system and probe projects created with the mode off before CR-c reads the state → DEVOS-205. CR-a2's answers are KK's comments read at the approval sync.
  - **DEVOS-205** (runner decision, 14 Nov 2026; built after CR-a2): system projects that never get an intake card are created with `continuous_run` false and `preflight_state` `approved` (today only the G1 probe, `packages/run-engine/src/g1-cli.ts` `PROBE_PROJECT_DATA`; a small change to an M1.x file, Lane A). An existing probe row still `pending` (created between CR-a2's migration and this change) is opened the same way on the next probe start; an `approved` row is not written (pre-review finding 1). Approving a doc without a pre-flight on a `pending` project sets `approved` (the doc approval is the whole intake decision there); the approval leaves `rejected` and `approved` as they are. Tested in memory (`pipeline.test.mjs`), on Postgres (`test-db/preflight.test.mjs`) and in `run-engine/test/g1.test.mjs` AT4. A mode-off project whose earlier intake card was rejected is re-opened by a new spec version → DEVOS-208.
  - **DEVOS-208** (runner decision, 14 Nov 2026): rule 4 also holds with the mode off. A new spec version without a pre-flight moves a `rejected` state to `pending` (conditional update under the same project lock; `approved` is not moved), and the doc approval then opens it as in DEVOS-205. Tested in memory (`pipeline.test.mjs`) and on Postgres (`test-db/preflight.test.mjs`).
  - **`preflightOpen(projectId)`** (`apps/api/src/preflight.ts`): reads `preflight_state` and the newest doc's secret items in one SQL statement (`preflightSnapshot`, one snapshot; Codex PR122-r2: two reads could pair an `approved` state with a newer, unapproved version's list), then `vault.hasProject(projectId, "preview/<NAME>")` for each; any read failure → false (fail closed).

## Interface (CR-a, CR-b)
- `PreflightItem = { id, kind: "decision" | "secret", text, options?: string[], default: string, blocks?: string[] }`. `id` is `PF-<n>` in order. A `secret` item carries the secret's **name** only (pattern `^[A-Z][A-Z0-9_]{1,63}$`), its default is `"enter in setup wizard"`, and it is never answered in the card.
- `buildPreflight(analysis, secretNames, envelope)`: `secretNames` is the list the caller derives from the S5 selection (empty until S5 exists); `envelope` is the project's M1.7 budget envelope. One `decision` item per open question M2.2-c routes `non-technical` (spec-wide or with an `owner`; an owned item's `blocks` is its requirement key), with default `"build as written; the Architect proposes the criteria"` for a `missing-acceptance` question and the first option, or `"Architect decides"`, otherwise; then always one budget item (`Monthly spend cap for this project`, default the envelope's cap) and one public-URL item (`Should the preview be reachable on a public URL?`, options `no` / `yes`, default `no — tailnet only`); then one `secret` item per name. Deterministic for the same input. No model call.
- Intake card (M2.2-d's existing `requirements` card, unchanged gate, action and target): its reason gains one line `Pre-flight: <n> questions, <m> secrets — PF-1: … (default: …); …`, cut to M2.3's 2,000-character limit; past the limit it ends with `+<k> more on the project page`. The full list is a new read-only section on the dashboard project page (`apps/dashboard/app/projects/[slug]`), listed in CR-a's files when built.
- KK answers items in the card's comment as `PF-<n>: <answer>` lines; any other text in the comment is kept as a note.
- `preflightOpen(projectId)`: true only when `preflight_state` is `approved` **and** `vault.hasProject(projectId, "preview/<NAME>")` is true for every `secret` item.
- `QueuedQuestion = { id, projectId, text (1–1,000 characters, one line), source, default (1–200), blocks: string[], queuedAt, batchId: string | null }`. `CardBatch = { id, projectId, istDay, state: "raising" | "raised", cardId: string | null }`. Batch card: gate `decision`, action `Answer the build questions for <project name>` (no count, so a retry has the same action), target `batch:<batchId>` (stable across days), reason `<n> questions` then one line per question `BQ-<n>: <text> (default: <default>)`, each line clipped to 200 characters; past M2.3's 2,000-character limit the reason ends with `+<k> more on the project page`, and the full batch is listed on the project page.

## Behaviour
1. **One intake decision.** In continuous-run mode (`project.continuous_run` true, the default for app projects created after CR-a), the requirements card is the only intake card; M2.2-c's `raiseQuestionCards` is not called for non-technical questions (technical ones still go to the Architect log). With the mode off, M2.2 behaves exactly as today.
2. **The build waits for the intake card and the secrets.** While `preflightOpen` is false, no task of that project starts; other projects are unaffected. If the card is approved but a secret is missing, the project page shows "waiting for secrets: <names>" and no new card is raised (KK enters them in the setup wizard; the intake card already listed them). Projects that existed before CR-a's migration are backfilled `continuous_run` false and `preflight_state` `approved`, so nothing already running stops.
3. **Defaults.** On approval, every `decision` item KK did not answer takes its default. Each answer or default is one `project_decision` row (`project_id`, `item_id`, `text`, `answer`, `source` `kk` | `default` | `default-provisional`, `approval_id`, `created_at`). A later KK comment can change an answer; that writes a new row and never stops running work.
4. **Rejection.** A rejected intake card keeps `preflight_state` `rejected` and the build closed. The way forward is M2.2's existing one: KK uploads a new spec version, which raises a new requirements card with a fresh pre-flight; `preflight_state` returns to `pending`.
5. **No secret values.** A card reason or comment with a secret-shaped value is refused by M2.3 (`card-contains-secret`); CR-a never puts a value in a card.
6. **Batching is opt-in by allow-list.** `queueQuestion` accepts a question only when its gate is `decision` **and** its text hits none of the stop-and-ask words. Anything else is refused with `not-batchable` and the caller raises the card at once.
   - **One word list, shared with M2.2-c.** CR-b splits M2.2-c's `NON_TECHNICAL` list in `packages/analyst/src/route.ts` into exported groups without changing what it matches (the existing route tests pass unchanged): `MONEY_WORDS` (prices, budgets, costs, payments, billing, fees, charges, plans, tiers, free, revenue, refunds, discounts, and buying, renting or hiring anything: buy … sponsorship), `LEGAL_WORDS` (legal … vendors) and `DELETION_WORDS` (delete … restore), plus the rest. The queue's list is those three groups plus the D11/D13 words `copyright`, `copyleft`, `gpl`, `drm`, `circumvent`, `crack`, `reverse`, `malware`, `exploit`. A word added to a group later reaches both rules at once, so they cannot drift.
   - **Matching covers inflections.** Each listed word gives a stem: the word itself, and the word without a final `e` (`truncate` → `truncat`, `purchase` → `purchas`, `delete` → `delet`). A question hits when any of its words starts with a stem, case-insensitive (`truncating`, `purchasing`, `deletion`, `licensed`, `restoring` all hit). It also hits on `₹` or `$` anywhere.
   - Runner decisions (PR113-r4, r5): the caller cannot mark a question urgent or not; the queue decides, and it fails toward interrupting, because `CardInput` has no category field and no gate covers legal, D11 or D13. Stem matching over-matches (`plan` hits `planet`, `free` hits `frequency`); a false hit only costs an immediate card, while a miss would let a KK decision run on a provisional default.
7. **A queued question blocks only its tasks, and only through M2.3.** The queue never writes task states. Until the flush, the tasks in `blocks` keep running on the question's default (recorded as `source` `default-provisional` in `project_decision`). The batch card is raised with `raiseCard(input, { blocks })`, so M2.3's `task_blocker` rows hold those tasks, and only those, until it is decided (DV-FR-012). If KK's answer differs from the default, CR-b files a follow-up task for the affected work. Runner decision: M2.3 exports no block-without-card call, and the delay is at most one day.
8. **Flush: one batch per project per IST day, with a stable identity and membership.** A batch is a `card_batch` row (unique on `project_id, ist_day`), not M2.3's pending-card dedupe (which keys on the action and only sees pending cards). `flushBatch` runs in two steps:
   1. **Claim (one transaction).** If the project has a `raising` batch from any earlier attempt, it is retried as is (step 2) and nothing new is claimed. Otherwise, when questions with `batchId` null exist and no batch exists for today, it inserts today's row (`state` `raising`) and sets `batchId` on exactly those questions. Membership is now stored before any card exists; a question queued later never joins this batch.
   2. **Raise, serialized per batch.** Lookup, raise and record run as one critical section under a Postgres session advisory lock, `pg_try_advisory_lock(hashtext('devos:card-batch:' || batchId))`, taken on one dedicated connection before the lookup and released only after the record (the M2.4 step-runner pattern). A flush that cannot take the lock does nothing for that batch: the holder finishes it, or leaves it `raising` for the next flush. Inside the lock the flush first re-reads the `card_batch` row; if it is already `raised`, it stops. It then looks up an existing card by the batch's target (M2.3 store listing, with the filter DEVOS-190 adds), so a card created by an attempt that failed before recording it is recorded instead of raised again, even if it was already decided. Only when there is none is `raiseCard(input, { blocks })` called, with the batch's own members, action and target (`batch:<batchId>`), so every retry sends the same card. If it fails, the batch stays `raising` and is retried by the next flush, whatever the day. If it succeeds, the row becomes `raised` with the card id. A holder that crashes drops its connection, which releases the lock, and the next flush's lookup finds any card it created.
   Runner decision (PR113-r7): the claim transaction cannot hold a row lock across `raiseCard`, because M2.3 runs its own bounded transactions; a session advisory lock spans them, and `try` (not wait) means a second flush never queues behind a slow raise. M2.3's dedupe covers pending cards only, so this lock, not the dedupe, is what keeps a decided card from being raised twice.
   A day that already has a batch raises nothing more; its later questions wait for the next day. The queue is empty → nothing is claimed.
9. **Batch answers.** The card says: approve to apply the answers in your comment (`BQ-<n>: <answer>`; unanswered questions take their defaults); reject to stop that work. On approval, `applyBatch` records each answer or default as a `project_decision` row, and M2.3 releases the blocked tasks. On rejection nothing is re-raised: M2.3 keeps the rejected card's blockers (its existing rule), so those tasks stay blocked, the questions are closed with KK's comment, and the project page lists the stopped tasks. Runner decision: M2.3 has no blocker-transfer operation, and adding one would widen the approvals core; a rejection here means "do not do this work as planned", which is what M2.3's rule already does.
10. **Failure.** Covered by rule 8: a batch whose card was not recorded stays `raising` with its members and target fixed, and the next flush retries exactly that card; ADR-0011 §9 holds because the retry is deduped (pending) or looked up (decided).
