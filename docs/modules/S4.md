## Goal
"Done when" (DEVOS-65), seen **from inside a project container**:
1. Coolify (8000/6001/6002), SSH (22), the DevOS API and dashboard, another project's containers and database, and cloud metadata (169.254.169.254) are unreachable.
2. Tailnet addresses (100.64.0.0/10, `fd7a:115c:a1e0::/48`) are unreachable unless declared.
3. Internet egress works only if declared.
4. CPU, memory and pid limits are visible in `docker inspect`.

## Design decisions (builder, recorded per ADR-0013)
1. **One address pool, one subnet per stack.** Every project stack (preview, live) runs on its own user-defined bridge network `devos-p-<slug>-<env>` with a fixed subnet from the pool `10.210.0.0/16` (IPv4, a /24 each — pool and index range amended by S4-b decision 1 to `10.208.0.0/14`, 0–1023 — index = the stack's port offset from M2.4 decision 1, so allocation is already unique and stable) and IPv6 disabled on that network. Coolify's shared `coolify` network is never attached to a project service. Docker's default bridge is never used. Why a fixed pool: host rules can then match "any project" with one CIDR and "this project" with one /24, without per-container rules that go stale.
2. **Generic host rules, small per-project state.** The host firewall is a static block that does not change per project:
   - `DOCKER-USER` (forwarded traffic): from `10.210.0.0/16` → drop to `10.210.0.0/16` unless same /24 (other projects), drop to every other private range (172.16/12 incl. `coolify` and the DevOS stack, 192.168/16, 10/8), drop to 100.64.0.0/10 and 169.254.0.0/16 unless the destination is in the ipset `devos-tailnet-<idx>`; internet egress is accepted only when the source /24 is in the ipset `devos-egress`; everything else from the pool is dropped. Replies (`ESTABLISHED,RELATED`) pass as in M0.1.
   - `INPUT` (traffic to the host itself — this is how a container would reach SSH, Coolify's published ports and the DevOS API on the host): from `10.210.0.0/16` → accept only DNS to the network gateway (53/udp+tcp) and drop the rest. M0.1/M0.2 allow private sources and `tailscale0` to SSH; without this rule a container could reach SSH.
   - The block lives in its own chains (`DEVOS-ISO-FWD`, `DEVOS-ISO-IN`), jumped to first from `DOCKER-USER` and `ufw-before-input`, and is written through `/etc/ufw/after.rules` + `before.rules` markers like M0.1, so it survives reboot and `ufw reload`. IPv6: project networks have no IPv6, and `ip6tables` gets the matching drop for `fd00::/8` sources not on the `coolify` network (defence in depth).
   Per-project state is only ipset membership (`devos-egress`, `devos-tailnet-<idx>`), not rules.
3. **Who decides "declared".** Egress and tailnet declarations come from the project's **approved** selection in the DevOS DB (M2.3 approval card; default: no egress, no tailnet), never from the project repo, a PR or anything an agent wrote. The host reads them from a file `/root/.devos/isolation/state.json` that DevOS writes through a narrow Coolify-free path: the API exposes `GET /internal/isolation-state` on the loopback interface only, authenticated by a server token (vault name `isolation_state_token`, generated by the installer, mode 600 on the host). The response carries only `{slug, env, idx, egress: bool, tailnet: [cidr]}`; `isolation-apply.sh` validates every field (slug `^[a-z0-9-]{1,40}$`, idx 0–255, CIDRs inside 100.64.0.0/10 or `fd7a:115c:a1e0::/48` only) and refuses the whole document on any invalid entry (keeps the last good state).
4. **Applied by the server agent, not by DevOS.** DevOS containers never get `NET_ADMIN` or the Docker socket for this. `scripts/server/isolation-apply.sh` joins the server agent's allow-list (installed only from a D1-passed SHA) and runs at the start of each tick under `timeout 60` (`curl --connect-timeout 5 --max-time 15` for the state read). It is idempotent: it rebuilds the two chains and the ipsets atomically (`iptables-restore --noflush` of a generated block, `ipset swap`) and changes nothing when the generated block equals the installed one.
5. **Self-test and automatic rollback.** After any change, the script checks from the host that SSH on `tailscale0`, Coolify `localhost:8000` and the DevOS API health answer. If any fails, it restores the previous block (kept in `/root/.devos/isolation/last-good.rules`) within the same run and posts `server-check` failure. The **one-command rollback** for KK (in case the host is reachable only through Hostinger's console): `bash /root/.devos/bin/isolation-apply.sh --remove`, which deletes the two jumps, chains and ipsets and leaves M0.1/M0.2 untouched. A `--dry-run` prints the generated block and changes nothing.
6. **Limits (DV-NFR-05).** Every project service gets `cpus`, `mem_limit`, `memswap_limit = mem_limit` and `pids_limit` in the Compose that M2.4-c hands to Coolify: defaults per stack `cpus: 1.0`, `mem_limit: 768m`, `pids_limit: 256` (preview: `0.5`, `512m`, `256`), from settings so KK can change them later in the wizard without code. The 4 vCPU / 16 GB KVM 4 (ADR-0002) then fits DevOS plus about six projects with both stacks running. A service without limits makes `afterStack` fail (`limits_missing`) rather than deploy unbounded. `no-new-privileges`, `cap_drop: [ALL]` (+ `NET_BIND_SERVICE` only if a service binds below 1024) and no `privileged`/host network/host PID/Docker socket mounts are enforced the same way (`compose_unsafe`).
7. **The hook (`afterStack`).** `packages/isolation` exports `isolationHook({ settings, store })` for M2.4's `provision.hooks.afterStack(project, env)`: it allocates nothing new (index comes from M2.4's port), validates and rewrites the stack's Compose (decision 6, network of decision 1) before Coolify gets it, and records the stack in the DB for the state endpoint. It never touches the host.
8. **Size split** (rules: > ~800 lines or more than one concern → task sub-issues, one PR each, in order):
   - **S4-a** (DEVOS-126) `packages/isolation`: subnet/name derivation, Compose validator + rewriter (limits, network, unsafe options), the `afterStack` hook, the state record and `GET /internal/isolation-state` (loopback + token). Unit tests (AT1–AT4, AT9). Needs M2.4-c.
   - **S4-b** (DEVOS-125) `scripts/server/isolation-apply.sh`: rule generation, atomic apply, self-test + rollback, `--remove`, `--dry-run`. Tested with a fake `iptables`/`iptables-restore`/`curl` harness and real TCP listeners (AT5–AT8).
   - **S4-b2** (DEVOS-127) server-agent wiring: the allow-list line, the per-tick call under `timeout 60`, the `server-check` failure report, boot persistence (an `/etc/ufw/after.rules` marker block re-running the last installed block), the IPv6 defence-in-depth drop with strict IPv6 tailnet entries, and the conntrack clean-up (S4-b decision 10). Separate because `scripts/server/server-agent.sh` is open in PR #31 (DEVOS-90); starts after it merges.
   - **S4-c** (DEVOS-128) `scripts/server/checks/project-isolation.sh`: the F3-1/F3-2 probe from inside a throwaway project container (AT10, AT11), plus the live run on `devos-probe-s4` (AT12), evidence for G2.

## S4-b decisions (builder, 12 Nov 2026, ADR-0013) — these amend decisions 1–5 above
1. **Pool `10.208.0.0/14`, index 0–1023** (amends decision 1). M2.4's port range allows up to 1000 stacks (20000–20999), so a `/16` (256 × `/24`) would run out. Stack index *i* → `10.(208 + i div 256).(i mod 256).0/24`, gateway `.1`. S4-a uses the same formula.
2. **Rules, not ipsets** (amends decisions 2 and 4). Declared egress and tailnet CIDRs are rules in the generated block (one `RETURN` per declared item, in index order), so the whole change is one `iptables-restore --noflush` — atomic for the table. An `ipset swap` would be a second, separately-failing step. The rule count is O(stacks), small at this scale. No `ipset` dependency.
3. **Where the jumps live.** `-I DOCKER-USER 1 -j DEVOS-ISO-FWD`, `-I FORWARD 1 -j DEVOS-ISO-FWD` and `-I INPUT 1 -j DEVOS-ISO-IN`, re-asserted on every run. The FORWARD jump exists because tailscaled inserts its own `ts-forward` jump at FORWARD position 1 (ending in `-o tailscale0 -j ACCEPT`) whenever it starts after Docker; pool → tailnet traffic would then be accepted before DOCKER-USER is reached (second pre-review, 12 Nov). Passing the chain twice is harmless: it only `RETURN`s or `DROP`s. Other tools that insert at position 1 (tailscaled's `ts-input`, fail2ban) push our jump down; the next run puts it back first in one restore, which shows as an "applied" line, not a fault (a jump that moved or was duplicated is put back first, exactly once). A `RETURN` from our chain hands the packet on to the M0.1/M0.2 rules unchanged, so non-project traffic behaves exactly as before. The FWD chain also drops `127/8`, `0/8`, `224/4` and `240/4` destinations.
4. **State document.** `GET /internal/isolation-state` returns exactly `{"stacks":[{"slug","env","idx","egress","tailnet"}]}` — no other key anywhere. Slug `^[a-z0-9]([a-z0-9-]{0,38}[a-z0-9])?$`, env `preview|live`, idx an integer 0–1023 unique per document, one entry per `slug/env`, egress boolean, tailnet CIDRs IPv4 inside `100.64.0.0/10` with prefix ≥ /10, IPv6 entries are refused until S4-b2 adds ip6tables rules and a strict IPv6 parser (project networks have no IPv6, so nothing needs them yet). Any violation refuses the whole document. The URL must be loopback http (default `http://127.0.0.1:$API_INTERNAL_PORT/internal/isolation-state`, port 3002); the token (`/root/.devos/secrets/isolation_state_token`) goes in a header read from a file descriptor, never on argv.
5. **Self-test, before and after.** Each target `host:port` in `ISOLATION_SELFTEST_TARGETS` (server-agent.conf) must accept a TCP connection within 3 s. Default: `127.0.0.1:8000` (Coolify) and, when `tailscale ip -4` answers, `<tailnet-ip>:22` and `<tailnet-ip>:$API_PORT`. It runs before and after the change. Passed before and fails after → the previous installed block is restored, or the S4 block removed when there was none, in the same run. Already failing before → the S4 chains (which match only pool sources) cannot be the cause, so the block is applied and kept, and the run exits 1 to report the host problem. Why: rolling back on an unrelated outage (e.g. Coolify restarting) would switch isolation off — the floor would fail open.
6. **Boot gap (accepted for S4-b, closed by S4-b2).** Until S4-b2 adds the `after.rules` block, the rules come back after a reboot on the agent's first tick, not at boot. The same holds after `ufw reload`, because M0.1's `:DOCKER-USER - [0:0]` flushes DOCKER-USER and so drops our jump; S4-b2's `after.rules` block closes both.
7. **One transaction, including the jumps** (pre-review, 12 Nov). The restore input is the chain block plus the jump changes (`-D` for every existing copy, then `-I <chain> 1`, only when the jump is not already the single first rule), all before one `COMMIT`. The whole input is built before `iptables-restore` starts (Codex PR54-r1): on the legacy backend restore holds the xtables lock until `COMMIT`, so the `iptables -S` queries behind the jump changes must not run while it reads; the test fakes share one lock file to prove it. There is no moment without the jump, and a failed restore changes nothing, so no "restore the previous block" step is needed after an apply failure.
8. **Strict parsing at the trust boundary** (pre-review, 12 Nov). The state is read with `jq -s` (exactly one document) and every field is checked against its pattern inside jq before it becomes a `@tsv` row; tailnet entries must match `^[0-9a-fA-F.:/]{1,49}$` (≤ 64 per stack) before the CIDR range checks. A newline, tab or comma inside any value refuses the whole document.
9. **Drift and locking.** "Unchanged" also requires the live chains to hold the block's rule count and to match the SHA-256 of `iptables -S` taken right after the last apply (`$DEVOS_DIR/isolation/live.sha256`), so a hand-flushed or hand-edited chain is rebuilt on the next run. Runs take `$DEVOS_DIR/isolation/.lock` (`flock -n`; a held lock → exit 3, `--remove` waits up to 60 s). Timeouts: state fetch 3 s connect / 10 s total, each `iptables` call 10 s, each restore 15 s, each self-test target 3 s, so a run fits the agent's 60 s budget.
10. **Existing connections (accepted for S4-b, S4-b2 item).** The early `ESTABLISHED,RELATED` return keeps connections that existed before a change (the first apply, or a revoked egress/tailnet declaration) until they close. S4-b2 deletes the conntrack entries of the stacks whose rights shrank (`conntrack -D -s <subnet>`) after a successful apply.
11. **Time budget.** The worst case can pass 60 s when every call hits its timeout; if the agent's `timeout 60` then kills a rollback, the new block stays in place, so isolation never fails open. S4-b2 may add one overall deadline.
12. **Notes for S4-c.** Check DNS resolution from an egress-declared container when the host's upstream resolver sits in a private or link-local range: Docker's embedded DNS forwards from the container's namespace, so the private-range drops apply to it before the egress `RETURN`. If it fails, S4-c adds a narrow `RETURN` for the host resolver on 53 only.

## S4-a decisions (builder, 12 Nov 2026, ADR-0013) — DEVOS-126
1. **Split S4-a in two PRs** (size and concern rule). **S4-a1** is the pure package `packages/isolation`: subnet/name derivation, the Compose hardener, the `afterStack` hook over an injected `IsolationStore`, and the state-document builder (AT1–AT3, the document half of AT4, AT9). **S4-a2** adds the Postgres store (a migration in M1.1's schema, so a second concern), the `GET /internal/isolation-state` route on loopback with the constant-time token check (the HTTP half of AT4), and the hook registration that M2.4-c2/M2.4-d calls. S4-a1 needs nothing from M2.4-c2: the hook's input (`{id, slug}`, `{name, port, portRangeStart, compose}`) is what M2.4-c1 already allocates.
   - **S4-a1 pre-review (runner-b, 12 Nov 2026):** (high, fixed) a literal `<<` key at any depth is refused: under `labels` it would be written back as a YAML merge and let Docker Compose add reserved `traefik.*`/`coolify.*` labels after validation; test added. (medium, fixed) the invalid-limits test now starts from valid settings, so each bad value is what fails. (low, for S4-a2) the store enforces a unique subnet index per stack (a DB constraint), so a port-range change or duplicate offset fails at the hook instead of making `stateDocument` refuse every project. (low, advisory) `shm_size` and `ulimits` values are not bounded; /dev/shm counts against the memory limit, so this is not an escape. (Codex PR69-r1, medium, fixed) a service that asks for no limit gets its default clamped to the per-service caps as well as to the stack budget, so lowering `caps` below the defaults always binds; test added.
2. **Index from the port.** `idx = port − portRangeStart` (M2.4-c1 decision: the port is allocated race-free through the inventory and never reused), so the subnet is as unique and stable as the port. An offset above 1023 is `bad_stack`.
3. **Limits.** Defaults per decision 6 (live `1.0` CPU / `768m` / `256` pids, preview `0.5` / `512m` / `256`). Caps (S4-a's choice, from settings): `2.0` CPUs, `2048m`, `1024` pids; anything above is clamped. A value that is set but does not limit (`0`, `-1`, a negative or non-numeric value, a fractional pid count) is `limits_missing`, not silently replaced: the app author asked for "unlimited", and only a person should decide what it gets instead. `deploy.resources.limits` values are read, moved to the top-level keys and removed (Compose refuses disagreeing pairs). `memswap_limit = mem_limit`.
   **Stack budget** (second pre-review: limits are per container, so 30 services would get 30× the default). Per env, the services of one stack together get at most live `2.0` CPUs / `3 GiB` / `2048` pids, preview `1.0` / `1.5 GiB` / `1024`, and at most 12 services. A service with no limit gets the per-env default lowered to an even share of what the explicit limits leave (app + db + cache with no limits get `0.66` CPU, `768m`, `256` pids each on live). Explicit limits over the budget, or a share below the minimum, is `limits_over_budget`. Six projects with both stacks at their budget come to 18 CPUs and 27 GiB, above the 4 vCPU / 16 GB host: CPU is shared fairly by the scheduler, and memory budgets are ceilings that idle stacks do not use; M4.4 monitoring watches the real total.
4. **An allow-list, not a deny-list** (pre-review 12 Nov: 7 high/medium bypasses of a deny-list). Any Compose key outside the list is `compose_unsafe`, so a feature nobody thought of fails closed.
   - **Document:** `services`, `networks`, `volumes`, `version` and inert `x-*` keys. Refused: `include`, `configs`, `secrets`, `name`, a literal `<<` merge key (the hook needs the parsed document with anchors and merges resolved). A declared network may not be `coolify`, `external` or carry `name:`; a declared volume may only be plain local (`driver: local`, `labels`) — no `name`, `external`, `driver_opts` (a bind of any host path) or other driver.
   - **Service keys:** `image`, `build`, `command`, `entrypoint`, `environment`, `working_dir`, `user`, `expose`, `volumes`, `tmpfs`, `healthcheck`, `restart`, `depends_on`, the three limits (+ `memswap_limit`, overwritten), `deploy`, `networks` (replaced), `labels`, `hostname`, `stop_grace_period`, `stop_signal`, `init`, `read_only`, `shm_size`, `stdin_open`, `tty`, `platform`, `pull_policy`, `cap_add` (only `NET_BIND_SERVICE`), `cap_drop` (overwritten), `security_opt` (only `no-new-privileges`), `privileged` (only `false`, then removed). `ports` is accepted and **dropped**: the published tailnet port is set by M2.4-c2 on the Coolify application, and a Compose `ports` entry could bind any host port or interface. `profiles`, `ulimits` (only `nofile`, `core`, `stack`, `msgqueue`, `sigpending`; not `nproc` or `memlock`) and inert `x-*` keys are allowed. `container_name`, `network_mode`, `pid`/`ipc`/…, `devices`, `gpus`, `runtime`, `sysctls`, `logging`, `env_file`, `extends`, `scale` and the rest are refused.
   - **Volumes:** only named volumes declared in the same file (short or long form), anonymous volumes (a container path alone) and tmpfs. No bind mount at all, so path spelling (`//etc`, `..`, `/var`, `/data/coolify`) cannot matter. Volume names and mount sources must match Docker's rule `^[a-zA-Z0-9][a-zA-Z0-9_.-]*$`, because Compose reads a source starting with `.`, `/` or `~` as a bind mount even when a volume of that name is declared (second pre-review: `volumes: {"..": null}` + `..:/host`).
   - **Build:** a string path or `{context, dockerfile, args, target}`, both paths relative and staying inside the repo after normalising, the Dockerfile taken relative to the context (no URL, no absolute path, and no context whose first segment looks like a host, e.g. `github.com/…`, which buildx fetches as a remote Git context). A committed symlink used as a context or Dockerfile cannot be seen by a pure check; S4-c's probe covers it. `network`, `ssh`, `secrets`, `additional_contexts`, `entitlements` are refused.
   - **Deploy:** `resources` (limits/reservations of `cpus`, `memory`, `pids` only — no device reservations), `restart_policy`, `replicas: 1`, `mode: replicated`. One container per service, so per-container limits bound the stack.
   - **Labels:** no key starting (after trimming) with `coolify`, `traefik`, `caddy` (including caddy-docker-proxy's `caddy_0` forms) or `com.docker`.
   - **Interpolation:** a `$` anywhere outside `environment`, `command`, `entrypoint` and `healthcheck` is refused, because Compose substitutes variables after the check (`${H:-/}` would become a host path). `$$`, Compose's escape for a literal `$`, is allowed.
   - Every service gets `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]` and only the project network. Limits below `0.01` CPU, `6 MiB` or `1` pid are `limits_missing` (Docker rounds them to 0, which is unlimited), and memory accepts Docker's units (`k`/`m`/`g`/`t`, with `b`/`ib`). Settings with a zero, negative or non-finite value are refused. Errors name the service and option, never a value.
5. **The state document refuses what the host refuses** (S4-b decision 4), and tailnet CIDRs with leading-zero octets, so DevOS never serves a document `isolation-apply.sh` would drop as a whole.

## Open risk found in S4-a (for S4-b2/S4-c)
- **Image builds run outside the pool.** `docker build` uses the daemon's default bridge (172.17/16), not the project network, so S4-b's pool rules do not cover a `RUN` step. S4-a refuses `build.network` (so not `host`), but a build can still reach private ranges from 172.17/16. S4-c's probe must cover a build step, and S4-b2 adds the matching drops for the build bridge if Coolify's own builds do not need them (follow-up issue filed).

## Out of scope
Public exposure of a project (M4.1, KK), per-project outbound allow-lists by domain (egress is all-or-nothing in v1; a domain allow-list needs a proxy and is a follow-up if the pilot needs it), DevOS's own containers (ADR-0011 hardening), rate limits on egress.

## Open technical risks (to resolve during S4-b, not KK questions)
- Coolify may attach its own network to Compose apps for its proxy. Since the proxy is off for projects (M2.4 decision 1), S4-a rewrites the Compose so only the project network is attached and S4-c verifies it with `docker inspect`. If Coolify re-adds `coolify`, S4-b's rules still drop pool → `coolify` traffic, so the floor holds; the check reports it.
- Docker publishes the stack's tailnet port with DNAT; inbound tailnet → container still passes M0.2's route rule, which is intended (KK reaches the app). Replies pass as `ESTABLISHED`.

## S4-a2 split and S4-a2a build notes (13 Nov 2026, runner B, ADR-0013)
**Split** (concern rule). S4-a2 (DEVOS-129) is two PRs: **S4-a2a** (DEVOS-173, this one) the `isolation_stack` table and the Postgres store; **S4-a2b** (DEVOS-174) `GET /internal/isolation-state` on loopback with the token check, and the hook registration in the M2.4-d wiring.

**S4-a2a decisions.**
1. **Where the store lives.** `apps/api/src/isolation-store.ts`, next to the other Prisma stores, so its real-Postgres test runs in the existing `api-db` job (no new CI job). apps/api does not import `@devos/isolation`: the store matches `IsolationStore` structurally, and S4-a2b's wiring passes it to `isolationHook({ store })`.
2. **Table** `isolation_stack` (additive migration `20261113000100_isolation_stack`, ADR-0011 §10): `project_id` (FK, restrict), `slug`, `env`, `idx`, `network`, `subnet`, timestamps. Unique (`project_id`, `env`), and unique `idx`, `subnet` and `network` across all stacks (the S4-a1 pre-review low note): a duplicate offset or a port-range change that collides fails inside the hook, before Coolify gets the stack, instead of making `stateDocument` refuse every project. Database checks repeat `network.ts`: env `preview|live`, index 0–1023, the slug pattern, and the network name and `/24` subnet derived exactly from slug, env and index, so even a write around the store cannot hold a row the state document would refuse, nor a stray value another stack's derivation needs (pre-review).
3. **Record = upsert per (project, env).** Re-recording the same stack is a no-op update; the store first checks the record is exactly what `stackNetwork(slug, env, idx)` derives (`isolation-stack-invalid` otherwise). A unique violation is `isolation-index-taken`; any other failure is `isolation-store-error`. Errors never carry the driver message (it can echo values). A concurrent first record of the same (project, env) also surfaces as `isolation-index-taken`; the provisioner holds the project lock, so this does not happen in practice, and a re-run records it.
4. **`listStacks`** returns exactly `projectId`, `slug`, `env`, `idx`, ordered by index. Egress and tailnet come from approved selections in S4-a2b (decision 3), never from this table. Teardown of rows (M2.5) is a follow-up of S4-a2b's wiring: the purge deletes by `project_id`.

**Pre-review (PASS, 4 low).** Fixed: each database check is tested alone and the rejection must name it; the subnet and network checks now pin the exact derivation (a `/16` or a foreign network name is refused). Follow-up (filed): teardown must delete a project's `isolation_stack` rows, or a purged project keeps its index and a later project on that port is refused; it lands before S4-a2b starts recording stacks.

**Tests.** `apps/api/test/isolation-store.test.mjs` (record checks, upsert and list over a fake client, fixed error codes), api 116/116 locally; `apps/api/test-db/isolation-store.test.mjs` (real Postgres in CI `api-db`: idempotent record, a taken index refused with nothing written, `listStacks`, each of the five database checks alone). Prisma's engine cannot download in the runner's sandbox, so `prisma validate`, `format --check` and the drift check run in CI `db`.
