## Goal
"Done when" (DEVOS-65), seen **from inside a project container**:
1. Coolify (8000/6001/6002), SSH (22), the DevOS API and dashboard, another project's containers and database, and cloud metadata (169.254.169.254) are unreachable.
2. Tailnet addresses (100.64.0.0/10, `fd7a:115c:a1e0::/48`) are unreachable unless declared.
3. Internet egress works only if declared.
4. CPU, memory and pid limits are visible in `docker inspect`.

## Design decisions (builder, recorded per ADR-0013)
1. **One address pool, one subnet per stack.** Every project stack (preview, live) runs on its own user-defined bridge network `devos-p-<slug>-<env>` with a fixed subnet from the pool `10.210.0.0/16` (IPv4, a /24 each — pool and index range amended by S4-b decision 1 to `10.208.0.0/14`, 0–1023 — index = the stack's port offset from M2.4 decision 1, so allocation is already unique and stable) and IPv6 disabled on that network. Coolify's shared `coolify` network is never attached to a project service. Docker's default bridge is never used. Why a fixed pool: host rules can then match "any project" with one CIDR and "this project" with one /24, without per-container rules that go stale.
2. **Generic host rules, small per-project state.** The host firewall is a static block that does not change per project:
   - `DOCKER-USER` (forwarded traffic): from `10.210.0.0/16` → drop to `10.210.0.0/16` unless same /24 (other projects), drop to every other private range (172.16/12 incl. `coolify` and the DevOS stack, 192.168/16, 10/8), drop to 100.64.0.0/10 and 169.254.0.0/16 unless the destination is in the ipset `devos-tailnet-<idx>`; internet egress is accepted only when the source /24 is in the ipset `devos-egress`; everything else from the pool is dropped. Replies (`ESTABLISHED,RELATED`) pass as in M0.1.
   - `INPUT` (traffic to the host itself — this is how a container would reach SSH, Coolify's published ports and the DevOS API on the host): from `10.210.0.0/16` → accept only DNS to the network gateway (53/udp+tcp) and drop the rest. M0.1/M0.2 allow private sources and `tailscale0` to SSH; without this rule a container could reach SSH.
   - The block lives in its own chains (`DEVOS-ISO-FWD`, `DEVOS-ISO-IN`), jumped to first from `DOCKER-USER` and `ufw-before-input`, and is written through `/etc/ufw/after.rules` + `before.rules` markers like M0.1, so it survives reboot and `ufw reload`. IPv6: project networks have no IPv6, and `ip6tables` gets the matching drop for `fd00::/8` sources not on the `coolify` network (defence in depth).
   Per-project state is only ipset membership (`devos-egress`, `devos-tailnet-<idx>`), not rules.
3. **Who decides "declared".** Egress and tailnet declarations come from the project's **approved** selection in the DevOS DB (M2.3 approval card; default: no egress, no tailnet), never from the project repo, a PR or anything an agent wrote. The host reads them from a file `/root/.devos/isolation/state.json` that DevOS writes through a narrow Coolify-free path: the API exposes `GET /internal/isolation-state` on the loopback interface only, authenticated by a server token (vault name `isolation_state_token`, generated by the installer, mode 600 on the host). The response carries only `{slug, env, idx, egress: bool, tailnet: [cidr]}`; `isolation-apply.sh` validates every field (slug `^[a-z0-9-]{1,40}$`, idx 0–255, CIDRs inside 100.64.0.0/10 or `fd7a:115c:a1e0::/48` only) and refuses the whole document on any invalid entry (keeps the last good state).
4. **Applied by the server agent, not by DevOS.** DevOS containers never get `NET_ADMIN` or the Docker socket for this. `scripts/server/isolation-apply.sh` joins the server agent's allow-list (installed only from a D1-passed SHA) and runs at the start of each tick under `timeout 60` (`curl --connect-timeout 5 --max-time 15` for the state read). It is idempotent: it rebuilds the two chains and the ipsets atomically (`iptables-restore --noflush` of a generated block, `ipset swap`) and changes nothing when the generated block equals the installed one.
5. **Self-test and automatic rollback.** After any change, the script checks from the host that SSH on `tailscale0`, Coolify `localhost:8000` and the DevOS API health answer. If any fails, it restores the previous block (kept in `/root/.devos/isolation/last-good.rules`) within the same run and posts `server-check` failure. The **one-command rollback** for KK (in case the host is reachable only through Hostinger's console): `bash /root/.devos/bin/isolation-apply.sh --remove`, which deletes the two jumps, chains and ipsets and leaves M0.1/M0.2 untouched. A `--dry-run` prints the generated block and changes nothing.
6. **Limits (DV-NFR-05).** Every project service gets `cpus`, `mem_limit`, `memswap_limit = mem_limit` and `pids_limit` in the Compose that M2.4-c hands to Coolify: defaults per stack `cpus: 1.0`, `mem_limit: 768m`, `pids_limit: 256` (preview: `0.5`, `512m`, `256`), from settings so KK can change them later in the wizard without code. The 4 vCPU / 16 GB KVM 4 (ADR-0002) then fits DevOS plus about six projects with both stacks running. A service without limits makes `afterStack` fail (`limits_missing`) rather than deploy unbounded. `no-new-privileges`, `cap_drop: [ALL]` (+ `NET_BIND_SERVICE` only if a service binds below 1024) and no `privileged`/host network/host PID/Docker socket mounts are enforced the same way (`compose_unsafe`).
7. **The hook (`afterStack`).** `packages/isolation` exports `isolationHook({ settings, store })` for M2.4's `provision.hooks.afterStack(project, env)`: it allocates nothing new (index comes from M2.4's port), validates and rewrites the stack's Compose (decision 6, network of decision 1) before Coolify gets it, and records the stack in the DB for the state endpoint. It never touches the host.
8. **Size split** (rules: > ~800 lines or more than one concern → task sub-issues, one PR each, in order):
   - **S4-a** (DEVOS-126) `packages/isolation`: subnet/name derivation, Compose validator + rewriter (limits, network, unsafe options), the `afterStack` hook, the state record and `GET /internal/isolation-state` (loopback + token). Unit tests (AT1–AT4, AT9). Needs M2.4-c.
   - **S4-b** (DEVOS-125) `scripts/server/isolation-apply.sh`: rule generation, atomic apply, self-test + rollback, `--remove`, `--dry-run`. Tested with a fake `iptables`/`iptables-restore`/`curl` harness and real TCP listeners (AT5–AT8).
   - **S4-b2** (DEVOS-127) server-agent wiring: the allow-list line, the per-tick call under `timeout 60`, the `server-check` failure report, boot persistence (an `/etc/ufw/after.rules` marker block re-running the last installed block) and the IPv6 defence-in-depth drop. Separate because `scripts/server/server-agent.sh` is open in PR #31 (DEVOS-90); starts after it merges.
   - **S4-c** (DEVOS-128) `scripts/server/checks/project-isolation.sh`: the F3-1/F3-2 probe from inside a throwaway project container (AT10, AT11), plus the live run on `devos-probe-s4` (AT12), evidence for G2.

## S4-b decisions (builder, 12 Nov 2026, ADR-0013) — these amend decisions 1–5 above
1. **Pool `10.208.0.0/14`, index 0–1023** (amends decision 1). M2.4's port range allows up to 1000 stacks (20000–20999), so a `/16` (256 × `/24`) would run out. Stack index *i* → `10.(208 + i div 256).(i mod 256).0/24`, gateway `.1`. S4-a uses the same formula.
2. **Rules, not ipsets** (amends decisions 2 and 4). Declared egress and tailnet CIDRs are rules in the generated block (one `RETURN` per declared item, in index order), so the whole change is one `iptables-restore --noflush` — atomic for the table. An `ipset swap` would be a second, separately-failing step. The rule count is O(stacks), small at this scale. No `ipset` dependency.
3. **Where the jumps live.** `-I DOCKER-USER 1 -j DEVOS-ISO-FWD` and `-I INPUT 1 -j DEVOS-ISO-IN`, re-asserted on every run (a jump that moved or was duplicated is put back first, exactly once). A `RETURN` from our chain hands the packet on to the M0.1/M0.2 rules unchanged, so non-project traffic behaves exactly as before. The FWD chain also drops `127/8`, `0/8`, `224/4` and `240/4` destinations.
4. **State document.** `GET /internal/isolation-state` returns exactly `{"stacks":[{"slug","env","idx","egress","tailnet"}]}` — no other key anywhere. Slug `^[a-z0-9]([a-z0-9-]{0,38}[a-z0-9])?$`, env `preview|live`, idx an integer 0–1023 unique per document, one entry per `slug/env`, egress boolean, tailnet CIDRs IPv4 inside `100.64.0.0/10` with prefix ≥ /10, or IPv6 inside `fd7a:115c:a1e0::/48` (accepted, no rule in v1: project networks have no IPv6). Any violation refuses the whole document. The URL must be loopback http (default `http://127.0.0.1:$API_INTERNAL_PORT/internal/isolation-state`, port 3002); the token (`/root/.devos/secrets/isolation_state_token`) goes in a header read from a file descriptor, never on argv.
5. **Self-test.** Each target `host:port` in `ISOLATION_SELFTEST_TARGETS` (server-agent.conf) must accept a TCP connection within 3 s. Default: `127.0.0.1:8000` (Coolify) and, when `tailscale ip -4` answers, `<tailnet-ip>:22` and `<tailnet-ip>:$API_PORT`. A failure restores the previous installed block, or removes the S4 block when there was none, in the same run.
6. **Boot gap (accepted for S4-b, closed by S4-b2).** Until S4-b2 adds the `after.rules` block, the rules come back after a reboot on the agent's first tick, not at boot.

## Acceptance tests
| # | Test | Pass when |
|---|------|-----------|
| AT1 | Names and subnets | Two projects get distinct, stable `/24`s inside `10.208.0.0/14` (S4-b decision 1); re-run gives the same; an index outside 0–1023 is refused |
| AT2 | Limits enforced | A Compose service without `cpus`/`mem_limit`/`pids_limit` gets the defaults; a value above the cap is clamped; `afterStack` fails `limits_missing` when it cannot set them |
| AT3 | Unsafe Compose refused | `privileged`, `network_mode: host`, `pid: host`, `cap_add: [NET_ADMIN]`, a `docker.sock` mount, or attaching the `coolify` network → `compose_unsafe`, nothing handed to Coolify |

| AT5 | Generated rules | For a fixed state, the generated block equals the golden file (`scripts/test/fixtures/isolation-golden.rules`): pool-to-pool drop except same /24, private ranges and 169.254/16 dropped, egress only for declared /24s, INPUT accepts only gateway DNS |
| AT6 | Bad state refused | An invalid slug, idx, a CIDR outside the tailnet ranges, or malformed JSON → nothing applied, last good state kept, failure reported |

| AT8 | Self-test + rollback | If the post-apply host probe fails, the previous block is restored in the same run; `--remove` leaves only the M0.1/M0.2 rules; `--dry-run` writes nothing |

## Out of scope
Public exposure of a project (M4.1, KK), per-project outbound allow-lists by domain (egress is all-or-nothing in v1; a domain allow-list needs a proxy and is a follow-up if the pilot needs it), DevOS's own containers (ADR-0011 hardening), rate limits on egress.

## Open technical risks (to resolve during S4-b, not KK questions)
- Coolify may attach its own network to Compose apps for its proxy. Since the proxy is off for projects (M2.4 decision 1), S4-a rewrites the Compose so only the project network is attached and S4-c verifies it with `docker inspect`. If Coolify re-adds `coolify`, S4-b's rules still drop pool → `coolify` traffic, so the floor holds; the check reports it.
- Docker publishes the stack's tailnet port with DNAT; inbound tailnet → container still passes M0.2's route rule, which is intended (KK reaches the app). Replies pass as `ESTABLISHED`.
