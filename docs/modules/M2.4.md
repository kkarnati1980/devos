## Goal
"Done when": **re-running provisioning creates nothing twice.** When KK approves a project's requirements (M2.3 gate), DevOS provisions, without a person, every resource the project needs, and records each one in the inventory under the project's ID. Running it again, after a crash at any step, or after a partial failure, finishes the job and never creates a second copy of anything.

## Decisions (builder, recorded per ADR-0013)
1. **No Cloudflare in M2.4.** The PRD row "Cloudflare subdomains behind Access" is superseded: H2 (DEVOS-41) was cancelled and access is tailnet-only (ADR-0003, ADR-0005). Each stack gets a tailnet URL `http://devos:<port>` with the port allocated from a fixed range (`DEVOS_PROJECT_PORTS`, default 20000–20999, two per project, preview even / live odd). Coolify's proxy and auto-generated domains are off (`autogenerate_domain:false`, as in M0.4). Putting a project on the public internet is a **launch decision for KK** (M4.1), not something M2.4 does. The `cloudflare` provider value stays in the enum (backward-compatible) and is unused.
2. **Create-or-get by deterministic name, adopt on find.** Every step is: look up by the deterministic name at the provider → if found and tagged to this project, adopt it (record it in `resource` if missing) → else create → record. The unique `(provider, kind, external_id)` index makes the record step idempotent. A found resource **not** tagged to this project (e.g. a repo `devos-<slug>` that DevOS did not create) is never adopted: the step fails with `name_conflict` (non-retryable) and a decision card asks KK what to do (rename or adopt), because touching a resource DevOS does not own is a non-technical call.
3. **Ownership marker.** `devos:<project id>` in the resource's description, written **in the create call itself**, so a resource is never left half-tagged after a crash. GitHub: the repo description ends with the marker and the repo must be private (a public repo with the marker is not ours). Coolify: the project/app `description` contains the marker. M2.5's leftover scan uses the same marker. (A repo topic was considered and dropped: it needs a second call after the create.)
4. **Crash safety with a step journal.** A new table `provision_step` (project, step key, status `pending|done|failed`, attempts, last error, external id) is written *before* each external create (`pending`) and after (`done`). On re-run, a `pending` step is resolved by lookup (decision 2), never by blind re-create. One provisioning job per project at a time: a Postgres session advisory lock keyed on the project ID (see the M2.4-a build notes).
5. **Retries.** Lookups (GET) are retried with backoff and jitter on `retryable` errors (ADR-0009). Creates (POST) are **not** retried blindly: after a timeout or 5xx the step re-runs its lookup first, so a create that actually succeeded is adopted, not duplicated (ADR-0011 §9: retries only for safe operations). Every call has a timeout (GitHub 15 s, Coolify 30 s).
6. **Policy before writes.** Each external create goes through the M1.7 policy engine (`action: provision.<provider>.<kind>`, `resource: project:<id>`). In `observe` mode it is logged; `deny` stops the step with `policy_denied` (not an attempt).
7. **Secrets.** Generated with `crypto.randomBytes(32)`, written to Coolify env vars over the API and stored in the vault (ciphertext). Never logged, never returned by any route, never in the repo, never in `provision_step.last_error` (errors are redacted by name). The GitHub and Coolify tokens are read from the vault by name (M1.4 names `github_token`, `coolify_api_token`). The vault today seals global secrets only (`project_id` null); per-project app secrets need a project-scoped `put` in M2.4-c, using the existing `vault_secret.project_id` column (no schema change).
8. **GitHub repo creation.** `POST /user/repos` (private, `auto_init:false`), then push the S3 core as one commit via the Git Data API (blobs → tree → commit → `refs/heads/main`), so no `git` binary or credentials touch disk. Re-run: if `main` exists and its tree matches the template manifest, adopt; if `main` exists with other content, leave it (never force-push).
9. **Backups.** M2.4 only records the schedule (`backup_schedule/nightly`) and the Coolify scheduled-backup setting for the live database if the stack has one. The off-site target (R2, H7 DEVOS-34) is M4.5's; until KK creates it, backups stay on the server and the record says so.
10. **Size split** (rules: > ~800 lines or more than one concern → task sub-issues, one PR each, in order):
    - **M2.4-a** `packages/provision` core: provider clients (GitHub repo, Coolify project) over a fixed-origin transport with timeouts, the create-or-get step runner, the step journal + advisory lock, `provision_step` migration, inventory writes. Tests with recorded fake providers + Postgres (AT1–AT4, AT8, AT9).
    - **M2.4-b** repo from the S3 core (decision 8) + ownership tag (AT5, AT6 core half). Needs S3-a merged.
    - **M2.4-c** Coolify project, environments, applications, ports, app secrets (AT7, AT10).
    - **M2.4-d** wiring: run-engine job triggered by the M2.3 requirements-approved event, `POST /projects/{id}/provision` (retry, CSRF), `GET /projects/{id}/provision` status, the dashboard panel, backup + budget records (AT11, AT12).

## M2.4-a build notes (DEVOS-107)
- **Transport** (`src/http.ts`): one origin per provider (`https://api.github.com`; Coolify from config, e.g. `http://devos:8000`), `redirect: "error"`, `AbortSignal.timeout` on every call (GitHub 15 s, Coolify 30 s). Reads retry 3× on network/timeout/429/5xx with backoff + jitter; writes get exactly one attempt. The token comes from a callback (the vault) at call time and is only ever put in the `authorization` header; error messages carry method, path and status, never a body or header.
- **Runner** (`src/runner.ts`): `runStep` = done in the journal → return it (no calls) · lookup → owned: adopt, not owned: `name_conflict` · policy (`allow` only; `deny` → `policy_denied`, `require_approval` → `approval_required`, neither counts as an attempt) · journal `pending` · one create · on timeout/network/5xx/409/422 look up again and adopt, else `create_unconfirmed` (retryable; the next run looks up first) · record in `resource` + journal `done`. `runProvision` runs steps in order under the project lock and stops at the first failure.
- **Policy is required:** `runProvision` refuses to run without an `authorize` function (fail closed, ADR-0006); tests pass the explicit `allowAll`.
- **GitHub owner check:** before `POST /user/repos` the client checks `GET /user` login = the configured owner, so a mismatch fails before anything is created (no orphan repo). A 409/422 on create with nothing found under our name is a permanent `provider_error`; only timeouts, network errors and 5xx end `create_unconfirmed` (retryable).
- **For M2.5:** a `done` journal row is trusted without re-checking the `resource` row; Purge must reset the project's `provision_step` rows (or the runner must re-check), otherwise re-provisioning after a purge would report stale ids.
- **Decision card on `name_conflict`** is raised by the M2.4-d wiring (it needs M2.3-b); M2.4-a returns the typed, non-retryable error.
- **Stores:** `PrismaStore` (journal + inventory upsert; another project's row → `resource_owned_elsewhere`; a soft-deleted own row is reactivated) and `MemoryStore` (tests). The lock is a **session** advisory lock `pg_advisory_lock(hashtext('devos:provision'), hashtext(<project id>))` on a dedicated connection, held until the run ends or the connection drops (never released by a transaction timer, pre-review r1); a waiter fails after `lockWaitMs` (Postgres `lock_timeout`); the runner pings the lock connection before every create and stops with `provision_lock_lost` if it is gone. Journal and inventory writes commit immediately, so a crash never loses the record of a resource that exists at the provider. Every DB call and the vault token read are bounded (10 s, ADR-0011 §9). Runs for the same project on one store instance queue in-process first; a lock-wait timeout is the typed `provision_busy` (retry later, not an attempt). **Deployment:** the lock's `databaseUrl` must be a direct connection or a session-mode pooler, never a transaction-mode pooler (a session lock there could land on different server connections).
- **Schema:** `provision_step` (+ enum `provision_step_status`), migration `20261111000400_provision_step`, additive only, with DB checks: a done step has an external id, attempts ≥ 0, `last_error` ≤ 300 chars.
- **Tests:** `packages/provision/test/runner.test.mjs` (fake GitHub + Coolify behind a fetch stub: AT1, AT2, AT3 per step, AT4, AT5, AT8, AT9, AT12, token never in errors/journal, origin/path guard) and `test-db/prisma-store.test.mjs` on Postgres in the `provision-db` workflow (AT1–AT3, AT8, inventory ownership, DB checks).

## Review log
**M2.4-a, Codex PR44-r1 (12 Nov 2026; 1 high and 1 medium, both accepted):**
- (high) `CoolifyClient.findProjectsByName` treated a 404 or a body that is not an array as "no project", so the runner could POST a duplicate. Only a 200 with an array now counts as a confirmed absence. Anything else is a `bad-response` ProviderError, and the step fails as `provider_error` with nothing created.
- (medium) The response body was read outside the fetch error handler. A body that stalled until the timeout raised a raw AbortError, which skipped the read retry and the write reconciliation (AT4/AT9, ADR-0011 §9). The body read is now mapped to a transient `timeout`/`network` ProviderError. A GET is retried; a POST is looked up before any second create.
- Regression tests: an inconclusive list (404, an object, an empty body) creates nothing; a stalled body is retried on GET, is transient on a write, and a Coolify create whose response stalls is adopted with one POST. Both tests fail on the r1 code. 24/24 pass.

**M2.4-a, Codex PR44-r2 (12 Nov 2026; 2 medium, both accepted):**
- A same-named list entry with no string `uuid` was silently dropped, so the lookup could still miss our project. Now any malformed entry (not an object, or a non-string `name`/`uuid`) makes the list inconclusive (`bad-response`), and nothing is created. The test covers three malformed shapes.
- The lock connection's connect, `SET lock_timeout`, advisory-lock wait and `end()` had no client-side bound (ADR-0011 §9). Each is now bounded: `dbTimeoutMs` for connect, setup and end, and `lockWaitMs + dbTimeoutMs` for the lock wait, so Postgres's own `lock_timeout` still answers first. A stalled `end()` no longer holds up the run or the in-process queue; closing the socket still releases the session lock. Regression test: each stall fails, or for `end()` returns, within its bound. 25/25 pass.

**M2.4-a, Codex PR44-r3 (12 Nov 2026; 1 medium, accepted):** the lock could drop during the `markPending` journal write and the create would still run. The runner now checks the lock again after that write, right before the external create (a test drops the lock inside `markPending`; nothing is created).

**M2.4-a, Codex PR44-r5 (12 Nov 2026; 1 medium, accepted):** the GitHub login was cached per client, and each request read the vault token separately, so a token swapped after the owner check could create a repo in another account. `Transport.pinned()` now reads one token snapshot. `GitHubClient.createOwnedRepo` runs `GET /user` and `POST /user/repos` on that snapshot, and the login is no longer cached. ## M2.4-c split and c1 build notes (12 Nov 2026, runner B, ADR-0013)
**Split.** Coolify applications (row 4) build from the project repo, which needs the S3 core commit from M2.4-b, and M2.4-b waits on S3-a (PR #32). App secrets (row 5) are written as application env vars. So M2.4-c is built as two PRs:
- **M2.4-c1 (DEVOS-109, this PR):** environments and ports (rows 3 and 6, AT10). These need only the Coolify project from M2.4-a.
- **M2.4-c2 (follow-up issue):** applications per environment, app secrets (Coolify env vars plus a project-scoped vault `put`, AT7), the `afterStack` hook for S4, and the matching teardown ops for M2.5-a3.

**c1 decisions.**
- **Environments:**
  - Looked up with `GET /api/v1/projects/{uuid}/environments` and created with `POST` `{name}` (the endpoints recorded by the M0.4 04b spike).
  - Only a 200 with an array of named entries proves absence, as for projects (Codex PR44-r1/r2); anything else is an inconclusive `bad-response`, and nothing is created.
  - Environments carry no description. Their ownership comes from the parent Coolify project, which the `coolify/project` step has already proven, and whose uuid is read from that step's `done` journal row. With no such row, the step fails before any call.
  - External id: `<project uuid>/<env>`, as in the table above.
- **Ports:**
  - Each port is allocated through the inventory itself: a `coolify/port` row whose external id is the port and whose name is `<slug>/<env>`. The unique `(provider, kind, external_id)` index makes the allocation race-free across projects. A port that another project inserted first fails with `resource_owned_elsewhere`, and the next free port is tried.
  - Preview gets even ports and production odd ports. The range is `DEVOS_PROJECT_PORTS`, default `20000-20999`, validated to lie within 1024–65535.
  - A re-run finds the project's own active row by name and keeps the same port.
  - When no free port is left, the step ends with `port_range_exhausted` (non-retryable), and its code is kept in the journal: the runner now keeps a step's own typed `StepError`.
  - A port once held by another project, even a purged one, is not reused. That leaves 500 projects per default range, and widening the range is a setting.
- **Store:** `ProvisionStore.listResources(provider, kind)` is added to both stores. Allocation needs every row, across projects and including deleted ones.

**Tests.**
- `test/stack.test.mjs` covers:
  - AT1 and AT2 for environments and ports, including a fresh journal that adopts and keeps the same ports;
  - AT4: an environment POST that times out after succeeding is adopted, with one POST;
  - AT10: distinct and stable ports, even/odd parity, an exhausted range, and a port taken concurrently being skipped;
  - range parsing;
  - no create without a provisioned parent project.
- `test-db`: AT10 on Postgres, with two projects provisioned at once getting distinct ports, and a re-run keeping them.

**c1 pre-review (PASS, 5 low).** Fixed: (1) a Postgres test for a port taken between read and insert; (4) the fake Coolify creates `production` with each project (Coolify v4 does, M0.4 04b), so that step adopts it. Deferred to c2: (2) a `provision_db` timeout during port allocation is recorded as non-retryable `provider_error` (a re-run still adopts the port; only the auto-retry hint is wrong); (3) the port lookup matches `<slug>/<env>`, so slugs must stay immutable once provisioned (they are: `project.slug` is the repo and Coolify name key).

**M2.4-c1, Codex PR50-r1 (12 Nov 2026; 1 medium, accepted):**
- **Problem.** The environment and port creates awaited reads after the runner's last lock check (the parent uuid from the journal, the port list). A run that lost the lock during those reads could still write, and a replacement run could give one stack two ports.
- **Fix:**
  - Both steps check `assertLockHeld` again after their reads: right before the environment POST, and before every port insert.

## M2.4-b build notes (DEVOS-108, 12 Nov 2026, runner B, ADR-0013)
**What it adds.** A `github/core` step (`src/core-repo.ts`) that runs after `github/repo`, plus `src/repo-content.ts`, which turns the S3 core into an in-memory file list.

**Decisions.**
- **The template comes in as files, not a path.** `coreTemplateFiles(apply, {devosSha})` calls S3's `apply()` (injected, so the package never imports from `scripts/`) into a fresh temp dir with no selection, reads it, and deletes the dir. It fails with `template-not-core-only` unless `.devos/template.json` has empty `selected` and `applied`. Each file carries its git blob SHA-1, so the tree on GitHub can be compared byte for byte without downloading blobs. Symlinks and other non-regular files are refused; paths with `..`, `.`, `.git` or unusual characters are refused; a template is capped at 500 files, 1 MB per file and 10 MB in all. The M2.4-d wiring must ship `scripts/template/` and `templates/golden-path/` in the worker image.
- **The empty-repo case.** GitHub's Git Data API answers 409 "Git Repository is empty" on a repo with no commits (the repo is created with `auto_init:false`, decision 8). So when the first blob write gets a 409, the step makes one bootstrap commit through the Contents API holding only `.devos/template.json` (a file of the core, with the same bytes), then pushes the full core as a second commit with the bootstrap as parent and moves `main` with `force:false` (a fast-forward). The final tree is still exactly the core. If GitHub accepts Git Data writes on an empty repo, the core is one root commit and no bootstrap is made. AT6 is worded for both.
- **Lookup = compare `main`'s tree with the core** (paths, modes and blob ids; a truncated tree listing is inconclusive, a `bad-response`):
  - equal → adopted (this covers a crash after the ref write, and a lost journal);
  - only the bootstrap file → treated as absent, and the create finishes the push on top of it (a crash right after the bootstrap commit);
  - anything else → `owned:false`, so the runner fails the step `name_conflict` (non-retryable); `main` is never overwritten or force-pushed. M2.4-d raises the decision card.
- **Ownership** comes from the `github/repo` step, which has already proven the repo is private and carries this project's marker. The commit itself carries no marker.
- **Not an inventory row.** The step is journalled with external id = the commit `main` points at, but `StepSpec.inventory: false` keeps it out of `resource`: the commit is deleted with the repo, and M2.5's purge must never meet a kind it has no ops for.
- **Writes and retries.** Every Git Data call is a write with exactly one attempt (decision 5). A blob id that differs from the local content hash is a `bad-response`. After the ref write, the step reads `main` again and fails unless it points at the new commit with the core tree. A ref write that times out after it happened is adopted by the runner's second lookup.
- **Policy action:** `provision.github.core`.

**Pre-review r1 (1 medium, 5 low; all accepted):**
- (medium) `.devos/template.json` holds `devosSha`, so a redeploy between two runs made DevOS's own bootstrap or core commit look like `other` → `name_conflict`. Now the manifest is compared without `devosSha` (it must still be a core-only golden-path manifest; the blob is read and its hash checked), and every other file must match exactly.
- (low) A 409 "empty" on the ref read now goes straight to the bootstrap; a 409 on the ref create is transient (the next run bootstraps first).
- (low) A stale read of `main` right after the push is transient, so the runner looks up again or ends `create_unconfirmed`, never a permanent error.
- (low) The step takes `assertLock` and re-checks the project lock before the bootstrap write and before the ref write (as c1 does, Codex PR50-r1).
- (low) Only a 404 or a 409 on the ref read means "absent"; any other answer is a `bad-response`.
- (low) A test for a valid but wrong blob id.

**Pre-review r2 (PASS, 5 low):** fixed (1) a 409 "empty" on a Git Data write just after the bootstrap is transient, so the next run carries on from the bootstrap; (3) a test for the root-commit path's ref create timing out after it happened; (5) the file cap is 100, under GitHub's secondary rate guide for content-creating requests. ## M2.4-c2 split and c2a build notes (12 Nov 2026, runner B, ADR-0013)
**Split** (concern rule). M2.4-c2 (DEVOS-120) is two PRs: **M2.4-c2a** (DEVOS-157, this PR) the Coolify application per environment and the S4 `afterStack` hook; **M2.4-c2b** (DEVOS-158) the generated app secrets as Coolify env vars plus the project-scoped vault `put` (AT7). The teardown ops for applications stay with M2.5-a3b (DEVOS-133).

**c2a decisions.**
- **Step** `coolify/application/<env>` (`src/application.ts`), after the environments and ports, policy action `provision.coolify.application`. Names (row 4): `devos-<slug>-preview` and `devos-<slug>-live`. S4 names the production stack `live` (`packages/isolation` `StackEnv`), so the hook gets `preview`/`live`, while Coolify keeps its `production` environment name.
- **Compose source.** The step reads `compose.yaml` from the repo at the core commit (the `github/core` journal row) with the Git Data reads M2.4-b already uses (tree, then blob, blob id checked against the content). It never reads a working copy or user input. A file over 64 KB, invalid YAML, duplicate keys or a document that is not a mapping is refused before the hook. Anchors are resolved; a `<<` merge key stays a literal key, which S4 refuses.
- **The hook is required.** `applicationStep` throws `provision-hooks-required` at construction without `hooks.afterStack`, so an unhardened stack can never reach Coolify (F3, fail closed). The hook gets `{id, slug}` and `{name, port, portRangeStart, compose}` (S4 decision 7). A refusal (S4 `compose_unsafe`, `limits_missing`, …) fails the step `provider_error`, non-retryable, and nothing is created. The M2.4-d wiring registers `isolationHook` from S4.
- **Create.** `POST /api/v1/applications/dockercompose` with `project_uuid`, `server_uuid` (`DEVOS_COOLIFY_SERVER_UUID`, set by M2.4-d), `environment_name`, `name`, a `description` carrying the ownership marker (decision 3), `docker_compose_raw` (the hardened Compose, base64), `instant_deploy:false` and `autogenerate_domain:false` (decision 1: tailnet only, no Coolify domain). M0.4 tested only `dockerimage` apps; the `dockercompose` endpoint and its body are confirmed by the AT13 live probe, which must also check that the stored description keeps the marker.
- **Lookup.** `GET /api/v1/applications`, filtered by name. As for projects, only a 200 with an array of well-formed entries (`name`, a uuid matching `^[A-Za-z0-9-]{1,64}$`, a string or null `description`) proves absence; anything else is an inconclusive `bad-response`. Our marker → adopt; same name without it → `name_conflict`. After the create, the application is read back from the list, so ownership comes from what Coolify stored; not yet listed → transient, so the runner looks up again instead of POSTing twice.
- **Lock.** All inputs (three journal rows, the Compose reads, the hook) are awaits after the runner's last lock check, so the step checks `assertLockHeld` again right before the POST (Codex PR50-r1 pattern).
- **c1 note 2 (fixed).** An inventory failure other than `resource_owned_elsewhere` during port allocation (for example a DB timeout) is now `provider_error`, **retryable**. If the insert committed, the re-run's lookup finds the row and keeps the port.
- **c1 note 3 (recorded).** The port lookup and the application name use the slug, so a project's slug must not change once provisioned. It does not: `project.slug` is the repo and Coolify name key.
- **New dependency:** `yaml` 2.8.1 (ISC licence; already in the workspace lockfile).

**Tests** (`test/application.test.mjs`): AT1 (both applications created from the repo's Compose as returned by the hook, marker in the create body, `instant_deploy:false`, no deploy call, inventory rows); AT2 (a re-run creates nothing; a lost journal adopts both and does not call the hook); AT3 (a crash after the create, before the DB write, is adopted) and AT4 (a POST that times out after it happened is adopted, one POST); a same-named foreign application → `name_conflict`; the hook is required and its refusal creates nothing; a policy deny creates nothing; no core commit, no `compose.yaml` or a lock lost after the hook → no POST; five inconclusive list shapes create nothing; Compose parsing limits; note 2 (retryable, and the re-run keeps the port). Provision suite 64/64.

The create now sends `autogenerate_domain:false`; the fake generates a domain unless told not to, and AT1 asserts the flag and that no domain was set.

- **Finding 2, the published port (fixed here).** S4 drops every Compose `ports` entry and leaves publishing to M2.4-c2, but the create never published the allocated port, so the tailnet address led nowhere. After the hook, `publishTailnetPort` adds to the core's `app` service exactly one binding, `<tailnet ip>:<port> → 3000/tcp` (`mode: host`). The bind address is the DevOS server's tailnet IPv4 (`ApplicationOptions.tailnetIp`, `DEVOS_TAILNET_IP`, set by the M2.4-d wiring), checked to lie in `100.64.0.0/10`; it is never `0.0.0.0`, so the stack is reachable on the tailnet only (decision 1). ## M2.4-c2b build notes (13 Nov 2026, runner B, ADR-0013)
**Scope.** Row 5 and decision 7: the generated app secrets of each environment, written as Coolify application env vars and sealed in the vault under a project-scoped `put` (AT7, plus AT1–AT4 for the secret steps). Teardown of these rows stays with DEVOS-131 (the vault scanner deletes by `project_id`; the env vars go with their application).

**Decisions.**
- **Steps** `vault/app_secret/<env>/<NAME>` (`packages/provision/src/app-secrets.ts`), after the applications: `SESSION_SECRET` and `DB_PASSWORD` per environment (`APP_SECRET_NAMES`), provider `vault`, kind `app_secret`, external id `<slug>/<env>/<NAME>`, policy action `provision.vault.app_secret`, `inventory:false` (not a resource row: DEVOS-131). The core uses neither yet; the add-ons read them.
- **Value.** `randomBytes(32)` as base64url (43 characters): printable, no whitespace, no `$`, so it passes the vault's value check and needs no quoting in Compose.
- **Port.** The step takes an injected `ProjectSecrets` (`has`, `put`), so `@devos/provision` never holds the vault key. apps/api implements it with `Vault.projectSecrets()` over the new `Vault.putProject` / `hasProject`: AES-256-GCM with AAD `devos-vault/v1\nproject:<id>\n<name>\n<keyVersion>` (a row moved to another project fails to open), `vault_secret.project_id` set, **no hint** (nothing about an app secret is shown), the audit event `vault.app_secret.saved|rotated` with the project and the name only, in the same transaction. Names are `<env>/<NAME>` (`^(preview|production)/[A-Z][A-Z0-9_]{0,63}$`). No schema change: the compound unique (`project_id`, `name`) is exact for non-null projects, and the M1.1 global trigger only guards `project_id` NULL rows. Global reads (`list`, `get`, `reveal`) still filter `project_id` NULL, so an app secret never shows in the wizard.
- **Present** = the vault row exists, the application (from the `coolify/application/<env>` journal row) lists the key (`GET /api/v1/applications/{uuid}/envs`) AND the listed value equals the vault copy (pre-review finding 1). The comparison happens inside apps/api (`ProjectSecrets.matches` → `Vault.matchesProject`: decrypt, constant-time compare); the provisioner hands the listed value over and drops it, keeping no copy, so no value outlives the lookup. Without the value check, a PATCH that failed, timed out or crashed after the vault put would be adopted with the vault and Coolify holding different values. Only a 200 array of keyed entries with string values is conclusive; anything else is `bad-response` and writes nothing.
- **Coolify `is_preview`.** Coolify's `is_preview` flag belongs to pull-request preview deployments of one application, which DevOS does not use (our `preview` stack is its own application). So every write sends `is_preview:false`, and `is_preview:true` entries do not count as present. This replaces the design sketch's "`is_preview` matching the env", which would have put the preview stack's secrets where its normal deployment never reads them. `is_literal:true` stops Coolify interpolating the value.
- **Create** = list the keys → generate → `assertLockHeld` → vault `put` (a rotation if a row exists) → `assertLockHeld` → Coolify `PATCH` when the key exists, else `POST`. The vault copy is written first, so an env var never exists without its vault copy. A crash or a rejected write between the two re-runs as a rotation (both places get one new value), harmless because M2.4 deploys nothing. A POST that times out goes to the runner's lookup (adopted if it happened, else `create_unconfirmed`); a 409/422 is looked up too.
- **Pre-review r2 (PASS, 2 low).** (L1, fixed) a listed variable with a null or missing value (an empty variable, or a token that may not read values) no longer makes the whole list inconclusive: its key counts as listed but can never match, so that secret is rewritten with `PATCH`. AT13 confirms the Coolify token can read env values; without that every run rotates. (L2, recorded) `matchesProject` is false for a row sealed under an older vault key version, so after a vault key rotation a re-run with a lost journal regenerates the app secrets in both places. It converges, and M2.4 deploys nothing; once stacks are deployed (M3.5) a rotation of the vault key must re-seal project rows first.
- **Build-time flag (recorded, pre-review finding 2).** Coolify's env-var body has a build-time flag whose name and default differ across v4 releases (`is_build_time`, or `is_buildtime`/`is_runtime`), and Coolify refuses unknown fields with a 422, so c2b sends none. AT13's live probe must read the stored env var back and confirm it is runtime-only (not a build ARG, which could reach build logs); if Coolify's default is build-time, M2.4-d sends the release's runtime-only field before any deploy (M3.5).
- **No value in any error.** Transport errors carry the method and path only; a vault or other non-provider error is journalled as its code (`provider_error`), never its message.

**Tests.** `packages/provision/test/app-secrets.test.mjs` (fake Coolify env endpoints that, like Coolify, return values): AT1 four secrets, same value in Coolify and the vault, distinct, not inventory rows; **AT7** captures every request except the env-var writes, every journal row (including a failed run's error line), the inventory, the audit events and all console/stdout/stderr output, and asserts no generated value appears; AT2 re-run and lost journal adopt without rotating; AT3 a crash between the two writes rotates on the re-run, on the POST path and on the PATCH path (a rejected, crashed or timed-out PATCH leaves a mismatch that the re-run rotates; pre-review finding 1); AT4 a POST that times out after or before it happened; an existing key is PATCHed, never duplicated; Coolify PR-preview entries do not count; fail closed (no application, policy deny, lost lock before the vault put, a vault failure, an inconclusive env list). Provision suite 77/77. apps/api: `test/setup.test.mjs` M2.4-c2b AT7 (project AAD, scoping, no hint, no global row, audit names only, input checks, a failed audit stores nothing), api 114/114; `test-db/stores.test.mjs` the Prisma upsert per (project, name) next to a same-named global row (runs in CI `api-db`).

**Wiring.** M2.4-d registers `appSecretSteps(cf, store, vault.projectSecrets(), project)` after `applicationSteps`, and only once M2.4-c2c (DEVOS-168) has merged (see the c2a notes). AT13's live probe confirms Coolify's `/applications/{uuid}/envs` bodies (`is_preview`, `is_literal`, PATCH by key) on the real server.

## M2.4-c2c split and c2c1 build notes (13 Nov 2026, runner B, ADR-0013)
**Split** (concern rule). M2.4-c2c (DEVOS-168) is two PRs:
- **M2.4-c2c1** (DEVOS-177, this PR): the per-project deploy key pair. The private half is a Coolify private key, the public half a read-only GitHub deploy key on the project repo. Both are create-or-get steps with inventory rows, and their teardown ops for M2.5-a3b.
- **M2.4-c2c2** (DEVOS-178): the application gets its repo source. The create moves to Coolify's private-deploy-key application (`private_key_uuid` from the `coolify/deploy_key` journal row, `git_repository`, branch `main`, `build_pack: dockercompose`). It also decides how the S4-hardened Compose stays the one that runs when Coolify re-reads the repo on deploy. c2a's behaviour (create-or-get, journal, marker, hook, tailnet port) is kept and re-tested there.

Row 4 is complete only when c2a, c2c1 and c2c2 have all merged. M2.4-d does not register `applicationSteps` before that.

**c2c1 decisions.**
- **Steps** (`src/deploy-key.ts`) run after `github/repo`, in this order:
  - `coolify/deploy_key`: provider `coolify`, kind `private_key`, policy `provision.coolify.private_key`.
  - `github/deploy_key`: provider `github`, kind `deploy_key`, policy `provision.github.deploy_key`, external id `<owner>/<repo>#<key id>`.
  - Both use the name and title `devos-<slug>-deploy`.
- **Key type and generation.** ed25519, generated in process with `node:crypto`. The private key is encoded as an unencrypted OpenSSH key; the encoder is ~20 lines, so no new dependency. A test decodes it independently and derives its public key with Node's own ed25519. Why ed25519: GitHub and Coolify both accept it, and the key is short.
- **F1: the private key is sent once and kept nowhere.** It goes in exactly one request, the Coolify `POST /api/v1/security/keys`, and its only reference is dropped in a `finally`. It is never in a step result, journal row, inventory row, error or log. Coolify's key list can return the private key itself, so each list entry is reduced to `uuid`, `name` and `description` at the parse. The test captures every other request, the journal, the inventory, errors and all console output, and asserts the key material appears in none of them.
- **The public key travels in the Coolify description.** The description is `DevOS deploy key <slug> devos:<project id> pub:ssh-ed25519 <base64>`. The public key is not a secret. So the GitHub step, and any re-run after a crash between the two steps, gets it from what Coolify stored, through the `coolify/deploy_key` journal row, without ever reading the private key.
  - Rejected alternative: storing the public key in DevOS's DB. That needs a schema change for one non-secret string.
  - Rejected alternative: deriving it from Coolify's `private_key` field. That would read the secret.
  - Trust note: anyone who can edit that description already controls Coolify, which holds every deploy credential.
- **Ownership.**
  - Coolify key: the marker and a parsable `pub:` in the description.
  - GitHub key: GitHub deploy keys have no description, so the key is ours when its title is ours, its key equals the described public key, and it is `read_only`.
  - A same-named Coolify key without the marker, or a same-titled GitHub key with another key or write access, is `name_conflict` (non-retryable, decision 2).
  - Two owned Coolify keys with our name are inconclusive (`bad-response`) and never adopted, because we cannot tell which one GitHub trusts.
- **Lookups prove absence only when conclusive.**
  - Coolify: only a 200 array of well-formed entries proves absence.
  - GitHub: one page of 100 (`per_page=100`). A full page is inconclusive, since a project repo holds one DevOS key.
  - Anything else is `bad-response` and creates nothing.
  - A Coolify create that answers 2xx but is not listed yet is transient. The runner looks up again (`create_unconfirmed`) instead of POSTing a second key.
- **Read-only.** The deploy key is created with `read_only: true`. A writable key under our title is a conflict, never adopted (least privilege).
- **Teardown ops** (`coolifyPrivateKeyOps`, `githubDeployKeyOps`), wired by M2.5-a3b (DEVOS-133):
  - Coolify inspect: our marker means owned.
  - GitHub inspect: owned when the repo is ours (private, with the marker) and the key is read-only.
  - Remove is one DELETE each; 404/410 means already gone.
  - Deleting the repo deletes its keys, so either order converges.
- **AT13 (live probe) must confirm:**
  - the `/security/keys` body (`name`, `description`, `private_key`);
  - that Coolify stores and lists the description unchanged;
  - that GitHub accepts the key read-only;
  - that the list response does not reach any log on the server side.

**Tests** (`test/deploy-key.test.mjs`, provision suite 88/88):
- The key pair is valid OpenSSH, and its public half is the published one.
- AT1: both halves are created, they match, the key is read-only, and both are inventoried.
- F1 capture: the private key appears only in the create body.
- AT2: a re-run, and a run with a lost journal, adopt without a new key.
- AT3: a crash after each create returns, before the DB write, is adopted on the re-run.
- AT4: a POST that times out after it happened is adopted, with one POST per half.
- A create not listed yet is `create_unconfirmed`, then adopted on the next run.
- The three conflicts above are `name_conflict`.
- Fail closed: no Coolify half yet, two owned keys, or five inconclusive list shapes create nothing.
- A policy deny creates nothing and is not counted as an attempt.
- Teardown: inspect, one DELETE each, then already gone.
