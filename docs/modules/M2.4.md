## Goal
"Done when": **re-running provisioning creates nothing twice.** When KK approves a project's requirements (M2.3 gate), DevOS provisions, without a person, every resource the project needs, and records each one in the inventory under the project's ID. Running it again, after a crash at any step, or after a partial failure, finishes the job and never creates a second copy of anything.

## Decisions (builder, recorded per ADR-0013)
1. **No Cloudflare in M2.4.** The PRD row "Cloudflare subdomains behind Access" is superseded: H2 (DEVOS-41) was cancelled and access is tailnet-only (ADR-0003, ADR-0005). Each stack gets a tailnet URL `http://devos:<port>` with the port allocated from a fixed range (`DEVOS_PROJECT_PORTS`, default 20000–20999, two per project, preview even / live odd). Coolify's proxy and auto-generated domains are off (`autogenerate_domain:false`, as in M0.4). Putting a project on the public internet is a **launch decision for KK** (M4.1), not something M2.4 does. The `cloudflare` provider value stays in the enum (backward-compatible) and is unused.
2. **Create-or-get by deterministic name, adopt on find.** Every step is: look up by the deterministic name at the provider → if found and tagged to this project, adopt it (record it in `resource` if missing) → else create → record. The unique `(provider, kind, external_id)` index makes the record step idempotent. A found resource **not** tagged to this project (e.g. a repo `devos-<slug>` that DevOS did not create) is never adopted: the step fails with `name_conflict` (non-retryable) and a decision card asks KK what to do (rename or adopt), because touching a resource DevOS does not own is a non-technical call.
3. **Ownership marker.** `devos:<project id>` in the resource's description, written **in the create call itself**, so a resource is never left half-tagged after a crash. GitHub: the repo description ends with the marker and the repo must be private (a public repo with the marker is not ours). Coolify: the project/app `description` contains the marker. M2.5's leftover scan uses the same marker. (A repo topic was considered and dropped: it needs a second call after the create.)
4. **Crash safety with a step journal.** A new table `provision_step` (project, step key, status `pending|done|failed`, attempts, last error, external id) is written *before* each external create (`pending`) and after (`done`). On re-run, a `pending` step is resolved by lookup (decision 2), never by blind re-create. One provisioning job per project at a time: a Postgres session advisory lock keyed on the project ID (see the M2.4-a build notes).
5. **Retries.** Lookups (GET) are retried with backoff and jitter on `retryable` errors (ADR-0009). Creates (POST) are **not** retried blindly: after a timeout or 5xx the step re-runs its lookup first, so a create that actually succeeded is adopted, not duplicated (ADR-0011 §9: retries only for safe operations). Every call has a timeout (GitHub 15 s, Coolify 30 s).
6. **Policy before writes.** Each external create goes through the M1.7 policy engine (`action: provision.<provider>.<kind>`, `resource: project:<id>`). In `observe` mode it is logged; `deny` stops the step with `policy_denied` (not an attempt).
7. **Secrets.** Generated with `crypto.randomBytes(32)`, written to Coolify env vars over the API and stored in the vault (ciphertext). Never logged, never returned by any route, never in the repo, never in `provision_step.last_error` (errors are redacted by name). The GitHub and Coolify tokens are read from the vault by name (M1.4 names `github_token`, `coolify_api_token`). The vault today seals global secrets only (`project_id` null); per-project app secrets need a project-scoped `put` in M2.4-c, using the existing `vault_secret.project_id` column (no schema change).
8. **GitHub repo creation.** `POST /user/repos` (private, `auto_init:false`), then push the S3 core as one commit via the Git Data API (blobs → tree → commit → `refs/heads/main`), so no `git` binary or credentials touch disk. Re-run: if `main` exists and its tree matches the template manifest, adopt; if `main` exists with other content, leave it (never force-push).
9. **Backups.** M2.4 only records the schedule (`backup_schedule/nightly`) and the Coolify scheduled-backup setting for the live database if the stack has one. The off-site target (R2, H7 DEVOS-34) is M4.5's; until KK creates it, backups stay on the server and the record says so.
10. **Size split** (rules: > ~800 lines or more than one concern → task sub-issues, one PR each, in order):
    - **M2.4-a** `packages/provision` core: provider clients (GitHub repo, Coolify project) over a fixed-origin transport with timeouts, the create-or-get step runner, the step journal + advisory lock, `provision_step` migration, inventory writes. Tests with recorded fake providers + Postgres (AT1–AT4, AT8, AT9).
    - **M2.4-b** repo from the S3 core (decision 8) + ownership tag (AT5, AT6 core half). Needs S3-a merged.
    - **M2.4-c** Coolify project, environments, applications, ports, app secrets (AT7, AT10).
    - **M2.4-d** wiring: run-engine job triggered by the M2.3 requirements-approved event, `POST /projects/{id}/provision` (retry, CSRF), `GET /projects/{id}/provision` status, the dashboard panel, backup + budget records (AT11, AT12).

## M2.4-a build notes (DEVOS-107)
- **Transport** (`src/http.ts`): one origin per provider (`https://api.github.com`; Coolify from config, e.g. `http://devos:8000`), `redirect: "error"`, `AbortSignal.timeout` on every call (GitHub 15 s, Coolify 30 s). Reads retry 3× on network/timeout/429/5xx with backoff + jitter; writes get exactly one attempt. The token comes from a callback (the vault) at call time and is only ever put in the `authorization` header; error messages carry method, path and status, never a body or header.
- **Runner** (`src/runner.ts`): `runStep` = done in the journal → return it (no calls) · lookup → owned: adopt, not owned: `name_conflict` · policy (`allow` only; `deny` → `policy_denied`, `require_approval` → `approval_required`, neither counts as an attempt) · journal `pending` · one create · on timeout/network/5xx/409/422 look up again and adopt, else `create_unconfirmed` (retryable; the next run looks up first) · record in `resource` + journal `done`. `runProvision` runs steps in order under the project lock and stops at the first failure.
- **Policy is required:** `runProvision` refuses to run without an `authorize` function (fail closed, ADR-0006); tests pass the explicit `allowAll`.
- **GitHub owner check:** before `POST /user/repos` the client checks `GET /user` login = the configured owner, so a mismatch fails before anything is created (no orphan repo). A 409/422 on create with nothing found under our name is a permanent `provider_error`; only timeouts, network errors and 5xx end `create_unconfirmed` (retryable).
- **For M2.5:** a `done` journal row is trusted without re-checking the `resource` row; Purge must reset the project's `provision_step` rows (or the runner must re-check), otherwise re-provisioning after a purge would report stale ids.
- **Decision card on `name_conflict`** is raised by the M2.4-d wiring (it needs M2.3-b); M2.4-a returns the typed, non-retryable error.
- **Stores:** `PrismaStore` (journal + inventory upsert; another project's row → `resource_owned_elsewhere`; a soft-deleted own row is reactivated) and `MemoryStore` (tests). The lock is a **session** advisory lock `pg_advisory_lock(hashtext('devos:provision'), hashtext(<project id>))` on a dedicated connection, held until the run ends or the connection drops (never released by a transaction timer, pre-review r1); a waiter fails after `lockWaitMs` (Postgres `lock_timeout`); the runner pings the lock connection before every create and stops with `provision_lock_lost` if it is gone. Journal and inventory writes commit immediately, so a crash never loses the record of a resource that exists at the provider. Every DB call and the vault token read are bounded (10 s, ADR-0011 §9). Runs for the same project on one store instance queue in-process first; a lock-wait timeout is the typed `provision_busy` (retry later, not an attempt). **Deployment:** the lock's `databaseUrl` must be a direct connection or a session-mode pooler, never a transaction-mode pooler (a session lock there could land on different server connections).
- **Schema:** `provision_step` (+ enum `provision_step_status`), migration `20261111000400_provision_step`, additive only, with DB checks: a done step has an external id, attempts ≥ 0, `last_error` ≤ 300 chars.
- **Tests:** `packages/provision/test/runner.test.mjs` (fake GitHub + Coolify behind a fetch stub: AT1, AT2, AT3 per step, AT4, AT5, AT8, AT9, AT12, token never in errors/journal, origin/path guard) and `test-db/prisma-store.test.mjs` on Postgres in the `provision-db` workflow (AT1–AT3, AT8, inventory ownership, DB checks).

## Review log
**M2.4-a, Codex PR44-r1 (12 Nov 2026; 1 high and 1 medium, both accepted):**
- (high) `CoolifyClient.findProjectsByName` treated a 404 or a body that is not an array as "no project", so the runner could POST a duplicate. Only a 200 with an array now counts as a confirmed absence. Anything else is a `bad-response` ProviderError, and the step fails as `provider_error` with nothing created.
- (medium) The response body was read outside the fetch error handler. A body that stalled until the timeout raised a raw AbortError, which skipped the read retry and the write reconciliation (AT4/AT9, ADR-0011 §9). The body read is now mapped to a transient `timeout`/`network` ProviderError. A GET is retried; a POST is looked up before any second create.
- Regression tests: an inconclusive list (404, an object, an empty body) creates nothing; a stalled body is retried on GET, is transient on a write, and a Coolify create whose response stalls is adopted with one POST. Both tests fail on the r1 code. 24/24 pass.

**M2.4-a, Codex PR44-r2 (12 Nov 2026; 2 medium, both accepted):**
- A same-named list entry with no string `uuid` was silently dropped, so the lookup could still miss our project. Now any malformed entry (not an object, or a non-string `name`/`uuid`) makes the list inconclusive (`bad-response`), and nothing is created. The test covers three malformed shapes.
- The lock connection's connect, `SET lock_timeout`, advisory-lock wait and `end()` had no client-side bound (ADR-0011 §9). Each is now bounded: `dbTimeoutMs` for connect, setup and end, and `lockWaitMs + dbTimeoutMs` for the lock wait, so Postgres's own `lock_timeout` still answers first. A stalled `end()` no longer holds up the run or the in-process queue; closing the socket still releases the session lock. Regression test: each stall fails, or for `end()` returns, within its bound. 25/25 pass.

**M2.4-a, Codex PR44-r3 (12 Nov 2026; 1 medium, accepted):** the lock could drop during the `markPending` journal write and the create would still run. The runner now checks the lock again after that write, right before the external create (a test drops the lock inside `markPending`; nothing is created).

**M2.4-a, Codex PR44-r5 (12 Nov 2026; 1 medium, accepted):** the GitHub login was cached per client, and each request read the vault token separately, so a token swapped after the owner check could create a repo in another account. `Transport.pinned()` now reads one token snapshot. `GitHubClient.createOwnedRepo` runs `GET /user` and `POST /user/repos` on that snapshot, and the login is no longer cached. ## M2.4-c split and c1 build notes (12 Nov 2026, runner B, ADR-0013)
**Split.** Coolify applications (row 4) build from the project repo, which needs the S3 core commit from M2.4-b, and M2.4-b waits on S3-a (PR #32). App secrets (row 5) are written as application env vars. So M2.4-c is built as two PRs:
- **M2.4-c1 (DEVOS-109, this PR):** environments and ports (rows 3 and 6, AT10). These need only the Coolify project from M2.4-a.
- **M2.4-c2 (follow-up issue):** applications per environment, app secrets (Coolify env vars plus a project-scoped vault `put`, AT7), the `afterStack` hook for S4, and the matching teardown ops for M2.5-a3.

**c1 decisions.**
- **Environments:**
  - Looked up with `GET /api/v1/projects/{uuid}/environments` and created with `POST` `{name}` (the endpoints recorded by the M0.4 04b spike).
  - Only a 200 with an array of named entries proves absence, as for projects (Codex PR44-r1/r2); anything else is an inconclusive `bad-response`, and nothing is created.
  - Environments carry no description. Their ownership comes from the parent Coolify project, which the `coolify/project` step has already proven, and whose uuid is read from that step's `done` journal row. With no such row, the step fails before any call.
  - External id: `<project uuid>/<env>`, as in the table above.
- **Ports:**
  - Each port is allocated through the inventory itself: a `coolify/port` row whose external id is the port and whose name is `<slug>/<env>`. The unique `(provider, kind, external_id)` index makes the allocation race-free across projects. A port that another project inserted first fails with `resource_owned_elsewhere`, and the next free port is tried.
  - Preview gets even ports and production odd ports. The range is `DEVOS_PROJECT_PORTS`, default `20000-20999`, validated to lie within 1024–65535.
  - A re-run finds the project's own active row by name and keeps the same port.
  - When no free port is left, the step ends with `port_range_exhausted` (non-retryable), and its code is kept in the journal: the runner now keeps a step's own typed `StepError`.
  - A port once held by another project, even a purged one, is not reused. That leaves 500 projects per default range, and widening the range is a setting.
- **Store:** `ProvisionStore.listResources(provider, kind)` is added to both stores. Allocation needs every row, across projects and including deleted ones.

**Tests.**
- `test/stack.test.mjs` covers:
  - AT1 and AT2 for environments and ports, including a fresh journal that adopts and keeps the same ports;
  - AT4: an environment POST that times out after succeeding is adopted, with one POST;
  - AT10: distinct and stable ports, even/odd parity, an exhausted range, and a port taken concurrently being skipped;
  - range parsing;
  - no create without a provisioned parent project.
- `test-db`: AT10 on Postgres, with two projects provisioned at once getting distinct ports, and a re-run keeping them.

**c1 pre-review (PASS, 5 low).** Fixed: (1) a Postgres test for a port taken between read and insert; (4) the fake Coolify creates `production` with each project (Coolify v4 does, M0.4 04b), so that step adopts it. **M2.4-c1, Codex PR50-r1 (12 Nov 2026; 1 medium, accepted):**

## M2.4-b build notes (DEVOS-108, 12 Nov 2026, runner B, ADR-0013)
**What it adds.** A `github/core` step (`src/core-repo.ts`) that runs after `github/repo`, plus `src/repo-content.ts`, which turns the S3 core into an in-memory file list.

**Decisions.**
- **The template comes in as files, not a path.** `coreTemplateFiles(apply, {devosSha})` calls S3's `apply()` (injected, so the package never imports from `scripts/`) into a fresh temp dir with no selection, reads it, and deletes the dir. It fails with `template-not-core-only` unless `.devos/template.json` has empty `selected` and `applied`. Each file carries its git blob SHA-1, so the tree on GitHub can be compared byte for byte without downloading blobs. Symlinks and other non-regular files are refused; paths with `..`, `.`, `.git` or unusual characters are refused; a template is capped at 500 files, 1 MB per file and 10 MB in all. The M2.4-d wiring must ship `scripts/template/` and `templates/golden-path/` in the worker image.
- **The empty-repo case.** GitHub's Git Data API answers 409 "Git Repository is empty" on a repo with no commits (the repo is created with `auto_init:false`, decision 8). So when the first blob write gets a 409, the step makes one bootstrap commit through the Contents API holding only `.devos/template.json` (a file of the core, with the same bytes), then pushes the full core as a second commit with the bootstrap as parent and moves `main` with `force:false` (a fast-forward). The final tree is still exactly the core. If GitHub accepts Git Data writes on an empty repo, the core is one root commit and no bootstrap is made. AT6 is worded for both.
- **Lookup = compare `main`'s tree with the core** (paths, modes and blob ids; a truncated tree listing is inconclusive, a `bad-response`):
  - equal → adopted (this covers a crash after the ref write, and a lost journal);
  - only the bootstrap file → treated as absent, and the create finishes the push on top of it (a crash right after the bootstrap commit);
  - anything else → `owned:false`, so the runner fails the step `name_conflict` (non-retryable); `main` is never overwritten or force-pushed. M2.4-d raises the decision card.
- **Ownership** comes from the `github/repo` step, which has already proven the repo is private and carries this project's marker. The commit itself carries no marker.
- **Not an inventory row.** The step is journalled with external id = the commit `main` points at, but `StepSpec.inventory: false` keeps it out of `resource`: the commit is deleted with the repo, and M2.5's purge must never meet a kind it has no ops for.
- **Writes and retries.** Every Git Data call is a write with exactly one attempt (decision 5). A blob id that differs from the local content hash is a `bad-response`. After the ref write, the step reads `main` again and fails unless it points at the new commit with the core tree. A ref write that times out after it happened is adopted by the runner's second lookup.
- **Policy action:** `provision.github.core`.

**Pre-review r1 (1 medium, 5 low; all accepted):**
- (medium) `.devos/template.json` holds `devosSha`, so a redeploy between two runs made DevOS's own bootstrap or core commit look like `other` → `name_conflict`. Now the manifest is compared without `devosSha` (it must still be a core-only golden-path manifest; the blob is read and its hash checked), and every other file must match exactly.
- (low) A 409 "empty" on the ref read now goes straight to the bootstrap; a 409 on the ref create is transient (the next run bootstraps first).
- (low) A stale read of `main` right after the push is transient, so the runner looks up again or ends `create_unconfirmed`, never a permanent error.
- (low) The step takes `assertLock` and re-checks the project lock before the bootstrap write and before the ref write (as c1 does, Codex PR50-r1).
- (low) Only a 404 or a 409 on the ref read means "absent"; any other answer is a `bad-response`.
- (low) A test for a valid but wrong blob id.

**Pre-review r2 (PASS, 5 low):** fixed (1) a 409 "empty" on a Git Data write just after the bootstrap is transient, so the next run carries on from the bootstrap; (3) a test for the root-commit path's ref create timing out after it happened; (5) the file cap is 100, under GitHub's secondary rate guide for content-creating requests. Left for **M2.4-d / AT13** (2): the empty-repo behaviour (409s, the Contents PUT with `branch:"main"` creating `main` as the default branch) is modelled on GitHub's documented behaviour in the fake; the live probe must assert `main` is the default branch and the history shape once on real GitHub. ## M2.4-c2b build notes (13 Nov 2026, runner B, ADR-0013)
**Scope.** Row 5 and decision 7: the generated app secrets of each environment, written as Coolify application env vars and sealed in the vault under a project-scoped `put` (AT7, plus AT1–AT4 for the secret steps). Teardown of these rows stays with DEVOS-131 (the vault scanner deletes by `project_id`; the env vars go with their application).

**Decisions.**
- **Steps** `vault/app_secret/<env>/<NAME>` (`packages/provision/src/app-secrets.ts`), after the applications: `SESSION_SECRET` and `DB_PASSWORD` per environment (`APP_SECRET_NAMES`), provider `vault`, kind `app_secret`, external id `<slug>/<env>/<NAME>`, policy action `provision.vault.app_secret`, `inventory:false` (not a resource row: DEVOS-131). The core uses neither yet; the add-ons read them.
- **Value.** `randomBytes(32)` as base64url (43 characters): printable, no whitespace, no `$`, so it passes the vault's value check and needs no quoting in Compose.
- **Port.** The step takes an injected `ProjectSecrets` (`has`, `put`), so `@devos/provision` never holds the vault key. apps/api implements it with `Vault.projectSecrets()` over the new `Vault.putProject` / `hasProject`: AES-256-GCM with AAD `devos-vault/v1\nproject:<id>\n<name>\n<keyVersion>` (a row moved to another project fails to open), `vault_secret.project_id` set, **no hint** (nothing about an app secret is shown), the audit event `vault.app_secret.saved|rotated` with the project and the name only, in the same transaction. Names are `<env>/<NAME>` (`^(preview|production)/[A-Z][A-Z0-9_]{0,63}$`). No schema change: the compound unique (`project_id`, `name`) is exact for non-null projects, and the M1.1 global trigger only guards `project_id` NULL rows. Global reads (`list`, `get`, `reveal`) still filter `project_id` NULL, so an app secret never shows in the wizard.
- **Present** = the vault row exists, the application (from the `coolify/application/<env>` journal row) lists the key (`GET /api/v1/applications/{uuid}/envs`) AND the listed value equals the vault copy (pre-review finding 1). The comparison happens inside apps/api (`ProjectSecrets.matches` → `Vault.matchesProject`: decrypt, constant-time compare); the provisioner hands the listed value over and drops it, keeping no copy, so no value outlives the lookup. Without the value check, a PATCH that failed, timed out or crashed after the vault put would be adopted with the vault and Coolify holding different values. Only a 200 array of keyed entries with string values is conclusive; anything else is `bad-response` and writes nothing.
- **Coolify `is_preview`.** Coolify's `is_preview` flag belongs to pull-request preview deployments of one application, which DevOS does not use (our `preview` stack is its own application). So every write sends `is_preview:false`, and `is_preview:true` entries do not count as present. This replaces the design sketch's "`is_preview` matching the env", which would have put the preview stack's secrets where its normal deployment never reads them. `is_literal:true` stops Coolify interpolating the value.
- **Create** = list the keys → generate → `assertLockHeld` → vault `put` (a rotation if a row exists) → `assertLockHeld` → Coolify `PATCH` when the key exists, else `POST`. The vault copy is written first, so an env var never exists without its vault copy. A crash or a rejected write between the two re-runs as a rotation (both places get one new value), harmless because M2.4 deploys nothing. A POST that times out goes to the runner's lookup (adopted if it happened, else `create_unconfirmed`); a 409/422 is looked up too.
- **Pre-review r2 (PASS, 2 low).** (L1, fixed) a listed variable with a null or missing value (an empty variable, or a token that may not read values) no longer makes the whole list inconclusive: its key counts as listed but can never match, so that secret is rewritten with `PATCH`. AT13 confirms the Coolify token can read env values; without that every run rotates. (L2, recorded) `matchesProject` is false for a row sealed under an older vault key version, so after a vault key rotation a re-run with a lost journal regenerates the app secrets in both places. It converges, and M2.4 deploys nothing; once stacks are deployed (M3.5) a rotation of the vault key must re-seal project rows first.
- **Build-time flag (recorded, pre-review finding 2).** Coolify's env-var body has a build-time flag whose name and default differ across v4 releases (`is_build_time`, or `is_buildtime`/`is_runtime`), and Coolify refuses unknown fields with a 422, so c2b sends none. AT13's live probe must read the stored env var back and confirm it is runtime-only (not a build ARG, which could reach build logs); if Coolify's default is build-time, M2.4-d sends the release's runtime-only field before any deploy (M3.5).
- **No value in any error.** Transport errors carry the method and path only; a vault or other non-provider error is journalled as its code (`provider_error`), never its message.

**Tests.** `packages/provision/test/app-secrets.test.mjs` (fake Coolify env endpoints that, like Coolify, return values): AT1 four secrets, same value in Coolify and the vault, distinct, not inventory rows; **AT7** captures every request except the env-var writes, every journal row (including a failed run's error line), the inventory, the audit events and all console/stdout/stderr output, and asserts no generated value appears; AT2 re-run and lost journal adopt without rotating; AT3 a crash between the two writes rotates on the re-run, on the POST path and on the PATCH path (a rejected, crashed or timed-out PATCH leaves a mismatch that the re-run rotates; pre-review finding 1); AT4 a POST that times out after or before it happened; an existing key is PATCHed, never duplicated; Coolify PR-preview entries do not count; fail closed (no application, policy deny, lost lock before the vault put, a vault failure, an inconclusive env list). **c2c1 decisions.**

The test captures every other request, the journal, the inventory, errors and all console output, and asserts the key material appears in none of them.

So the GitHub step, and any re-run after a crash between the two steps, gets it from what Coolify stored, through the `coolify/deploy_key` journal row, without ever reading the private key.
  - Rejected alternative: storing the public key in DevOS's DB. That needs a schema change for one non-secret string.
  - Rejected alternative: deriving it from Coolify's `private_key` field. That would read the secret.
  - Trust note: anyone who can edit that description already controls Coolify, which holds every deploy credential.

**Create.** `coolify/application/<env>` moves from `POST /api/v1/applications/dockercompose` (inline) to `POST /api/v1/applications/private-deploy-key` with `project_uuid`, `server_uuid`, `environment_name`, `name`, the marker `description`, `private_key_uuid` (the `coolify/deploy_key` journal row from c2c1), `git_repository: git@github.com:kkarnati1980/devos-<slug>.git`, `git_branch: main`, `build_pack: dockercompose`, `docker_compose_location` (below), `instant_deploy:false`, `autogenerate_domain:false`. **How the hardened Compose stays the one that runs (the open question from c2a).** A git-based `dockercompose` application loads its Compose file from the repo at deploy time, so `docker_compose_raw` set at create cannot be relied on: Coolify may overwrite it from the clone. Decision: the S4-hardened, port-published Compose is itself committed to the project repo, and the application points at it.
- **File:** `deploy/compose.<env>.devos.yaml` (one per environment, since the tailnet port differs), generated by the same path as c2a (core `compose.yaml` → S4 `afterStack` hook → `publishTailnetPort`), with a header comment saying it is generated by DevOS and must not be edited by hand. `docker_compose_location` is `/deploy/compose.<env>.devos.yaml`. `docker_compose_raw` is still sent with the same bytes, so Coolify's stored copy equals the file either way.
- **Commit:** a create-or-get step `github/deploy_compose` before the application steps: it writes both files in one commit on `main` with the Git Data API that M2.4-b uses (tree, blob, commit, fast-forward ref update, `force:false`). Re-run: a tree that already holds byte-equal files creates nothing; a different existing file is `compose_drift`, non-retryable, never overwritten silently (it means someone changed a DevOS-owned file).
- **Why this way:** it holds whether or not Coolify re-reads the repo; it keeps one source of truth (the repo) that the S4 checks and the live probe can read; and it avoids Coolify-only fields (custom start commands) whose behaviour is not documented as stable.
- **Keeping it true after provisioning (follow-ups, not this PR):** app builders must not edit `deploy/*.devos.yaml` (to be added to the golden-path owned-path rules and checked in CI); M4.2 (auto-deploy) regenerates and compares the files before each deploy; S4-c's live probe (F3-1/F3-2) checks the running stack, which is the final word.
- **AT13 (live, server agent):** after one deploy of `devos-probe-m24`, Coolify's stored Compose for each application equals `deploy/compose.<env>.devos.yaml` byte for byte, and `docker inspect` on the running `app` container shows the S4 network, limits and the single tailnet port binding.

**Decisions (technical, runner B):**
- **Where the hook runs.** The S4 hook, its 30 s bound and `publishTailnetPort` move from the application step into `github/deploy_compose`, which generates both files (core `compose.yaml` at the `github/core` commit → hook → port), compares them with `main` and commits once. The application step no longer runs the hook: it reads `deploy/compose.<env>.devos.yaml` from the `github/deploy_compose` commit, re-checks that it publishes exactly this stack's tailnet binding on `app` and nothing else (`assertPublished`), and sends those bytes as `docker_compose_raw`. So the c2a hook tests (required, refusal, hang, array, leaky ports, lock lost after the hook) now cover the deploy step, and no Git write happens on any of them.
- **Order.** `applicationSteps` returns `[github/deploy_compose, coolify/application/preview, coolify/application/production]`; the M2.4-d wiring registers it after `deployKeySteps`. The step's policy action is `provision.github.deploy_compose`; journalled, `inventory: false` (the files go with the repo).
- **Lookup.** Without this run's generated bytes there is nothing to compare, so a fresh lookup returns null and `create` decides: byte-equal files → the current head, no commit, no ref move; a different file → `compose_drift`. After a create whose outcome is unknown (ref PATCH timed out), the runner's second lookup compares with the bytes just generated and adopts. Accepted cost: a lost journal row shows as `created`, not `adopted`, asks the policy again and re-runs the hook; nothing is written.
- **Conflicting application name.** If an application name is taken, the deploy commit has already been made. That is intended: the file is DevOS-owned and does nothing without an application, and a re-run finds it byte-equal.
- **Lost `github/core` row.** `mainState` ignores exactly `deploy/compose.(preview|production).devos.yaml`, so the core is still adopted after the deploy commit; any other extra file is still `name_conflict`.
- **Tree rebuild.** The new tree is `main`'s blob entries plus the two files. A submodule or other non-blob mode on `main` is refused (`repo-entry-unsupported`) before any write.
- **Create body (pre-review).** Adds `ports_exposes: "3000"` (Coolify requires it on the git-based creates). **AT13 must also confirm** on the real server that `/applications/private-deploy-key` accepts `docker_compose_raw` base64-encoded (as the inline endpoint does) and rejects no field we send; if it rejects `docker_compose_raw`, drop it, since the committed file is the source either way. AT13 also confirms that the core's `build: .` resolves to the repo root (Coolify runs Compose with the checkout as the project directory), i.e. the image builds from `deploy/compose.<env>.devos.yaml`.
- **Missing deploy key rows.** The deploy step does not need the key rows, so with them missing the deploy commit is still made and only the applications fail; same reasoning as the name-conflict case.
- **File on `main` at create time (Codex PR115-r1).** Coolify clones `main`, not the journalled commit, and a resumed run skips the done deploy step. So before the POST the application step also reads `deploy/compose.<env>.devos.yaml` on the current `main` head and requires the very blob (same blob sha, mode `100644`) that the `github/deploy_compose` commit holds. A missing, edited or re-moded file is `compose_drift`, non-retryable, and no application is created; DevOS never re-commits over it. Chosen over re-running the deploy step on every attempt because that would re-run the hook and ask the policy again for a step that is done.

**d1 decisions.**
- **Trigger = a stage change in the approval's transaction.** `approveDoc` already runs under the project lock. It also moves `project.stage` from `intake` to `provisioning` (`updateMany where stage = intake`). The job is "projects in `provisioning`", so an approval queues exactly one job, and a retried or second approval queues none, because the stage is no longer `intake`. Nothing is written outside the transaction, so a crash can neither lose the job nor double it (AT11, trigger half). The change is additive: no new column, and the `provisioning` enum value already exists.
- **Runner = an API-side sweep, not the run-engine queue.** The run-engine queue carries model runs with cost reservations and turns. Provisioning makes no model call and must not take a run budget. A `ProvisionSweep` in `apps/api` (the same pattern as `analystSweep`: a timer, no overlapping ticks, every 60 s and at start-up) takes each `provisioning` project. A step that is already `done` is a lookup, never a create (AT2/AT3).
- **End states.** All steps `done` → stage `building`. A retryable failure leaves the stage at `provisioning`, so the next tick re-runs it; the journal makes that safe. After 5 failed ticks in a row, or on any non-retryable error, the project stays in `provisioning` and is parked: the sweep skips it until d2's `POST` retry. The step's failure is in `provision_step`. The parked set is kept in memory, so an API restart runs a parked project once more. That is safe, because a `done` step is only a lookup, and a non-retryable stop parks it again after one tick. `name_conflict` → one M2.3 decision card ("rename or adopt"), keyed on (project, step), so a re-run never opens a second card.
- **Policy.** `RunOptions.authorize` is the M1.7 grants engine (`provision.<provider>.<kind>`, `project:<id>`). Without a policy engine (no vault or DB), the sweep is off, with a logged code; it never runs with `allowAll` (fail closed).

## M2.4-d3c-2b decisions (DEVOS-234 part 2b, 16 Nov 2026, runner B, ADR-0013)

A read failure is a failed cycle, not a retry: the cycle purges and the next one runs in 7 days (or on the next provisioning change). The list is sorted, without repeats, and cut to the CLI's 120-character detail with a final `more-<n>`, so `safeDetail` always prints it.

Because `docker exec -d` returns before the shell runs, a step just started is never started again within a 10 s grace window.
3. **One cycle per check run where it fits.** (Pre-review 1: a step that leaves the phase where it was, such as a provider retry or a purge still running, ends the run as in progress instead of taking another step, so a retryable stop is retried on the next check run, not every few seconds.) The server agent runs its checks on each new main SHA and every 6 hours (DEVOS-90), not every tick, so one `step` per run could never finish a cycle inside `PROBE_PHASE_MAX_MS` (2 h). The check therefore keeps taking steps while the last one ended `in_progress`, until 80 s have passed (each docker call has its own 15 s timeout, so the check ends under the agent's 120 s limit). A long purge simply carries over to the next run.
4. **Verdict.** A step ending the cycle: exit 0 pass / 1 fail (with the fixed code). The probe off (`skipped`: no provider token, or no KK grant: `probe-purge-not-approved`) or still in progress: exit 3. Between cycles (`probed`) the check runs the read-only `report` and returns its exit (0 last cycle passed, 1 failed, 3 none). Any other CLI exit (2 usage) is a failure.
5. **Safety.** Only fixed strings reach `sh -c` (plus `PROBE_STATE_DIR`, a test-only override from the agent's own environment); nothing read from the probe or the server becomes part of a command. Output is the CLI's own JSON lines (fixed codes only, at most 2000 bytes each); no secret.
6. **KK's grant (d3c-2a decision 4), recorded, not sent yet.** The probe stays off (`probe-purge-not-approved`, exit 3) until KK issues a `teardown.archive` + `teardown.purge` grant on `project:<probe id>`. Today a grant is issued only through an approval card in the inbox (M2.3) or `POST /grants`, and the dashboard has no page for a free-standing grant, so there is nothing KK could click yet. Runner decision: KK gets no card until a click path exists; the follow-up (to file once Linear accepts new issues) is for the probe to raise an M2.3 approval request ("allow the weekly test project to be cleaned up") when it has no grant, so KK approves it from the inbox like any other card. Until then the check reports skipped, which blocks nothing.
7. **Hung step (pre-review 2).** A step whose pid file is older than 2 h (`PROBE_PHASE_MAX_MS`) while its process still runs fails the check (`hung`), so AT13 can never sit at "in progress" for ever.
8. **Recorded (low).** Two overlapping check runs (a `/recheck` seconds after a run that started a step at its last moment) could both start a step before either pid is written; the CLI's project lock covers the provisioner and the purge, and the phase log takes one row per step. A pid reused by another process after a container restart would read as "running" until that process ends; the step is then started on a later run. The window is small (the probe's pid file lives in the container's `/tmp`, which a recreate clears).

### AT13 probe failure diagnostics (DEVOS-21, 23 Nov 2026, runner B, ADR-0013)
- **Why:** the first cycle after KK's grant (server check on `692ad6a`, 23 Nov 2026, 16:29 IST) ended `purge-failed` / `purge-permission`. Two facts were missing from the check output: which provider refused (GitHub or Coolify, or the purge preflight), and why `run1` failed (the cycle went `run1` → `purge`, so run1 failed). Without them the KK step (which token needs which permission) cannot be named, and a card to KK on a guess could send him to the wrong setting.
- **Decision 1 (refusing provider):** `purgeStop` maps `provider_forbidden` to `purge-permission:<provider>/<kind>` when the teardown error names a resource (same `KIND_RE` filter as `purge-ownership`; the resource name is never printed), to `purge-permission:preflight` when it has none (in `@devos/teardown` only the purge preflight throws `provider_forbidden` without a resource), and to `purge-permission:resource` when it names a resource whose provider or kind fails `KIND_RE` (pre-review 1: never misread as the preflight). This supersedes the plain `purge-permission` in the d3c-2 sections above. `approval_required` and `policy_denied` keep their codes.
- **Decision 2 (earlier failure):** a failed purge's done row keeps the earlier failure as `cause` (pre-review L1) and now also its `detail` as `causeDetail`. `step` and `report` print both, through the same `safeDetail` filter as `detail` (anything outside our code shape prints `probe-detail-hidden`). This reverses the d3c-1 choice to keep the cause in the DB row only: it is a fixed code like `detail`, and the server check is the only place runners can read it (no server access).
- **Effect on the next cycle:** these files are in the probe fingerprint (`apps/api/dist/provision-*.js`), so the deploy that carries this change starts a new cycle at once. Its probe row still has active resource rows, so it starts with the purge (`previous-purge-pending`), and the server check then names the refusing provider. Its `cause` is `previous-purge-pending` with no detail: the 23 Nov cycle's run1 detail was not stored as `causeDetail` (pre-review 2), so why run1 failed shows only on a later cycle that reaches `run1` again (once the purge passes). The KK card follows from that line, per the d3c-2 rule ("grant repo delete on the provisioning token through the setup wizard" when it is GitHub).
- **Tests:** `apps/api/test/provision-probe-purge.test.mjs` (provider/kind named, preflight, odd kind hidden), `provision-probe.test.mjs` (cause detail on the record and the tick; no cause without an earlier failure), `provision-probe-cli.test.mjs` (step and report print cause and cause detail; an odd cause detail is hidden).

### AT13 probe failure diagnostics, part 2: which preflight token (DEVOS-21, 23 Nov 2026, runner B, ADR-0013)
- **Why:** the server check on `04a7b18` (23 Nov 2026, 17:03 IST) shows cycle 2 ended `purge-failed` / `purge-permission:preflight` (cause `previous-purge-pending`). The purge preflight runs two checks (`githubTokenScopeCheck`, `coolifyTokenScopeCheck`, see "M2.5" decisions and DEVOS-235), and each can refuse for several reasons. Each reason is a different KK step (give the GitHub token all repositories; use the token of the repo owner's account; use the Coolify token of the right team), so the card cannot be written until the code names one.
- **Decision 3 (preflight reason):** `purgeStop` appends a fixed reason to `:preflight`, read by `preflightReason` from the teardown message. `purgeProject` wraps a preflight throw as `purge preflight: <message>` and both checks start every message with their own code (`github-token-scope:` / `coolify-token-scope:`), so the match is anchored on our own text, never a provider body. Reasons: `github-counts` (`/user` answered 200 without the login or repository counts), `github-owner` (the token's login is not the repo owner), `github-list` (the owned-repo list is unreadable), `github-repos` (the token sees fewer repos than the account owns), `github-scopes` (part 3 below: a classic token without the private count and without the `repo` scope), `coolify-id` (a recorded id is not a uuid), `coolify-team` (404 for a recorded Coolify project: another team's token), `coolify-answer` (an inconclusive answer). Pre-review 1: the transport throws a non-transient `ProviderError` for a missing token and for any non-2xx answer but 404, and teardown wraps its message the same way, so those name the token too: `github-no-token` / `coolify-no-token` (no token in the vault), `<token>-http-401` (expired or revoked), `-http-403` (not allowed), `-http-422` (the provider refused the request as invalid); another status prints only the token name. Codex PR222-r1/r2: in production the tokens are read first when `teardownWiring` pins the two clients, before `purgeProject` runs. That throw is left on its old path (rethrown, so `probeStep` keeps the phase in progress and the next tick retries, bounded by `PROBE_PHASE_MAX_MS`), because `readToken` reports an absent token, a failed vault read and a vault timeout all as `no-token`, and a vault outage must never end a cycle as a credential problem (r2 reverses the r1 mapping). An absent token is already named before any cycle: `offReasonFor` skips the probe with `provisioner.ready()`'s reason. With the production wiring the preflight runs on the pinned snapshot, so `<token>-no-token` there is kept only for a check built on an unpinned client. A new reason from a known check prints only `:preflight:github` / `:preflight:coolify`; any other preflight message stays plain `:preflight`. Only these codes are printed: no message text, count, login or status (the CLI `safeDetail` filter accepts the shape).
- **Why parse the message, not change @devos/teardown:** the smallest change that names the token, in the probe's own file. The table is tied to the real messages by a test that runs the real checks inside the real `purgeProject`, so a reworded check message fails CI instead of silently falling back.
- **Effect on the next cycle:** `apps/api/dist/provision-probe-purge.js` is in the probe fingerprint, so the deploy that carries this starts cycle 3 at once; it again starts with the pending purge, and the server check names the token and reason. The KK card follows from that line.
- **Tests:** `apps/api/test/provision-probe-purge.test.mjs` "DEVOS-21 part 2" (all seven check reasons through the real checks and the real `purgeProject` over a fake http layer that answers as the real transport does; the transport's thrown `ProviderError` for 401, 403, 422, another status and a missing token; a failed pin, through the real `teardownWiring` and `probePurge`, stays retryable with nothing run after it; unknown reason keeps the token name; foreign message stays plain; the anchor holds).

### AT13 probe failure diagnostics, part 3: a classic token's `repo` scope proves the purge preflight (DEVOS-21, 23 Nov 2026, runner B, ADR-0013)
- **Why:** the server check on `2f4a5fa` (23 Nov 2026, 18:08 IST) shows the AT13 probe purge refused with `purge-permission:preflight:github-counts`: `GET /user` answered 200 without `owned_private_repos`. GitHub's "Get the authenticated user" documentation (REST, users) says classic personal access tokens and OAuth app tokens "need the `read:user` scope, or the broader `user` scope" for the private user response, and "tokens without these scopes receive the public user response" (login and `public_repos`, no private counts). A provisioning token with `repo` and `delete_repo` but no `read:user` is valid and least-privilege, so the check refused a token that sees everything.
- **Scope:** every changed source file is in this module (`packages/provision/**`, the DEVOS-21 probe files). `githubTokenScopeCheck` lives in `packages/provision/src/teardown-ops.ts`, a file M2.5 added to this package; its rule (M2.5, "M2.5-a2 build notes") is unchanged in meaning: the token must see every repo its owner owns. Codex PR223-r1 finding 1: the first head also edited `packages/teardown/test/teardown.test.mjs` and M2.5's contract; those edits were moved here and the tests to `packages/provision/test/github-token-scope.test.mjs`.
- **Decision 1 (the other proof):** a classic token cannot be narrowed to selected repositories; with the `repo` scope it sees every repository its owner owns. GitHub reports a classic or OAuth app token's scopes in the `X-OAuth-Scopes` response header. So when the `owned_private_repos` field is **absent**, the check passes only if that header (on the same pinned `/user` answer) lists `repo` exactly (trimmed, comma-separated; `public_repo`, `repo:status`, `repository` are not `repo`), the login is the owner (unchanged), the owned-repo list reads to its end (a page is the last only when it is short and its `Link` header names no `rel="next"`, Codex PR223-r3; the purge's leftover scan `githubScanner` reads pages by the same rule through the shared `linkHasNext`, Codex PR223-r4, which reads `rel` in any parameter position and as a space-separated relation list per RFC 8288, Codex PR223-r5, with a tokenizer so a `<`, `,` or `;` inside a quoted value never splits a link, a nameless parameter or a `rel` with no value (bare, `rel=`, `rel=""`) is unparseable too (Codex PR223-r7), and each relation type in `rel` must be a registered name (a letter, then letters, digits, `.` or `-`) or an absolute URI per RFC 8288 §3.3 (any RFC 3986 scheme, e.g. `urn:example:x`, with a non-empty path, an optional query and at most one fragment, so `urn:x#one#two` is unparseable; Codex PR223-r18/r19), so `rel="next,"` is unparseable (Codex PR223-r14), and the grammar is an allow-list: a parameter name and an unquoted value are each one or more RFC 7230 token characters, so any other character where a name or unquoted value is expected (e.g. `rel=next"`, `re"l=next`, `rel=ne<xt`, `title=`) is unparseable (Codex PR223-r9), and each link target between `<` and `>` must be an absolute `http(s)` URI, `scheme://host[:port]` (reg-name host, numeric port, no userinfo, no brackets) with an optional path of pchar and `/`, an optional `?query` and `#fragment` that add only `/` and `?`, valid `%` escapes, and it must also parse as a WHATWG URL, whatever its `rel`; so `<bad target>`, a relative target, a second `#` or a port like `:abc` is unparseable (Codex PR223-r10/r11/r12); and every `rel=next` target must be exactly the request the reader makes next (the origin of the reader's fixed transport, compared as a WHATWG origin so scheme, host and port all match, Codex PR223-r13; path `/user/repos` and exactly the query `per_page=100`, `page=<next>`, `affiliation=owner`, each once, nothing extra), so a header that skips a page (page 1 naming page 3), shifts the offset (`per_page=50`) or names two different next pages is unparseable too (Codex PR223-r11/r12); a `rel=last` link must agree: its target is the same request with one decimal `page` no lower than the page just read (the same value if repeated), and a last page beyond the current one with no `rel=next`, or a `rel=next` when the current page is the last one, is unparseable, so a short page 1 naming page 3 as last without a next link is never the end of the listing (Codex PR223-r15); a last page told by an earlier page binds every later page of the same read (a later page without a `Link` header, or naming another last page, before that page is unparseable), and the preflight requires the list read to its end whether or not the private count is present, so a met count never stands in for a page GitHub still advertises (Codex PR223-r16); a full page with no `rel=next` is the last page when a validated `rel=last` names that page, so exactly a page-cap's worth of repos still reads as complete (Codex PR223-r17); on the count path every entry must also be a repo (a numeric id seen once, a non-empty name), so a repeated entry never makes up the count (Codex PR223-r18); the `owner.login` check stays on the scope path only, because the count is already the owner's own and M2.5's teardown fixtures (packages/teardown, not M2.4's files) list repos without `owner` (Codex PR223-r19); an entry that names an owner must name this owner on both paths, and on the scope path every entry carries a boolean `private` and the public entries alone must reach `public_repos`, so private repos never stand in for public ones (Codex PR223-r20); every link must carry exactly one `rel` parameter (RFC 8288 §3.3: `rel` MUST be present), so a link with no `rel` (e.g. a short page whose `Link` names page 2 with only a `title`) or with two `rel`s is unparseable, never "no next page"; and the leftover scan refuses a repository seen twice across pages (by full name, case-insensitive, or by numeric id when present; a non-numeric id is a malformed entry) with `bad-response`, because a repeated row means the listing shifted and a repository may have been skipped (Codex PR223-r21); an unparseable header on any page makes the whole listing inconclusive: the preflight refuses with `github-list` and the leftover scan fails with `bad-response`, never "complete" (Codex PR223-r8, replacing the r6 "read on" rule), so a repo on a later page is never missed after the preflight passes; a page-cap hit is `github-list`), every entry in it is an identifiable repo of the owner (a numeric id seen once, a non-empty name, `owner.login` = the owner; otherwise `github-list`, Codex PR223-r2), and it holds at least `public_repos`. Both counts must be non-negative safe integers, or the answer is `github-counts` (Codex PR223-r5). This is the same fact proved from the token's type instead of a count, so the check is not weaker. When the count is present the old rule runs unchanged.
- **Decision 2 (still refused):** no header or an empty one (a fine-grained or app token: GitHub sends no scopes) keeps `github-counts`; a header without `repo` is the new reason `github-scopes`. Codex PR223-r1 finding 2: a field that is present with a non-number value (null, a string, an object) is malformed and stays `github-counts`; only an absent field takes the scope proof. If the server's token is fine-grained, the next card asks KK for a classic token with `repo`, `delete_repo` and `read:user`.
- **Decision 3 (transport):** `HttpResult` gains an optional read-only `headers` on 2xx answers (additive; no existing caller reads it). Callers read one named header; headers are never logged or put in an error.
