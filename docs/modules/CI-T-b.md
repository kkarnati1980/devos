# CI-T-b — ci-gate aggregator (DEVOS-152, task of DEVOS-139)

- **Lane:** C (runner B). **Spec:** KK, `claude/devos-ci-minutes-reduction-spec-v1.0.1.md`, constraint C2 and G4. **Decision:** `docs/decisions/0017-ci-gate.md`. **Used by:** DEVOS-143 / DEVOS-145 (the `main` ruleset requires this check).
- **Owned files:** `.github/workflows/ci-gate.yml`, `scripts/ci/ci-gate.mjs`, `scripts/test/ci-gate.test.mjs`, `scripts/test/ci-gate-workflow.test.mjs` (DEVOS-202), this contract, the decision note.

## Purpose
One check, `ci-gate`, that always reports on every PR into `main` and is green only when every other PR check on the head SHA is green. Path filters (a later DEVOS-139 step) can then skip jobs without leaving a required check unreported or a PR silently mergeable.

## Behaviour
1. **Expected set.** The PR head's `.github/workflows/*.yml` (the gate's own file excluded). The base commit's workflows are read too: if the PR removes or narrows a check `main` runs, the gate fails at once (exit 2), because removing a check needs its own approved change (G5). The head files stand in for the merge commit GitHub runs; a workflow changed on both sides can differ, and the base check covers the removal case. In each: every job of every workflow whose `pull_request` trigger applies to the PR's base branch (`branches` / `branches-ignore` with exact names or `*`). A check is named by the job's `name`, else its id. Push-only workflows are not expected.
2. **Fails closed** (exit 2) on anything it cannot reason about yet: `paths` / `paths-ignore` / `types` on `pull_request`, a job `if:`, a matrix, a reusable-workflow job, a computed job name, a branch glob, two jobs with one check name, an empty expected set, missing inputs, or an API read error. Path-filter support lands with the path-filter step, behind this gate.
3. **Wait.** Reads the head SHA's check runs (GitHub REST with `filter=all` so no older same-named run is hidden, 15 s timeout per call, paginated, up to 3 attempts per page for a 5xx, 429 or network error; a 4xx or a third failure is exit 2) every 20 s. Only runs by the `github-actions` app count, so another app posting a same-named success is ignored. A name reported from more than one check suite (another workflow run with a job of the same name, e.g. push-triggered) fails as `reported-by-more-than-one-workflow-run`; a re-run stays in its suite. (Closing and reopening a PR on the same SHA starts new suites, so the gate fails; push a new commit instead.) The newest run of each name counts (re-runs). Any completed conclusion other than `success` (failure, cancelled, timed_out, skipped, neutral, action_required, stale) fails at once. Not every check finished after 27 minutes → fail (the job's timeout is 30).
4. **Trust (DEVOS-202, notes 0017 and 0023).** `pull_request` runs the PR's own copy of `ci-gate.yml`; changes to the workflow are caught by the floor guard's content rules (a changed or removed step is a `ci-step-*` hit) and by Codex review. The gate's **code** runs from the PR's **base** commit, the way `floor-guard.yml` runs the base guard. A third checkout puts the whole `pull_request.base.sha` tree at `.gate-src`; the step "Use the base commit's copy of the gate's code and its yaml" then (a) refuses (exit 2), changing nothing, if the base lacks `scripts/ci/ci-gate.mjs`, `scripts/release/merge.mjs`, `scripts/release/required-checks.json`, `scripts/floor-guard/floor-guard.mjs` or `scripts/gates/kk-only.mjs`, or if the head puts something on the gate's module-resolution path or into the install: a `node_modules` anywhere under `scripts/`, a symlinked `scripts/` or gate directory, a `.pnpmfile.cjs` (head or base), or an `.npmrc` unlike the base's; (b) replaces the head's `scripts/ci/`, `scripts/release/` and `scripts/floor-guard/` directories and `scripts/gates/kk-only.mjs` with the base copies (head-only files there are dropped); (c) moves the base checkout to `$RUNNER_TEMP/gate-base` (outside the workspace), installs its root dependencies from the base lockfile there (`--ignore-scripts --ignore-pnpmfile`), refuses (exit 2) if that install has no `yaml`, and points the workspace's `node_modules/yaml` at the base install. The next step, unchanged, runs `node scripts/ci/ci-gate.mjs` in the head checkout, so the gate and every relative import from it (`merge.mjs`, `required-checks.json`, `floor-guard.mjs`, `kk-only.mjs`) and `yaml` are the base's, while the head's workflow list and git history are still what it judges. A head's edits to these paths take effect for `ci-gate` only after they merge. A ruleset "required workflow" from the base branch would also pin the workflow file; it stays recorded for DEVOS-145.
4a. **Deadline.** 27 minutes from the gate's start, inside its 30-minute job timeout (the 0016 ceiling). A watched job still running then is close to its own 30-minute timeout; the gate fails closed and is re-run. **Re-runs:** the gate fails at the first failed check; after re-running that job, re-run `ci-gate` too (it is not re-triggered by other workflows).
4b. **Entry.** The CLI runs `main()` whenever it is the script node was asked to run, resolved through symlinks, spaces and `%`, so it can never exit 0 without checking.
5. **Exit codes:** 0 pass · 1 a check failed or did not finish in time · 2 error. Only 0 is a pass.

- recorded: the 27-minute deadline stays inside the 30-minute job ceiling from 0016 (a longer gate would need that ceiling raised for this one job; the gate fails closed if a job runs that long); re-running a failed job also needs a manual `ci-gate` re-run (documented above).
Re-review (CHANGES_REQUESTED, 7 findings): fixed — a same-named run from another workflow run can no longer stand in for a check (medium); a removed check fails at once instead of after the deadline (low); a suite test added. Recorded:
- **Stale green (medium), for DEVOS-145:** once `ci-gate` passes it does not look again, so a later failing re-run of a watched job leaves it green. DEVOS-145 must keep each job that has no path filter as its own required check alongside `ci-gate`, or add a re-trigger, before `ci-gate` is the only required CI check.
- **Merge order (medium):** this PR merges after #68 (DEVOS-139 step 1, `0016-ci-throughput.md`), which gives every watched job a timeout of 30 minutes or less; the 27-minute deadline assumes those.
- Tag-pinned Actions match every other workflow (repo-wide C3 follow-up); `main()` end to end with a stubbed `fetch` is left to the throwaway-PR proof in DEVOS-139.
- **Codex PR73-r1 (1 medium, fixed):** the check-runs read now passes `filter=all`; GitHub's default `latest` could hide an older failed run of the same name from another suite before the suite rule saw it. AT8 asserts the parameter.

## Codex PR73-r3 (13 Nov 2026; 1 medium, accepted)
- `expectedUnion` returned the head-only set when `GATE_BASE_WORKFLOWS_DIR` was absent or empty, so a misconfigured run skipped the base comparison. It now refuses that with a `GateError` (exit 2) before reading any workflow; the workflow always sets the input. Test: `undefined`, `""` and blanks are refused.

## Codex PR73-r4 (13 Nov 2026; 1 medium, accepted)
- `evaluate()` caught an unrelated workflow only when both suites had already reported, so a push-only job of the same name that reported first could satisfy an expected check. **Decision (runner B):** each expected check is now owned by the workflow file that defines it (`checkOwners`). Each poll reads the head SHA's workflow runs (`GET /actions/runs?head_sha=…&event=pull_request`, same timeout, paging and retry rules; the job gains `actions: read`) and tags every check run with the file of its PR workflow run, or null (`attributeRuns`). A run counts only when that file owns its name; anything else is ignored, so the expected check stays pending until its own PR run reports, and the 27-minute deadline still fails closed. Check runs are read before workflow runs, so a suite created between the two reads is still attributed. The multi-suite rule now applies only to PR runs of the owning file (e.g. a reopen). Rejected alternative: matching on the workflow run's `name` — names are not unique; the file path is.

## DEVOS-202: base copy of the gate (runner B, 14 Nov 2026)
- **Decision:** the gate's code (`scripts/ci/`, `scripts/release/` with `required-checks.json`, `scripts/floor-guard/`, `scripts/gates/kk-only.mjs`) and its `yaml` come from `pull_request.base.sha`; see Behaviour 4. Reason: note 0023's gap (a head could change the rules its own `ci-gate` result is judged by) is closed the way `floor-guard.yml` closes it for the guard, with no new guard paths and no extra PRs.
- **Why a swap step rather than editing the existing steps:** a first draft changed the base checkout, the install step and the gate step. Each changed step is a floor-guard `ci-step-*` hit, and the pre-review found two of them KK-only (long texts fail closed in the KK-only classifier), which would have stalled the PR on KK for a technical change. Adding one checkout and one step leaves every existing step byte-identical, so the floor guard reports no hit.
- **No bootstrap fallback:** unlike `floor-guard.yml`, a base without the gate files exits 2 instead of using the head's copy. Every PR base is `main`, which has had them since DEVOS-152/DEVOS-179, so a fallback would only be a way round the rule.
- **Still from the head, and the residual risk:** the workflow file itself (covered as above), the Node version (`.nvmrc`), and the existing head install step, whose `yaml` link is then replaced. That install runs before the swap, so code the head makes pnpm run at install time could tamper with the job. The swap step narrows this (it refuses the known carriers listed in Behaviour 4 (a) and adds `--ignore-pnpmfile` to the base install) but cannot undo what already ran. Accepted for now, because (1) the workflow file is the head's anyway, so `ci-gate` is a consistency check against honest rule drift rather than a boundary against a hostile head; (2) the merge gate is the Release script, run from `main` (note 0023, reason 1); (3) removing or changing that step is a KK-only floor-guard hit. Follow-up: **DEVOS-206** (drop the head install and run the gate from `$RUNNER_TEMP/gate-base`, decided together with DEVOS-145's base-branch required workflow).
- **Pre-review (runner B, 14 Nov 2026), round 1:** 2 findings, 2 fixed — the KK-only hits (medium; fixed by the redesign above, 0 floor-guard hits) and a too-broad exemption in AT13's "no head copy" scan (low; that scan is gone, AT13 now runs the steps and checks the exact step layout).
