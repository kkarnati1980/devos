# S3 — Modular golden-path template (contract)

- **Linear:** DEVOS-64 · parent DEVOS-61 (Phase PS) · P2 · Lane B · blocks M2.4 (DEVOS-21) and G2 (DEVOS-46)
- **Split (size rule, 11 Nov 2026):** the module is over 800 changed lines and more than one concern, so it is built as task sub-issues, one PR each, in this order:
  - **S3-a** core + the `apply` tool + floor checks for the core (DEVOS-92);
  - **S3-b** add-ons SM-01 … SM-06 (DEVOS-93);
  - **S3-c** add-ons SM-07 … SM-12 (DEVOS-94);
  - **S3-d** add-ons SM-13 … SM-18 (DEVOS-95).
  M2.4 needs only S3-a (repos are created from the core; add-ons are applied later from the selection by M3.2), so M2.4 can start once S3-a merges.
- **Depends on:** S1 (catalogue, check IDs). Applies ADR-0010 (modular standard), ADR-0011 (timeouts on outbound calls), D13 (licences).
- **Source:** Phase PS build standard v1.1.0 §6 (S3 row) and §7 (M2.4 amendment); build plan v1.0.3.

## Goal
A template every DevOS-built app starts from:
- **Core** (always): F1 config (no secret reaches the client), F2 `safeFetch`, F3 Compose limits, `/health` + `/ready`, JSON logging with a request ID.
- **Add-ons**: one per selectable module (SM-01 … SM-18), copied in only when that module is selected for the project.

## Done when (DEVOS-64)
1. The core alone passes the floor checks.
2. Each add-on applied alone passes its Lite checks.
3. Unselected add-ons are absent from the generated repo.

## Design decisions (technical, made by runner B on 11 Nov 2026 under KK's standing order)
- **Stack: Node.js 22, ESM JavaScript, no runtime dependencies in the core.** The core uses only `node:http`, `node:https`, `node:dns`, `node:net` and `node:crypto`. Reasons: the floor code (`safeFetch` above all) must be small enough to review line by line; no third-party package in the core means no licence or vulnerability work for every app (SM-14 then starts from zero findings); DevOS itself is Node 22, so the sandbox, tests and CI images are shared. Add-ons may add pinned dependencies with permissive licences (MIT, ISC, BSD, Apache-2.0) only; anything else is a D13 card.
- **floor-check scope (F2-1):** any import, dynamic import or `require` of `node:http`, `node:https`, `node:http2`, `node:net`, `node:tls` or `node:dgram` outside `src/safe-fetch.mjs` is a finding (so aliases and namespace imports cannot slip through); the one exception is `src/server.mjs`, which may import `node:http` only as a default/namespace import or `{ createServer }`, and may use that binding only for `createServer`, `STATUS_CODES` and `METHODS`. Also flagged anywhere: `globalThis.fetch`, `node:module`, `node:child_process`, `node:worker_threads` and `import()` of a computed name. Also flagged: `fetch(`, HTTP client packages, `XMLHttpRequest`/`WebSocket`/`EventSource`, Python HTTP clients and sockets. Only the root `test/` folder is exempt (tests use `fetch` against local stubs); only root-level `dist`/`build`/`coverage` are skipped. Browser code under `public/` is not F2 (it talks to its own origin) and is covered by F1-4. A static check cannot prove there is no other egress path; F3-1 (S4's probe) is the backstop.
- **Layout in the DevOS repo:** `templates/golden-path/core/` (the core app), `templates/golden-path/addons/<SM-id>/` (one directory per add-on, each with an `addon.json` naming its module, the files it adds and the Lite check IDs its tests cover), `scripts/template/apply.mjs` (the generator), `scripts/template/floor-check.mjs` (static floor checks for a generated repo).
- **Selection input:** `apply.mjs --out <dir> [--select SM-01,SM-09,…]`. The selector (S5) owns `selection.md`; M2.4/M3.2 pass the selected IDs to `apply`, so S3 does not parse `selection.md` and the two modules cannot drift. An ID that is not a selectable module in `build-standard.yaml` is refused (exit 2, nothing written). A selected module whose add-on is not built yet is listed under `pending` in the manifest, never silently skipped.
- **Manifest:** `apply` writes `.devos/template.json` in the generated repo: template version, the DevOS SHA it came from (`--sha`, default `git rev-parse HEAD` of the DevOS checkout), `selected`, `applied`, `pending`. S6 and the Codex reviewer read it.
- **`apply` never overwrites:** the output directory must be empty or absent (exit 2 otherwise), so it cannot clobber a project.
- **F1 in the core:** `src/config.mjs` reads the environment once on the server. `clientConfig()` returns only the keys listed in `CLIENT_CONFIG_KEYS` (empty by default); a listed key whose name looks like a secret (`SECRET`, `TOKEN`, `KEY`, `PASSWORD`, `PRIVATE`) is refused at start-up. Client code lives under `public/` and must not read `process.env` (static check).
- **F2 in the core:** `src/safe-fetch.mjs`:
  - only `http:` and `https:`;
  - the host is resolved once, every resolved address is checked, and the connection is pinned to a checked address (no second lookup, so DNS rebinding cannot swap it);
  - refused ranges: IPv4 0/8, 10/8, 100.64/10 (CGNAT and the tailnet), 127/8, 169.254/16 (metadata), 172.16/12, 192.168/16, 192.0.0/24, 198.18/15, 224/4 and above, plus the Docker default 172.17/16 (inside 172.16/12); IPv6 `::`, `::1`, `fc00::/7` (ULA), `fe80::/10`, `ff00::/8`, and IPv4-mapped / NAT64 forms of the IPv4 ranges;
  - IP literals in any encoding are normalised by `node:net` / WHATWG URL before the check (decimal, octal, hex IPv4 become dotted quads);
  - also refused: IPv6 `fec0::/10`, `100::/64`, SIIT `::ffff:0:0/96` and 6to4 `2002::/16` when the embedded IPv4 is internal;
  - redirects are followed manually (at most 5) and every hop is checked again; 303 (and 301/302 after a non-GET) becomes GET without a body, 307/308 keep the method and body; when a redirect changes origin, only plain headers are kept (`accept`, `accept-language`, `accept-encoding`, `user-agent`, `content-type`, `content-language`, `cache-control`, `pragma`); every other header, so any credential under any name, is dropped;
  - requests use `agent: false`: no keep-alive pool keyed by hostname and no environment proxy (`NODE_USE_ENV_PROXY`), so nothing resolves the name a second time;
  - every failure is a `SafeFetchError` with a `code` (`scheme`, `credentials`, `url`, `dns`, `blocked-address`, `allow-hosts`, `redirects`, `timeout`, `too-large`, `network`, `request`);
  - a timeout on the whole request (default 10 s) and a response size cap (default 5 MB);
  - an `allowHosts` option for tests and for declared internal services is the only bypass. Entries must be exact DNS hostnames (no IP literals, wildcards or `localhost`). It applies to the URL the caller passed and to redirects that have never left that origin, so a public URL can never redirect into a declared service, and a detour through another origin cannot come back into it.
- **F3 in the core:** `compose.yaml` sets `cpus`, `mem_limit`, `pids_limit` and a project-only network on every service; the host-side rules are S4's.
- **Ops in the core:** `GET /health` (liveness: `{status:"ok", sha}`) and `GET /ready` (readiness: runs registered checks, 503 with reasons if any fails); JSON log lines with a request ID taken from `X-Request-Id` when it is a safe token, otherwise generated; every other route 404s (SM-02 deny-by-default starts here).
- **Floor checks that a repo can run itself:** `floor-check.mjs <dir>` runs the static parts: F2-1 (no raw HTTP client outside `safe-fetch.mjs`: `fetch(`, `http.request`, `https.request`, `http.get`, `https.get`, `axios`, `undici`, `got`, `node-fetch`, `requests`, `httpx`), F1-4 (no `process.env` under `public/`; `CLIENT_CONFIG_KEYS` has no secret-shaped name), F3-2 static (every Compose service has the three limits). The scanning checks (F1-1…F1-3) are gitleaks in CI and S6; F3-1 is S4's probe.

## S3-b split and S3-b1 build notes (12 Nov 2026, runner B, ADR-0013)
**Split.** Six add-ons are six reviewable concerns, so S3-b (DEVOS-93) is built as one task sub-issue and one PR per add-on, in order: **S3-b1 SM-01 (DEVOS-136, this PR)**, then SM-02 … SM-06, each filed when it starts.

**Add-on layout** (the shape `apply.mjs` already expects): `templates/golden-path/addons/<id>/addon.json` plus `files/`, copied onto the core and never overwriting a core file. `addon.json` holds `id`, `name`, `files` (every path the add-on adds), `checks` (each Lite check ID → the test file that covers it) and a one-line `usage`. DevOS CI (`scripts/test/template.test.mjs`) checks every built add-on the same way: applied alone, the manifest says `selected = applied = [id]`; `floor-check` passes; exactly the listed files are added (so no other add-on comes with it); every Lite check ID of the module in `build-standard.yaml` is named in its mapped test file; and the add-on's own tests pass.

**SM-01 decisions (API input and contracts, SM-01-L1).**
- **No dependency.** `src/validate.mjs` is a small schema validator (string, integer, number, boolean, array, object) instead of a library: the core has no dependencies, the rule set needed for SM-01-L1 is small, and every rule is tested here. An app that needs JSON Schema in full can swap it later (M3.2 decides per project).
- **Safe defaults:** strings ≤ 1000 characters and lists ≤ 100 items unless the schema says otherwise; unknown object fields are refused (so `__proto__` and mass assignment are refused); a route part with no schema must be empty (an unexpected query or body is a 400).
- **`validated({ body, query, params }, handler)`** wraps a core route. The body must be `application/json` (415), at most 100 KB (413, checked on `Content-Length` and while reading) and arrive within 10 s (408); bad JSON is a 400. Query and params arrive as text and are coerced to numbers or booleans only where the schema asks; a repeated query key is a list, refused unless the schema is a list. On any failure the answer is `400 {error:"invalid-input", details:[{in, path, message}]}` (at most 20), and the handler, the only path to the database, never runs.
- **No reflection.** Error messages name the field and the rule, never the value sent.
- **Contract tests:** `invalidCases(schema, validExample)` generates the invalid variants (each required field missing, each field of the wrong type, each length, range, format, enum and list-size rule broken, an unknown field, a non-object), keeping only those the schema really refuses. The add-on's test posts each one and expects a 4xx with the handler never reached. SM-01-F1 (contract tests from a separate API schema) is Full-tier and not in this add-on.
- **Params:** the core router matches exact paths and has no params yet. `validated` checks whatever the app's router puts in `ctx.params`.

**Pre-review r1 (1 medium, 3 low; all fixed):** (medium) a `__proto__` query or params key was assigned as a prototype and so escaped the unknown-field rule; coerced input is now built with own data properties, and `__proto__`/`constructor` keys are a 400 on routes with and without a query schema. (low) A chunked body over the limit now gets its 413 (and a slow one its 408) before the socket is closed, instead of a reset. (low) An unknown field is named only when it is a plain identifier, so a crafted key is never echoed. (low) `validated()` checks the whole schema when the route is set up (types, list `items`, patterns).

**Pre-review r2 (1 medium, 4 low; 4 fixed):** (medium) a string over its length cap still ran its `pattern`, so a nested-quantifier pattern could stall the server; validation now stops at the cap, so no pattern runs on more text than the schema allows. (low) `application/*+json` bodies (merge-patch, problem) are accepted. (low) `assertAllValidated(routes)` lets an app test that every route is wrapped (SM-01-L1 "each route"). (low) `checkSchema` also checks that `required` names are properties, `enum` is a list and limits are numbers. **Not changed (low):** `invalidCases` breaks top-level fields only; nested list items and nested objects are validated, but an app that wants generated cases for them writes them by hand (recorded in `usage`).

**Codex PR63-r1 (2 medium; both accepted):** (1) a route without a body schema accepted a JSON body of `{}`, because the "must be empty" rule treated an empty object as absent. Only query and params may be empty objects now; any body at all, even `{}`, is a 400 there. (2) `invalidCases` broke `maxItems` but never `minItems`; it now also sends a list one item short. Tests: a GET with `{}`, `[]` or `null` on a no-body route gets 400; the generated cases include "too few items" (both fail on the r1 code).

**Tests:** `addons/SM-01/files/test/sm-01-validate.test.mjs` (6: generated contract cases on the body, query rules and coercion, params, malformed bodies 400/413/415 and `__proto__`, no reflection), plus the per-add-on harness test in `scripts/test/template.test.mjs` (16/16).

## DEVOS-159: AT4/AT6 start-up wait (12 Nov 2026, runner B)

- **Cause.** The AT4/AT6 `/health` test polled for a fixed 5 s window. On a loaded CI runner the generated server took longer to start, so the test failed with "the server never answered /health" (seen on #74, `4483e56`).
- **Decision.** The test now waits for the server's own `"msg":"listening"` log line, bounded at 30 s, then requires one `/health` answer with status 200 and a JSON body (10 s bound). A start that exits with `EADDRINUSE` on the random port is retried on a new port, at most 3 times. The `/health` assertions (status 200, JSON body) are unchanged; the test adds one check (the "listening" line) and changes only the wait. Retry and exit detection listen on `close` (after stdio has drained) and on spawn `error`; the test waits for the child to close after killing it. A server that never logs "listening" still fails the test (checked by renaming the log message: the test fails with `never logged "listening" (timeout)`).

## S3-b2 SM-02 build notes (13 Nov 2026, runner B, ADR-0013)
DEVOS-182, the second add-on of S3-b. Files: `addons/SM-02/files/src/access.mjs` and `addons/SM-02/files/test/sm-02-access.test.mjs`.

**Decisions (technical, runner B):**
- **Who a caller is (SM-02 Lite: "KK's tailnet identity or a service token").**
  - *Tailnet (opt-in):* the `Tailscale-User-Login` header that `tailscale serve` sets. The header proves nothing by itself, so it is believed only when the TCP peer is in an explicit `trustedProxies` list of IP addresses (empty by default; CIDRs, names and empty strings are refused at set-up). Setting `tailnetLogins` also needs `identityProxy: "tailscale-serve"` and a non-empty `trustedProxies`, and a non-loopback entry (a Docker gateway, say) also needs `nonLoopbackProxy: true`; `trustedProxies` without `tailnetLogins` is refused. From any other peer the header is ignored. The login must be in `tailnetLogins` (exact, case-insensitive); a trusted peer with an unknown login gets 403.
    - **Residual risk, recorded:** the add-on cannot see what sits at a trusted address. Only `tailscale serve` (which overwrites the `Tailscale-User-*` headers) may connect from it; any other proxy there (nginx, Traefik, docker-proxy on a published port) would forward a client's header and let anyone claim a listed login. That is why the flags above make the app state its set-up explicitly, why service tokens are the default, and why S4 (no route into the project network) and M2.4 (how the app is published) carry the deployment side. Verifying the login with tailscaled's `whois` would remove the risk but needs a socket client, which F2-1 forbids outside `safeFetch`; it is left to M2.4 if a project needs tailnet logins behind a shared proxy.
  - *Service:* `Authorization: Bearer <token>`, 32–256 URL-safe characters. The app holds only SHA-256 digests (`SERVICE_TOKEN_SHA256_<NAME>` in the server environment, read by `serviceTokensFromEnv`), so a leaked config file holds no usable token. Every configured digest is compared with `timingSafeEqual`, with no early exit. An offered bearer header decides alone: a bad token is 401 and never falls back to the tailnet header. The scheme name is case-insensitive (RFC 7235).
  - Reasons: no login screen or session store is needed for Lite (sessions are SM-02-F1, Full tier). Both identities are already how DevOS callers work (KK on the tailnet, agents with tokens). No dependency is added.
- **Deny by default.** The core already answers 404 for any route not in the table and serves `/health` and `/ready` before the table. `guard.protectAll(routes)` wraps every app route; it refuses to wrap the two open core routes. A guard with no callers configured throws at set-up, so a misconfigured app fails at start-up instead of serving nothing silently.
- **Route inventory (SM-02-L1, evidence `route_list`).** `routeInventory(routes)` lists each route as open, guarded and owner-checked. `assertAllGuarded(routes)` throws, naming every route that is not behind the guard. The markers are module-private `WeakSet`s, so a handler cannot claim to be guarded by setting a property.
- **No IDOR (SM-02-L2).** `owned(resolve, handler)` wraps a route that takes an ID. `resolve(req, ctx)` reads the ID once and returns `{ id, owner, value }` (owner is `tailnet:<login>` or `service:<name>`) or null; the handler gets it as `ctx.resource` and uses only that, so the check and the use cannot read different IDs. `singleParam(req, name)` gives null for a missing or repeated query key, so `?id=mine&id=theirs` is refused. Another owner's resource and a missing one both answer `404 {error:"not-found"}`, so a caller cannot probe which IDs exist. Without a caller (`owned` used without the guard) it answers 401: fail closed. `assertOwned(routes, idRoutes)` lets an app test that every route taking an ID is owner-checked.
- **Order with SM-01.** Nest as `guard.protect(owned(resolve, validated(schema, handler)))`: the guard first, then the owner check, then the body/query schema. `resolve` is the only code that reads the ID, so it checks the ID's own shape (`singleParam`, then a length or pattern test) before any lookup. This keeps `assertOwned` accurate, since `protect` carries the owner-checked marker from its direct child only.
- **No reflection.** 401, 403 and 404 bodies are fixed and never contain the token, login or ID sent.
- **`trustedProxies` entries** must be written the way Node reports a peer address: a dotted IPv4, `::ffff:` + a dotted IPv4, or an IPv6 address in its canonical lower-case compressed form. Anything else (a CIDR, a name, `0:0:0:0:0:0:0:1`, bracket tricks) is refused at set-up, because it could never match and tailnet log-in would silently fail.
- **Not in this add-on:** sessions, a login page and two-user row-level tests (SM-02-F1, SM-02-F2) are Full tier. Running `assertAllGuarded`/`assertOwned` on a generated app's real route table and storing `routeInventory` as the `route_list` evidence is M3.2's job (the Builder wires the app's routes and its tests); the add-on ships the helpers and proves them on sample routes.

DEVOS-183, the third add-on of S3-b. Files: `addons/SM-03/files/src/browser-safety.mjs` and `addons/SM-03/files/test/sm-03-browser.test.mjs`. Built from main, independent of S3-b2 (DEVOS-182): the two add-ons share no file.

**Decisions (technical, runner B):**
- **Cross-origin writes (SM-03-L1): an Origin check, not CSRF tokens.** `createOriginGuard({ allowedOrigins })` wraps routes; for POST, PUT, PATCH and DELETE it refuses with a fixed `403 {error:"cross-origin-refused"}` when `Sec-Fetch-Site` is present and not `same-origin`, or `Origin` is present and not exactly one of the allowed origins (`null`, another scheme or port, a repeated header: all refused). A request with neither header passes only when it carries an `Authorization` header: browsers send `Origin` on every cross-origin write, and a page on another origin cannot add `Authorization` without a CORS preflight, which the core never answers (no OPTIONS route, deny by default). Reasons: no session store or token plumbing is needed (Lite has no sessions; SM-02 callers are tailnet logins and bearer tokens), it covers form posts and `fetch` alike, and it fails closed for a browser that sends nothing. GET and HEAD are never state-changing (stated in `usage`).

Values split over several interpolations are judged together; a static URL with no value in it is the author's. A nested `html` result is spliced verbatim in text position only: it was itself checked from text and ends in text, so the parent tokenizes it the same way.

Each pattern runs on the whole file (a sink split over lines is found) and is reported at its first line; comments and strings are included: a false positive costs a rewrite, a missed sink costs an XSS. There is no allow-annotation in Lite: the check says "no sinks", and "on untrusted data" is for the reviewer when a project asks for one (a waiver from KK). The add-on's own test runs it on the generated app, so the app's test suite fails on a sink from then on. The patterns are built from pieces so the module and its test do not match themselves.
- **Not in this add-on:** CSP and the security-header set (SM-03-F1) and the seeded-XSS E2E (SM-03-F2) are Full tier. Wiring the guard into a real app's route table is M3.2's, as for SM-01 and SM-02.

**S3-b3 deadlock resolution (runner B, 14 Nov 2026, ADR-0013 DEADLOCKS): a fail-closed HTML subset instead of a model of the full parser.**
- **Why:** thirteen Codex rounds (pre-review and PR98-r1 to r13) each found one more place where `MarkupState` read markup differently from a browser: foreign content (SVG and MathML, their integration points, CDATA), `select` and `template`, comments and bogus comments, unquoted values, and nested fragments. Each fix was correct, but the next round found another case, and every round is a paid review. The HTML tree builder decides how later text is tokenized, so a partial model of it can always be out-run. That makes three or more failed attempts on the same task.
- **Decision:** `html` now accepts only a subset in which the browser's tokenizer state follows from the token stream alone.
  - Tags: `html head body title meta link script main header footer nav section article aside h1–h6 p div span a ul ol li dl dt dd table thead tbody tfoot tr th td caption form label input button textarea img br hr strong em b i small code pre blockquote`.
  - Attributes: `id class title lang dir role hidden tabindex href rel target src alt width height loading action method for name value type placeholder checked disabled required readonly min max step maxlength autocomplete colspan rowspan charset content defer async` and `aria-*`.
  - Syntax: `<name attr attr="value">`, `</name>` (spaces only before `>`), `/>`, and one leading `<!DOCTYPE html>`. Every `<` in static text must start such a tag (write `&lt;`).
  - Refused: every other tag (so `svg`, `math`, `select`, `template`, `noscript`, `style`, `iframe`, `xmp`, `plaintext`…), every other attribute (so `on…`, `style`, `srcdoc`, `srcset`, `formaction`, `data-*`), comments, `<!…>` and `<?…>`, unquoted and single-quoted values, and non-ASCII whitespace inside a tag.
  - Text states: `<title>` and `<textarea>` (with or without `/>`) are RCDATA, and inside them static text may hold no `<` except the exact end tag. `<script>` is allowed only as `<script …></script>` with nothing between and no value in its attributes.
  - None of these elements changes tokenization in any HTML insertion mode the subset can reach (no foreign content, select, template, frameset or noscript is reachable), so this parser and the browser agree on every token.
- **Effect:** a parser mismatch can now only make `html` throw; it cannot pass an unsafe page. Every r1–r13 fixture is kept as a regression and now throws. Templates that used markup outside the subset (`<svg>`, `<select>`, comments, single-quoted values, `srcset`, inline `<script>` text, a bare `<` in text) are refused; this is the narrowing.
- **Removed as no longer needed:** foreign-content tracking, select tracking, the bogus-comment, comment and CDATA rules, the RCDATA-entry flag for nested results and the end-tag-in-attribute rule. `<p title="a</title&gt;">` is now accepted, because without foreign content an attribute value cannot end RCDATA.
- **Follow-up:** richer markup (SVG icons, `<select>`, inline styles and scripts behind a CSP nonce) belongs to M3.2 or the Full tier (SM-03-F1), filed as DEVOS-191.

## S3-b4 SM-04 build notes (13 Nov 2026, runner B, ADR-0013)
DEVOS-184, the fourth add-on of S3-b. Files: `addons/SM-04/files/src/outbound.mjs` and `addons/SM-04/files/test/sm-04-outbound.test.mjs`. Built from main; it shares no file with SM-02 (#97) or SM-03 (#98).

**Decisions (technical, runner B):**
- **No defaults (SM-04-L1 says "explicit").** `outbound({ name, baseUrl, timeoutMs })` makes one client per external dependency and refuses to be built without an integer `timeoutMs` from 1 ms to 120 s. Each `call(path, opts)` goes through the core's `safeFetch` (F2) with that timeout. A call may lower the timeout but never raise it past the client's or drop it, and the path must stay on the client's origin. A timeout becomes an `OutboundTimeout` (`code: "timeout"`, dependency name, ms), so logs and callers can tell which dependency hung.
- **Non-HTTP calls.** `withDeadline(name, timeoutMs, (signal) => work)` covers a database query, a queue or an SDK. It also has no default. At the deadline it aborts the signal it handed to the work and rejects, even if the work ignores the signal. A late failure after the deadline is swallowed, not left as an unhandled rejection. Reason: the core has no database or SDK of its own, so the add-on gives the one wrapper they all need; SM-06 and the app's own clients pass the signal on.
- **Auto part of "auto + review".** `findUntimedCalls(root)` reads `src/` in a code view where comments and string and template text are blanked, keeping offsets and `${…}` expressions. Words and parentheses in comments or strings therefore neither hide a call nor fake one. A `/` where an expression can start (after an operator, `(`, `,`, `=`, a keyword such as `return`, or at the start of the file) opens a regex literal, which is blanked like a string. So `/^https?:\/\//` or ``/`/`` cannot hide the lines after it. The rules are inverse, as for F2-1:
  - The only accepted use of `safeFetch` is a direct call whose second top-level argument is an object literal that names `timeoutMs` at its top level. Shorthand, a quoted key and a trailing `as const` are allowed.
    - The last `timeoutMs` counts. No spread may come after it, because `...opts` could carry `timeoutMs: undefined`. A spread before it is fine.
    - The value must not be `undefined`, `null` or `void`.
    - A number literal (decimal, hex, octal, binary or exponent) must be from 1 ms to 120 s.
  - Every other use of the name is reported: an alias, a value, `?.()`, `.call`, spread arguments, options passed in a variable, or a `timeoutMs` nested in another argument.
  - Any reference to `safe-fetch` other than a plain named import is reported, including a namespace import, a dynamic import and a mention in a comment. That false positive is cheap and is recorded here.

**Add-on:** `templates/golden-path/addons/SM-05/` adds `src/queue.mjs` and `test/sm-05-queue.test.mjs`; `addon.json` maps SM-05-L1 to that test.

**Runner decisions (technical).**
- **No dependency, one process.** The core has no dependencies and no database. A queue library such as BullMQ would add Redis, and pg-boss would add Postgres, so neither fits a template that must run alone. `createQueue` is a small in-process queue. An app that later needs several workers or a broker swaps it for a library (M3.2 decides per project). The Full-tier concurrency and load check (SM-05-F1) is not in this add-on.
- **Retry policy:**
  - `maxAttempts` (default 3);
  - `backoffMs` (default 1 s, 5 s, 30 s; the last value repeats);
  - `timeoutMs` per attempt (default 60 s). At the timeout the handler's `signal` aborts and the attempt counts as failed, even if the handler ignores the signal (ADR-0011 timeouts);
  - `concurrency` (default 1).
  - Every option is range-checked at set-up.
  - A job type with no handler is refused when it is enqueued.
- **Dead letters:**
  - A job that fails every attempt is marked `dead`, with its attempt count, its last error (at most 500 characters) and when it died.
  - `deadLetters()` lists them without the payload. `retryDead(id)` queues the job again with a fresh attempt count. `discardDead(id)` drops it.
  - `deadLetterRoutes(queue)` gives `GET /admin/dead-letters` and `POST …/retry` / `…/discard` with body `{"id":"<uuid>"}`. Bad input is a 400 and an unknown id is a 404. The body is kept up to 1 KB; past 64 KB or 10 s the connection is closed.
  - The routes are deliberately not guarded here. The app mounts them behind SM-02's auth guard and SM-03's origin guard, which are separate add-ons, as the usage line says.
- **Durability:**
  - `fileStore(path)` writes the whole job list to a temporary file (mode 600), fsyncs it, and renames it over the old one, so a crash or a power loss leaves either the old list or the new one. On load, a list whose jobs do not have a valid id, type, status and count is refused rather than half-trusted.
  - A job that was running when the process died keeps that attempt in its count, so a job that kills the process still reaches the dead-letter list instead of crashing every boot. A job with no attempts left is dead-lettered at start-up as `interrupted`; the others are queued again.
  - A store write that fails (for example a full disk) is reported as an `onEvent` `store.error`, and the queue keeps working from memory; the next change writes the whole list again.
  - `stop()` aborts running attempts the same way: they run again on the next start and are not counted as failures.
  - Done jobs are dropped.
  - `memoryStore()` is for tests, or for work that may be lost on restart.
- **Payloads are stored**, so the usage line and the code comments say never to put a secret in one. A payload must be JSON; it is copied when enqueued. A handler's error message is kept as `lastError` and shown in the dead-letter list, so the same applies to it.
- **Known limit (recorded):** a handler that ignores its abort signal may still be running after its attempt ended (timeout or `stop()`), and the queue does not wait for it. Handlers should honour the signal or be safe to run twice.
- **Pre-review (2 medium, 5 low; 6 fixed, 1 recorded):** (medium) a job that crashed the process was requeued on every boot and never dead-lettered; it now keeps its attempt count, and a job with no attempts left is dead-lettered at start-up. (low) `idle()` now resolves after `stop()`; the store fsyncs before the rename and validates what it loads; the retry timer is no longer `unref`'d, so a worker with no server stays up for a backoff retry; the usage line warns about error text. Test: 4,000 such stored jobs are all dead-lettered (the previous code fails it with a stack overflow). (2) `fileStore` fsynced the file but not its directory, so the rename (and a newly made directory) could be lost on power loss; it now fsyncs the directory after the rename, and the parent of any directory it creates. **Codex PR104-r2 (1 medium; fixed):** with several new directories (`data/queue/jobs.json` and none existing) only the outermost's parent and the final directory were fsynced, not the directories in between; now every directory it made and the parent of the outermost are fsynced. ## S3-c split and S3-c1 SM-07 build notes (16 Nov 2026, runner B, DEVOS-231, ADR-0013)
**Split.** S3-c (DEVOS-94) is built like S3-b: one task sub-issue and one PR per add-on, in order. **S3-c1 SM-07 (DEVOS-231, this PR)** comes first, then SM-08 … SM-12, each filed when it starts.

**Add-on:** `templates/golden-path/addons/SM-07/` adds `src/idempotency.mjs` and `test/sm-07-idempotency.test.mjs`. `addon.json` maps SM-07-L1 to that test.

**Runner decisions (technical).**
- **No driver, no dependency** (as SM-06). The store is an interface with three calls: `claim(scope, owner, key, hash, token)`, `complete(scope, owner, key, token, result)` and `release(scope, owner, key, token)`. It comes in two forms:
  - `memoryStore()`, for tests and single-process apps;
  - `sqlStore(query)`, over any `query(text, params) → { rows }`.
  The table is `IDEMPOTENCY_SQL`, which the app puts in a migration. Its `(scope, owner, key)` primary key is the unique constraint SM-07-L1 asks for. `scope` names the operation (`orders.create`), so two operations never share a key space.
- **Keys are per caller** (pre-review r1, medium). Behind SM-02's `protect()`, `withIdempotency` keys by `ctx.caller.id` (`owner`; `''` without callers). One caller therefore never gets another caller's stored answer, and never a 422 that reveals another caller's key is in use. The owner sits in the key, not only in the request hash, because the hash alone still leaks a key's existence.
- **One rule, `idempotent(store, { scope, key, request }, fn)`:**
  - The first caller inserts a `running` row (`INSERT … ON CONFLICT DO NOTHING`) and runs `fn`.
  - On success the row becomes `done`, with the JSON result. A later caller with the same request gets that result back as a replay, and `fn` never reruns.
  - The same key with a different request (a sha256 of the request with its keys sorted) is a 422, `idempotency-key-reused`. It is never answered with another request's result.
  - A caller that arrives while the key is `running` gets a 409, `idempotency-key-in-progress`. The effect is never run twice in parallel.
  - A throw from `fn` deletes the `running` row, so a retry runs it again.
  - A row released between the `INSERT` and the `SELECT` is claimed again, at most 3 times; after that it is a 409, `idempotency-claim-contended`.
- **No lock expiry (fail closed).** A process that dies mid-effect leaves its row `running`, and the key answers 409 until the row is deleted. The same happens when the effect has run but its result cannot be stored: the result is not JSON (a BigInt, a cycle), or the `complete` write fails. The client gets a 500 for a create that did happen, and retries get 409; the effect never runs twice (pre-review r1). Reason: if a lock expired, a slow effect that is still running could be run a second time, which is exactly the duplicate SM-07 forbids. Clearing a stuck row is an operator action, recorded in `usage`.
- **Create routes: `withIdempotency(store, scope, handler)`.**
  - The key comes from the `Idempotency-Key` header: 1–200 characters of `[A-Za-z0-9._:-]`.
  - A missing key is a 400, `idempotency-key-required`. A malformed or repeated header is a 400, `idempotency-key-invalid`. Both answer before the handler runs.
  - The handler returns `{ status, body }` instead of writing `res`, so its first answer can be stored and replayed. A replay carries `idempotent-replayed: true`.
  - A 5xx answer is sent but not stored, and frees the key, like a throw. A 4xx is the final answer and is stored.
  - The request is the method, the path and `ctx.input`: SM-01's `validated()` goes outside the wrapper, so the hash covers the checked input. A `fingerprint(req, ctx)` option replaces it.
- **Job handlers: `idempotentJob(store, scope, handler)`** wraps an SM-05 handler `(payload, ctx)`.
  - The key is `payload.idempotencyKey`, or `keyOf(payload)`; the request is the payload.
  - A replayed or re-enqueued job returns the stored result without running the effect.
  - A job without a valid key fails, and SM-05 retries it and then dead-letters it.
- **SM-07-F1 (double submit, replay) is the add-on's own test**, although F1 is the Full tier. The cases are the core behaviour of L1's key, so they ship with it.

**Known limits (recorded).**
- **Pre-review r2 (1 medium, 5 low; 5 fixed, 1 recorded):**
  - (medium, fixed) A stored string result was parsed twice: node-postgres already parses `jsonb`, so `"msg-123"` broke every replay and `"123"` came back as a number. The store now selects `result::text` and always parses it itself, whatever the driver does. Tested with string, numeric-looking, number, boolean and null results.
  - (low, fixed) A **claim token** (`claim_id`, a random UUID per claim) is checked by `complete` and `release`. Without it, after an operator cleared a stuck row, the slow first process could free or finish the newer claim on the same key.
  - (low, fixed) The request hash reads the request as JSON first. A `Date` hashes as its ISO text instead of `{}`, so two different dates are two requests; a BigInt or a cycle throws.
  - (low, fixed) The test no longer claims to send a repeated header. Node joins duplicate headers into `"a, b"`, which the key pattern refuses; the `Array.isArray` branch is a guard.
  - (low, fixed) The contract's store signatures and primary key match the code.
  - (low, recorded) A route **without callers** shares one key space (`owner = ''`). A client that knows another client's key can tell that it is in use, and, with the same request, gets the stored answer. Keys should be random UUIDs; a public create route that returns anything private passes a `fingerprint` or puts a per-client id in `owner`. This is stated in `usage`.
- The SQL store's test runs against a small emulation of its four statements, matched as exact text, and the table text is checked for the primary key. The app's own test runs them on its real database, because the template has no database.
- An SM-05 job that times out is not released: SM-05 races the handler against its abort, so the `idempotent()` call stays pending and its row stays `running`. Retries get 409, use up their attempts and dead-letter the job, even when the slow effect later finishes and marks the row `done`. The effect runs again only if it throws (for example on its own abort), which frees the key. An effect that must never repeat passes SM-05's `signal` to its own call (pre-review r1, corrected).
- There is no route inventory check (like SM-01's `assertAllValidated`). `validated()` wraps the handler, so a marker on the inner wrapper is not visible from the route table. SM-07-L1 is "auto + review", and the review checks that every create route is wrapped.

**Tests:** `sm-07-idempotency.test.mjs` has 13 tests: the 8 below, plus per-caller keys, string and scalar results, the claim token, the JSON request hash, and fail closed on an unstorable result. They run over the core server on a real socket:
- a double submit creates once and replays the first answer;
- missing, malformed and over-long keys are refused before the handler runs;

## S3-c2 SM-08 build notes (16 Nov 2026, runner B, DEVOS-232, ADR-0013)
**Add-on:** `templates/golden-path/addons/SM-08/` adds `src/retention.mjs` and `test/sm-08-retention.test.mjs`. `addon.json` maps SM-08-L1 to that test.

**Runner decisions (technical).**
- **No driver, no dependency** (as SM-06 and SM-07). The purge takes any `query(text, params) → { rows }` with Postgres `$n` placeholders.
- **One declared policy, no default period.** `retentionPolicy([{ name, table, column, key = "id", type = "timestamptz", days }])` checks and freezes the app's data classes:
  - `days` is a whole number from 1 to 36500 and has no default. How long each class is kept is the app owner's (content) decision, so the template never guesses one;
  - a duplicate class name or an unknown field (a typo such as `day`) is refused;
  - `table` (`schema.table` allowed), `column` and `key` must be lower-case SQL names. They are double-quoted into the statement, never interpolated raw.
  - `key` must be unique and NOT NULL (normally the primary key).
  - Only a policy built by `retentionPolicy()` (kept in a private `WeakSet`) is accepted by the purge, so an unchecked look-alike can never put raw names into the SQL (pre-review r1, low).
- **The purge: `purgeExpired(query, policy, { now, batchSize = 1000, maxBatches = 100, signal })`.**
  - The cutoff is fixed once per run, per class: `now − days`.
  - One statement per batch: `DELETE … WHERE key IN (SELECT key … WHERE column < <cutoff> ORDER BY column LIMIT $2) AND column < <cutoff> RETURNING key`. Only rows strictly older than the cutoff go; a row exactly at the cutoff, a newer row and a row whose age is NULL are kept. The oldest rows go first.
  - **The age test is repeated outside the sub-select** (pre-review r1, high). Without it, a row whose age changed after the statement's snapshot (a session refreshed by `last_seen_at = now()`, a recycle-bin row restored by clearing `deleted_at`) was still deleted, because Postgres re-checks only the outer condition on the new row version, and the key had not changed. The repeat also means a non-unique key can never take a current row with an old one (pre-review r1, medium). Reproduced and fixed on Postgres 16 by the reviewer.
  - **The cutoff is cast to the column's type** (pre-review r1, medium), never left to the session `TimeZone`: `timestamptz` → `$1::timestamptz`; `timestamp` (without time zone, holding UTC, as Prisma's `DateTime`) → `$1::timestamptz AT TIME ZONE 'UTC'`; `date` → that, `::date`, so a row dated on the cutoff day (UTC) is kept and nothing goes early. Checked by hand on Postgres 16 with `TimeZone = Asia/Kolkata`: a naive-UTC row 3 hours after the cutoff and a row dated on the cutoff day were kept; older ones went.
  - A client that does not return `{ rows }` fails the run instead of reporting nothing deleted (pre-review r1, low).
  - A class stops when a batch deletes fewer than `batchSize` rows. After `maxBatches` it stops with `more: true` (rows may remain; when the last batch emptied the class exactly, the next run simply deletes 0), and the next run carries on, so one run never holds the database for long.
  - An aborted `signal` stops the run before the next batch and throws the signal's reason, so SM-05 counts the attempt as failed and retries it.
- **The purge job: `purgeJob(query, policy, options)`** is an SM-05 handler `(payload, { signal })`. It ignores the payload: periods, tables and columns come only from the policy, so a job's payload can never widen what is deleted. The app enqueues it daily.
- **Deletes are final.** A class that soft-deletes first (a recycle bin) points `column` at its `deleted_at`, so only rows deleted longer ago than the period are purged. This is stated in `usage`.

**Known limits (recorded).**
- SM-08-L1 is "review": the review checks that every personal or growing table is in the policy. There is no automatic table inventory, because the template has no schema to read.
- SM-08-F1's second half (the weekly test-restore lists this project) is DevOS-side backup work, not template code; it belongs to the M3.2 database add-on and its backup follow-up (DEVOS-229). The purge half of F1 is in the add-on's own test.
- The test runs the purge against a small emulation of its one statement, matched as exact text. The app's own test runs it on its real database, because the template has none. The statement itself was run by hand on Postgres 16 (batch of 1 deleted the oldest row; the cutoff row, a newer row and a NULL row were kept).
- Each age column needs an index, or every batch scans the table. This is stated in `usage`.
- A class whose `type` is left at `timestamptz` while its column is really `timestamp` (a common Prisma `DateTime` case) brings the session time-zone shift back: under a non-UTC session rows can go up to the zone offset early. Declaring the type is part of the SM-08-L1 review (pre-review r2, low, recorded). Reading the column type from `information_schema` once per run is a possible later option.

**Pre-review r1 (1 high, 2 medium, 4 low; all 7 accepted):** the high, both mediums, and the frozen-policy, `{ rows }` and test-coverage lows are fixed as above; the `more: true` low is recorded as documented behaviour.

**Tests:** `sm-08-retention.test.mjs` has 6 tests:
- every class declares its own period (no default; bad, missing and out-of-range periods, duplicates and unknown fields refused);
- unsafe table, column and key names are refused, names are quoted, and the age test is repeated outside the sub-select;
- the cutoff is cast to the column's type (`timestamptz`, `timestamp`, `date`), and an unknown type is refused;
- the purge removes expired rows only (1 ms past the cutoff goes; the cutoff, newer and NULL rows stay), and a second run deletes nothing;
- batches are bounded, oldest first, and `maxBatches` leaves the rest for the next run; a frozen look-alike policy and a client without `{ rows }` are refused;
- the purge job ignores its payload and stops on abort before the next batch.

## S3-c4 SM-10 build notes (16 Nov 2026, runner B, DEVOS-94, ADR-0013)
**Add-on:** `templates/golden-path/addons/SM-10/` adds `src/flags.mjs` and `test/sm-10-flags.test.mjs`. `addon.json` maps SM-10-L1 to that test.

**Tracking.** Linear's free plan is at its issue limit (KK, 16 Nov), so this add-on is built under DEVOS-94 itself (branch `kishore/devos-94-…`, PR body `Part of DEVOS-94`), not a new sub-issue. SM-11 and SM-12 follow the same way; the PR for the last one says `Fixes DEVOS-94`.

**Runner decisions (technical).**
- **No driver, no dependency, no timer.** A kill switch is read at run time from a `source()` an operator can change while the app runs. Two are bundled:
  - `dbSource(query)` reads the `kill_switch` table (`KILL_SWITCH_SQL`: `phase` primary key, `enabled`, `updated_at`, `updated_by`); `setKillSwitch(query, phase, enabled, by)` writes it and records who did it;
  - `fileSource(path)` reads a JSON file such as `{"phase-2": false}` on a mounted volume. A missing file means every phase is at its default.
  The state is re-read lazily, at most every `refreshMs` (5 s), when a guarded route, `current()` or `clientFlags()` asks. There is no background timer, so the add-on never keeps a process alive. A switch therefore takes effect within about `refreshMs` plus one read, with no redeploy and no restart (SM-10-L1).
- **Phases are declared once.** `killSwitches({ phases })` refuses an empty, duplicate or badly formed phase name, and `guard()` / `isOn()` throw on an undeclared one, so a typo fails loudly instead of hiding nothing.
- **A phase is on unless someone turns it off.** A kill switch exists to hide a phase; a phase the source does not list is at its default (`defaults`, else on). Removing a phase's line or row returns it to its default.
- **Failures keep the last good state** (fail static). A source that throws, hangs past `timeoutMs` (2 s; its `AbortSignal` is aborted), or returns something other than an object keeps the last good state, and `onError` is told. Before the first good read, the defaults hold. A value that is not `true`/`false` keeps that phase's last good value; an unknown name is reported and not used. Reason: a broken flags store must neither hide every phase nor show a phase an operator turned off, so the safest state is the last one read. A throwing `onError`, or an async one that rejects, never breaks the app (found while pre-reviewing SM-12, same fix).
- **One read at a time.** Concurrent callers share one in-flight read. A read that timed out but has not settled (a hung `kill_switch` query holding a pool connection) blocks new reads until it settles: each refresh then reports "previous source read still pending" and keeps the last good state, so a hung flags store can never drain the app's database pool (pre-review r1, medium). `dbSource` calls `query(text, params)` with exactly two arguments, because in node-postgres a third one is the callback slot (passing `{ signal }` there made every read fail and could throw inside pg's callbacks; pre-review r2, high, fixed and tested). A query that never settles freezes the flags at the last good state, so `usage` tells the app to set `statement_timeout` (or pg's `query_timeout`) on that connection (pre-review r2, low).
- **Requests never wait for the source** (stale-while-revalidate, pre-review r1, low). Only the very first read is awaited. After it, `guard()` and `clientFlags()` answer from the current state at once and start a background re-read when it is older than `refreshMs`, so a switch takes effect on the first request after that re-read lands (within about `refreshMs` plus one read). `current()` waits for a re-read; `settled()` resolves when no read is in flight.
- **An unknown name is reported once** per change of the set of unknown names, not on every read (pre-review r1, low).
- **Hiding = 404.** `guard(phase, handler)` answers exactly the core's deny-by-default 404 (`{"error":"not-found"}`) while the phase is off, so a hidden route looks like one that does not exist. `clientFlags()` gives the UI `{ [phase]: boolean }` to hide screens and links; `usage` says the UI alone is not enough, every route of the phase is guarded.

**Known limits (recorded).**
- SM-10-L1 is "auto": the test proves the mechanism. That every route of a phase is wrapped is not checked automatically, because the template has no route-to-phase map; the review checks it.
- Background jobs of a phase are not wrapped by the add-on (an SM-05 handler that returned early would count as done). `usage` says such a job checks `isOn(phase)` after `await current()`.
- There is no admin route: turning a switch is an operator action (`setKillSwitch` from a script or an SM-02-guarded route the app adds).
- SM-10-F1 (a flag per feature, each toggled in a test) is Full tier. The same `killSwitches` works per feature (a "phase" name per feature), but the per-feature tests are the app's.
- The test runs `dbSource`/`setKillSwitch` against a small emulation of their two statements, matched as exact text; the app's own test runs them on its real database.

**Pre-review r1 (1 medium, 3 low; all 4 accepted and fixed):** the hung-query pool drain (medium), request-path latency, the "deleted line returns to default" test proving nothing (it now turns a phase off, then deletes its line), and repeated unknown-name reports.

**Pre-review r2 (1 high, 2 low; all 3 accepted and fixed):** the r1 signal argument broke node-postgres (high, removed; the hung-query test now asserts two arguments); the timing wording now matches stale-while-revalidate; `usage` asks for a statement timeout.

**Tests:** `sm-10-flags.test.mjs` has 5 tests over the core server on a real socket:
- a phase turned off in the switch file hides its routes (404, the same as a missing route) and its UI flag once the background re-read after `refreshMs` lands, other phases untouched, and turning it back on shows it again, all on one running server;

**Runner decisions (technical).**
- **No driver, no dependency, no vendor SDK.** The meter wraps any paid call; the app's own provider client runs inside it.
- **One declaration, no default cap.** `paidServices([{ name, unit, monthlyCap }])` checks and freezes the list: a missing, zero, fractional or unsafe cap, a duplicate name, an unknown field (a typo such as `cap`) or a bad unit is refused. How much may be spent is the app owner's (money) decision, so the template never guesses a cap. Only a list from `paidServices()` is accepted by the meter.
- **Whole numbers in the service's unit** (`usd-cents`, `minutes`, `tokens`), so sums never drift as floats would.
- **Reserve, run, settle.** `meter.charge(service, estimate, fn)`:
  1. reserves `estimate` against this month's cap; if month-to-date + estimate would pass the cap it throws `CapExceededError` (`code: "cap-exceeded"`, `status: 429`) and `fn` never runs, so a refused call spends nothing;
  2. runs `fn`; when it returns `{ cost }`, the reservation is corrected to the real cost. A real cost above the estimate is recorded as is (it was spent) and can take the month past the cap; the next charge is then refused;
  3. when `fn` throws, the estimate stays recorded: a failed paid call may still have been billed, so the meter over-counts rather than under-counts (the safe direction for money).
  A reservation up to exactly the cap is allowed. The estimate is a whole number of at least 1 and must be an **upper bound** of the real cost (e.g. max tokens × price): concurrent calls are held under the cap by their estimates, so a zero estimate would disable the cap for concurrent calls (pre-review r1, medium).
  4. if correcting to the real cost fails after `fn` succeeded (a malformed `cost`, a store error), the estimate stays, `onError` is told, and `fn`'s result is still returned: the call was paid for, and failing it would invite a paid retry (pre-review r1, low). A throwing or rejecting (async) `onError` is swallowed (pre-review r2, low).
- **Atomic across instances.** `pgStore(query)` keeps one `paid_usage` row per service and month (`PAID_USAGE_SQL`, `spent >= 0`). The reserve is `INSERT … ON CONFLICT DO NOTHING`, then one conditional `UPDATE … SET spent = spent + $3 WHERE … AND spent + $3 <= $4 RETURNING spent`. Postgres re-checks the condition on the newest row version after a concurrent update, so callers on any instance can never pass the cap together. Checked by hand on Postgres 16 with node-postgres (a 10-connection pool, 40 concurrent charges of 7 against a cap of 60: exactly 8 succeeded, spent 56). `memoryStore()` is for one process and tests.
- **The budget month** is `YYYY-MM` in the meter's `timeZone` (default UTC; an unknown zone throws at start-up). A new month starts a fresh cap.
- **Usage in the project budget.** `meter.report()` returns the budget record: `{ month, services: [{ service, unit, monthlyCap, spent, remaining }] }`. The app serves it to the DevOS project budget (the `budget_record` evidence).

- How DevOS reads `report()` into the project budget (a route, a pull by the server agent) is DevOS-side (M4.x reports/budget work), not template code.

**Runner decisions (technical).**
- **The check reads files; CI runs the scan.** The floor allows no child process outside `src/safe-fetch.mjs` (F2-1), and a scan needs the registry, so `deps-check.mjs` never runs npm or reaches the network. CI runs `npm audit --json --package-lock-only > audit.json || true` and hands the JSON over with `--audit`. `|| true` is safe because the check, not npm's exit code, decides, and an audit that did not run (npm's `{ error }` answer, an empty file, an unknown format) fails closed (`audit-failed` / `audit-unreadable` / `audit-missing`).
- **Lockfile rules.** `package-lock.json` must exist, be lockfile version 2 or 3, declare in its root entry exactly the `dependencies`, `devDependencies`, `optionalDependencies` and `peerDependencies` of `package.json` (same names and specs; a name in both `dependencies` and `optionalDependencies` is compared under the optional ones only, as npm writes it), and resolve each declared dependency to a `node_modules/<name>` entry with a version, or, for a local package (`file:`, `link:`, a workspace), a link entry with its resolved path. Required peer dependencies are resolved like the others (npm 7+ installs them); a peer marked `optional` in `peerDependenciesMeta` needs no entry (Codex PR187-r1, medium, accepted). Otherwise `lockfile-missing` / `lockfile-unreadable` / `lockfile-version-unsupported` / `lockfile-out-of-sync`. Package names are read with `Object.hasOwn`, so a name like `constructor` is not taken as resolved.
- **Counting.** From npm's audit format 2: the per-severity counts in `metadata.vulnerabilities` and the per-package list are both read, and the larger count is used, so a report cannot hide a finding in either place. Any high or critical count fails (`high-vulnerabilities`, `critical-vulnerabilities`); lower ones are recorded and pass. An unknown severity, a non-integer count, or a per-package list that is missing or not an object fails closed (Codex PR187-r2, medium, accepted).
- **Evidence.** `--out` writes the `scan_report` record (`check`, `ok`, `findings`, the lockfile's `sha256`, counts per severity, `time`) to a temp file and renames it. Exit 0 only when `ok`.
- **No dependency added**; the core keeps no runtime dependency.

**Known limits (recorded).**
- The audit's freshness is the CI job's: the check cannot prove `audit.json` was produced from this lockfile. The `usage` runs both in the same job, and the report stores the lockfile's sha256 so a reviewer can match them.
- SM-14-F1 (licence report, D13) is Full tier and not in this add-on; the `usage` repeats the permissive-licence rule from the S3 design decisions.
- `apply` copies files only, so the CI steps are in `usage` (the core ships no CI workflow).

## S3-d2 SM-15 build notes (17 Nov 2026, runner B, DEVOS-95, ADR-0013)
**Add-on:** `templates/golden-path/addons/SM-15/` adds `src/user-url.mjs` and `test/sm-15-ssrf.test.mjs`. `addon.json` maps SM-15-L1 to that test.

**Runner decisions (technical).**
- **A wrapper, not a second fetcher.** `fetchUserUrl(input)` checks the input and calls the core `safeFetch`, which keeps every address check (F2) on every hop. No address rule is duplicated, so the floor stays the one place to fix a bypass.
- **Input.** Text only (not a `URL` object or anything with a `toString`), trimmed, at most 2048 characters both as typed and once parsed (non-ASCII is percent-encoded, so the parsed form can be far longer), absolute `http:`/`https:` only, no user name or password, and a host. Anything else is a `SafeFetchError` (`url`, `scheme`, `credentials`) before any lookup.
- **Never `allowHosts`.** A user URL can never reach a declared internal service; passing `allowHosts` is a `TypeError`, and the wrapper always passes `allowHosts: []`.
- **GET and HEAD only, no body.** A user URL is read, never written to.
- **Caps.** 8 s, 2 MB and 3 redirects (`USER_URL_LIMITS`, frozen), tighter than `safeFetch`'s 10 s / 5 MB / 5. A caller may lower a cap, never raise it (`TypeError`). `safeFetch`'s deadline covers the whole request, so a slow drip is cut at the cap, not at the first byte.
- **What the user sees.** `publicMessage(err)` gives fixed wording per code. `blocked-address` and `dns` read the same, and no message repeats the host or the resolver's error, so the answer is no oracle for internal names.
- **Test seam.** `makeUserUrlFetcher({ transport })` lets the tests put a local stub in for a public server through `safeFetch`'s `allowHosts` (the core tests' approach). The parameter is not named `fetch`, which floor-check F2-1 reads as a raw client.
- **AT6 fixture.** `scripts/test/template.test.mjs` AT6 used SM-15 as an example of a selected add-on that is not built yet. SM-15 is now built, so the example is SM-16 and SM-17; the assertion is unchanged (as for SM-09 in S3-c3).

**Known limits (recorded).**
- Ports are not limited: a user URL may name any port on a public address. `safeFetch` follows redirects itself, so a wrapper cannot check each hop's port; a per-hop port rule belongs in the floor and is out of S3-d2's scope.
- Timing can still differ between a refused internal name and a missing one (one is refused after the lookup, the other fails in it).
- SM-15-F1 (per-domain rate limits) is Full tier and not in this add-on.
- Teredo (`2001::/32`) is not in the floor's blocked list. It is no practical route to an internal address, and the floor is outside S3-d2; recorded with the port rule as a floor follow-up line on DEVOS-95.

**Tests:** `sm-15-ssrf.test.mjs` has 7 tests: the corpus of 64 cases (loopback, private, CGNAT, Docker and metadata addresses; decimal, hex, octal, short, percent-encoded and full-width IPv4; IPv6 loopback, ULA, link-local, multicast, site-local, mapped, NAT64, 6to4 and SIIT forms; `localhost`, a trailing dot, internal names, a name with any internal answer, IPv6 answers; `file`, `gopher`, `dict`, `ldap`, `ftp`, `data`, `javascript`, `ws`; credentials and `user@host`; not-a-URL inputs); redirects from a public page to internal targets and other schemes, and one hop over the cap; DNS rebinding (one lookup per request and per hop, and a name with any internal answer refused; socket pinning on the checked path is the core safe-fetch tests' job); size (with and without a content length) and time caps (no answer, slow drip); caps lowered but never raised; no `allowHosts`, body or other method; and messages that never tell an internal name from a missing one. ## S3-d3 SM-16 build notes (17 Nov 2026, runner B, DEVOS-95, ADR-0013)
**Add-on:** `templates/golden-path/addons/SM-16/` adds `src/ai-guard.mjs` and `test/sm-16-ai.test.mjs`. `addon.json` maps SM-16-L1 to that test.

**Runner decisions (technical).**
- **No LLM SDK.** The add-on shapes what goes to a model and checks what comes back; it adds no provider client and no dependency, so it works with whichever model a project picks, and the core keeps no runtime dependency. Calling a model is the project's own code, through `safeFetch` (F2).
- **Data blocks.** `dataBlock(source, content)` wraps content in `<untrusted-data id="<24 hex>" source="…">` … `</untrusted-data id="<same id>">`. The id is fresh random bytes for every block and is redrawn if the content happens to contain it, so content cannot close the block; a block it imitates (even with a 24-hex id) stays inside the real one. The system rule tells the model that only the closing tag with the block's own id ends it. The redraw is tested with an injected id source (`newId`, for tests only). The content is kept whole (not rewritten), so the model still sees what the user sent. `source` is a short plain label (no quotes).
- **Where content goes.** `buildMessages` puts the app's instructions and the data rule in the system message and puts the task and then one block per piece of content in the user message. Untrusted text never reaches the system message. A sparse `data` list is refused.
- **Tool results.** `toolResultBlock(toolName, result)` returns a tool's result (search hits, a fetched page, a file) to the model in its own data block (`source="tool <name>"`; structured results are serialised as JSON inside it), because a read-only tool can still return attacker-written text.
- **Tools.** Every tool states `sideEffect` (`true` or `false`; anything missing, not a boolean, or listed twice is refused). `toolsFor(tools, allow)` offers every read-only tool and only the side-effect tools named in the allow-list; `checkToolCall` refuses any call to a tool that was not offered, before it runs. The default allow-list is empty.
- **Output.** `escapeOutput` escapes `& < > " ' \` = /` as numeric entities, and is safe in element text and quoted attribute values only. The `usage` forbids model output in `href`, `src`, `script`, `style` or an event handler (escaping does not make `javascript:` safe there) and forbids eval, `new Function`, a shell or a query on it. The add-on carries its own escaper so it works without SM-03.
- **Auto + review.** SM-16-L1's `How` is "auto + review": the tests prove the helpers; the reviewer checks that the app's model calls go through them (the `usage` says so).
- **AT6 fixture.** AT6's not-yet-built example moves to SM-17 and SM-18; the assertion is unchanged.

**Known limits (recorded).** Delimiting lowers the risk of prompt injection; it does not remove it. A model can still be talked into a wrong answer inside the task, which is why side-effect tools are off unless allow-listed. SM-16-F1 (an injection corpus run against a live model, and a per-request token cap) is Full tier and not in this add-on.

**Tests:** `sm-16-ai.test.mjs` has 5 tests, all driven by a seeded injection probe (fake closing tags, fake blocks with a short and a 24-hex id, "ignore all previous instructions", script and `onerror` markup): the content stays whole in one block it cannot close, the forged block lies inside it, the id is fresh per block and redrawn when the content holds it; the system rule names the matching-id close; nothing untrusted reaches the system message or sits outside a block; the injected tool names, unknown names and `__proto__` are refused while read-only and allow-listed tools pass; tool results come back in a data block; and output is escaped, never decoded. ## S3-d4 SM-17 build notes (17 Nov 2026, runner B, DEVOS-95, ADR-0013)
**Add-on:** `templates/golden-path/addons/SM-17/` adds `src/uploads.mjs` and `test/sm-17-uploads.test.mjs`. `addon.json` maps SM-17-L1 to that test.

**Runner decisions (technical).**
- **The bytes decide the type.** `sniffType` reads magic bytes for five types: PNG, JPEG, GIF, WebP and PDF. The name and the client's content type never decide. `checkUpload` refuses an unknown or not-allowed type (`type-not-allowed`, which covers a program or a page renamed as an image) and an allowed type under another type's name (`name-mismatch`). An app narrows `allow` to what it needs. SVG and HTML are not on the list because they can carry script.
- **Size.** `checkUpload` caps the bytes (`maxBytes`, 10 MB by default, exactly-at-cap passes). `readBody(req, maxBytes)` refuses a declared `Content-Length` over the cap before reading, and stops a chunked body as it grows past the cap, so an oversize upload is never buffered whole.
- **Storage.** `createStore({ dir, webRoot })` takes an absolute folder and resolves links (`realpathSync.native`, through the nearest existing ancestor). It checks before it creates anything, and again after. It refuses a folder that is the web root or inside it, including one reached through a link and one named `..x` inside it. Names are 128 random bits plus the sniffed extension. The user's name is never used. Files are written with `wx` (never overwritten) and mode 0600 in a 0700 folder; an existing folder is tightened to 0700. The stored extension comes from the sniffed type, never from the caller. `path`/`read` accept only that exact name shape, so `../` and other extensions are `not-found`. `save` takes only bytes whose sniffed type and size match the `checkUpload` result passed with them.
- **No dependency**, and no multipart parser: the core has none. A project that needs `multipart/form-data` adds a permissive-licence parser and still passes each file through `checkUpload`. The limit is recorded below.
- **AT6 fixture.** AT6's not-yet-built example moves to SM-13 and SM-18. The assertion is unchanged.

**Known limits (recorded).**
- Magic bytes prove the start of a file, not the whole of it. A polyglot (for example a PDF with a script inside) passes. The `usage` therefore says to serve stored files with the stored type, `nosniff`, and `attachment` for non-images, through a route that checks access.
- No virus scan and no image re-encoding. Both are outside Lite.
- No multipart parsing, as above.
- `save` checks that the bytes' sniffed type and size match the result passed with them; it cannot prove `checkUpload` ran with the app's own cap and allow-list, so the `usage` makes `checkUpload` the step before `save`.

- **Size:** empty and oversize files are refused, a file exactly at the cap passes, and a real HTTP server answers 413 for a declared length over the cap and for a chunked body that grows past it.

## S3-d5 SM-18 build notes (17 Nov 2026, runner B, DEVOS-95, ADR-0013)
**Add-on:** `templates/golden-path/addons/SM-18/` adds `src/integration-error.mjs`, `src/webhook.mjs`, `src/events.mjs`, `src/cache.mjs`, `src/token-vault.mjs` and `test/sm-18-integrations.test.mjs`. `addon.json` maps SM-18-L1 to that test. The Lite text says "only the sub-parts that apply", so each sub-part is its own file and the `usage` tells the app to delete the ones it does not use.

**Runner decisions (technical).**
- **No dependency and no provider SDK.** Everything uses `node:crypto` only; the core keeps no runtime dependency. A provider with its own signing scheme (Stripe, Razorpay) keeps its official verifier, which a project adds under the permissive-licence rule; the window, replay store and ledger still apply (the `usage` says so).
- **Webhooks.** `verifyWebhook` checks an HMAC-SHA256 over `<timestamp>.<raw body>` with `timingSafeEqual` on 32-byte digests (every listed secret is tried, no early exit, so two secrets work while one is rotated). Order: signature first, so an unsigned request can never fill the replay store; then a ±5-minute window (`toleranceSec` 1–900); then a replay claim on `<timestamp>.<signature>` that lives exactly as long as the window can pass. The body must be the raw bytes (parsed JSON is a `TypeError`). `readRawBody` caps the body at 1 MB (declared length refused before reading, a growing body cut and drained). `memoryReplayStore` is bounded (`max`); when it is full of live entries it refuses (`replay-store-full`, answered 503) instead of forgetting one, because forgetting would let that delivery replay. `verifyWebhook` returns `release()`: when processing fails and the app answers 5xx, it releases the claim so the provider's resend is accepted (pre-review finding 2).
- **Payment events.** `createEventLedger({ rank, store }).apply(event, handler)`: dedupe by event id; per object, the last applied `(version, rank)` wins, and an older event is recorded as `stale` without running the handler; equal order is applied. One object's events run one at a time (a per-object promise chain), so concurrent deliveries cannot both pass the check. A failing handler records nothing, so the retry is applied. A database store adds `transaction(fn)`; the ledger then runs the check, the handler and the record in that one transaction and hands it to the handler, so the effect and the record commit together (pre-review finding 4). The memory store keeps event ids 7 days (providers retry for about 3).
- **Cache.** Every entry has a TTL; an LRU bound (`max`). `write(keys, writer)` drops the keys before and after the write (also when the write fails). A load that started before an invalidation never stores its value: the store step checks that its own promise is still the registered load, which an invalidation removes. No per-key generation map, so nothing grows with the number of keys written (pre-review finding 1). Errors are never cached, including a loader that throws at once.
- **Tokens.** AES-256-GCM, a fresh 12-byte IV per seal, a 16-byte tag pinned on decrypt, and AAD binding the format version, key id, provider, owner, scopes and expiry, so a record moved to another owner or with its scopes or expiry edited fails to open. Keys come from `TOKEN_KEYS` (`<id>:<32-byte base64>`, canonical base64 only, first key encrypts, all decrypt; `rewrap` moves a record to the current key). Least scope: the app declares the scopes it needs per provider; `scopesFor` asks only for a declared subset, `seal` refuses a broader grant, and `open` needs the owner, the provider and the scopes the call needs. No error message carries a key, a token or a signature.
- **AT6 fixture.** SM-18 is built, so AT6's not-yet-built example is SM-13 alone; the assertion is unchanged.

**Known limits (recorded).**
- The memory replay store, event store and cache are per process. An app with more than one instance needs the shared or database stores the `usage` describes; the contracts are tested, a real database store is the app's.
- The ledger's chain is per object id: the same event id sent under two different object ids is not serialised. Providers send one event for one object, so this is recorded, not fixed.
- `verifyWebhook` takes a bare hex signature; header formats (`sha256=…`, `t=…,v1=…`) are parsed by the app, as the `usage` says.
- `rewrap` needs the record's scopes still declared and the token not expired; a narrowed declaration or an expired token means the user connects again.
- SM-18-F1 (replay, out-of-order and stale-read tests at Full tier) goes beyond Lite; the Lite tests already cover those three cases at unit level.

**Tests:** `sm-18-integrations.test.mjs` has 4 tests, one per sub-part:
- **Webhook:** valid once, replay refused, released claim accepted once more; missing, malformed, wrong-secret, changed-body and changed-timestamp signatures refused; parsed JSON refused; a delivery outside the window either way refused; refused deliveries never fill the store; rotation with two secrets; a full store refuses and prunes expired entries; the raw-body cap (chunked and declared).
- **Events:** duplicate applied once; a late and a same-second earlier state are stale and remembered; three concurrent deliveries apply once; concurrent out-of-order events leave the newest; a failing handler records nothing; bad events refused; a transactional store rolls the handler's write back when the record fails, then applies once and dedupes.
- **Cache:** TTL hit and expiry; a write is seen at once; a load that began before a write never puts its old value back; a failed write still drops the key; concurrent reads share one load; async and sync loader errors are not cached; the LRU bound.
- **Tokens:** the stored record never holds the token; open for the owner and a granted scope; a fresh IV; a broader grant, an undeclared provider or scope, another owner, an edited record and an expired token refused; rotation, rewrap and an unknown key; bad `TOKEN_KEYS` refused without echoing the key.

With SM-18 applied alone, `floor-check` passes, the add-on's app passes 26/26, and the template harness passes 16/16.

**Pre-review round 1 (CHANGES_REQUESTED; 2 medium, 5 low, 2 info; all 9 accepted):** the cache's generation map grew without bound (medium, fixed: the registered-load check); the replay claim could not be released after a failed processing step (medium, fixed: `release()`); the `usage` now answers 503 for a full store and 413 for an oversize body and keeps "the window" only where the provider signs a timestamp (low); the ledger takes a store transaction (low); `scopesFor` refuses a string (low); an oversize body is drained instead of paused (low); the key-echo test is an `assert.throws` (low); header parsing and `rewrap`'s limits are in the `usage` and known limits (info).
