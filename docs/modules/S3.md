# S3 — Modular golden-path template (contract)

- **Linear:** DEVOS-64 · parent DEVOS-61 (Phase PS) · P2 · Lane B · blocks M2.4 (DEVOS-21) and G2 (DEVOS-46)
- **Split (size rule, 11 Nov 2026):** the module is over 800 changed lines and more than one concern, so it is built as task sub-issues, one PR each, in this order:
  - **S3-a** core + the `apply` tool + floor checks for the core (DEVOS-92);
  - **S3-b** add-ons SM-01 … SM-06 (DEVOS-93);
  - **S3-c** add-ons SM-07 … SM-12 (DEVOS-94);
  - **S3-d** add-ons SM-13 … SM-18 (DEVOS-95).
  M2.4 needs only S3-a (repos are created from the core; add-ons are applied later from the selection by M3.2), so M2.4 can start once S3-a merges.
- **Depends on:** S1 (catalogue, check IDs). Applies ADR-0010 (modular standard), ADR-0011 (timeouts on outbound calls), D13 (licences).
- **Source:** Phase PS build standard v1.1.0 §6 (S3 row) and §7 (M2.4 amendment); build plan v1.0.3.

## Goal
A template every DevOS-built app starts from:
- **Core** (always): F1 config (no secret reaches the client), F2 `safeFetch`, F3 Compose limits, `/health` + `/ready`, JSON logging with a request ID.
- **Add-ons**: one per selectable module (SM-01 … SM-18), copied in only when that module is selected for the project.

## Done when (DEVOS-64)
1. The core alone passes the floor checks.
2. Each add-on applied alone passes its Lite checks.
3. Unselected add-ons are absent from the generated repo.

## Design decisions (technical, made by runner B on 11 Nov 2026 under KK's standing order)
- **Stack: Node.js 22, ESM JavaScript, no runtime dependencies in the core.** The core uses only `node:http`, `node:https`, `node:dns`, `node:net` and `node:crypto`. Reasons: the floor code (`safeFetch` above all) must be small enough to review line by line; no third-party package in the core means no licence or vulnerability work for every app (SM-14 then starts from zero findings); DevOS itself is Node 22, so the sandbox, tests and CI images are shared. Add-ons may add pinned dependencies with permissive licences (MIT, ISC, BSD, Apache-2.0) only; anything else is a D13 card.
- **floor-check scope (F2-1):** any import, dynamic import or `require` of `node:http`, `node:https`, `node:http2`, `node:net`, `node:tls` or `node:dgram` outside `src/safe-fetch.mjs` is a finding (so aliases and namespace imports cannot slip through); the one exception is `src/server.mjs`, which may import `node:http` only as a default/namespace import or `{ createServer }`, and may use that binding only for `createServer`, `STATUS_CODES` and `METHODS`. Also flagged anywhere: `globalThis.fetch`, `node:module`, `node:child_process`, `node:worker_threads` and `import()` of a computed name. Also flagged: `fetch(`, HTTP client packages, `XMLHttpRequest`/`WebSocket`/`EventSource`, Python HTTP clients and sockets. Only the root `test/` folder is exempt (tests use `fetch` against local stubs); only root-level `dist`/`build`/`coverage` are skipped. Browser code under `public/` is not F2 (it talks to its own origin) and is covered by F1-4. A static check cannot prove there is no other egress path; F3-1 (S4's probe) is the backstop.
- **Layout in the DevOS repo:** `templates/golden-path/core/` (the core app), `templates/golden-path/addons/<SM-id>/` (one directory per add-on, each with an `addon.json` naming its module, the files it adds and the Lite check IDs its tests cover), `scripts/template/apply.mjs` (the generator), `scripts/template/floor-check.mjs` (static floor checks for a generated repo).
- **Selection input:** `apply.mjs --out <dir> [--select SM-01,SM-09,…]`. The selector (S5) owns `selection.md`; M2.4/M3.2 pass the selected IDs to `apply`, so S3 does not parse `selection.md` and the two modules cannot drift. An ID that is not a selectable module in `build-standard.yaml` is refused (exit 2, nothing written). A selected module whose add-on is not built yet is listed under `pending` in the manifest, never silently skipped.
- **Manifest:** `apply` writes `.devos/template.json` in the generated repo: template version, the DevOS SHA it came from (`--sha`, default `git rev-parse HEAD` of the DevOS checkout), `selected`, `applied`, `pending`. S6 and the Codex reviewer read it.
- **`apply` never overwrites:** the output directory must be empty or absent (exit 2 otherwise), so it cannot clobber a project.
- **F1 in the core:** `src/config.mjs` reads the environment once on the server. `clientConfig()` returns only the keys listed in `CLIENT_CONFIG_KEYS` (empty by default); a listed key whose name looks like a secret (`SECRET`, `TOKEN`, `KEY`, `PASSWORD`, `PRIVATE`) is refused at start-up. Client code lives under `public/` and must not read `process.env` (static check).
- **F2 in the core:** `src/safe-fetch.mjs`:
  - only `http:` and `https:`;
  - the host is resolved once, every resolved address is checked, and the connection is pinned to a checked address (no second lookup, so DNS rebinding cannot swap it);
  - refused ranges: IPv4 0/8, 10/8, 100.64/10 (CGNAT and the tailnet), 127/8, 169.254/16 (metadata), 172.16/12, 192.168/16, 192.0.0/24, 198.18/15, 224/4 and above, plus the Docker default 172.17/16 (inside 172.16/12); IPv6 `::`, `::1`, `fc00::/7` (ULA), `fe80::/10`, `ff00::/8`, and IPv4-mapped / NAT64 forms of the IPv4 ranges;
  - IP literals in any encoding are normalised by `node:net` / WHATWG URL before the check (decimal, octal, hex IPv4 become dotted quads);
  - also refused: IPv6 `fec0::/10`, `100::/64`, SIIT `::ffff:0:0/96` and 6to4 `2002::/16` when the embedded IPv4 is internal;
  - redirects are followed manually (at most 5) and every hop is checked again; 303 (and 301/302 after a non-GET) becomes GET without a body, 307/308 keep the method and body; when a redirect changes origin, only plain headers are kept (`accept`, `accept-language`, `accept-encoding`, `user-agent`, `content-type`, `content-language`, `cache-control`, `pragma`); every other header, so any credential under any name, is dropped;
  - requests use `agent: false`: no keep-alive pool keyed by hostname and no environment proxy (`NODE_USE_ENV_PROXY`), so nothing resolves the name a second time;
  - every failure is a `SafeFetchError` with a `code` (`scheme`, `credentials`, `url`, `dns`, `blocked-address`, `allow-hosts`, `redirects`, `timeout`, `too-large`, `network`, `request`);
  - a timeout on the whole request (default 10 s) and a response size cap (default 5 MB);
  - an `allowHosts` option for tests and for declared internal services is the only bypass. Entries must be exact DNS hostnames (no IP literals, wildcards or `localhost`). It applies to the URL the caller passed and to redirects that have never left that origin, so a public URL can never redirect into a declared service, and a detour through another origin cannot come back into it.
- **F3 in the core:** `compose.yaml` sets `cpus`, `mem_limit`, `pids_limit` and a project-only network on every service; the host-side rules are S4's.
- **Ops in the core:** `GET /health` (liveness: `{status:"ok", sha}`) and `GET /ready` (readiness: runs registered checks, 503 with reasons if any fails); JSON log lines with a request ID taken from `X-Request-Id` when it is a safe token, otherwise generated; every other route 404s (SM-02 deny-by-default starts here).
- **Floor checks that a repo can run itself:** `floor-check.mjs <dir>` runs the static parts: F2-1 (no raw HTTP client outside `safe-fetch.mjs`: `fetch(`, `http.request`, `https.request`, `http.get`, `https.get`, `axios`, `undici`, `got`, `node-fetch`, `requests`, `httpx`), F1-4 (no `process.env` under `public/`; `CLIENT_CONFIG_KEYS` has no secret-shaped name), F3-2 static (every Compose service has the three limits). The scanning checks (F1-1…F1-3) are gitleaks in CI and S6; F3-1 is S4's probe.

## S3-b split and S3-b1 build notes (12 Nov 2026, runner B, ADR-0013)
**Split.** Six add-ons are six reviewable concerns, so S3-b (DEVOS-93) is built as one task sub-issue and one PR per add-on, in order: **S3-b1 SM-01 (DEVOS-136, this PR)**, then SM-02 … SM-06, each filed when it starts.

**Add-on layout** (the shape `apply.mjs` already expects): `templates/golden-path/addons/<id>/addon.json` plus `files/`, copied onto the core and never overwriting a core file. `addon.json` holds `id`, `name`, `files` (every path the add-on adds), `checks` (each Lite check ID → the test file that covers it) and a one-line `usage`. DevOS CI (`scripts/test/template.test.mjs`) checks every built add-on the same way: applied alone, the manifest says `selected = applied = [id]`; `floor-check` passes; exactly the listed files are added (so no other add-on comes with it); every Lite check ID of the module in `build-standard.yaml` is named in its mapped test file; and the add-on's own tests pass.

**SM-01 decisions (API input and contracts, SM-01-L1).**
- **No dependency.** `src/validate.mjs` is a small schema validator (string, integer, number, boolean, array, object) instead of a library: the core has no dependencies, the rule set needed for SM-01-L1 is small, and every rule is tested here. An app that needs JSON Schema in full can swap it later (M3.2 decides per project).
- **Safe defaults:** strings ≤ 1000 characters and lists ≤ 100 items unless the schema says otherwise; unknown object fields are refused (so `__proto__` and mass assignment are refused); a route part with no schema must be empty (an unexpected query or body is a 400).
- **`validated({ body, query, params }, handler)`** wraps a core route. The body must be `application/json` (415), at most 100 KB (413, checked on `Content-Length` and while reading) and arrive within 10 s (408); bad JSON is a 400. Query and params arrive as text and are coerced to numbers or booleans only where the schema asks; a repeated query key is a list, refused unless the schema is a list. On any failure the answer is `400 {error:"invalid-input", details:[{in, path, message}]}` (at most 20), and the handler, the only path to the database, never runs.
- **No reflection.** Error messages name the field and the rule, never the value sent.
- **Contract tests:** `invalidCases(schema, validExample)` generates the invalid variants (each required field missing, each field of the wrong type, each length, range, format, enum and list-size rule broken, an unknown field, a non-object), keeping only those the schema really refuses. The add-on's test posts each one and expects a 4xx with the handler never reached. SM-01-F1 (contract tests from a separate API schema) is Full-tier and not in this add-on.
- **Params:** the core router matches exact paths and has no params yet. `validated` checks whatever the app's router puts in `ctx.params`.

**Pre-review r1 (1 medium, 3 low; all fixed):** (medium) a `__proto__` query or params key was assigned as a prototype and so escaped the unknown-field rule; coerced input is now built with own data properties, and `__proto__`/`constructor` keys are a 400 on routes with and without a query schema. (low) A chunked body over the limit now gets its 413 (and a slow one its 408) before the socket is closed, instead of a reset. (low) An unknown field is named only when it is a plain identifier, so a crafted key is never echoed. (low) `validated()` checks the whole schema when the route is set up (types, list `items`, patterns).

**Pre-review r2 (1 medium, 4 low; 4 fixed):** (medium) a string over its length cap still ran its `pattern`, so a nested-quantifier pattern could stall the server; validation now stops at the cap, so no pattern runs on more text than the schema allows. (low) `application/*+json` bodies (merge-patch, problem) are accepted. (low) `assertAllValidated(routes)` lets an app test that every route is wrapped (SM-01-L1 "each route"). (low) `checkSchema` also checks that `required` names are properties, `enum` is a list and limits are numbers. **Not changed (low):** `invalidCases` breaks top-level fields only; nested list items and nested objects are validated, but an app that wants generated cases for them writes them by hand (recorded in `usage`).

**Codex PR63-r1 (2 medium; both accepted):** (1) a route without a body schema accepted a JSON body of `{}`, because the "must be empty" rule treated an empty object as absent. Only query and params may be empty objects now; any body at all, even `{}`, is a 400 there. (2) `invalidCases` broke `maxItems` but never `minItems`; it now also sends a list one item short. Tests: a GET with `{}`, `[]` or `null` on a no-body route gets 400; the generated cases include "too few items" (both fail on the r1 code).

**Tests:** `addons/SM-01/files/test/sm-01-validate.test.mjs` (6: generated contract cases on the body, query rules and coercion, params, malformed bodies 400/413/415 and `__proto__`, no reflection), plus the per-add-on harness test in `scripts/test/template.test.mjs` (16/16).

## DEVOS-159: AT4/AT6 start-up wait (12 Nov 2026, runner B)

- **Cause.** The AT4/AT6 `/health` test polled for a fixed 5 s window. On a loaded CI runner the generated server took longer to start, so the test failed with "the server never answered /health" (seen on #74, `4483e56`).
- **Decision.** The test now waits for the server's own `"msg":"listening"` log line, bounded at 30 s, then requires one `/health` answer with status 200 and a JSON body (10 s bound). A start that exits with `EADDRINUSE` on the random port is retried on a new port, at most 3 times. The `/health` assertions (status 200, JSON body) are unchanged; the test adds one check (the "listening" line) and changes only the wait. Retry and exit detection listen on `close` (after stdio has drained) and on spawn `error`; the test waits for the child to close after killing it. A server that never logs "listening" still fails the test (checked by renaming the log message: the test fails with `never logged "listening" (timeout)`).

## S3-b2 SM-02 build notes (13 Nov 2026, runner B, ADR-0013)
DEVOS-182, the second add-on of S3-b. Files: `addons/SM-02/files/src/access.mjs` and `addons/SM-02/files/test/sm-02-access.test.mjs`.

**Decisions (technical, runner B):**
- **Who a caller is (SM-02 Lite: "KK's tailnet identity or a service token").**
  - *Tailnet (opt-in):* the `Tailscale-User-Login` header that `tailscale serve` sets. The header proves nothing by itself, so it is believed only when the TCP peer is in an explicit `trustedProxies` list of IP addresses (empty by default; CIDRs, names and empty strings are refused at set-up). Setting `tailnetLogins` also needs `identityProxy: "tailscale-serve"` and a non-empty `trustedProxies`, and a non-loopback entry (a Docker gateway, say) also needs `nonLoopbackProxy: true`; `trustedProxies` without `tailnetLogins` is refused. From any other peer the header is ignored. The login must be in `tailnetLogins` (exact, case-insensitive); a trusted peer with an unknown login gets 403.
    - **Residual risk, recorded:** the add-on cannot see what sits at a trusted address. Only `tailscale serve` (which overwrites the `Tailscale-User-*` headers) may connect from it; any other proxy there (nginx, Traefik, docker-proxy on a published port) would forward a client's header and let anyone claim a listed login. That is why the flags above make the app state its set-up explicitly, why service tokens are the default, and why S4 (no route into the project network) and M2.4 (how the app is published) carry the deployment side. Verifying the login with tailscaled's `whois` would remove the risk but needs a socket client, which F2-1 forbids outside `safeFetch`; it is left to M2.4 if a project needs tailnet logins behind a shared proxy.
  - *Service:* `Authorization: Bearer <token>`, 32–256 URL-safe characters. The app holds only SHA-256 digests (`SERVICE_TOKEN_SHA256_<NAME>` in the server environment, read by `serviceTokensFromEnv`), so a leaked config file holds no usable token. Every configured digest is compared with `timingSafeEqual`, with no early exit. An offered bearer header decides alone: a bad token is 401 and never falls back to the tailnet header. The scheme name is case-insensitive (RFC 7235).
  - Reasons: no login screen or session store is needed for Lite (sessions are SM-02-F1, Full tier). Both identities are already how DevOS callers work (KK on the tailnet, agents with tokens). No dependency is added.
- **Deny by default.** The core already answers 404 for any route not in the table and serves `/health` and `/ready` before the table. `guard.protectAll(routes)` wraps every app route; it refuses to wrap the two open core routes. A guard with no callers configured throws at set-up, so a misconfigured app fails at start-up instead of serving nothing silently.
- **Route inventory (SM-02-L1, evidence `route_list`).** `routeInventory(routes)` lists each route as open, guarded and owner-checked. `assertAllGuarded(routes)` throws, naming every route that is not behind the guard. The markers are module-private `WeakSet`s, so a handler cannot claim to be guarded by setting a property.
- **No IDOR (SM-02-L2).** `owned(resolve, handler)` wraps a route that takes an ID. `resolve(req, ctx)` reads the ID once and returns `{ id, owner, value }` (owner is `tailnet:<login>` or `service:<name>`) or null; the handler gets it as `ctx.resource` and uses only that, so the check and the use cannot read different IDs. `singleParam(req, name)` gives null for a missing or repeated query key, so `?id=mine&id=theirs` is refused. Another owner's resource and a missing one both answer `404 {error:"not-found"}`, so a caller cannot probe which IDs exist. Without a caller (`owned` used without the guard) it answers 401: fail closed. `assertOwned(routes, idRoutes)` lets an app test that every route taking an ID is owner-checked.
- **Order with SM-01.** Nest as `guard.protect(owned(resolve, validated(schema, handler)))`: the guard first, then the owner check, then the body/query schema. `resolve` is the only code that reads the ID, so it checks the ID's own shape (`singleParam`, then a length or pattern test) before any lookup. This keeps `assertOwned` accurate, since `protect` carries the owner-checked marker from its direct child only.
- **No reflection.** 401, 403 and 404 bodies are fixed and never contain the token, login or ID sent.
- **`trustedProxies` entries** must be written the way Node reports a peer address: a dotted IPv4, `::ffff:` + a dotted IPv4, or an IPv6 address in its canonical lower-case compressed form. Anything else (a CIDR, a name, `0:0:0:0:0:0:0:1`, bracket tricks) is refused at set-up, because it could never match and tailnet log-in would silently fail.
- **Not in this add-on:** sessions, a login page and two-user row-level tests (SM-02-F1, SM-02-F2) are Full tier. Running `assertAllGuarded`/`assertOwned` on a generated app's real route table and storing `routeInventory` as the `route_list` evidence is M3.2's job (the Builder wires the app's routes and its tests); the add-on ships the helpers and proves them on sample routes.

- **Cross-origin writes (SM-03-L1): an Origin check, not CSRF tokens.** `createOriginGuard({ allowedOrigins })` wraps routes; for POST, PUT, PATCH and DELETE it refuses with a fixed `403 {error:"cross-origin-refused"}` when `Sec-Fetch-Site` is present and not `same-origin`, or `Origin` is present and not exactly one of the allowed origins (`null`, another scheme or port, a repeated header: all refused). Reasons: no session store or token plumbing is needed (Lite has no sessions; SM-02 callers are tailnet logins and bearer tokens), it covers form posts and `fetch` alike, and it fails closed for a browser that sends nothing. GET and HEAD are never state-changing (stated in `usage`).

Each pattern runs on the whole file (a sink split over lines is found) and is reported at its first line; comments and strings are included: a false positive costs a rewrite, a missed sink costs an XSS. There is no allow-annotation in Lite: the check says "no sinks", and "on untrusted data" is for the reviewer when a project asks for one (a waiver from KK). The add-on's own test runs it on the generated app, so the app's test suite fails on a sink from then on. The patterns are built from pieces so the module and its test do not match themselves.
- **Not in this add-on:** CSP and the security-header set (SM-03-F1) and the seeded-XSS E2E (SM-03-F2) are Full tier. Wiring the guard into a real app's route table is M3.2's, as for SM-01 and SM-02.

**S3-b3 deadlock resolution (runner B, 14 Nov 2026, ADR-0013 DEADLOCKS): a fail-closed HTML subset instead of a model of the full parser.**
- **Why:** thirteen Codex rounds (pre-review and PR98-r1 to r13) each found one more place where `MarkupState` read markup differently from a browser: foreign content (SVG and MathML, their integration points, CDATA), `select` and `template`, comments and bogus comments, unquoted values, and nested fragments. Each fix was correct, but the next round found another case, and every round is a paid review. The HTML tree builder decides how later text is tokenized, so a partial model of it can always be out-run. That makes three or more failed attempts on the same task.
- **Decision:** `html` now accepts only a subset in which the browser's tokenizer state follows from the token stream alone.
  - Tags: `html head body title meta link script main header footer nav section article aside h1–h6 p div span a ul ol li dl dt dd table thead tbody tfoot tr th td caption form label input button textarea img br hr strong em b i small code pre blockquote`.
  - Attributes: `id class title lang dir role hidden tabindex href rel target src alt width height loading action method for name value type placeholder checked disabled required readonly min max step maxlength autocomplete colspan rowspan charset content defer async` and `aria-*`.
  - Syntax: `<name attr attr="value">`, `</name>` (spaces only before `>`), `/>`, and one leading `<!DOCTYPE html>`. Every `<` in static text must start such a tag (write `&lt;`).
  - Refused: every other tag (so `svg`, `math`, `select`, `template`, `noscript`, `style`, `iframe`, `xmp`, `plaintext`…), every other attribute (so `on…`, `style`, `srcdoc`, `srcset`, `formaction`, `data-*`), comments, `<!…>` and `<?…>`, unquoted and single-quoted values, and non-ASCII whitespace inside a tag.
  - Text states: `<title>` and `<textarea>` (with or without `/>`) are RCDATA, and inside them static text may hold no `<` except the exact end tag. `<script>` is allowed only as `<script …></script>` with nothing between and no value in its attributes.
  - None of these elements changes tokenization in any HTML insertion mode the subset can reach (no foreign content, select, template, frameset or noscript is reachable), so this parser and the browser agree on every token.
- **Effect:** a parser mismatch can now only make `html` throw; it cannot pass an unsafe page. Every r1–r13 fixture is kept as a regression and now throws. Templates that used markup outside the subset (`<svg>`, `<select>`, comments, single-quoted values, `srcset`, inline `<script>` text, a bare `<` in text) are refused; this is the narrowing.
- **Removed as no longer needed:** foreign-content tracking, select tracking, the bogus-comment, comment and CDATA rules, the RCDATA-entry flag for nested results and the end-tag-in-attribute rule. `<p title="a</title&gt;">` is now accepted, because without foreign content an attribute value cannot end RCDATA.
- **Follow-up:** richer markup (SVG icons, `<select>`, inline styles and scripts behind a CSP nonce) belongs to M3.2 or the Full tier (SM-03-F1), filed as DEVOS-191.

## S3-b4 SM-04 build notes (13 Nov 2026, runner B, ADR-0013)
DEVOS-184, the fourth add-on of S3-b. Files: `addons/SM-04/files/src/outbound.mjs` and `addons/SM-04/files/test/sm-04-outbound.test.mjs`. Built from main; it shares no file with SM-02 (#97) or SM-03 (#98).

**Decisions (technical, runner B):**
- **No defaults (SM-04-L1 says "explicit").** `outbound({ name, baseUrl, timeoutMs })` makes one client per external dependency and refuses to be built without an integer `timeoutMs` from 1 ms to 120 s. Each `call(path, opts)` goes through the core's `safeFetch` (F2) with that timeout. A call may lower the timeout but never raise it past the client's or drop it, and the path must stay on the client's origin. A timeout becomes an `OutboundTimeout` (`code: "timeout"`, dependency name, ms), so logs and callers can tell which dependency hung.
- **Non-HTTP calls.** `withDeadline(name, timeoutMs, (signal) => work)` covers a database query, a queue or an SDK. It also has no default. At the deadline it aborts the signal it handed to the work and rejects, even if the work ignores the signal. A late failure after the deadline is swallowed, not left as an unhandled rejection. Reason: the core has no database or SDK of its own, so the add-on gives the one wrapper they all need; SM-06 and the app's own clients pass the signal on.
- **Auto part of "auto + review".** `findUntimedCalls(root)` reads `src/` in a code view where comments and string and template text are blanked, keeping offsets and `${…}` expressions. Words and parentheses in comments or strings therefore neither hide a call nor fake one. A `/` where an expression can start (after an operator, `(`, `,`, `=`, a keyword such as `return`, or at the start of the file) opens a regex literal, which is blanked like a string. So `/^https?:\/\//` or ``/`/`` cannot hide the lines after it. The rules are inverse, as for F2-1:
  - The only accepted use of `safeFetch` is a direct call whose second top-level argument is an object literal that names `timeoutMs` at its top level. Shorthand, a quoted key and a trailing `as const` are allowed.
    - The last `timeoutMs` counts. No spread may come after it, because `...opts` could carry `timeoutMs: undefined`. A spread before it is fine.
    - The value must not be `undefined`, `null` or `void`.
    - A number literal (decimal, hex, octal, binary or exponent) must be from 1 ms to 120 s.
  - Every other use of the name is reported: an alias, a value, `?.()`, `.call`, spread arguments, options passed in a variable, or a `timeoutMs` nested in another argument.
  - Any reference to `safe-fetch` other than a plain named import is reported, including a namespace import, a dynamic import and a mention in a comment. That false positive is cheap and is recorded here.
    - A plain named import has no rename. It may list other names and may come from any relative path.
    - It may end with a line comment.
  - Each hit names its reason.
  - `safeFetch`'s own 10 s default is a fallback, not an explicit timeout.
  - The add-on's test runs the check on the generated app, so from then on the app's suite fails on an untimed call.
  - Calls through `outbound()` always carry a timeout. Calls that are not HTTP cannot be found statically and are the reviewer's.

## S3-b5 SM-05 build notes (14 Nov 2026, runner B, DEVOS-188, ADR-0013)
**Add-on:** `templates/golden-path/addons/SM-05/` adds `src/queue.mjs` and `test/sm-05-queue.test.mjs`; `addon.json` maps SM-05-L1 to that test.

**Runner decisions (technical).**
- **No dependency, one process.** The core has no dependencies and no database. A queue library such as BullMQ would add Redis, and pg-boss would add Postgres, so neither fits a template that must run alone. `createQueue` is a small in-process queue. An app that later needs several workers or a broker swaps it for a library (M3.2 decides per project). The Full-tier concurrency and load check (SM-05-F1) is not in this add-on.
- **Retry policy:**
  - `maxAttempts` (default 3);
  - `backoffMs` (default 1 s, 5 s, 30 s; the last value repeats);
  - `timeoutMs` per attempt (default 60 s). At the timeout the handler's `signal` aborts and the attempt counts as failed, even if the handler ignores the signal (ADR-0011 timeouts);
  - `concurrency` (default 1).
  - Every option is range-checked at set-up.
  - A job type with no handler is refused when it is enqueued.
- **Dead letters:**
  - A job that fails every attempt is marked `dead`, with its attempt count, its last error (at most 500 characters) and when it died.
  - `deadLetters()` lists them without the payload. `retryDead(id)` queues the job again with a fresh attempt count. `discardDead(id)` drops it.
  - `deadLetterRoutes(queue)` gives `GET /admin/dead-letters` and `POST …/retry` / `…/discard` with body `{"id":"<uuid>"}`. Bad input is a 400 and an unknown id is a 404. The body is kept up to 1 KB; past 64 KB or 10 s the connection is closed.
  - The routes are deliberately not guarded here. The app mounts them behind SM-02's auth guard and SM-03's origin guard, which are separate add-ons, as the usage line says.
- **Durability:**
  - `fileStore(path)` writes the whole job list to a temporary file (mode 600), fsyncs it, and renames it over the old one, so a crash or a power loss leaves either the old list or the new one. On load, a list whose jobs do not have a valid id, type, status and count is refused rather than half-trusted.
  - A job that was running when the process died keeps that attempt in its count, so a job that kills the process still reaches the dead-letter list instead of crashing every boot. A job with no attempts left is dead-lettered at start-up as `interrupted`; the others are queued again.
  - A store write that fails (for example a full disk) is reported as an `onEvent` `store.error`, and the queue keeps working from memory; the next change writes the whole list again.
  - `stop()` aborts running attempts the same way: they run again on the next start and are not counted as failures.
  - Done jobs are dropped.
  - `memoryStore()` is for tests, or for work that may be lost on restart.
- **Payloads are stored**, so the usage line and the code comments say never to put a secret in one. A payload must be JSON; it is copied when enqueued. A handler's error message is kept as `lastError` and shown in the dead-letter list, so the same applies to it.
- **Known limit (recorded):** a handler that ignores its abort signal may still be running after its attempt ended (timeout or `stop()`), and the queue does not wait for it. Handlers should honour the signal or be safe to run twice.
- **Pre-review (2 medium, 5 low; 6 fixed, 1 recorded):** (medium) a job that crashed the process was requeued on every boot and never dead-lettered; it now keeps its attempt count, and a job with no attempts left is dead-lettered at start-up. (medium) a failed store write was an unhandled rejection that could wedge the queue; writes are now caught and reported. (low) `idle()` now resolves after `stop()`; the store fsyncs before the rename and validates what it loads; the retry timer is no longer `unref`'d, so a worker with no server stays up for a backoff retry; the usage line warns about error text. (low, recorded) the signal-ignoring handler above. **Pre-review r2 (PASS, 5 low; 5 fixed):** `onEvent` is guarded, so a throwing callback cannot crash the worker or flip a job's outcome; a stored job is run only by an own handler (`Object.hasOwn`), otherwise dead-lettered at once; the next-due time is found without spreading every job into one call; an aborted admin request settles; a test title no longer claims a request. **Codex PR104-r1 (2 medium; fixed):** (1) an attempt that ends before its first await (a stored job with no handler) called `pump()` from its own `finally`, so a backlog of them recursed once per job and could exhaust the stack; the next pump is now queued as a microtask. Test: 4,000 such stored jobs are all dead-lettered (the previous code fails it with a stack overflow). (2) `fileStore` fsynced the file but not its directory, so the rename (and a newly made directory) could be lost on power loss; it now fsyncs the directory after the rename, and the parent of any directory it creates. **Codex PR104-r2 (1 medium; fixed):** with several new directories (`data/queue/jobs.json` and none existing) only the outermost's parent and the final directory were fsynced, not the directories in between; now every directory it made and the parent of the outermost are fsynced. The restart test uses a three-level new path.

**Tests:** `sm-05-queue.test.mjs` has ten tests, all SM-05-L1:
- work waits for `start()`, and a flaky job succeeds on its third attempt;
- a poisoned job is dead-lettered after `maxAttempts` with its last error and no payload, and a retry runs it again with a fresh count;
- a hanging attempt is aborted at the timeout;
- the file store keeps dead and cut-off jobs across a restart; the cut-off job runs again, and the dead one runs only after a retry;
- a job that was running when the process died keeps its count, and is dead-lettered at start-up when it has no attempts left; an invalid stored list is refused;
- a store that cannot write is reported and the queue keeps working;
- the admin routes list, retry, discard, and refuse bad ids and an oversized body;
- a stored job whose type has no own handler (e.g. `constructor`) is dead-lettered at once, and a throwing `onEvent` callback changes no outcome;
- set-up checks.

The template harness (`scripts/test/template.test.mjs`) passes 16/16 with SM-05 applied alone.

## S3-b6 SM-06 build notes (14 Nov 2026, runner B, DEVOS-207, ADR-0013)
**Add-on:** `templates/golden-path/addons/SM-06/` adds `src/db.mjs`, `src/migrations-check.mjs` and `test/sm-06-data.test.mjs`. `addon.json` maps SM-06-L1 and SM-06-L2 to that test. This is the last S3-b add-on (DEVOS-93).

**Runner decisions (technical).**
- **No driver, no dependency.** The core has no database. Choosing `pg`, Prisma or Drizzle is the app's call (M3.2), so the add-on ships only what works with any of them: a pool-limit reader, a transaction wrapper and a migration check. Where an app keeps its migrations as SQL (Prisma's `migration.sql` and Drizzle's output both are), the check reads them.
- **SM-06-L1 helpers:**
  - `poolConfig(env)`: `DB_POOL_MAX` is required, a whole number 1–50, with no default, so every project sets its own limit. `DB_STATEMENT_TIMEOUT_MS` is 100–600,000 (default 10 s) and `DB_CONNECT_TIMEOUT_MS` is 100–60,000 (default 5 s), per ADR-0011's timeouts. A bad value stops start-up.
  - `withTransaction(client, fn)`: `BEGIN`, `fn`, `COMMIT`. On a throw it runs `ROLLBACK` and re-throws the original error, and a failing `ROLLBACK` never hides that error. A nested call on the same client is refused. The client must be one connection, never the pool (stated in the code and the usage line).
  - The FK index rule is a warning from the migration check: a `REFERENCES` or `FOREIGN KEY` column with no index, primary key or unique key that leads with it. It fails only with `--strict`, because SM-06-L1 is a review check.
- **SM-06-L2 check** (`node src/migrations-check.mjs [--dir migrations] [--strict] [files…]`; exit 0 pass · 1 refused · 2 usage or read error):
  - **Refused:** `DROP` of a table, view, materialized view, schema, type, domain, sequence, function or procedure; dropping a column; `RENAME` of any of those or an index; a column type change; `SET NOT NULL`; an `ADD COLUMN … NOT NULL` clause without `DEFAULT` (each clause of a multi-clause `ALTER TABLE` on its own, as Prisma writes them; identity and serial columns supply values and pass); `DROP DEFAULT`; `TRUNCATE`; a `DELETE` or `UPDATE` with no top-level `WHERE` (quoted and schema-qualified names, `ONLY`, aliases, CTEs and `RETURNING` included; a `WHERE` only inside a subquery or a literal does not count). Rules read the statement with string-literal contents blanked, so text inside a literal never trips or clears one.
  - **Allowed:** the expand forms, such as a nullable column, `NOT NULL DEFAULT`, `DROP NOT NULL`, `DROP CONSTRAINT`, `SET DEFAULT`, and `DELETE`/`UPDATE … WHERE`.
  - **Contract step:** a later contract step is allowed by `-- sm06: contract <reason of 10+ characters>` on the line right above the statement. It is printed as `CONTRACT`, never silent.
  - **No git call:** the app names the files, e.g. `git diff --name-only --diff-filter=AMR origin/main -- 'migrations/*.sql' | xargs -r …` (`-r`, so a PR with no new migration checks nothing rather than the whole folder). The template floor check (F2-1) keeps child processes out of `src/`, and a named-file list keeps the check pure.
- **Known limits (recorded):** statements are split on `;` outside quotes and comments, and dollar-quoted bodies are skipped whole. The rules read statement text, not a parsed schema. So a destructive statement built dynamically inside a function body, or one run through `EXECUTE`, is not seen; an unterminated comment or quote hides the rest of its file (Postgres would refuse that file too). Pre-review r2 (4 low, recorded): a `DELETE`/`UPDATE` inside a CTE body (`WITH d AS (DELETE FROM t RETURNING id) SELECT …`) is not seen; a quoted column named like a keyword (`"rename"`) is refused and needs the contract comment; `NOT NULL DEFAULT NULL` passes; `DROP INDEX`/`DROP TRIGGER` and adding a validated `CHECK`/`UNIQUE` constraint are left to review (the old release keeps working, though a new constraint can refuse its writes; add constraints `NOT VALID` first). Review (SM-06-L1) covers those. The Full tier (SM-06-F1 query counts, SM-06-F2 colliding writes) is not in this add-on.

**Pre-review (2 high, 3 medium, 5 low; all fixed):** (high) a multi-clause `ADD COLUMN` with one `DEFAULT` hid a `NOT NULL` column without one; now each clause is checked. (high) whole-table `UPDATE`/`DELETE` missed quoted schema-qualified names, `ONLY`, aliases, CTEs, `RETURNING`, and a `WHERE` inside a literal or subquery; now matched on the top-level text with literals blanked. (medium) words inside literals caused false refusals; literals are blanked. (medium) renames and drops of materialized views, schemas, sequences, functions and domains were missed. (medium) `xargs` without `-r` checked the whole folder on a PR with no migration. (low) E-string escapes, a padded contract reason, identity/serial columns, absolute paths, and an inline `ADD COLUMN … REFERENCES` without an index.

**Tests:** `sm-06-data.test.mjs` has six tests, covering:
- each refused statement, and its allowed form;
- comments, quoted text and function bodies that only mention a destructive statement;
- the contract comment (too short, or not directly above, is still refused);
- FK index warnings, cleared by an index, `CONCURRENTLY`/`USING` or a unique index;
- the CLI's exit codes, including `--strict`, named files, a missing file and no migrations folder;
- the pool-limit bounds;
- transaction commit, rollback, a failing rollback, nesting refused and reuse.
