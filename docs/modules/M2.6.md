## Goal
Every DevOS-built project is mirrored into Linear as D10 describes, and kept in step: DevOS is the source of truth for structure and agent-owned status; KK's changes to human tasks in Linear flow back.

## Design decisions (technical, runner B, 11 Nov 2026, under KK's standing order)
- **Package:** `packages/linear-sync` (TypeScript, built like `packages/policy`), used by the API (manual "Sync now" route, later) and the worker (scheduled job). No Linear SDK: Linear's GraphQL API is called with Node's `fetch`, one function per operation. Reason: the official SDK pulls a large dependency tree for ~10 operations we need; a hand-written client keeps the D13/SM-14 surface at zero and lets every call carry the ADR-0011 timeout.
- **Transport:** `POST https://api.linear.app/graphql` only (egress allow-list: `api.linear.app`), `Authorization: <key>` header built from the vault at call time, `AbortSignal.timeout(15 s)` on every call. Retries: only for reads and for idempotent upserts keyed by our own markers (below), on network errors, 429 and 5xx, with exponential backoff + jitter, at most 3 attempts; a create is retried only after a read-back shows it did not happen. Linear's rate limit headers (`X-RateLimit-Requests-Remaining`) below 50 pause the sync until the reset time.
- **Idempotency markers:** every Linear object DevOS creates carries a hidden marker so a retry or a crash between "created in Linear" and "id saved in DevOS" never makes a duplicate:
  - a plain-text last line `devos-ref: <kind>/<uuid>` (kind `project`, `milestone`, `module`, `task`). Plain text, not an HTML comment, because Linear stores descriptions as rich text and may drop comments or escape punctuation; the reader tolerates an escaped `/`. Descriptions are compared after normalising escapes, emphasis/code marks and whitespace, so a re-rendered description is not rewritten every sync.
  Before any create, the sync searches the Linear project for the marker; if found, it adopts that id.
- **Where ids live:** `module.linear_issue` and `task.linear_issue` (already in M1.1). The Linear project and milestone ids are stored as `resource` rows with a new `ResourceProvider` value `linear` (kinds `project`, `milestone`; `external_id` = Linear id). A resource row's `name` is the DevOS id it mirrors (the project id or the milestone id), so a lookup never depends on display names. The migration only **adds** the enum value (backward compatible, ADR-0011). Teardown (M2.5) then sees the Linear project like every other provisioned resource.
- **Mapping (DevOS → Linear):**
  - project → Linear project in team **Devos** (`DEVOS_LINEAR_TEAM_KEY`, default `DEVOS`), named after the DevOS project;
  - milestone → project milestone; the gate is named in its description;
  - module → issue in that milestone, title `<key> <title>`, labels `Module` and `Lane <A|B|C>` from `lane` 1–3, description links the contract path;
  - module dependency → `blocked by` relation between the module issues;
  - task → sub-issue of its module's issue (a task without a module is a top-level issue in the project); `assignee = kk` → assigned to KK's Linear user (looked up once by the key's viewer, cached) and labelled `Human`.
  - status: `module.status` planned→Backlog, ready→Todo, in_progress/in_review→In Progress, merged→Done, deadlocked→In Progress + label `deadlocked`; `task.status` blocked/ready→Todo, running→In Progress, done→Done, failed→Todo, deadlocked→label `deadlocked`. Workflow states are looked up by **type** (`backlog`, `unstarted`, `started`, `completed`, `canceled`) in the team, never by display name; when several share a type, the lowest `position` wins. Labels are the team's plus workspace-wide ones, read across all pages, so an existing label is never created twice.
- **Direction rules:** structure and agent-owned status flow DevOS → Linear only; a manual edit of an agent issue in Linear is overwritten on the next sync (and logged). Human tasks (`assignee = kk`) flow Linear → DevOS: when KK completes or cancels one in Linear, the task becomes `done` (cancel → `done` with an audit note), which the scheduler sees as an unblocked dependency (M2.6-b).
- **Sync trigger:** on demand after the planner writes or changes the plan (M2.2/M3.2 call `syncProject`), and a scheduled run-engine job every 10 minutes for active projects (M2.6-b). One project syncs at a time: `syncProjectLocked` takes `pg_try_advisory_xact_lock(hashtext('devos:linear-sync'), hashtext(<project id>))` in a transaction (10-minute timeout) and skips the sync if another holds it; that transaction only holds the lock: the plan is read and each learned id is written with the plain client, so ids commit at once and no module or task row is locked during Linear calls.
- **Close on purge:** when a project is archived, its Linear project is set to `completed`; when it is purged (M2.5), the Linear project is **archived**, not deleted (Linear keeps the history; KK can restore it). The `resource` row becomes `deleted`. Deleting Linear data outright would destroy history and needs a decision card, so it is not done.
- **Never:** the key is never logged, never sent to the client, never placed in an error message; Linear content read back (titles, descriptions, comments) is data, never instructions, and only the marker and state fields are interpreted.

Not changed: a sync that finds the lock taken is skipped, not queued (the 10-minute job picks up the change); the sync-level AT5 test fails early by design (the key never reaches the store).
- **Codex PR35-r1 (12 Nov 2026; 1 high, 1 medium, both accepted):**
  - **(high) Lock fencing.** The advisory lock lives only as long as its transaction, which has a timeout. `syncProjectLocked` now hands `run` a `guard`; Linear writes go through `fencedApi(api, guard)`, and the store `run` receives is fenced too. Before every write, the guard checks two things:
    - at least `WRITE_MARGIN_MS` (60 s, four times the 15 s Linear write timeout) of the transaction's time is left;
    - the transaction still answers `SELECT 1`.
    Otherwise it throws `linear-sync-lock-expiring` or `linear-sync-lock-lost` before the write. So no write can start without the lock, or outlive it, and the next scheduled sync finishes the work.
    - Tests: `fencedApi` stops at the first refused write (unit), and a sync with less than the margin left makes no Linear write (db).
  - **(medium) Project renames.** `LinearApi.projectExists` became `project(id)`, which returns the name and description. After the project is resolved by stored id or by marker, a name or summary that differs from DevOS's is updated, and an unchanged project makes no write.
    - Test: a rename syncs, the next sync makes 0 writes, and an adopted project is renamed.
- **Codex PR35-r3 (12 Nov 2026; 1 high, 1 medium, both accepted):**
  - **(high) Bounded key read.** The guard runs before the write, but the client then read the API key from the vault with no bound, so a stalled vault could start the mutation after the lock expired. The key read now has its own timeout (`keyTimeoutMs`, default 10 s, `LinearError("timeout")`), so one fenced write takes at most key 10 s + call 15 s = 25 s, inside `WRITE_MARGIN_MS` (60 s). Tests: a never-resolving key fails the mutate without sending any request; the defaults fit the margin.
  - **(medium) Milestones paginated.** `milestones()` read one page of 250 without `pageInfo`, so a stored id on a later page looked missing and the sync could create a duplicate. It now follows `pageInfo` to the end (100 per page, at most 50 pages) and refuses a page that claims more without a cursor. Tests: two pages are joined; a cursorless "has next" page is refused.
- **Codex PR35-r4 (12 Nov 2026; 2 medium, both accepted):**
  - **(medium) Bounded store writes.** The guard ran before each id write, but the write itself used the plain client with no timeout, so it could wait on a row lock until after the sync lock expired and then overwrite a later sync's id. Every `PrismaSyncStore` write and the plan read now run in their own transaction with `SET LOCAL statement_timeout` and `lock_timeout` of 10 s, a 15 s transaction timeout and a 5 s wait for a connection. 20 s is well inside the 60 s write margin, so a write that passed the guard ends (commit or rollback) while the lock is still held; `syncProjectLocked` refuses a configuration where it would not. Also meets ADR-0011's timeout rule for these DB calls.
  - **(medium) Searches fail closed.** `findProject` returned null after 50 pages even when Linear said more existed, so a marker beyond the limit looked absent and AT3 could create a duplicate project. It now returns null only after the last page and throws `bad-response` when the page limit runs out or a page claims more without a cursor. The label list in `team()` and the issue list get the same rules (a cut-off label list would create a duplicate label).
  - Tests: 3 API tests (exhausted project search, last-page null and no-cursor refusal, exhausted label list), 1 unit test that every store write and the plan read run bounded, and 1 Postgres test (`test:db`, CI) that an id write blocked by a `FOR UPDATE` row lock gives up within 20 s and never commits.
- **Codex PR35-r5 (12 Nov 2026; 1 medium, accepted):** `issues()` read each issue's `inverseRelations` without paging, so a blocker past the first page looked missing and an unchanged plan would call `addBlockedBy` again (AT2). Nested lists now request `first: 50` with `pageInfo`. An issue with more relations has the rest read through `issue(id).inverseRelations`, every page, failing closed on a missing cursor or the page limit. An issue with more than 50 labels fails the read (`bad-response`) instead of looking unlabelled; DevOS sets two or three labels, so this only stops a sync on a hand-edited outlier. Tests: relations across three pages, and the two fail-closed cases.
- **Codex PR35-r6 (12 Nov 2026; 1 medium, accepted):** the client no longer accepts an endpoint override: any `endpoint` other than `https://api.linear.app/graphql` throws at construction, every call goes to that constant, and `redirect: "manual"` with a refused 3xx (`bad-response`, not retried) keeps the key from ever following a redirect (F2, ADR-0011). Test: three foreign endpoints refused; a 302 makes exactly one call and fails.
- **Codex PR35-r7 (12 Nov 2026; 1 medium, accepted):** `upsert` created missing labels with `Promise.all`, which rejects on the first failure while the other creates are still in flight, so a label write could outlive the per-project lock. Missing labels are now created one at a time, so a failure leaves nothing running when the sync returns. Test: with two missing labels and the second failing, at most one create is ever in flight and none is left after the rejection (fails on the old code).
- **Codex PR35-r8 (12 Nov 2026; 1 medium, accepted):** `fetch` resolves at the headers, so a reset or timeout while reading a 200 body was caught by the JSON parse and became `bad-response`, which is never retried. The body is now read as text first: a failure there keeps the transport class (`timeout` for TimeoutError/AbortError, else `network`, so reads retry it and mutations still do not), and only whole text that is not a JSON object is `bad-response`. Test: a body cut off twice then a good answer succeeds in 3 calls; three body timeouts end as `timeout`; a cut-off mutation is not retried; bad JSON is one call and `bad-response` (fails on the old code).
- **Codex PR35-r10 (12 Nov 2026; 1 medium, accepted):** the lock guard checked the write margin before its `SELECT 1` probe, but not after it, so a slow probe could hand out permission to write with less than `WRITE_MARGIN_MS` of lock time left. The guard now checks the margin again after the probe, right before it returns. Test (`test-db`): a clock that passes the first check and then jumps after the probe fails the sync with `linear-sync-lock-expiring`, with no Linear project created (fails on the old code).
- **M2.6-a2 (DEVOS-132; runner review after PR35-r9, 12 Nov 2026; 2 medium, both accepted):**
  - **Query complexity.** Linear refuses a query over 10,000 complexity points (1 per object, 0.1 per field, children multiplied by `first`). One issue node with labels and relations at 50 each is about 170 points, so 100 issues per page (~17,000) would fail every live sync at the first issue read while stubbed tests stay green. The issues query now reads `ISSUE_PAGE` = 25 per page (~4,250); `ISSUES_QUERY_COST` is computed from the same constants and a test asserts it is at most `LINEAR_MAX_COMPLEXITY`.
  - **Moved issues.** An agent issue moved to another Linear project (or with its project cleared) was missing from the project's issue list and so was created again. A stored id missing from the list is now looked up with `issueRef(id)` (an `issues(filter: { id })` read, archived included, so a deleted issue is `null`, not an error). If it still exists it is moved back with `updateIssue(id, { projectId })` and the list is read again; only a gone issue is re-created. `updateIssue` therefore sends `projectId` when set (never `teamId`). Tests: a moved module issue makes 0 creates and is moved back with its marker restored; `issueRef` maps found, project-less and gone issues; an update sends a set project but never the team.
  - **Pre-review (12 Nov 2026; 1 medium, 3 low).** (medium, fixed) A move Linear refuses (for example the issue now sits in a team the project does not include) used to fail every later sync of the project. Now a refused move (a GraphQL refusal or a 4xx other than 429) is logged in the sync result and that issue is left as it is: neither updated nor created again; the rest of the project syncs. A transient failure still fails the sync, which retries later. Test: a refused move with a cleared project; 0 creates, the log names the issue, another task still updates, and a network error is not swallowed. (low, recorded) Linear keeps deleted issues in the trash, archived, for about 30 days, and `includeArchived` returns them, so a moved-then-deleted issue is found and moved back rather than re-created until the trash empties; the same holds for issues deleted inside the project, so this is not a regression. (low, recorded) `ISSUES_QUERY_COST` is computed from the page constants, not by scoring the query text; a re-score of one node is about 175 points, so 25 per page stays under 10,000 with a wide margin. (low, recorded) sync-level tests for a gone issue and a moved task sub-issue are follow-ups for M2.6-b, which reworks these loops.
  - **Codex PR64-r1 (1 medium, accepted):** a stuck module was kept in the module map but was missing from the issue list, so when it was the dependent side of a dependency the relation loop could not see its existing blocked-by list and added the relation again on every sync. Relations to or from a stuck issue are now skipped entirely. Test: with either side of a dependency stuck, two syncs make no relation or create writes (fails on the r1 code).

## M2.6-b2 split and M2.6-b2a build notes (runner B, 12 Nov 2026, ADR-0013)

1. **Split M2.6-b2 (DEVOS-156)** by the concern rule. Nothing in the repo constructs a Linear client at runtime yet (the on-demand trigger is not wired either), so the scheduler and its wiring are separate concerns:
   - **M2.6-b2a (DEVOS-156, this PR): AT8 in `packages/linear-sync`.** `src/schedule.ts`:
     - `listActiveProjects(db)` is one bounded read. It returns projects whose `stage` is not `archived` or `purged` and whose `archived_at` is null, oldest first.
     - `syncActiveProjects({list, syncOne, log})` syncs them strictly one at a time, in list order. A project that throws is logged and recorded in `failed`; the others still sync. A project whose lock is held is recorded in `skipped`.
     - `lockedSyncOne(db, api, opts)` is the production `syncOne`. It runs `syncProject` under `syncProjectLocked`, with fenced Linear and store writes. So a scheduled sync never overlaps an on-demand or another worker's sync of the same project. Under the lock it reads the project's stage again: a project archived or purged after the sweep listed it is reported as `inactive` and gets no Linear or store write. Each sync's divergence log and inbound completions go to `opts.log`.
     - `startSchedule(tick, {intervalMs = 10 min})` arms the next tick only after the current one finishes, so ticks never overlap. "Every 10 minutes" therefore means 10 minutes after the previous sweep ended. The first tick waits one interval. A failing tick is logged and the schedule continues. `stop()` cancels the next tick and waits for a running one.
   - **M2.6-b2b (follow-up):** runtime wiring (the Linear client from the vault key, started from the worker), AT7 (archive/purge, after M2.5-b), and the dashboard "Open in Linear" links. The AT7 archive/purge write must take the same per-project advisory lock, so a sync that started before the archive cannot overwrite the "completed" state (round-2 pre-review note).
2. **Why a timer chain, not a BullMQ repeatable job:** the sweep is cheap, every project sync already takes its own advisory lock, and two workers running the sweep at once only produce `skipped` results for one of them. A repeatable job would add Redis state for no extra safety. The b2b wiring can move it onto the queue later without changing this API.
3. **Tests:** `test/schedule.test.mjs` (unit: order, one at a time, failure isolation, skip, schedule no-overlap, stop, first-tick delay) and `test-db/schedule.test.mjs` (Postgres: archived, purged and `archived_at` projects are not listed; a held lock is skipped; the free project is synced through `lockedSyncOne` and gets its Linear `resource` row; a project archived between the list read and its sync is `inactive`, with no Linear write).
4. **Pre-review (12 Nov 2026; round 1: 1 high, 1 medium, 3 low, 4 fixed; round 2: PASS, 3 low, 2 addressed):** the test-db lock holder used a bare `pg_advisory_xact_lock` select, whose `void` result the pg adapter cannot read; it now uses the wrapped form already used in `policy` and `approvals` (high). The stage is re-checked under the lock (medium). Sync logs are no longer dropped, and the period wording is exact (low). Not changed: the schedule test uses real timers with a wide margin (a 10 ms interval over a 200 ms window, asserting at least 3 ticks).

## DEVOS-162: internal task kinds are not mirrored (runner B, 12 Nov 2026)

- M2.2-d3b records each analyst model-pass run as a `task` of kind `analysis`. That is bookkeeping, not planned work. `syncProject` now drops every task whose kind is in `INTERNAL_TASK_KINDS` (`["analysis"]`) before it reads or writes anything. Such a task is never created, updated, adopted by marker or given a stored Linear id.
- **Why the filter is in `syncProject`, not the Prisma query:** the `analysis` enum value arrives with M2.2-d3b's migration. Filtering on a string in the sync works before and after that migration, it covers every caller (on demand and the scheduled sweep), and it keeps `loadPlan` a plain read.
- **Tests:** `test/sync.test.mjs`, two "DEVOS-162" tests. (1) A plan with two `analysis` tasks (one failed, one done) produces the same Linear issues as the plan without them. No issue carries their ids, no id is stored, and a second sync writes nothing. (2) An `analysis` task with a stored Linear id, whose issue carries its marker, causes no write at all (no update, move or re-title). Both fail without the filter. `INTERNAL_TASK_KINDS` is frozen. Pre-review: PASS with 3 low findings, all fixed.

## M2.6-b2b split and M2.6-b2b1 decisions (DEVOS-163, runner B, 16 Nov 2026, ADR-0013)

1. **Split (concern rule).** M2.6-b2b holds three reviewable concerns, so it is built as three PRs:
   - **M2.6-b2b1 (DEVOS-163, this PR):** runtime wiring of the M2.6-b2a schedule. `apps/api/src/linear-sync-runtime.ts` builds the Linear client from the vault key (`linear_api_key`, read by name at call time), `graphqlApi`, and `startSchedule(syncActiveProjects({ list: listActiveProjects(db), syncOne: lockedSyncOne(db, api, { teamKey }) }))`. `main.ts` starts it and stops it on SIGTERM/SIGINT, like the other jobs. **Tests:** a wiring test showing the schedule starts and stops with the process, and is off (with a logged code) when switched off, without a vault, or without the module.
   - **M2.6-b2b2 (sub-issue, AT7):** archive marks the Linear project completed; purge archives it and marks its `resource` row deleted (G2 evidence). The write takes the same per-project advisory lock as the sync.
   - **M2.6-b2b3 (sub-issue):** the dashboard "Open in Linear" links.
2. **Off by default (`DEVOS_LINEAR_SYNC=on` turns it on).** Per D10, every active DevOS project is mirrored into the one Devos Linear team, which creates a Linear project, milestones and issues for it. KK's Linear workspace is on the free plan (250 issues), and on 16 Nov it reached that limit. Turning the mirror on therefore spends Linear capacity, which is KK's call (a plan or budget question). So the code ships wired but switched off. Without the switch, the API logs `linear-sync-off` with code `linear-sync-disabled` and makes no Linear call. The switch is a server setting (the Coolify env), never set from the repo.
3. **Team.** `DEVOS_LINEAR_TEAM_KEY` (default `DEVOS`), as in the M2.6 mapping; a value that is not 1–10 letters or digits turns the schedule off (`linear-team-key-invalid`) instead of syncing into a guessed team.
4. **Failure isolation and logs.** Each tick first checks that the vault holds `linear_api_key`. Without it, the tick logs one `linear-sync-skipped` warning with code `linear-key-not-set`, and lists, locks and syncs nothing. The schedule keeps going, and the API never stops for it. A project whose sync throws is logged as `linear-sync-project-failed` with a fixed code and the project id only; the error's message (it may quote Linear) is never logged. The sync's own lines (`SyncResult.log` and `inbound`) are fixed text plus ids and at most 40 characters of a DevOS task title, never Linear or provider error text (`packages/linear-sync/src/sync.ts`). ## M2.6-b2b2 decisions (DEVOS-247, runner B, 17 Nov 2026, ADR-0013)

1. **Shape: Linear rows are teardown resources.** Linear project and milestone ids are already `resource` rows (provider `linear`), so M2.5's own Archive, Restore and Purge reach them; before this PR a purge of a project with Linear rows stopped with `unsupported_resource`. `packages/linear-sync/src/teardown-ops.ts` adds `linearTeardownOps(db, api, projectId, makeError)` (ResourceOps for `linear/project` and `linear/milestone`, typed structurally so the package does not depend on `@devos/provision`) and `linearScanner(api, teamKey, makeError)`. `apps/api/src/linear-sync-runtime.ts` `buildLinearTeardown` builds them; `teardownWiring` appends them to the ops and scanners of every archive, restore and purge (`teardown-runtime.ts`, both the routes and the purge job). **On only when the sync is on** (`DEVOS_LINEAR_SYNC=on`, the same database, vault, module and team key; same off codes). With the sync off, no Linear rows are created, and a project that still has Linear rows from an earlier "on" period stops its purge with `unsupported_resource` before any delete (fail closed, visible on the stop-report card) instead of leaving Linear behind.
2. **What each action does in Linear (AT7).**
   - Archive: the Linear project moves to the workspace's first project status of type `completed` (`projectStatuses`, lowest position, then `projectUpdate { statusId }`).
   - Restore: back to the first status of type `started`. The project's previous Linear status is not stored; `started` matches a project that is being built again.
   - Purge: `projectArchive` (archived in Linear, never deleted or trashed); the purge then marks the row deleted (G2 evidence).
   - A milestone has no Linear write of its own: it is archived with its project. Its `inspect` answers "nothing left to remove", so the purge marks its row deleted without a call.
3. **Ownership and idempotence.** A Linear project is ours only when its marker (`devos-ref: project/<id>`) names this project **and** the row's name is this project id. A Linear project that is already archived, or gone, reads as removed, so a re-run after a crash never writes again.
4. **Same lock as the sync.** Every Linear write takes `pg_advisory_xact_lock(hashtext('devos:linear-sync'), hashtext(projectId))` (wrapped as `SELECT 1 AS locked FROM (…)`, like every other advisory lock here), the key `syncProjectLocked` uses, in its own transaction. Unlike the sync (which skips a held lock), a teardown write waits for it, at most 60 s (`lock_timeout`, which covers advisory locks); the transaction is bounded at 120 s. Only the one write runs inside the lock: the status id is read before it (pre-review r2), and the write is fenced like the sync's (`LockGuard`): it starts only while at least `WRITE_MARGIN_MS` (60 s, longer than a write's key read plus its 15 s timeout; writes are never retried) of the transaction is left and a `SELECT 1` on the lock's transaction succeeds, else it is "busy" and nothing is written. Only a lock timeout (SQLSTATE 55P03) is read as "still held"; any other failure of the lock query is a non-transient error with fixed text (pre-review 1). A lock still held is a retryable `timeout`, so the purge stops as `delete_unconfirmed`/`provider_error` retryable and the next run continues. A sync writes the project's status only in the known-gap-7 case (an active DevOS project whose Linear project is archived; see "DEVOS-97 known gap 7" below), and it skips archived and purged projects under the same lock (AT8), so it cannot undo "completed".
5. **Errors.** Linear failures become `@devos/provision` `ProviderError("linear", …)` (injected as `makeError`, so `@devos/teardown` classifies them) with fixed text only: network/timeout/5xx/429 stay transient (retryable), a GraphQL refusal or bad response is not, a missing key is `no-token`. Linear's own error text never reaches a card, scan report or log. The leftover scanner wraps its errors the same way.
6. **Leftover scan.** The `linear` scanner finds every Linear project in the team carrying the project's marker (`findProjects`: archived included, every page, fail closed) and reports each one that is not archived (pre-review 2: a hand-made duplicate is not hidden behind an archived one). A failed read is a scan error, so the purge is never "clean" without looking.
7. **Known gap (recorded).** If a purge archives the Linear project and then stops on a later provider (the GitHub repo goes last) and KK restores the project, the Linear project stays archived: its row is already marked deleted, so Restore does not see it. The next sync finds it by marker (archived included) and revives the row, but does not unarchive it. Low impact (the mirror is read-only for agents). **Closed by DEVOS-97 (17 Nov 2026):** the sync now unarchives it; see "DEVOS-97 known gap 7" below.
8. **Pre-review (1 medium, 5 low; 2 fixed, 4 recorded).**
   - (medium, fixed) The lock used a new SQL form and read every lock-query error as "busy". Now the wrapped form, only 55P03 is busy, and `test-db/teardown-lock.test.mjs` proves on Postgres that a free lock runs the write, a held lock is waited for, a lock still held after the wait is busy (the write never runs), and a sync is skipped while a teardown write holds the lock. Run locally against Postgres 16 through the `pg` driver (Prisma's engine cannot download here); CI's `linear-sync-db` job runs it through Prisma.
   - (low, fixed) The scanner reported only the first marked project; see decision 6.
   - (low, recorded) `projectArchive` may be marked deprecated in Linear's schema in favour of `projectDelete`, which trashes (a delete). The contract asks for an archive, so `projectArchive` stays. If Linear ever removes it, every purge of a synced project stops with a non-transient `bad-response` on the stop-report card (fail closed, visible); it is never replaced by a delete without a KK decision (data deletion).
   - (low, recorded) The teardown builds its own `LinearClient`, so the rate-limit pause is not shared with the sync's client. Teardowns are rare (one project, a few calls), and both clients honour Linear's 429 and Retry-After; sharing one client is a follow-up line on DEVOS-97.
   - (low, recorded) With the sync on, Archive also needs Linear to answer. A Linear outage or a missing key stops an Archive at the Linear row, after the Coolify stops ran and before the stage changes: the same behaviour as any other provider in M2.5 (retryable on a transient error; Archive can be re-run).
   - (r2, medium, fixed) The status read (retried, with Retry-After sleeps) ran inside the lock, so the 120 s bound could expire and the write run without the lock. Now the read is outside and the write is fenced (decision 4); a unit test shows a write refused, with nothing written, once less than the margin is left.
   - (r2, low, recorded) With the sync on, every purge (even of a project without Linear rows) needs the `linear` scan, so a Linear outage or a missing key keeps a purge at `purged = false` after the deletes, until a later run scans clean. Fail closed, retryable.
   - (r2, low, recorded) Milestone rows can be marked deleted before the project's `projectArchive` is confirmed (same rank, newer rows first). If that archive then fails, the milestone rows are deleted though Linear did not change; the sync revives them by marker. Same family as known gap 7.
   - (low, recorded) No test checks that `buildRuntime` passes `linear:` into the teardown routes and purge job; the AT7 tests call `teardownWiring` directly. Removing the argument fails closed (`unsupported_resource`). A runtime test is a follow-up line on DEVOS-97.
9. **Tests.** `packages/linear-sync/test-db/teardown-lock.test.mjs` (the lock on Postgres, above), `packages/linear-sync/test/teardown-ops.test.mjs` (real ops over a fake Prisma and Linear: lock key and wait, completed/started/archived writes inside the lock, ownership, idempotence, error mapping with no Linear text, the scanner, and the GraphQL shapes) and `apps/api/test/linear-teardown.test.mjs` (off codes; the real `@devos/teardown` Archive, Restore and Purge through `teardownWiring` with the Linear parts: completed, started, archived, both rows deleted, `purged`; without the parts, `unsupported_resource` before any delete).

## DEVOS-97 known gap 7 (runner B, 17 Nov 2026, ADR-0013)

1. **The sync unarchives.** `syncProject` reads the Linear project's `archivedAt` (both `project(id)` and the marker search `findProject` now return it). When the Linear project is archived, it reads the workspace's first `started` project status (`projectStatusId`, the same read the teardown uses), then `projectUnarchive` (one write; never a delete), then `projectUpdate { statusId }` to that status (the state Restore sets), logs one fixed line and goes on with the usual name, summary, milestone and issue sync. The resource row is stored again as before (adopted by marker when the purge marked it deleted).
2. **Why the sync and not Restore.** Restore works from resource rows that are not deleted; after a purge that stopped later, the Linear row is already deleted, so Restore would need a second Linear search path (marker scan, archived included) inside M2.5's flow. The sync already finds the project by marker under the per-project lock, and it runs only for an active project: the stage is read again under the lock (`lockedSyncOne`, AT8), and a teardown write takes the same lock. So an archived Linear project seen by the sync belongs to a project that is active again. One place, no schema change, no change to `@devos/teardown`.
3. **Scope of the rule.** The same happens if someone archives the Linear project by hand while the DevOS project is active: DevOS owns the mirror (as for its name and summary), so it is unarchived and set to started. A Linear project that is not archived never gets a status write from the sync. **A trashed project is restored too (pre-review 1, medium, accepted by amending this decision).** Both project reads include archived projects, and Linear also reports a trashed project (a hand `projectDelete`, or `projectArchive` if Linear ever maps it to the trash; the M2.6-b2b2 decision 8 note) with `archivedAt` set; `projectUnarchive` then takes it out of the trash. This is kept on purpose: before this change the sync already kept writing into such a project (found by stored id or marker, archived included), so restoring it only makes the mirror visible again; it removes nothing, and DevOS owns the mirror of an active project. Telling the two apart (`trashed`) would also leave gap 7 open if the purge's `projectArchive` lands in the trash. Removing the mirror of an active project for good is a KK decision (data deletion), done by archiving the DevOS project, never by deleting in Linear.
4. **Order and failure.** Both writes are fenced by the lock guard (`fencedApi` now lists `unarchiveProject` and `updateProjectStatus`) and never retried. The status id is read before either write, so a missing `started` status fails the project's sync before any write. Writing the status first (so a failed pair retries while the project is still archived) is not used: whether Linear accepts `projectUpdate` on an archived project is not documented, and a refusal would fail that project's sync on every tick (pre-review 4, low, recorded). If the unarchive succeeds and the status write then fails, the project is unarchived but keeps "completed" until a later Archive/Restore; the sync logs the project failure by code and id only (decision 4 of M2.6-b2b1) and the next sync does not retry the status, because the project is no longer archived. Cosmetic only (the mirror is read-only for agents), recorded rather than tracked with stored state.
5. **Tests.** `packages/linear-sync/test/sync.test.mjs`: an archived Linear project of an active project, found by stored id and by marker, is unarchived and moved to started with exactly those two writes, its id is stored again, and a second sync writes nothing; a project that is not archived gets no status write; a refused lock guard writes nothing, and a guard that refuses the second write stops before the status write; with no `started` status the sync fails before any write and the project stays archived. Pre-review: r1 4 findings (1 medium, 3 low): 2 test gaps fixed, 1 medium and 1 low recorded above with reasons; r2 PASS with 1 low (a stale code comment), fixed. `packages/linear-sync/test/teardown-ops.test.mjs`: the GraphQL shapes (`projectUnarchive(id: $id)`, `archivedAt` in both project reads, a refused unarchive fails closed).

## M2.6-b2b3 decisions (DEVOS-248, runner B, 17 Nov 2026, ADR-0013)

1. **Links are read from Linear by the stored ids, not stored.** DevOS stores only Linear ids: the project's `resource` row (provider `linear`, kind `project`, status `active`) and each module's `linear_issue`. Linear's URLs need the workspace key and Linear's own slug id, which DevOS does not keep, so building them from the ids would guess. Storing each `url` would need a schema change and a second write path in the sync for a value Linear can change (a project rename changes its slug). So `GET /projects/by-slug/{slug}/linear-links` reads the stored ids and asks Linear for their `url` fields in at most two read queries (`projects(filter: {id: {eq}})` and `issues(filter: {id: {in}})`, archived included), never a write. `packages/linear-sync/src/links.ts` (`linearLinks`) does the reading; `apps/api/src/linear-links.ts` is the route and its wiring (`buildLinearLinks`).
2. **No link without a stored id.** Only stored ids that are UUIDs are sent (at most 100 issues); a project or module without a stored id gets no entry, and with no stored id at all the route answers without calling Linear.
3. **https on linear.app only, checked three times.** The package keeps only `https://linear.app/...` URLs (no credentials, no port), the route filters again (`linksView`), and the dashboard panel checks once more (`linearHref`) before rendering an `href`. A `javascript:` URL or a look-alike host (`linear.app.evil.example`) is dropped. Every text is rendered by React (escaped); links open with `rel="noreferrer noopener"`.
4. **On only with the sync.** The route answers `{ enabled: false }` and makes no Linear call unless `DEVOS_LINEAR_SYNC=on` with the database, the vault and the module (the same switch and off codes as M2.6-b2b1/b2; an off code other than `linear-sync-disabled` is logged as `linear-links-off`). The key is read from the vault by name at call time.
5. **Failures are fixed codes.** Linear failing, or the read taking longer than 15 s (`LINEAR_LINKS_TIMEOUT_MS`), answers 502 `linear-unreachable`; a store failure answers 503 `linear-links-store-failed`; an unknown slug 404 `project-not-found`. Linear's text never leaves the API. The route sits behind the global session check (`x-devos-access: session` in `openapi.yaml`). The 15 s bound ends the request, not the client's read: a slow read may finish its own retries (15 s per attempt, at most 3 attempts, reads only) in the background (pre-review, low, recorded). The page is KK-only and loaded by hand, so this is a handful of extra reads at most; an abortable per-call budget on `LinearClient` is a follow-up line on DEVOS-97.
6. **Where the links are shown.** The module board is still M1.3's mock source (no project-detail API yet), so the links are a "Linear" panel on the project page, read client-side with KK's session like the other panels: "Open the project in Linear" and "Open <module key> in Linear" per module with a link. When the board reads the API, the module links can move onto the cards without an API change (follow-up line on DEVOS-97).

## DEVOS-97 follow-up: a missing Linear key is `no-token` (runner B, 17 Nov 2026, ADR-0013)
Codex PR185-r1 (low): the client wrapped every failure of the `apiKey` callback as `LinearError("bad-response")`, so a teardown with no Linear key stored reported `bad-response`, not the `no-token` that decision 5 of M2.6-b2b2 promises (the plain-`Error` branch in `toProviderError` was never reached through the real client).
1. **A key-not-set code on the client.** `LinearError` gains the code `no-key`. The client exports `LINEAR_KEY_NOT_SET` (`"linear-key-not-set"`, the message every runtime `apiKey` callback already throws when the vault has no `linear_api_key`); when the callback throws exactly that message the client throws `LinearError("no-key", "Linear API key is not set")`. Any other callback failure stays `bad-response`, and a stalled read stays `timeout`. `no-key` is not transient, so it is never retried, and no request is sent.
2. **Teardown mapping.** `toProviderError` maps `no-key` to `no-token` with fixed text. The sync job is unchanged: `no-key` is not one of its "refused" codes, so it is handled like the old `bad-response` (each sync tick already checks the key first and skips with `linear-key-not-set` before it syncs any project).
3. **Tests.** `test/client.test.mjs`: a callback throwing `LINEAR_KEY_NOT_SET` is `no-key` for a query and a mutation, with no request sent; another vault failure is still `bad-response`. `test/teardown-ops.test.mjs`: through a real `LinearClient` + `graphqlApi`, inspect, archive, unarchive, remove and the leftover scan all reject with `no-token`, nothing is sent, and a vault failing for another reason is `bad-response`.

## DEVOS-97 follow-up: an abortable per-call budget on `LinearClient` (runner B, 17 Nov 2026, ADR-0013)
Closes the M2.6-b2b3 decision 5 note: the links route's 15 s bound ended the answer, not the client's background reads.
1. **`signal` per call.** `query` and `mutate` take an optional third argument `{ signal }` (`LinearCallOptions`). Once the signal aborts, the call stops: no new attempt starts, a backoff wait is cut short, and the request in flight is cancelled (its fetch signal is `AbortSignal.any([signal, timeout])`). The call then fails with `LinearError("timeout", "Linear call budget ended")`, unless the attempt had already failed with a non-transient code (refused, `no-key`, bad response), which is kept. An abort during the vault key read takes effect when that read settles (at most `keyTimeoutMs`), and no request is sent after it. Without a signal nothing changes (the sync job and teardown pass none).
2. **Links.** `linearLinks(client, ids, { signal })` passes the signal to both reads. The route creates an `AbortController` per request, aborts it when `LINEAR_LINKS_TIMEOUT_MS` ends, and also in `finally`, so nothing of a request keeps running after its answer. The answer codes are unchanged (502 `linear-unreachable`).
3. **Tests.** `test/client.test.mjs`: already aborted → no request; aborted during the backoff after a 503 → no second attempt even with a backoff that never ends; aborted in flight → the fetch signal is aborted and the call is not retried; no signal → retries as before. `test/links.test.mjs`: the signal reaches every read. `apps/api/test/linear-links.test.mjs`: on the slow-service case the signal handed to the service is aborted by the bound's timer, before the answer. Pre-review: 4 findings (1 medium, 3 low), all fixed: a read aborted in flight is tested (the mutate case alone proved nothing), the route test checks the timer's abort, a real non-transient error keeps its code, and the key-read wording above.
