## Goal
Every DevOS-built project is mirrored into Linear as D10 describes, and kept in step: DevOS is the source of truth for structure and agent-owned status; KK's changes to human tasks in Linear flow back.

## Design decisions (technical, runner B, 11 Nov 2026, under KK's standing order)
- **Package:** `packages/linear-sync` (TypeScript, built like `packages/policy`), used by the API (manual "Sync now" route, later) and the worker (scheduled job). No Linear SDK: Linear's GraphQL API is called with Node's `fetch`, one function per operation. Reason: the official SDK pulls a large dependency tree for ~10 operations we need; a hand-written client keeps the D13/SM-14 surface at zero and lets every call carry the ADR-0011 timeout.
- **Transport:** `POST https://api.linear.app/graphql` only (egress allow-list: `api.linear.app`), `Authorization: <key>` header built from the vault at call time, `AbortSignal.timeout(15 s)` on every call. Retries: only for reads and for idempotent upserts keyed by our own markers (below), on network errors, 429 and 5xx, with exponential backoff + jitter, at most 3 attempts; a create is retried only after a read-back shows it did not happen. Linear's rate limit headers (`X-RateLimit-Requests-Remaining`) below 50 pause the sync until the reset time.
- **Idempotency markers:** every Linear object DevOS creates carries a hidden marker so a retry or a crash between "created in Linear" and "id saved in DevOS" never makes a duplicate:
  - a plain-text last line `devos-ref: <kind>/<uuid>` (kind `project`, `milestone`, `module`, `task`). Plain text, not an HTML comment, because Linear stores descriptions as rich text and may drop comments or escape punctuation; the reader tolerates an escaped `/`. Descriptions are compared after normalising escapes, emphasis/code marks and whitespace, so a re-rendered description is not rewritten every sync.
  Before any create, the sync searches the Linear project for the marker; if found, it adopts that id.
- **Where ids live:** `module.linear_issue` and `task.linear_issue` (already in M1.1). The Linear project and milestone ids are stored as `resource` rows with a new `ResourceProvider` value `linear` (kinds `project`, `milestone`; `external_id` = Linear id). A resource row's `name` is the DevOS id it mirrors (the project id or the milestone id), so a lookup never depends on display names. The migration only **adds** the enum value (backward compatible, ADR-0011). Teardown (M2.5) then sees the Linear project like every other provisioned resource.
- **Mapping (DevOS → Linear):**
  - project → Linear project in team **Devos** (`DEVOS_LINEAR_TEAM_KEY`, default `DEVOS`), named after the DevOS project;
  - milestone → project milestone; the gate is named in its description;
  - module → issue in that milestone, title `<key> <title>`, labels `Module` and `Lane <A|B|C>` from `lane` 1–3, description links the contract path;
  - module dependency → `blocked by` relation between the module issues;
  - task → sub-issue of its module's issue (a task without a module is a top-level issue in the project); `assignee = kk` → assigned to KK's Linear user (looked up once by the key's viewer, cached) and labelled `Human`.
  - status: `module.status` planned→Backlog, ready→Todo, in_progress/in_review→In Progress, merged→Done, deadlocked→In Progress + label `deadlocked`; `task.status` blocked/ready→Todo, running→In Progress, done→Done, failed→Todo, deadlocked→label `deadlocked`. Workflow states are looked up by **type** (`backlog`, `unstarted`, `started`, `completed`, `canceled`) in the team, never by display name; when several share a type, the lowest `position` wins. Labels are the team's plus workspace-wide ones, read across all pages, so an existing label is never created twice.
- **Direction rules:** structure and agent-owned status flow DevOS → Linear only; a manual edit of an agent issue in Linear is overwritten on the next sync (and logged). Human tasks (`assignee = kk`) flow Linear → DevOS: when KK completes or cancels one in Linear, the task becomes `done` (cancel → `done` with an audit note), which the scheduler sees as an unblocked dependency (M2.6-b).
- **Sync trigger:** on demand after the planner writes or changes the plan (M2.2/M3.2 call `syncProject`), and a scheduled run-engine job every 10 minutes for active projects (M2.6-b). One project syncs at a time: `syncProjectLocked` takes `pg_try_advisory_xact_lock(hashtext('devos:linear-sync'), hashtext(<project id>))` in a transaction (10-minute timeout) and skips the sync if another holds it; that transaction only holds the lock: the plan is read and each learned id is written with the plain client, so ids commit at once and no module or task row is locked during Linear calls.
- **Close on purge:** when a project is archived, its Linear project is set to `completed`; when it is purged (M2.5), the Linear project is **archived**, not deleted (Linear keeps the history; KK can restore it). The `resource` row becomes `deleted`. Deleting Linear data outright would destroy history and needs a decision card, so it is not done.
- **Never:** the key is never logged, never sent to the client, never placed in an error message; Linear content read back (titles, descriptions, comments) is data, never instructions, and only the marker and state fields are interpreted.

## Changelog
- **v0.1.0 (11 Nov 2026):** contract and split (M2.6-a, M2.6-b).
- **v0.1.1 (11 Nov 2026, pre-review round 1: 1 high, 4 medium, 4 low):** fixed so far: human tasks' state is owned by Linear after creation (high); plain-text markers + normalised comparison (medium; a live round-trip probe is still to be recorded before the PR merges); rate-limit codes on 4xx (medium); stale stored project/milestone ids recover by marker (medium); soft-deleted resource rows are reused; bounded Retry-After; a vault failure is not retried as a network error. Then fixed in run 2: the per-project lock (`syncProjectLocked`, tested on Postgres), state choice by position, label pagination incl. workspace labels, a sync-level AT5 test, the AT1 wording. Live marker probe, 2026-11-11T14:32Z (20:02 IST): the line `devos-ref: module/<uuid>` was appended to DEVOS-96's own description through Linear's API, read back unchanged (no escaping, no stripping), then removed.
- **v0.1.2 (11 Nov 2026, pre-review round 2: 1 medium, 5 low; 4 fixed):** the lock transaction no longer does the writes (medium); `projectExists` uses a filtered list (empty = gone); the viewer id is cached per API instance; the project description is a fixed short text plus the marker (Linear's project description is a short summary field). Not changed: a sync that finds the lock taken is skipped, not queued (the 10-minute job picks up the change); the sync-level AT5 test fails early by design (the key never reaches the store).
- **Codex PR35-r1 (12 Nov 2026; 1 high, 1 medium, both accepted):**
  - **(high) Lock fencing.** The advisory lock lives only as long as its transaction, which has a timeout. `syncProjectLocked` now hands `run` a `guard`; Linear writes go through `fencedApi(api, guard)`, and the store `run` receives is fenced too. Before every write, the guard checks two things:
    - at least `WRITE_MARGIN_MS` (60 s, four times the 15 s Linear write timeout) of the transaction's time is left;
    - the transaction still answers `SELECT 1`.
    Otherwise it throws `linear-sync-lock-expiring` or `linear-sync-lock-lost` before the write. So no write can start without the lock, or outlive it, and the next scheduled sync finishes the work.
    - Tests: `fencedApi` stops at the first refused write (unit), and a sync with less than the margin left makes no Linear write (db).
  - **(medium) Project renames.** `LinearApi.projectExists` became `project(id)`, which returns the name and description. After the project is resolved by stored id or by marker, a name or summary that differs from DevOS's is updated, and an unchanged project makes no write.
    - Test: a rename syncs, the next sync makes 0 writes, and an adopted project is renamed.
- **Codex PR35-r3 (12 Nov 2026; 1 high, 1 medium, both accepted):**
  - **(high) Bounded key read.** The guard runs before the write, but the client then read the API key from the vault with no bound, so a stalled vault could start the mutation after the lock expired. The key read now has its own timeout (`keyTimeoutMs`, default 10 s, `LinearError("timeout")`), so one fenced write takes at most key 10 s + call 15 s = 25 s, inside `WRITE_MARGIN_MS` (60 s). Tests: a never-resolving key fails the mutate without sending any request; the defaults fit the margin.
  - **(medium) Milestones paginated.** `milestones()` read one page of 250 without `pageInfo`, so a stored id on a later page looked missing and the sync could create a duplicate. It now follows `pageInfo` to the end (100 per page, at most 50 pages) and refuses a page that claims more without a cursor. Tests: two pages are joined; a cursorless "has next" page is refused.
- **Codex PR35-r4 (12 Nov 2026; 2 medium, both accepted):**
  - **(medium) Bounded store writes.** The guard ran before each id write, but the write itself used the plain client with no timeout, so it could wait on a row lock until after the sync lock expired and then overwrite a later sync's id. Every `PrismaSyncStore` write and the plan read now run in their own transaction with `SET LOCAL statement_timeout` and `lock_timeout` of 10 s, a 15 s transaction timeout and a 5 s wait for a connection. 20 s is well inside the 60 s write margin, so a write that passed the guard ends (commit or rollback) while the lock is still held; `syncProjectLocked` refuses a configuration where it would not. Also meets ADR-0011's timeout rule for these DB calls.
  - **(medium) Searches fail closed.** `findProject` returned null after 50 pages even when Linear said more existed, so a marker beyond the limit looked absent and AT3 could create a duplicate project. It now returns null only after the last page and throws `bad-response` when the page limit runs out or a page claims more without a cursor. The label list in `team()` and the issue list get the same rules (a cut-off label list would create a duplicate label).
  - Tests: 3 API tests (exhausted project search, last-page null and no-cursor refusal, exhausted label list), 1 unit test that every store write and the plan read run bounded, and 1 Postgres test (`test:db`, CI) that an id write blocked by a `FOR UPDATE` row lock gives up within 20 s and never commits.
- **Codex PR35-r5 (12 Nov 2026; 1 medium, accepted):** `issues()` read each issue's `inverseRelations` without paging, so a blocker past the first page looked missing and an unchanged plan would call `addBlockedBy` again (AT2). Nested lists now request `first: 50` with `pageInfo`. An issue with more relations has the rest read through `issue(id).inverseRelations`, every page, failing closed on a missing cursor or the page limit. An issue with more than 50 labels fails the read (`bad-response`) instead of looking unlabelled; DevOS sets two or three labels, so this only stops a sync on a hand-edited outlier. Tests: relations across three pages, and the two fail-closed cases.
- **Codex PR35-r6 (12 Nov 2026; 1 medium, accepted):** the client no longer accepts an endpoint override: any `endpoint` other than `https://api.linear.app/graphql` throws at construction, every call goes to that constant, and `redirect: "manual"` with a refused 3xx (`bad-response`, not retried) keeps the key from ever following a redirect (F2, ADR-0011). Test: three foreign endpoints refused; a 302 makes exactly one call and fails.
- **Codex PR35-r7 (12 Nov 2026; 1 medium, accepted):** `upsert` created missing labels with `Promise.all`, which rejects on the first failure while the other creates are still in flight, so a label write could outlive the per-project lock. Missing labels are now created one at a time, so a failure leaves nothing running when the sync returns. Test: with two missing labels and the second failing, at most one create is ever in flight and none is left after the rejection (fails on the old code).
- **Codex PR35-r8 (12 Nov 2026; 1 medium, accepted):** `fetch` resolves at the headers, so a reset or timeout while reading a 200 body was caught by the JSON parse and became `bad-response`, which is never retried. The body is now read as text first: a failure there keeps the transport class (`timeout` for TimeoutError/AbortError, else `network`, so reads retry it and mutations still do not), and only whole text that is not a JSON object is `bad-response`. Test: a body cut off twice then a good answer succeeds in 3 calls; three body timeouts end as `timeout`; a cut-off mutation is not retried; bad JSON is one call and `bad-response` (fails on the old code).
- **Codex PR35-r10 (12 Nov 2026; 1 medium, accepted):** the lock guard checked the write margin before its `SELECT 1` probe, but not after it, so a slow probe could hand out permission to write with less than `WRITE_MARGIN_MS` of lock time left. The guard now checks the margin again after the probe, right before it returns. Test (`test-db`): a clock that passes the first check and then jumps after the probe fails the sync with `linear-sync-lock-expiring`, with no Linear project created (fails on the old code).
- **M2.6-a2 (DEVOS-132; runner review after PR35-r9, 12 Nov 2026; 2 medium, both accepted):**
  - **Query complexity.** Linear refuses a query over 10,000 complexity points (1 per object, 0.1 per field, children multiplied by `first`). One issue node with labels and relations at 50 each is about 170 points, so 100 issues per page (~17,000) would fail every live sync at the first issue read while stubbed tests stay green. The issues query now reads `ISSUE_PAGE` = 25 per page (~4,250); `ISSUES_QUERY_COST` is computed from the same constants and a test asserts it is at most `LINEAR_MAX_COMPLEXITY`.
  - **Moved issues.** An agent issue moved to another Linear project (or with its project cleared) was missing from the project's issue list and so was created again. A stored id missing from the list is now looked up with `issueRef(id)` (an `issues(filter: { id })` read, archived included, so a deleted issue is `null`, not an error). If it still exists it is moved back with `updateIssue(id, { projectId })` and the list is read again; only a gone issue is re-created. `updateIssue` therefore sends `projectId` when set (never `teamId`). Tests: a moved module issue makes 0 creates and is moved back with its marker restored; `issueRef` maps found, project-less and gone issues; an update sends a set project but never the team.
  - **Pre-review (12 Nov 2026; 1 medium, 3 low).** (medium, fixed) A move Linear refuses (for example the issue now sits in a team the project does not include) used to fail every later sync of the project. Now a refused move (a GraphQL refusal or a 4xx other than 429) is logged in the sync result and that issue is left as it is: neither updated nor created again; the rest of the project syncs. A transient failure still fails the sync, which retries later. Test: a refused move with a cleared project; 0 creates, the log names the issue, another task still updates, and a network error is not swallowed. (low, recorded) Linear keeps deleted issues in the trash, archived, for about 30 days, and `includeArchived` returns them, so a moved-then-deleted issue is found and moved back rather than re-created until the trash empties; the same holds for issues deleted inside the project, so this is not a regression. (low, recorded) `ISSUES_QUERY_COST` is computed from the page constants, not by scoring the query text; a re-score of one node is about 175 points, so 25 per page stays under 10,000 with a wide margin. (low, recorded) sync-level tests for a gone issue and a moved task sub-issue are follow-ups for M2.6-b, which reworks these loops.
  - **Codex PR64-r1 (1 medium, accepted):** a stuck module was kept in the module map but was missing from the issue list, so when it was the dependent side of a dependency the relation loop could not see its existing blocked-by list and added the relation again on every sync. Relations to or from a stuck issue are now skipped entirely. Test: with either side of a dependency stuck, two syncs make no relation or create writes (fails on the r1 code).

## M2.6-b decisions (builder, 12 Nov 2026, ADR-0013)
1. **Split M2.6-b** (concern rule): **M2.6-b1** (DEVOS-155, this PR) is the inbound half of AT6 inside `packages/linear-sync`: `syncProject` reads each human task's Linear state and, when KK completed or cancelled it there and DevOS does not yet have it `done`, calls `SyncStore.completeHumanTask(taskId, how)` and reports it in `SyncResult.inbound`; no Linear write. The Prisma store does one bounded transaction: `updateMany` on the task with `projectId`, `assignee = kk` and `status <> done` as the guard, then an `audit_event` (`actor kk`, `task.completed_in_linear` or `task.canceled_in_linear`, details `{taskId, how}`) only when a row changed, so it is idempotent and an agent task or another project's task is never touched. The fenced store checks the lock guard first, like the id writes. The agent-issue half of AT6 (a hand edit is reverted and logged) was already in M2.6-a and is now tested under AT6. **M2.6-b2** (DEVOS-156, follow-up): archive/purge handling (AT7, after M2.5-b), the 10-minute scheduled job over active projects (AT8) and the dashboard "Open in Linear" links.
2. **Cancel = done.** Per the direction rules, a cancelled human task is `done` for the scheduler; the audit action keeps the difference.
3. **Reopened in Linear.** A human task that KK reopens in Linear after DevOS took it as `done` stays `done` (dependent work may already have started) and nothing is written; every sync logs the divergence so it stays visible. `completeHumanTask` returns whether a row changed, and only a real change is reported in `SyncResult.inbound`.
- **Pre-review (12 Nov 2026; 1 medium, 4 low; all fixed):** the Postgres test now seeds an open agent task and tries another project's store while the human task is still open, so the `assignee` and `projectId` guards are each proven alone (medium); the fencing test shows a failed guard writes nothing; `completeHumanTask` is in the bounded-write count; the reopen case is logged; `inbound` reports only real changes; an end-to-end Postgres test runs `syncProject` with `PrismaSyncStore`. "Within one poll" is shown per sync here; the 10-minute job is M2.6-b2 (AT8).

## M2.6-b2 split and M2.6-b2a build notes (runner B, 12 Nov 2026, ADR-0013)

1. **Split M2.6-b2 (DEVOS-156)** by the concern rule. Nothing in the repo constructs a Linear client at runtime yet (the on-demand trigger is not wired either), so the scheduler and its wiring are separate concerns:
   - **M2.6-b2a (DEVOS-156, this PR): AT8 in `packages/linear-sync`.** `src/schedule.ts`:
     - `listActiveProjects(db)` is one bounded read. It returns projects whose `stage` is not `archived` or `purged` and whose `archived_at` is null, oldest first.
     - `syncActiveProjects({list, syncOne, log})` syncs them strictly one at a time, in list order. A project that throws is logged and recorded in `failed`; the others still sync. A project whose lock is held is recorded in `skipped`.
     - `lockedSyncOne(db, api, opts)` is the production `syncOne`. It runs `syncProject` under `syncProjectLocked`, with fenced Linear and store writes. So a scheduled sync never overlaps an on-demand or another worker's sync of the same project. Under the lock it reads the project's stage again: a project archived or purged after the sweep listed it is reported as `inactive` and gets no Linear or store write. Each sync's divergence log and inbound completions go to `opts.log`.
     - `startSchedule(tick, {intervalMs = 10 min})` arms the next tick only after the current one finishes, so ticks never overlap. "Every 10 minutes" therefore means 10 minutes after the previous sweep ended. The first tick waits one interval. A failing tick is logged and the schedule continues. `stop()` cancels the next tick and waits for a running one.
   - **M2.6-b2b (follow-up):** runtime wiring (the Linear client from the vault key, started from the worker), AT7 (archive/purge, after M2.5-b), and the dashboard "Open in Linear" links.
2. **Why a timer chain, not a BullMQ repeatable job:** the sweep is cheap, every project sync already takes its own advisory lock, and two workers running the sweep at once only produce `skipped` results for one of them. A repeatable job would add Redis state for no extra safety. The b2b wiring can move it onto the queue later without changing this API.
3. **Tests:** `test/schedule.test.mjs` (unit: order, one at a time, failure isolation, skip, schedule no-overlap, stop, first-tick delay) and `test-db/schedule.test.mjs` (Postgres: archived, purged and `archived_at` projects are not listed; a held lock is skipped; the free project is synced through `lockedSyncOne` and gets its Linear `resource` row; a project archived between the list read and its sync is `inactive`, with no Linear write).
4. **Pre-review (12 Nov 2026; 1 high, 1 medium, 3 low; 4 fixed):** the test-db lock holder used a bare `pg_advisory_xact_lock` select, whose `void` result the pg adapter cannot read; it now uses the wrapped form already used in `policy` and `approvals` (high). The stage is re-checked under the lock (medium). Sync logs are no longer dropped, and the period wording is exact (low). Not changed: the schedule test uses real timers with a wide margin (a 10 ms interval over a 200 ms window, asserting at least 3 ticks).
