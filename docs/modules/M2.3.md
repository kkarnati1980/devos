## Goal
"Done when": **approve or reject changes project state; blocked tasks wait** while unrelated work continues.

## Decision cards (`apps/api/src/approvals.ts`)
- A **card** is one `approval` row in the **ACTION / TARGET / REASON** shape: `gate` (requirements, decision, first_launch, destructive_or_spend, purge), `action`, `target`, `reason`, optional `costUsd` and `consequence`, optional `projectId`.
- **Validation (BS-A01):** action and target 1–200 characters, one line; reason 1–2,000; consequence ≤ 2,000; `costUsd` a non-negative decimal with ≤ 6 places; UUIDs for ids; unknown fields refused; secret-shaped text refused with `card-contains-secret` (same detector as M1.6, cards are notified out of the server).
- **`raiseCard(input, { blocks: taskIds[] })`** — creates the card and its `task_blocker` rows, sets each listed task to `blocked`, writes `audit_event` `approval.raised`, all in **one transaction**; then sends one M1.6 notice of kind `approval` (title = ACTION, body = TARGET + REASON, `approvalId` set). A notification failure never undoes the card (the feed shows the failed delivery; no automatic resend, ADR-0011 §9).
- **Dedupe:** a second `raiseCard` for the same `(projectId, gate, action, target)` while a pending card exists returns that card and only adds the new blockers.
- **From policy (ADR-0006):** `cardForDecision(decision, request)` turns an M1.7 decision whose `enforcedOutcome` is `require_approval` into a card (action = request action, target = request resource, reason = decision reason, gate = the matched gate rule's `constraints.gateName` or `decision`) and blocks the requesting task. Any other outcome is refused (`card-not-required`).

## Deciding (KK only)
- **`approve(kkSession, approvalId, scope)`** and **`reject(kkSession, approvalId, comment?)`** need `verifyKkSession(session)` = true and an identity `kk:…`; otherwise `not-kk` (403). Agents and unverified sessions can never decide.
- Only a `pending` card can be decided (`card-not-pending`, 409). The decision is written with `status`, `decided_at` and `decided_by`, plus `audit_event` `approval.approved` / `approval.rejected`, in **one transaction** that locks the card row (`SELECT … FOR UPDATE`), so two concurrent decisions cannot both succeed.
- **Approve** issues exactly one grant through M1.7 `issueGrant` with `approvalId` set: `scopeAction` = card action, `scopeResource` = card target, `projectId` = card project, optional `sha` (40-hex), `expiresAt` (default 24 h, at most 90 days), `maxUses` (default 1, at most 100). The grant lives in the M1.7 store's own transaction, so the order is: issue the grant, then decide the card under its row lock. If `issueGrant` fails, nothing is decided. If the card is no longer pending (a concurrent decision won) or the decision cannot be stored, the grant just issued is revoked at once, so **at most one live grant** exists per card.
- **Purge (gate 5)** additionally needs `confirmationHash` = SHA-256 of the typed confirmation phrase `PURGE <target>`; a mismatch is `purge-confirmation-mismatch` and nothing changes.
- **Reject** stores KK's optional comment as `approval_comment` (author `kk:…`). Rejected cards never issue grants.
- **Comments:** `comment(kkSession, approvalId, body)` on any card; 1–2,000 characters.

## Blocked tasks wait (DV-FR-012)
- A task with any blocker whose card is `pending`, `rejected` or `expired` stays `blocked`; the M1.5 scheduler only claims `ready` tasks, so unrelated tasks keep running.
- When a card is **approved**, each task it blocks becomes `ready` **only if** none of its other blockers is still pending, rejected or expired — in the same transaction as the decision.
- When a card is **rejected**, its tasks stay `blocked` and the project's milestone it gates cannot close.
- **Expiry:** `expireCards(now)` sets pending cards older than their gate's window (default 7 days) to `expired` (audited); a task blocked by an expired card stays blocked. A grant that expires before it is used leaves the work blocked: M1.7 `decide` refuses it with `grant-expired`, and the caller raises a fresh card.

## Gate engine (`apps/api/src/gates.ts`, D10)
- `closeMilestone(milestoneId, approvalId)` closes a milestone only when the approval is `approved`, belongs to the same project, and its gate equals the milestone's `gate_name`; otherwise `gate-evidence-missing` (409). The M1.1 AT18 trigger is the backstop; this check gives the friendly error first.
- Every transition is evaluated through M1.7 `decide` (action `gate.transition`, resource `milestone:<id>`); a deny stops it with the policy reason code.

## Pre-review decisions (runner-b, 11 Nov 2026, M2.3-a)
A separate review agent found 2 high, 4 medium and 3 low issues. All were accepted. Decisions and reasons:
- **Raise vs approve (high).** `raise` now locks the pending twin with `SELECT … FOR UPDATE` after the dedupe advisory lock, before touching any task row (the same card-then-task order `decide` uses). Postgres re-checks `status = 'pending'` after the lock wait, so a twin approved in the meantime is not reused; a fresh card is created. Without this, a new blocker could land on an approved card and its task would stay blocked for ever. Test AT8b (db) races the two calls.
- **No wildcards (high).** Card action and target become the grant scope, which M1.7 matches with `*` wildcards, so `*` is refused in both (`invalid-input`). A grant is always exactly the card KK read (ADR-0006 "scoped").
- **Gate source (medium).** The caller can no longer choose the gate. `cardForDecision` asks an optional `gateForRules(matchedRuleIds)` dependency (wired in M2.3-b), else `decision`. M1.7 `RuleConstraints` has no `gateName` field yet; the M2.3-b wiring maps rule ids to gates and a follow-up adds the field to M1.7. An action named `…purge…` is always gate 5, so its typed confirmation cannot be skipped.
- **Approve limits (medium).** `approve()` validates its options itself (`maxUses` 1–100, whole hours 1 h–90 days, 40-hex SHA), because services call it without a route.
- **Loser grant revoke (medium).** It is retried once (revoke is idempotent, ADR-0011 §9). If both attempts fail, `approval.grant_revoke_failed` is audited and `approvals-store-error` is raised. A failure is never swallowed.
- **AT5 wording (medium).** The approved task becomes `ready` (AT2). The expired grant is what keeps the work gated: `decide` refuses it, and the refused attempt raises a fresh card that blocks the task again. The AT5 text above now says exactly this, and the test asserts it.
- **Card window (low).** One window (default 7 days) applies to every gate for now. Per-gate windows wait until a gate needs a different one.
- **Project scope (low).** A project card may block only tasks of that project (`task-other-project`, 409).
- **Text (low).** Unicode line/paragraph separators, C1 controls and bidi overrides/isolates are refused in card text. Reject and comment bodies get the secret check (F1).
- **Round 2 (3 medium accepted, 4 low → follow-up DEVOS-104):** (1) `raise` locks the task rows in id order (`FOR NO KEY UPDATE`) right after the card, and `decide` uses the same lock mode and order, so a multi-task raise and an approve sharing tasks cannot deadlock (test: "multi-task raise racing an approve", db). (2) A `running` task that raises a card is parked as `blocked` too, so it never returns to `ready` while a blocker is pending (DV-FR-012). (3) The purge rule moved into `parseCard`: any card whose action names a purge is gate 5, however it is raised.

## Codex PR41-r1 (12 Nov 2026; 2 medium, both accepted)
- **The grant is forwarded.** `closeMilestone(identity, milestoneId, approvalId, { approvalGrantId })` passes KK's grant to M1.7 `decide`, so a `gate.transition` rule with `require_approval` can be lifted. M1.7 checks the grant's scope, expiry, uses and revocation, and refuses a grant used by its own issuer. So the caller is the acting agent (for example release), not KK's own session. M2.3-b's route takes the grant id returned by `approve`. A malformed id is `invalid-input`. Test: without the grant the close is refused (403 `approval-required…`); with it the milestone closes.
- **The gate match is atomic.** `GateStore.close` now receives the validated gate and project. Inside the closing transaction, the Prisma store locks the approval row (`FOR SHARE`) and re-checks that its status is approved and that its gate and project match. It also updates the milestone only where `gate_name` and `project_id` still equal the validated values. A concurrent `gate_name` change or a revoked approval then matches no row, and the call fails with `gate-evidence-missing` (409), not `milestone-closed`. Test: the gate or the approval status changes during `decide`, and nothing closes. 67/67 API unit tests pass; the Postgres path runs in CI.

## Codex PR41-r3 (12 Nov 2026; 1 medium, accepted)
- **Finding:** the closing transaction locked the approval `FOR SHARE`. Two concurrent closes could both hold that share lock, and the `milestone_gate_approved` trigger then runs `UPDATE approval …`, which needs a row lock that conflicts with the other share lock. The result was a deadlock (same milestone, or two milestones sharing one approval).
- **Fix (runner B, technical):** the approval is locked `FOR UPDATE` before the milestone update. Every close now takes its locks in one order (approval, then milestone), so concurrent closes queue instead of deadlocking. Nothing else locks a milestone and then an approval.
- **Test:** `test-db/approvals.test.mjs` "PR41-r3". It runs five rounds against Postgres in CI (`api-db`). Each round runs four concurrent closes of one milestone (exactly one closes; the others get `milestone-closed`) and two concurrent closes of different milestones that share the approval (both close). No deadlock error.

## DEVOS-104 low follow-ups (runner-b, 12 Nov 2026)
- **Item 1: a decision with no resource → `card-needs-resource`.** A card's grant is scoped to the card's target, and an M1.7 grant matches only a named resource (`grantProblem` → `grant-scope-resource` when the request has none). A card on a placeholder target such as `none` could therefore never be lifted: approving it would loop the task through fresh cards (pre-review, high), and a real resource named `none` would share its card. So `cardForDecision` refuses a missing or blank resource with its own code, `card-needs-resource`, before any card or task change; the caller re-asks with the resource it acts on. Runner decision (ADR-0013); the alternative (M1.7 grants for resource-less requests) widens grant scope and is not needed by any current caller.
- **Item 2: expiry takes effect at the sweep (documented).** Refusing an over-age card at approve time was tried and dropped: a pending card past the window can still gain a twin decision in `raise` before the sweep, and that task would then wait on a card that can never be approved (pre-review, medium). Expiry is therefore one event, the `expireCards` sweep; until it runs, a pending card can be approved or rejected as usual. M2.3-b runs the sweep on a schedule short enough that the gap is small.
- **Item 3** (route error mapping) moved to M2.3-b (DEVOS-103); `card-needs-resource` gets a fixed route error there. **Item 4** (`gateName` in M1.7 `RuleConstraints`) moved to DEVOS-134.
- Tests (`apps/api/test/approvals.test.mjs`): an empty, blank or missing resource is refused with `card-needs-resource`, no card stored and the task still `ready`; a card past the window but before the sweep can still be approved, and the sweep then finds nothing. api 79/79.


## DEVOS-164: expire named pending cards (runner-b, 13 Nov 2026, ADR-0013)
Asked by runner A for M2.2-d3c2 (DEVOS-165): the analyst must expire the pending cards of a superseded requirements version, and a requirements card it could not link. The age sweep (`expireCards`) cannot name cards. Additive; no route, no schema change.
- **`Approvals.expireCardsById(ids, reason)`** (system only, no route): each named card that is still `pending` becomes `expired` with `decidedBy = "system:expiry"`, one `approval.expired` audit row per card whose details carry `{ gate, approvalId, reason }`. Ids are compared in lower case; approved, rejected, already expired, unknown and non-UUID ids are ignored; duplicates count once. Tasks stay `blocked`, as for age expiry (a task blocked by an expired card stays blocked). Returns the ids this call expired, in id order, so a second call returns `[]` (idempotent).
- **Input (BS-A01):** `ids` must be an array of at most 2,000 strings of at most 64 characters each (raw bound, checked first; else `invalid-input`); at most `EXPIRE_IDS_MAX` = 500 distinct UUIDs per call (else `invalid-input`; the caller batches). `reason` is one line, 1–500 characters after trimming (else `invalid-input`), and must not look like a secret (`card-contains-secret`), since it is stored in the audit row. A refused call changes nothing.
- **`ApprovalStore.expireIds(ids, at, reason)`.** Postgres: one transaction, `SELECT … WHERE id = ANY($ids) AND status = 'pending' ORDER BY id FOR UPDATE`, then one `UPDATE` of the locked ids and one `audit_event` `createMany` for the batch (pre-review: per-row round trips for 500 cards could outrun the 10 s transaction timeout). **Runner decision:** `FOR UPDATE` without `SKIP LOCKED` (unlike the age sweep), so a call waits for a concurrent `decide` on the same card and Postgres re-checks the `pending` condition on the committed row: a card is either decided or expired, never both, and the caller's list is not silently cut short by a lock. Id order matches the sweep and `decide`, so the two cannot deadlock. Memory store: same semantics under its promise lock.
- **Approve racing an expiry:** if the expiry wins, `approve` gets `card-not-pending` and revokes the grant it just issued (existing AT7 path), so no live grant remains.
- **Acceptance tests:**
  - `test/approvals.test.mjs`: a named pending card → expired, one audit row with the reason, task still blocked, approve then refused `card-not-pending`; an approved card, an unknown id and a non-UUID are left alone; an unnamed pending card is untouched; a repeat call expires and audits nothing; boundaries: 500 distinct UUIDs (with duplicates, an upper-case id and a non-UUID on top) and a 500-character reason are accepted; input refusals (non-array, non-string id, blank/multi-line/over-long/non-string reason, a secret-shaped reason, 501 ids) change nothing.
  - `test-db/approvals.test.mjs` (Postgres, api-db): the same on the Prisma store with the audit row's `projectId`; a rejected card is left alone; **deterministic lock tests:** (a) a transaction holds the card's row lock and approves it; the expiry is still waiting after 400 ms, and after the commit it returns `[]` with no `approval.expired` row (wait and re-check); (b) a held lock that changes nothing and rolls back does not cut the expiry short: the card expires (fails under `SKIP LOCKED`); **batch:** 500 named cards (ids in upper case) expire in one call with 500 audit rows; **race smoke:** five rounds of `expireCardsById` against `approve` on one card: exactly one wins, with matching audit rows (expired 1/approved 0 or 0/1), no live grant and the task blocked when the expiry wins, one live grant and the task ready when the approval wins.
