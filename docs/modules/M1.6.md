## Notices (`apps/api/src/notify.ts`)
- A **notice** is `{kind, title, body, reasons[], projectId?, approvalId?}`. Kinds: `test`, `standard_selection` (needs ≥ 1 reason), `approval` (for M2.3), `info`.
- **Validation (BS-A01):** title 1–120 characters, one line; body ≤ 2,000; ≤ 10 reasons of 1–300; no control characters except newlines in body and reasons; UUIDs for the ids; unknown fields refused. A notice whose text looks like it carries a secret (API-key, token, private-key or `password:`-style shapes) is refused with `notice-contains-secret`: notices leave the server.
- **Every caller is validated (PR18-r1):** `Notifier.notify()` runs `parseNotice` itself, so an internal caller cannot store or send an invalid or secret-shaped notice; it throws `NoticeError(code)` (a route answers 400) and nothing is stored or sent.
- **Fan-out:** `Notifier.notify()` stores **one `notification` row per enabled channel** (same `notice_id`), then delivers to MyBrain and email in parallel. The dashboard row is `sent` at once (the feed is the delivery). Each other row ends `sent` or `failed` with `attempts` + 1 and a **fixed error code** (`mybrain-http-<status>`, `mybrain-timeout`, `mybrain-network`, `mybrain-not-configured`, `mybrain-no-target`, `email-recipient-refused`, `email-timeout`, `email-starttls-unavailable`, `email-not-configured`, …). A transport or upstream message is never stored, returned or logged. A failed channel never stops the others. If the notice or any delivery outcome cannot be stored, `notify()` fails with `notifications-store-error` (the route answers 503, never 201), after the other channels have finished (PR18-r1).
- **No automatic retry** (ADR-0011 §9: a webhook POST and an SMTP send are not safe to repeat). A failed row stays visible in the feed; re-sending is a new notice. A retry queue with idempotency keys can come with M2.3 if KK wants it.
- Internal callers (the M1.7 standard-selection notice, M2.3 approval cards, M4.6 reports) call `notify()` directly; only the test card has a route.

## Channels
| Channel | Target (`notification_channel.target`) | Delivery |
|---|---|---|
| dashboard | — | The feed (`GET /notifications`) |
| mybrain | The bell webhook URL: `https:` only, a host name (no IP literal, no `localhost`/`localhost.`/`*.localhost`), no credentials, no fragment | `POST` JSON, signed (below), through `bell.ts` (F2, PR18-r1): the name is resolved, **every** address must be public (no loopback, private, CGNAT/Tailscale, link-local/metadata, ULA, documentation, multicast or IPv4-mapped private), and the connection is **pinned** to the checked address; otherwise `mybrain-blocked-address` / `mybrain-dns` and nothing is sent. No redirect is followed (a 3xx is `mybrain-http-3xx`); one deadline (`DEVOS_OUTBOUND_TIMEOUT_MS`) covers resolve, connect and response, and no request starts after it (PR18-r2); any 2xx = sent; the response is destroyed as soon as its status is read, so its body is never read and nothing stays open |
| email | KK's address (validated; no CR/LF) | SMTP (below) |

A channel without a `notification_channel` row is enabled with no target. **The feed lists the newest 50 notices across every stored channel row** (PR18-r1), so a notice and its failed deliveries stay visible with the dashboard channel off. KK sets `enabled` and `target` on the notifications page; each change is audited (`notification.channel.updated`, channel and field names only) **in the same transaction** as the change.

## MyBrain bell (BS-A23, ADR-0011 §7)
- **Payload (fixed shape):** `{v: 1, source: "devos", id, kind, title, summary, reasons, link, createdAt}`. `summary` is the body cut to 500 characters; `link` is `DEVOS_DASHBOARD_URL/notifications#<id>` (or null). No project id, no secrets, no personal data.
- **Headers:** `x-devos-timestamp: <unix seconds>`, `x-devos-signature: v1=<hex HMAC-SHA256(key, "<timestamp>.<raw body>")>`, `x-devos-notice-id`.
- **Receiver rule (for MyBrain):** recompute the signature over the raw body with a constant-time compare; refuse a timestamp more than 5 minutes from now; de-duplicate on `x-devos-notice-id`. The receiver is MyBrain work (a MyBrain issue), not part of this PR; the tests use a stub receiver that applies exactly this rule.

## Email (`apps/api/src/smtp.ts`)
- A minimal SMTP client on `node:net`/`node:tls`, **no dependency** (nodemailer was evaluated: every release up to 10.1.x carries open high/moderate advisories in `pnpm audit`, which S2 would fail).
- **TLS required:** `DEVOS_SMTP_SECURITY=tls` (implicit TLS, default port 465) or `starttls` (port 587; refused with `email-starttls-unavailable` when the server does not offer it, so nothing is sent in clear). `plain` is allowed **only** to a loopback relay (`127.0.0.1`, `::1`, `localhost`); any other host stops start-up with `config-smtp-plain-not-loopback`. TLS 1.2 minimum, certificate verified.
- `AUTH PLAIN` when `DEVOS_SMTP_USER` is set; a user without the vault password sends nothing (`email-not-configured`).
- One plain-text message: `From: DevOS <DEVOS_SMTP_FROM>`, `To`, `Subject: [DevOS] <title>` (CR/LF removed, RFC 2047 for non-ASCII), `Date`, `Message-ID`, `Auto-Submitted: auto-generated`, base64 UTF-8 body (so no body line can end the DATA section). The body adds the reasons and the dashboard link.
- One deadline (`DEVOS_OUTBOUND_TIMEOUT_MS`) for the whole exchange; the socket is destroyed on every path.

## Secrets (F1; M1.4 amendment)
- **`mybrain_bell_key`** (the HMAC key shared with MyBrain) and **`smtp_password`** are added to the M1.4 vault names, so KK enters them in the setup wizard like every other secret (write-only, last 4 shown). M1.4's wizard is "complete" only when they are set too.
- The notifier reads them with `Vault.reveal` **at send time** and never returns, logs or stores them; `GET /notifications/channels` reports only `configured: true|false` from vault metadata (nothing is decrypted for it).
- Non-secret configuration is environment: `DEVOS_SMTP_HOST`, `DEVOS_SMTP_PORT`, `DEVOS_SMTP_SECURITY`, `DEVOS_SMTP_USER`, `DEVOS_SMTP_FROM`, `DEVOS_DASHBOARD_URL` (an exact origin, for links). A malformed value stops start-up with a `config-*` code, never the value.

## Routes (added to `apps/api/openapi.yaml`; all `session`, deny by default)
| Route | Notes |
|---|---|
| `GET /notifications` | Dashboard feed: newest 50 notices, each with its per-channel deliveries |
| `GET /notifications/channels` | `[{kind, enabled, target, configured}]` |
| `PUT /notifications/channels/{kind}` | `{enabled?, target?}`; 400 with a field code; audited |
| `POST /notifications/test` | Sends the test card to every enabled channel → `{notice, deliveries}` |

Writes pass M1.2's CSRF checks. Without the database the routes answer 503 `notifications-not-configured`; a store error → 503 `notifications-store-error` (no driver message). Every store operation, reads included, runs in a Prisma transaction with `timeout` and `maxWait` = `DEVOS_OUTBOUND_TIMEOUT_MS` (as M1.4).

## Migration (`20261106000200_notifications`, additive, ADR-0011 §10)
`notification` gains nullable `notice_id UUID`, `kind TEXT`, `title TEXT`, `body TEXT`, `reasons JSONB`, `project_id UUID` (FK `project`, restrict); unique (`notice_id`, `channel`); indexes (`channel`, `created_at`) and (`project_id`). Checks, added `NOT VALID` so existing rows never block the migration and enforced for every new or updated row: a notice row has a **non-null** known kind, a 1–120 character title, a non-null body ≤ 2,000 and a non-null array of reasons (explicit `IS NOT NULL`, because a CHECK that evaluates to UNKNOWN passes; PR18-r1); `error` is NULL or a fixed code `^[a-z0-9-]{1,64}$`. The previous release does not write notifications, so it keeps working.
