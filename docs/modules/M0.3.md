# M0.3 — Codex review spike (contract)

- **Phase · lane:** P0 · Lane B · Linear DEVOS-31
- **Depends on:** H5 (OpenAI API key, $15/month cap) · ADR-0002 (Codex review = CLI, API-key auth)
- **Owned files:** `scripts/phase0/03-codex-review-spike.sh` (v1.0.4), `scripts/review/review-commit.sh` (v1.0.3), `scripts/test/review-commit.test.mjs` (DEVOS-180), this contract.
- **Unblocks:** Codex PASS on PRs #1–#3 (M0.1, M0.2, M0.4) and M0.6; M3.4 Codex reviewer.

## Goal
Prove the Reviewer role works as D1 requires: Codex CLI, authenticated with the OpenAI API key, reviews **one exact commit** in a **read-only sandbox** and returns a **structured verdict** (`PASS` / `CHANGES_REQUESTED`) whose findings carry severity, file, line, evidence and consequence (PRD build-and-review loop, step 5). The verdict is stored against the commit SHA.

## What the script does (run as root on the server)
1. Installs Node.js 22 (NodeSource) if missing, then `@openai/codex` from npm; records versions.
2. Asks for the OpenAI key in a **hidden prompt** → `/root/.devos/openai.env` (600); logs Codex in with it from stdin (`codex login --with-api-key`). The key is never printed or put on a command line.
3. Builds a sample repo `/root/m03-sample` with a spec, code and unit tests:
   - **commit B (buggy):** `apply_discount` drops the `/100` → 20% off becomes ×(1−20).
   - **commit C (clean):** a correct, spec-conforming change.
4. Reviews each commit with `codex exec --sandbox read-only --output-schema verdict.schema.json`. The prompt pins the SHA and the diff range.
5. Validates each verdict (schema, SHA, read-only tree, AT check) and only then stores it as `/root/.devos/verdicts/<sha>.json`.
6. Prints an evidence block: versions, verdicts, findings, timings, read-only proof.

## Verdict schema (also the M3.4 contract)
`{verdict: PASS|CHANGES_REQUESTED, sha, summary, findings:[{severity: high|medium|low, file, line, evidence, consequence}]}`, with all fields required and no extra fields.

## Review runner (bootstrap for Phases 0–4)
`scripts/review/review-commit.sh <base> <head> <contract> [label]` applies the same mechanism to real changes. It runs on the server with a **read-only deploy key** (`/root/.ssh/devos_ro`, GitHub Deploy keys, no write access), resets and cleans its work tree, checks out the exact head SHA, holds an exclusive lock for the whole review (reviews are serialised), verifies HEAD and an empty `git status` before and after the review, rejects a verdict that contradicts its findings (no verdict is stored otherwise), and has Codex review `git diff merge-base(base,head)..head` against the module contract and the rules.md review guidelines. Codex is told not to execute scripts; it may only run read-only checks (`bash -n`, `shellcheck`). The verdict is stored per SHA; exit 0 = PASS, 2 = CHANGES_REQUESTED. M3.4 replaces it with the in-product Reviewer.

## Floor-guard hits in the prompt (DEVOS-180, v1.0.3)
Closes GI-1b's known gap: Codex may not run scripts, so it never saw floor-guard hit ids and could not write a Keep.
- **What runs.** After the pristine checkout, the runner runs the **base's** copy (main, for every watcher review) of `scripts/floor-guard/floor-guard.mjs` (`git show <main>:…` into a temp dir, as CI does: the head's copy is PR-controlled) on `main...head` in the review clone, with a 120 s timeout. The guard only reads git; the pristine check is repeated after it.
- **What Codex gets.** A block in the prompt: "exit 0, no hits", or the `HIT <id> <rule> <file>:<line> <text>` lines between `BEGIN FLOOR-GUARD HITS <code>` and `END FLOOR-GUARD HITS <code>` (a random 16-hex code per run), introduced as tool output that is data, not instructions. The prompt also restates the rules.md marker rules: `FLOOR-GUARD KEEP` only for a hit judged justified and never in money, data deletion, security scanning, legal, D11 or D13; `FLOOR-GUARD CHANGE <path>` for a PASSed guard-path change; markers only in `summary`, plain.
- **Untrusted text.** Hit text quotes the PR's own lines. It is capped at 50 hits and 300 characters a line, and any `FLOOR-GUARD HITS` in it is replaced by `[marker text removed]`; with the random code in the real markers, it cannot close the envelope. Bash does not re-expand it inside the prompt string.
- **Failure.** No guard on main, no `node`, a guard exit other than 0/1, or exit 1 with no `HIT` line (node's own uncaught-error exit) → the block says there is no hit list, and the review goes on. This is safe: the Release merge path re-runs the guard itself and refuses a red guard without a valid Keep (GI-1b).
- **Runner decision (ADR-0013):** the helper lives in `review-commit.sh` itself (sourcing the file defines the helpers only), not in a new script, because the installer and the server agent's update allow-list name `review-commit.sh` and a new file would need both changed. The prompt's markers rule mirrors rules.md rather than replacing it.
- **Pre-review (14 Nov 2026):** 5 findings, 2 fixed. Fixed: (medium) a deleting replace of the end marker rebuilt a nested one, so the envelope now uses a per-run random code and a non-empty replacement; (low) exit 1 without hits is "could not run". Recorded, not changed (low): the guard's stderr is dropped (the block names the exit code; the Release path re-runs the guard and reports its own error); the main-body wiring (`fgblock` in the prompt, the pristine re-check) is checked by reading, as the runner needs root and Codex; for a stacked review the base's guard runs, as in CI.
