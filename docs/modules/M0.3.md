# M0.3 — Codex review spike (contract)

- **Phase · lane:** P0 · Lane B · Linear DEVOS-31
- **Depends on:** H5 (OpenAI API key, $15/month cap) · ADR-0002 (Codex review = CLI, API-key auth)
- **Owned files:** `scripts/phase0/03-codex-review-spike.sh` (v1.0.4), `scripts/review/review-commit.sh` (v1.0.2), this contract.
- **Unblocks:** Codex PASS on PRs #1–#3 (M0.1, M0.2, M0.4) and M0.6; M3.4 Codex reviewer.

## Goal
Prove the Reviewer role works as D1 requires: Codex CLI, authenticated with the OpenAI API key, reviews **one exact commit** in a **read-only sandbox** and returns a **structured verdict** (`PASS` / `CHANGES_REQUESTED`) whose findings carry severity, file, line, evidence and consequence (PRD build-and-review loop, step 5). The verdict is stored against the commit SHA.

## What the script does (run as root on the server)
1. Installs Node.js 22 (NodeSource) if missing, then `@openai/codex` from npm; records versions.
2. Asks for the OpenAI key in a **hidden prompt** → `/root/.devos/openai.env` (600); logs Codex in with it from stdin (`codex login --with-api-key`). The key is never printed or put on a command line.
3. Builds a sample repo `/root/m03-sample` with a spec, code and unit tests:
   - **commit B (buggy):** `apply_discount` drops the `/100` → 20% off becomes ×(1−20).
   - **commit C (clean):** a correct, spec-conforming change.
4. Reviews each commit with `codex exec --sandbox read-only --output-schema verdict.schema.json`. The prompt pins the SHA and the diff range.
5. Validates each verdict (schema, SHA, read-only tree, AT check) and only then stores it as `/root/.devos/verdicts/<sha>.json`.
6. Prints an evidence block: versions, verdicts, findings, timings, read-only proof.

## Verdict schema (also the M3.4 contract)
`{verdict: PASS|CHANGES_REQUESTED, sha, summary, findings:[{severity: high|medium|low, file, line, evidence, consequence}]}`, with all fields required and no extra fields.

## Acceptance tests
| # | Test | Pass when |
|---|------|-----------|
| AT1 | Install + auth | `codex --version` printed; `codex login status` logged in; key file 600; key never printed |
| AT2 | Review buggy commit B | `CHANGES_REQUESTED`, ≥ 1 high/medium finding on `discount.py` **at the planted-bug line** (derived from commit B: the `price * (1 - pct)` line) — wording-independent |
| AT3 | Review clean commit C | `PASS`, no high/medium findings |
| AT4 | Structure | both outputs parse as JSON and match the schema: exact keys, enums, non-empty strings, integer line ≥ 0, list of findings; verdict consistent with findings (PASS ⇒ no high/medium; CHANGES_REQUESTED ⇒ ≥ 1 high/medium) |
| AT5 | Read-only | `git status --porcelain` is empty after both reviews and HEAD is unchanged |
| AT6 | Per-SHA storage | `/root/.devos/verdicts/<shaB>.json` and `<shaC>.json` exist, each with its own `sha` |
| AT7 | Cost/time | wall time per review recorded; spend visible in the OpenAI usage page (KK) |

## Review runner (bootstrap for Phases 0–4)
`scripts/review/review-commit.sh <base> <head> <contract> [label]` applies the same mechanism to real changes. It runs on the server with a **read-only deploy key** (`/root/.ssh/devos_ro`, GitHub Deploy keys, no write access), resets and cleans its work tree, checks out the exact head SHA, holds an exclusive lock for the whole review (reviews are serialised), verifies HEAD and an empty `git status` before and after the review, rejects a verdict that contradicts its findings (no verdict is stored otherwise), and has Codex review `git diff merge-base(base,head)..head` against the module contract and the rules.md review guidelines. Codex is told not to execute scripts; it may only run read-only checks (`bash -n`, `shellcheck`). The verdict is stored per SHA; exit 0 = PASS, 2 = CHANGES_REQUESTED. M3.4 replaces it with the in-product Reviewer.

## Fallback
If `--output-schema` is unavailable, ask for JSON in the prompt and validate the last message. If `codex login --with-api-key` is unavailable, use the CLI's documented API-key method and log it as an ADR.

## Done when
AT1–AT7 pass with evidence on DEVOS-31. Then use it to review PRs #1–#3.
