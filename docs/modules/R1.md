## Goal
DevOS runs on its own server as **one Coolify Docker Compose application** built from a PASSed `main` SHA, so G1's server-side evidence can exist: the dashboard is reachable on the tailnet only, caps are saved, a killed run resumes with its reservation reconciled, and the receipt chain verifies.

## Design

### R1-a Images (one multi-target `Dockerfile`)
- Base `node:22-bookworm-slim` (matches `.nvmrc`), pnpm 9.12.0 through corepack, `pnpm install --frozen-lockfile`, `pnpm -r build` in a build stage.
- Targets: `api` (`node apps/api/dist/main.js`), `dashboard` (`node apps/dashboard/server.mjs`), `worker` (`node packages/run-engine/dist/worker-main.js`), `migrate` (`prisma migrate deploy` from `packages/db`).
- `ARG GIT_SHA` → `ENV GIT_SHA`; the API's `/health` reports it. Compose passes `GIT_SHA` (falling back to Coolify's `SOURCE_COMMIT`).
- Runtime stages run as the unprivileged `node` user. No secret is ever a build argument or baked into a layer; `.dockerignore` excludes `.env*`, `.git`, `node_modules`, build output.
- v1 keeps the whole built workspace in each runtime image (simple, deterministic). Slimming with `pnpm deploy` is a follow-up, not a blocker.

### R1-b Compose application (`deploy/compose.yaml`)
| Service | Image / target | Notes |
|---|---|---|
| `postgres` | `postgres:17` | named volume; healthcheck `pg_isready`; no published port |
| `redis` | `redis:7.4` | AOF on; no published port |
| `migrate` | `migrate` | one-shot; `depends_on postgres: service_healthy`; `prisma migrate deploy` (apply-only, M1.1) |
| `api` | `api` | `depends_on migrate: service_completed_successfully`; port published on `${DEVOS_BIND_IP}` only (M1.2 deploy requirement: no proxy, the tailnet peer address reaches whois); tailscaled socket mounted **read-only**; `DEVOS_COOKIE_SECURE=1` and the dashboard's `https://` origin in `DEVOS_ALLOWED_ORIGINS` (M1.3-a) |
| `dashboard` | `dashboard` | port published on `${DEVOS_BIND_IP}` only; `HOST=0.0.0.0` inside the container; cert directory mounted **read-only**, `DEVOS_TLS_CERT_FILE`/`DEVOS_TLS_KEY_FILE` point into it (M1.3-a) |
| `worker` | `worker` | `depends_on migrate`; Redis + Postgres on the compose network only |

- `DEVOS_BIND_IP` is **required** (`${DEVOS_BIND_IP:?}`): on the server it is the tailnet IPv4; compose refuses to start without it, so a port can never fall back to `0.0.0.0` (ADR-0005, F3).
- Configuration is by name only. Every secret (`POSTGRES_PASSWORD`, `DEVOS_SESSION_KEY`, `DEVOS_POLICY_HMAC_KEY`, `DEVOS_VAULT_KEY`, …) comes from Coolify env; `DATABASE_URL` is never interpolated in compose: `deploy/with-db-url.mjs` builds it inside each container from `POSTGRES_PASSWORD` with the password URL-encoded (any character is safe), passes it to the service command and drops the raw password (PR20-r1). It also removes every empty `DEVOS_*` variable first, so an optional setting left unset in Coolify reaches the service as unset, not as `""`, and the services' own defaults apply (e.g. M1.6 SMTP port and security; PR20-r2). Provider keys and caps are entered in the M1.4 wizard (H9), not in env.
- Every service has `restart: unless-stopped`, a memory limit and a healthcheck where the image has one.
- Host paths that differ outside the server (`DEVOS_TAILSCALE_SOCKET_HOST`, `DEVOS_TLS_DIR`) are variables, so CI can boot the same file.

### R1-c Worker entry point (`worker-main.ts`)
- Builds the M1.5 `RunEngine` with `PrismaRunStore`, the M1.7 `PolicyEngine` and a `RunQueue` on `REDIS_URL`, then consumes the queue. Config errors stop start-up with a `config-*` code, never a value (same rule as the API, PR14-r2).
- Adapters: a provider without a configured runtime fails its run **non-retryable** with `provider_unconfigured`; nothing is silently skipped. Wiring the Claude Agent SDK and Codex binaries into the image is M3.x.
- On SIGTERM: stop taking jobs and wait up to 50 s (`DRAIN_TIMEOUT_MS`, under compose's 60 s `stop_grace_period`) for the active job, then close the database. Exit 0 only when the job settled; a drain that times out or fails is logged and exits 1, and the cut-short job resumes from its M1.5 checkpoint (PR20-r1).

### R1-d Server check (`scripts/server/checks/health-sha.sh`, run by the server agent; 0 pass, 1 fail, 3 skipped)
The API's `/health` on the tailnet IP answers 200 and its `sha` equals `DEVOS_SHA` (the deployed code is the PASSed code, D1). Skipped while nothing answers (not deployed yet). Port `API_PORT` from `server-agent.conf` (default 3001). Prints no secret. It runs next to the server agent's `dashboard-tailnet-only.sh`.

### Moved to R2 (DEVOS-80)
Split on 6 Nov 2026 by the runner so R1 stays one reviewable PR: the behavioural G1 checks (`caps-saved`, `run-resume` with a no-spend probe adapter, `receipt-chain`), the daily `tailscale cert` renewal (a server-agent allow-list amendment), and API in-process TLS (due with the first dashboard screen that calls the API; until then the dashboard does not call the API). R2 later moved the cert renewal and API TLS on to DEVOS-81 (R3); R2 adds the label `io.devos.service: worker` to the compose worker so its checks can find it.

## Not in R1
Provider runtimes inside the worker (M3.x) · everything listed under R2 above · public exposure of anything (never) · backups of the DevOS Postgres (M4.x) · Coolify app creation (KK, see below) · image slimming (follow-up).

## KK steps (sent when R1 merges, per the HARD RULE)
1. Issue the dashboard certificate once with `tailscale cert` into `/root/.devos/tls` (readable by uid 1000).
2. Create the Coolify Docker Compose application from `deploy/compose.yaml` on `main`, set the env names listed in `deploy/README.md` (values never in chat).
3. `ROTATE_COOLIFY=1 bash /root/.devos/bin/install-server-agent.sh` to add the app UUID and token.
4. `bash /root/.devos/bin/install-server-agent.sh --deploy-on` to approve first launch (deploy-on-PASS).
5. H9 (DEVOS-36): enter keys and caps in the wizard.
