## Goal
KK's setup wizard (H9) works on the server: the HTTPS dashboard page at `https://<MagicDNS name>:3000/setup` calls the API at `https://<MagicDNS name>:3001` and the browser allows it.

## Why (9 Nov 2026)
`/setup` said "The API address is not configured (DEVOS_API_ORIGIN)": compose never passed it. Passing it is not enough: an HTTPS page cannot call a plain-HTTP API (mixed content). On 9 Nov Coolify also dropped the values of the optional `DEVOS_POLICY_HMAC_KEY`, `DEVOS_VAULT_KEY`, `DEVOS_TLS_CERT_FILE` and `DEVOS_TLS_KEY_FILE`.

## Scope change (9 Nov 2026, runner)
The daily `tailscale cert` renewal (DEVOS-81's first item) needs a server-agent allow-list amendment and is not what blocks H9. It moved to **DEVOS-87 (R3-d)**, so the urgent part ships as one reviewable PR. Today's certificate is valid for 90 days.

## Design

### R3-a API in-process HTTPS
- `loadTls(env, secure)` in `config.ts`, called in `main.ts` right after `loadConfig` (before the database or the vault). Same rules as the dashboard (M1.3-a, DEVOS-84):
  - `DEVOS_COOKIE_SECURE=1`: both `DEVOS_TLS_CERT_FILE` and `DEVOS_TLS_KEY_FILE` must name readable, non-empty files, or start-up stops with **`config-tls-required`**. Never a plain-HTTP fallback.
  - `0`/unset: no files → plain HTTP (tests, local); one of the two → `config-tls-incomplete`; unreadable → `config-tls-unreadable`.
  - Errors carry the code only; a path or file content is never logged (`startupErrorCode`, PR14-r2).
- `createApp({ …, tls })` passes `{ cert, key, minVersion: "TLSv1.2" }` as Nest `httpsOptions`. TLS terminates in the API process, so the TCP peer (the whois identity, M1.2) is unchanged. HSTS is already sent when secure (M1.2).
- The `api` image healthcheck speaks HTTPS whenever `DEVOS_TLS_CERT_FILE` is set. It is a loopback liveness probe: it skips name verification (the certificate names the MagicDNS host, not `127.0.0.1`), sends nothing and reads only the status code. Every real client and the server checks verify the certificate.

### R3-b Compose
- The api mounts the same read-only `/certs` bind (`${DEVOS_TLS_DIR:-/root/.devos/tls}`, never created) as the dashboard and gets `DEVOS_TLS_CERT_FILE` / `DEVOS_TLS_KEY_FILE`.
- The dashboard gets `DEVOS_API_ORIGIN` (on the server `https://<MagicDNS name>:3001`). It only widens CSP `connect-src` to that exact origin (M1.4); the wizard pages read it per request.
- **Required (`${NAME:?NAME is required}`)**, so Coolify keeps them and a dropped or blank value stops the deploy with a plain message: `DEVOS_POLICY_HMAC_KEY` (api, worker), `DEVOS_VAULT_KEY` (api), `DEVOS_TLS_CERT_FILE`, `DEVOS_TLS_KEY_FILE` (api, dashboard), `DEVOS_API_ORIGIN` (dashboard). `DEVOS_VAULT_KEY_VERSION` and the SMTP settings stay optional.

### R3-c Server checks
- `health-sha.sh` v1.1.0 calls `https://<MagicDNS name>:<API_PORT>/health` with `--resolve <name>:<port>:<tailnet IP>` (the probe never leaves the tailnet) and curl's default certificate verification (never `-k`). The name comes from `tailscale status --json` (`.Self.DNSName`), as in `dashboard-tailnet-only.sh` v1.1.0.
- Exit 3 (skipped, not deployed) **only** on connection refused (curl exit 7). Plain HTTP, a bad certificate (35, 60…) or a timeout (28) fails (1). No MagicDNS name fails.
- The R2 checks run inside the worker container and do not call the API; unchanged.

### R3-d Cert renewal (DEVOS-87, 10 Nov 2026)
- **Linear:** DEVOS-87 (split from DEVOS-81 on 9 Nov 2026) · P1 · High · Lane A · not a G1 blocker (the current certificate is valid for 90 days).
- `scripts/server/cert-renew.sh` is added to the server agent's **allow-list** (server-agent v1.3.0), so it is installed only from a `main` SHA that passed D1. It takes no argument and runs nothing taken from GitHub content.
- **When:** at the start of a tick (before anything that needs GitHub), once every 24 hours; after a failure, again after 1 hour. Never while a deployment is in flight (it restarts containers). The result is kept in `/root/.devos/agent/cert-renew.state`; the redacted output goes to the agent log.
- **What:**
  1. `tailscale cert --cert-file … --key-file … <MagicDNS name>` (name from `tailscale status --json`, `.Self.DNSName`) into a mode-700 temp dir inside the TLS dir (same filesystem, so the rename is atomic). Timeout 120 s.
  2. The new pair must be non-empty, parse, be valid now (not expired, `openssl x509 -checkend 0`, and notBefore not in the future, Codex PR28-r1), name the MagicDNS host (`-checkhost`), and the key must match the certificate (same public key). Otherwise nothing changes.
  3. Same bytes as the current files → nothing else (tailscale reuses a certificate until it is near expiry).
  4. Changed → each file takes the old file's owner and mode (the containers run as uid 1000; tailscale writes the key 600), the old pair is backed up, both are renamed into place (restored if a rename fails), then the **running** api and dashboard containers are restarted with `docker restart`, found by the new compose labels `io.devos.service: api` / `dashboard` (Coolify renames containers). Both load the files at start-up only.
  5. A failed restart, or no running api or dashboard container, is a failure and leaves `agent/cert-restart-pending`, so the next run restarts even though the files are then unchanged.
- **Files:** the TLS dir is `DEVOS_TLS_DIR` (default `/root/.devos/tls`; `TLS_DIR=` in `/root/.devos/server-agent.conf` overrides it). File names: `TLS_CERT_NAME=` / `TLS_KEY_NAME=` in that file, else the single non-empty `*.crt` and `*.key` already in the dir; more than one fails with a message naming the setting.
- **Exit:** 0 renewed or unchanged, 1 failed, 3 skipped (no `tailscale`, or no TLS dir yet: the first certificate is still issued by hand, deploy README).
- **Bootstrap:** the merge that adds the script is installed by the older agent, whose allow-list does not have it. Agent v1.3.0 therefore installs again from the recorded `installed.sha` (only when its `installed.<sha>` marker exists, i.e. it passed D1) when an allow-listed file is missing from `bin/`.
- **Limits:** the labels reach the containers with the first deploy of this SHA; until then a renewal that changes the files fails at the restart step and retries hourly. No key material and no secret is printed.
- **Applies:** ADR-0011 §9 (timeouts on every outbound call: `tailscale` 10/120 s, `docker` 20/120 s, the whole script 300 s), F1 (nothing secret printed), the server-agent safety rules (allow-listed actions only).
