## Goal
"Done when": **create → purge → scan finds 0.** KK removes a project from the dashboard in two steps. **Archive** stops it and keeps everything for 30 days. **Purge**, only after KK confirms, deletes everything DevOS created for it. A leftover scan then searches every provider for anything still carrying the project's marker or name and must find nothing.

## The two steps
| Step | Who starts it | What happens | Reversible |
|------|---------------|--------------|------------|
| **Archive** | KK (dashboard "Remove project" → Archive, CSRF) or the M4.x lifecycle | 1. Cancel queued runs and stop running ones (M1.5 cancel). 2. Final backup of the live database, if the stack has one (Coolify backup trigger), recorded as a `resource` `backup_schedule/final`. 3. Stop every Coolify application of the project (preview and live). 4. Archive the GitHub repo (`PATCH /repos/{owner}/{repo}` `archived:true`): read-only, nothing deleted. 5. `project.stage = archived`, `archived_at = now`, `purge_after = now + archive window` (setting, default 30 days). | Yes: **Restore** un-archives the repo and moves the stage back to its previous value (stacks stay stopped; the next deploy starts them) |
| **Purge** | Only a KK decision on a purge card (M2.3) | For every active `resource` of the project, in reverse creation order: delete it at the provider (Coolify applications with their volumes → environments → project; backup records and stored dumps; the GitHub repo last), then mark the row `status=deleted`, `deleted_at=now`. Then delete the project's vault app secrets (DEVOS-131). Reset the project's `provision_step` rows. Run the leftover scan. `stage = purged` only when the scan finds 0. | **No** |

## Decisions (builder, recorded per ADR-0013)
1. **Purge is never automatic.** When `purge_after` passes, a scheduled job (daily, 03:10 IST) raises one decision card per project: "Purge project <name>? This deletes its code, stacks, data and backups for good." Options: *Purge now* / *Keep archived another 30 days* / *Restore*. No answer = nothing happens; the card is re-raised once after 7 days. Deleting data is KK's call (rules.md), so the code path to delete is reachable only through an approved card, and the policy action `teardown.purge` is `require_approval` by default.
2. **KK can purge early.** Archive → Purge in the same day is allowed, but only through the same card (no direct delete button). The card names what will be deleted (counts per provider from the inventory) so the decision is informed.
3. **Ownership is checked before every delete.** A resource is deleted only if it still carries the `devos:<project id>` marker at the provider (M2.4 decision 3) **and** the GitHub repo is private. A resource that lost its marker is not deleted; the purge stops with `ownership_mismatch` (non-retryable) and a card asks KK. DevOS never deletes something it cannot prove it owns.
4. **Delete is idempotent; 404 = already gone.** A delete that returns 404/410 counts as done. A delete that times out or returns 5xx is followed by a lookup: gone → done; still there → `delete_unconfirmed` (retryable; the next purge run retries the delete, which is safe because a delete of an absent resource is a no-op). Every call has a timeout (GitHub 15 s, Coolify 30 s), reusing M2.4's transport.
5. **Crash safety.** The purge walks the inventory, not a separate journal: a row is marked `deleted` only after the provider confirms, so a crash at any point leaves the remaining rows `active` and a re-run continues. One teardown job per project at a time, under the same session advisory lock key as provisioning (`hashtext('devos:provision'), hashtext(<project id>)`), so provisioning and teardown of one project can never interleave.
6. **The leftover scan is independent of the inventory.** It does not trust `resource` rows. It searches: GitHub repos of the owner named `devos-<slug>` or whose description carries the marker; Coolify projects, applications and their volumes whose name or description carries the marker or `devos-<slug>`; vault rows with this `project_id`; backup records and stored dumps under `<slug>/`; active `resource` rows; and the project's port allocation. Each hit is listed with provider, kind, id and name. The report is stored (`audit_event` `teardown.scan`, JSON) and shown on the project page. **0 hits → `purged`.** Any hit → stage stays `archived`, the report lists the hits, and a card tells KK in plain words what is left.
7. **Secrets.** Vault app secrets are deleted (row removed, not soft-deleted: a sealed secret of a purged project has no restore value). No secret value is ever read during teardown; deletes are by name.
8. **The project row is kept**, stage `purged`, with its cost history and audit trail (KK's spend reports stay correct). Requirements, specs and run logs stay; they hold no secrets and are small. Removing them is out of scope.
9. **GitHub token permission.** Archiving needs "Administration: read and write" on the fine-grained token; deleting a repo needs the same. If the token lacks it, the step fails `provider_forbidden` with a plain message, and a card asks KK to add the permission (step-by-step, setup wizard). This is checked once by the live probe (AT10) before G2.
10. **Size split** (rules: > ~800 lines or more than one concern → task sub-issues, one PR each, in order):
    - **M2.5-a** `packages/teardown` core: provider delete/stop/archive ops (`teardown-ops.ts`), ownership check, Archive + Restore + Purge runners over the inventory, `provision_step` reset, the leftover scanner and its report. Fake providers + Postgres tests (AT1–AT8). Needs M2.4-a; the Coolify half needs M2.4-c's client.
    - **M2.5-b** wiring: `POST /projects/{id}/archive`, `POST /projects/{id}/restore` (CSRF), the purge card through M2.3 and the run-engine purge job, the daily purge-due job, `GET /projects/{id}/teardown` (state + last scan report), the dashboard panel (AT9). Needs M2.3-b and M2.4-d.
    - **Live probe** (AT10) after both merge and M2.4's AT13 probe has run: it purges `devos-probe-m24`.

## M2.5-a split (builder decision, 12 Nov 2026, ADR-0013)
M2.5-a as planned covers four concerns (provider ops, runners, Postgres store, Coolify app/volume teardown that needs M2.4-c). Per the size rule it is built in three PRs, in order:
- **M2.5-a1 (DEVOS-111, this PR):** `packages/provision/src/teardown-ops.ts` (GitHub repo inspect/archive/unarchive/delete, Coolify project inspect/delete, GitHub and Coolify leftover scanners; M2.4's existing functions untouched), `packages/teardown` (Archive, Restore, Purge, `scanLeftovers`, inventory scanner, `TeardownStore` interface, `MemoryTeardownStore` over M2.4's `MemoryStore`). Tests on fake providers: AT1, AT2, AT3 (policy half), AT4, AT5, AT6, AT7, AT8.
- **M2.5-a2:** `PrismaTeardownStore` under the provisioning advisory lock, a backward-compatible migration for `project.previous_stage` (ADR-0011 §10), `teardown.scan` audit rows, the inventory upsert reviving a slug after purge (a deleted row must not block a fresh create, AT7 on Postgres), vault/backup/port scanners, `.github/workflows/teardown-db.yml` with AT1, AT4 and AT7 on Postgres.
- **M2.5-a3 (DEVOS-118):** Coolify environments and host ports, the two kinds M2.4-c1 (DEVOS-109) provisions. Without ops for them, every purge of a provisioned project stops with `unsupported_resource`.
- **M2.5-a3b (follow-up, after M2.4-c2 / DEVOS-120):** Coolify applications and volumes (stop on Archive, delete on Purge, scan) and the final backup on Archive. Split out because applications and volumes are not provisioned until M2.4-c2 (see "M2.5-a3 build notes").

Decisions made in a1:
- **Order:** Coolify → vault → backups → R2 → Cloudflare → GitHub repo last; newest first within a provider. Project vault secrets (not inventory rows) go after all of these (DEVOS-131).
- **No half purges on unknown kinds:** before any delete, every active row must have ops; otherwise `unsupported_resource` and zero deletes.
- **Ownership on Archive and Restore too:** a resource that lost the marker is not archived or un-archived (`ownership_mismatch`).
- **A failed scanner is never "clean":** its error is in the report and the stage stays `archived`.
- **The GitHub scan is bounded** (20 pages × 100 repos); a full last page adds a `scan-incomplete` hit rather than reporting 0.
- **401/403 on any write → `provider_forbidden`** (decision 9), non-retryable; its message names the stage and the status (`<stage> of <resource> was refused by <provider> (http <nnn>): the token lacks the permission`, added by M2.4 "AT13 fix and diagnostics, part 12", 24 Nov 2026); other non-transient HTTP errors → `provider_error`, non-retryable; transient lookup failures → `provider_error`, retryable.
- **One policy check per purge.** `teardown.purge` is checked once, before any provider call; KK's approved purge card covers the whole purge of that project (one decision, one grant). Archive and Restore likewise check `teardown.archive` / `teardown.restore` once.
- **The step journal is reset before the first delete** (pre-review finding 1), so a purge that stops half way and is then Restored never leaves a stale `done` step; the next provision re-creates what was deleted.
- **Archive and Restore prove ownership of every resource before their first write** (pre-review finding 3).
- **GitHub token scope (pre-review finding 2).** GitHub answers 404 for a private repo the token cannot see, so a narrowed token could make a repo look gone. The token must cover all repositories of the owner; the AT10 live probe checks this (it lists the owner's repos and requires `devos-probe-m24` to be visible before the purge), and M2.5-a2 adds the same check to the purge preflight.

## Codex PR48-r1 (12 Nov 2026; 1 high, 1 medium, both accepted)
- **(high) The scan must be complete.** `purgeProject` now refuses with `scan_incomplete` (non-retryable) before any provider call unless its scanners include `inventory` plus one scanner named after every provider that has teardown ops or inventory rows. An empty or partial scanner list can therefore never lead to `purged`. Scanners are wired in code (M2.5-b), never from input.
- **(medium) Only a 404 proves absence.** GitHub and Coolify `inspect` treat only a 404 as gone. A 200 must carry the repo or project object; a 204, an empty 200, JSON `null` or the wrong shape is an inconclusive `bad-response`. The purge then stops with `provider_error`, and the row stays active.
- Tests: the scanner check is refused with 0 calls for three incomplete lists; four inconclusive lookup shapes each leave the repo and its row in place. Result: 13/13.

## Codex PR48-r4 (12 Nov 2026; 1 medium, accepted)
- **The GitHub scan validates every field it matches on.** Each entry needs a string `full_name` and a string `name`, and that name must equal the repo part of `full_name`; `description` must be a string or null. Anything else makes the scan inconclusive (`bad-response`). The report then has an error, and the stage stays `archived`. The Coolify scan checks `description` the same way.
- Test: four malformed shapes (no name, a name that does not match `full_name`, a non-string description, a Coolify object description). None of them can produce a clean scan. Result: 14/14.

## Codex PR48-r5 (12 Nov 2026; 1 medium, accepted)
- **`description` must be present.** It has to be a string or an explicit null. An entry that omits it is inconclusive in both the GitHub and the Coolify scan, because only the marker in the description could identify a leftover with another name. Test: an omitted description is refused for both providers. Result: 14/14.

## Codex PR55-r1 (12 Nov 2026; 1 high, accepted)
- **The preflight checks the account as well as the scope.** `githubTokenScopeCheck(gh, { owner })` now requires the token's `GET /user` login to equal the repository owner, case-insensitive, on the same pinned snapshot. `owner` is required and validated.

## DEVOS-131 build notes (12 Nov 2026, runner B, ADR-0013)
**Vault secrets in the purge.**
- Vault app secrets are not inventory rows, so before this nothing deleted them and `vault` was not a required scanner. Now:

- **One pinned GitHub token per purge** (the issue's second bullet) was already delivered in the M2.5-a2 pre-review (`pinnedGitHub`, "One token snapshot per purge" above). M2.5-b must build the purge's GitHub ops, scanner and preflight from that one client. Nothing more is needed here.

## DEVOS-175 build notes (14 Nov 2026, runner B, ADR-0013)
- **What:** S4-a2a (DEVOS-173) added `isolation_stack` (project FK, restrict) with a stack index, subnet and network that are unique across all stacks. A purge kept those rows, so a purged project would hold its index for ever and a later project given that index would be refused (`isolation-index-taken`).
- **Fix:** `PrismaTeardownStore.markPurged` deletes the project's `isolation_stack` rows in the same transaction that sets the stage to `purged` and writes the `teardown.purged` audit event; the event's details carry `{ isolationStacksDeleted: <n> }`. Only that project's rows are deleted.
- **Runner decision (technical): delete at the purge's last step, not during the provider deletes.** `markPurged` runs only when the leftover scan found 0, after the Coolify environments (and their Docker networks) are gone, so the rows describe nothing that still exists, and a purge stopped by a leftover keeps them, which keeps the index reserved while the stack may still be live. Archive keeps the rows, because a restore brings the same stacks back. The memory store has no isolation rows, so it is unchanged. Hard delete, not soft: the rows are derived bookkeeping (index → subnet → network), the purge is KK's confirmed decision (gate 5), and a kept row would block the index, which is the bug.
- **Test:** `test-db/teardown.test.mjs` "DEVOS-175 on Postgres": a project with preview and live stacks and a second project with one stack. A card is acted on only if the project is `archived` and the card was raised at or after the current `archived_at`: a Restore after the approval, or a Restore then a new Archive, never purges on the old card (`teardown-purge-skipped`, pre-review 1). ## DEVOS-236 decisions: a server-side scan for orphaned application volumes (21 Nov 2026, runner B, ADR-0013)
Follow-up from the M2.5-a3b pre-review (finding 4, low). A purge deletes each Coolify application with `delete_volumes=true` and waits until Coolify answers 404, but Coolify's API cannot list the volumes of an application that is gone. If Coolify's delete job stops after the application record and before its volumes, decision 6's scan cannot see them. This check is the host-side backstop.
1. **Two read-only halves.** `apps/api/src/teardown-volumes-cli.ts` (`purged-apps`), run in the API container like the AT13 probe CLI, prints one JSON line: the `external_id`s of `resource` rows with `provider=coolify`, `kind=application`, `status=deleted` (what a purge recorded as deleted), sorted and without duplicates. `scripts/server/checks/teardown-orphan-volumes.sh`, a server check the agent installs from `scripts/server/checks/`, runs it, lists the host's volumes with `docker volume ls -q` and reads their labels as JSON with one `docker volume inspect` (pre-review 1–2: labels split from text could be faked by a comma in a value or hidden by a newline). Neither writes anything: the CLI only calls `findMany` in a transaction with a 10 s timeout, and the check never runs `docker volume rm` or `prune` (tested). Deleting a leftover stays a purge decision.
2. **What counts as a hit.** A volume whose name is a purged uuid or starts with one followed by `-` or `_` (Coolify names an application's volumes after its uuid), or one with a label whose value is exactly a purged uuid (e.g. `com.docker.compose.project=<uuid>`). A uuid inside a longer word, or as a prefix of a longer id, is not a hit (tested), so a live application's volume is not reported. **Live applications (Codex PR209-r12).** Coolify uuids may contain `-`, so a purged `app12345` would also name a live `app12345-prod_data`. The CLI therefore also prints `live`: the uuids of Coolify application rows that are not deleted (same shape check; a malformed live id is left out, since it can only make the check report more; a uuid both deleted and live counts as live). A missing or malformed `live` list is unreadable. The rule is: a label value that is exactly a purged uuid is a hit; otherwise a label value that is a live uuid keeps the volume off the list; otherwise a name match counts only for the longest purged uuid it names, and not when a longer live uuid names it too. Coolify applications DevOS did not create are not in either list; their uuids are Coolify's own (no dash), so they cannot extend a purged uuid with a `-` or `_` boundary. Tested in both halves. Both lists come from one REPEATABLE READ transaction, one snapshot, so a purge that marks a row deleted between the two reads can never leave it out of both (Codex PR209-r13; the same isolation `card-batch-view.ts` uses).
3. **Never clean by default.** The check fails (exit 1) on any hit, listing up to 15 volume names with their uuid; on an unreadable or malformed list; on a failed or timed-out read; on a failed `docker volume ls`; and when any deleted row has an id it cannot match safely (uuids must be 8–64 letters, digits or dashes; the CLI counts the others as `invalid` and never prints them). More than 2000 deleted application rows fail with `teardown-volumes-too-many-rows` rather than being cut silently. It also fails on a failed or timed-out `docker ps`, on a uuid list whose elements are not all strings of the uuid shape (anchored with `\A`/`\z`, so a trailing newline fails, Codex PR209-r3), and on `docker volume inspect` output that does not describe exactly the listed volumes, each with a `Labels` field (an object of strings, or null) (Codex PR209-r1). It skips (exit 3) only when DevOS is not deployed: no `docker` on the host (as every server check reports a host before its first deploy), or a successful `docker ps` that finds no running API container. Once the API container runs, a CLI that reports no database (its exit 3) is a failure, and so is empty `docker volume inspect` output for listed volumes (Codex PR209-r2). A missing database password is not a skip: `deploy/with-db-url.mjs` exits 1 first, so it fails closed, as `provision-probe.sh` does (pre-review 3). Output is fixed lines plus names reduced to `A-Za-z0-9._:/=,+-`, 120 characters; a database error is a fixed code, and the check prints only the CLI's own codes (`usage`, `teardown-volumes-read-failed`, `teardown-volumes-too-many-rows`, `teardown-volumes-error`): any other error text from the container shows as `unrecognised error`, never copied (Codex PR209-r5). The uuid and volume lists reach jq through temp files, never as arguments, so 2000 rows of 64-character uuids stay under Linux's per-argument limit (Codex PR209-r4). A successful read must print exactly one non-empty line, the JSON result; a second result or any other line fails as unreadable (Codex PR209-r6). That line, and the whole `docker volume inspect` output, must each be exactly one JSON value; two values (even on one line) fail as unreadable (Codex PR209-r7). Both outputs are captured to files and refused when they hold a NUL byte, which a command substitution would drop silently (Codex PR209-r8). In `docker ps` output, blank lines are ignored and every other line must be a container id, so a blank first line never turns a listed API container into a skip (Codex PR209-r9). The `docker ps` output is captured to a file as well and refused when it holds a NUL byte, so a NUL can never become a blank line and a skip (Codex PR209-r10). Every read of a captured file is checked: a failed `cat` or a failed NUL scan (`tr`, under pipefail) fails as unreadable, so a read error never looks like an empty container or volume list (Codex PR209-r11).
4. **Why not inside the purge.** The API container has no Docker socket (F3), and the purge's scan must stay provider-API-only and independent of the host. The server agent already runs every check on each SHA and every 6 hours, so a leftover volume turns `server-check` red within hours of a purge. It scans this host only, which is right while Coolify deploys project stacks to the server it runs on (`DEVOS_COOLIFY_SERVER_UUID` is this host's server, M2.4-d4b); a remote Coolify server would need its own scan (pre-review 6).
6. **A hit is cleared by KK (pre-review 5).** The application's row is already `deleted`, so no purge reaches the volume again. Removing it deletes data, so it is KK's decision: the check stays red until he removes the named volume himself (`docker volume rm <name>` on the server), and a runner that sees the hit sends him a card per the HARD RULE. No code removes it.
7. **The 2000-row limit (pre-review 4).** Deleted rows only grow, so far past today's scale the check would stay red with `teardown-volumes-too-many-rows`. Raising it, or reading only rows deleted in the last 90 days once older hits have been cleared, is a checklist line on DEVOS-16.
8. **Owned files (added to M2.5):** `apps/api/src/teardown-volumes-cli.ts`, `apps/api/test/teardown-volumes-cli.test.mjs`, `scripts/server/checks/teardown-orphan-volumes.sh`, `scripts/test/teardown-orphan-volumes.test.mjs`.

5a. **Trust boundary of the shell check (runner B decision, 25 Nov 2026, after Codex PR238-r14; ADR-0013 deadlock rule).** Rounds r3 to r14 each found one more helper output the evaluator could never produce and the script still accepted. The helper is in-repo, tested code that runs the real `evaluateRules`, inside DevOS's own API container; it is not untrusted input, and its own tests (`teardown-rules-cli.test.mjs`) are where evaluator fidelity is proven. So the script's contract is bounded to: (i) shape (one line, exactly the helper's keys, id-shaped ids, the fixed reason codes, its own compact JSON form); (ii) the single-row invariants listed in item 5, all already enforced; (iii) the verdict recomputed from the rows, and the exit code agreeing with it; (iv) the cross-row rules already in place (distinct ids within the rule count, equal complete match sets give equal answers, shared ids in the same relative order). It does **not** re-derive one row's rule effects from the other row: that would mean re-implementing the evaluator in jq (the helper would have to print each rule's effect and gate flag, and the script would re-run deny > require_approval > allow over them), a second copy of M1.7's logic that can drift from the first. An output that passes (i)–(iv) but that the evaluator could not produce, such as r14's (Archive `denied-by` on [a], Restore `allowed-by` on [a, b], observe mode), can only come from a helper bug; that is caught by the helper's tests, not by this script. Codex PR238-r14 (1 medium) is therefore disputed with this reasoning, and later findings of the same class (a cross-row effect contradiction the helper cannot emit) are answered by this item. A finding that the helper itself can emit such output is a helper bug and is always accepted.

## M2.5-b5 decisions (DEVOS-255, 25 Nov 2026, runner B, ADR-0013)

1. **KK's early ask holds the lifecycle lock (from Codex PR239-r21, medium).** `TeardownSweepJob.askPurge` (M2.5-b3) checked the stage, then read cards, grants and counts and raised the card without the lock, so an ask that passed its check could persist a card after a purge and its final expiry. `askPurge` now runs its whole body, from the project read through the raise, inside the new optional `locked` dep, wired in `buildTeardownSweep` to the same store's `withProjectLock` that Archive, Restore and Purge take (production always passes it). An ask that arrives during a purge waits for it (the store's `PURGE_LOCK_WAIT_MS`, as a Restore does) and then answers `not_archived`; a lock that cannot be taken throws, which the route already answers 503 `teardown-store-failed`, and nothing is raised. The purge never calls `askPurge`, so the lock is never nested. The sweep's `project-not-archived` expiry stays as a backstop. **AT1.**
2. **The daily run's raise holds the lifecycle lock on a fresh read (from Codex PR239-r22, medium).** The daily purge-due run (`duePass`) raised its card from the row `listDue` returned, without the lock, so a purge that finished (with its final card expiry) between the due check and the raise, or a Restore and a new Archive in that gap, could leave a pending purge card for a purged row or for an archive not yet due. A lock that cannot be taken counts as a failed raise (`teardown-card-failed`, `purge-due`), so the daily run stays open and the next tick tries again; nothing is raised. The pass never purges, so the lock is never nested. **AT2–AT4.**

3. **Never queue on this process's own running purge (pre-review 1, high, fixed).** The store's `withProjectLock` first waits in an unbounded in-process queue, and a purge may run on past its 10-minute limit holding the lock. So both paths check the job's in-process `purging` set before taking the lock: the early ask answers `purge-already-approved` at once (as in M2.5-b3), and the daily run skips that row (its approved card already blocks a new one). A purge in another process is bounded by the store's database lock wait (`lock_timeout`). **Recorded (pre-review 2, 3):** the `locked` wiring in `buildTeardownSweep` is one line covered by typecheck, not a test of its own; and decision 2 covers a row that was purged or restored and archived again. A purge that *stops* with the row still `archived` sets `stopsOwed` only after it releases the lock, so in that short gap the daily run can still raise a normal purge card for the still-archived project. That card is still valid for that project, so it is not a stale card.

Both paths now build the card, then call the new `lockHeld` dep (wired to the store's `assertLockHeld`, which pings the lock session, as Archive, Restore and Purge already do before each step) and only then write it. A lost lock throws `provision_lock_lost`: the ask answers 503 `teardown-store-failed`, the daily run counts a failed raise and tries again on the next tick, and nothing is raised. The remaining window, between the ping and the write, is the same one every lifecycle step in M2.5-a has, and the sweep's `project-not-archived` expiry stays as the backstop. **Test:** a lost lock raises nothing in either path, and the next attempt raises once.
