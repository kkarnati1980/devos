## Goal
"Done when": **create → purge → scan finds 0.** KK removes a project from the dashboard in two steps. **Archive** stops it and keeps everything for 30 days. **Purge**, only after KK confirms, deletes everything DevOS created for it. A leftover scan then searches every provider for anything still carrying the project's marker or name and must find nothing.

## The two steps
| Step | Who starts it | What happens | Reversible |
|------|---------------|--------------|------------|
| **Archive** | KK (dashboard "Remove project" → Archive, CSRF) or the M4.x lifecycle | 1. Cancel queued runs and stop running ones (M1.5 cancel). 2. Final backup of the live database, if the stack has one (Coolify backup trigger), recorded as a `resource` `backup_schedule/final`. 3. Stop every Coolify application of the project (preview and live). 4. Archive the GitHub repo (`PATCH /repos/{owner}/{repo}` `archived:true`): read-only, nothing deleted. 5. `project.stage = archived`, `archived_at = now`, `purge_after = now + archive window` (setting, default 30 days). | Yes: **Restore** un-archives the repo and moves the stage back to its previous value (stacks stay stopped; the next deploy starts them) |
| **Purge** | Only a KK decision on a purge card (M2.3) | For every active `resource` of the project, in reverse creation order: delete it at the provider (Coolify applications with their volumes → environments → project; backup records and stored dumps; the GitHub repo last), then mark the row `status=deleted`, `deleted_at=now`. Then delete the project's vault app secrets (DEVOS-131). Reset the project's `provision_step` rows. Run the leftover scan. `stage = purged` only when the scan finds 0. | **No** |

## Decisions (builder, recorded per ADR-0013)
1. **Purge is never automatic.** When `purge_after` passes, a scheduled job (daily, 03:10 IST) raises one decision card per project: "Purge project <name>? This deletes its code, stacks, data and backups for good." Options: *Purge now* / *Keep archived another 30 days* / *Restore*. No answer = nothing happens; the card is re-raised once after 7 days. Deleting data is KK's call (rules.md), so the code path to delete is reachable only through an approved card, and the policy action `teardown.purge` is `require_approval` by default.
2. **KK can purge early.** Archive → Purge in the same day is allowed, but only through the same card (no direct delete button). The card names what will be deleted (counts per provider from the inventory) so the decision is informed.
3. **Ownership is checked before every delete.** A resource is deleted only if it still carries the `devos:<project id>` marker at the provider (M2.4 decision 3) **and** the GitHub repo is private. A resource that lost its marker is not deleted; the purge stops with `ownership_mismatch` (non-retryable) and a card asks KK. DevOS never deletes something it cannot prove it owns.
4. **Delete is idempotent; 404 = already gone.** A delete that returns 404/410 counts as done. A delete that times out or returns 5xx is followed by a lookup: gone → done; still there → `delete_unconfirmed` (retryable; the next purge run retries the delete, which is safe because a delete of an absent resource is a no-op). Every call has a timeout (GitHub 15 s, Coolify 30 s), reusing M2.4's transport.
5. **Crash safety.** The purge walks the inventory, not a separate journal: a row is marked `deleted` only after the provider confirms, so a crash at any point leaves the remaining rows `active` and a re-run continues. One teardown job per project at a time, under the same session advisory lock key as provisioning (`hashtext('devos:provision'), hashtext(<project id>)`), so provisioning and teardown of one project can never interleave.
6. **The leftover scan is independent of the inventory.** It does not trust `resource` rows. It searches: GitHub repos of the owner named `devos-<slug>` or whose description carries the marker; Coolify projects, applications and their volumes whose name or description carries the marker or `devos-<slug>`; vault rows with this `project_id`; backup records and stored dumps under `<slug>/`; active `resource` rows; and the project's port allocation. Each hit is listed with provider, kind, id and name. The report is stored (`audit_event` `teardown.scan`, JSON) and shown on the project page. **0 hits → `purged`.** Any hit → stage stays `archived`, the report lists the hits, and a card tells KK in plain words what is left.
7. **Secrets.** Vault app secrets are deleted (row removed, not soft-deleted: a sealed secret of a purged project has no restore value). No secret value is ever read during teardown; deletes are by name.
8. **The project row is kept**, stage `purged`, with its cost history and audit trail (KK's spend reports stay correct). Requirements, specs and run logs stay; they hold no secrets and are small. Removing them is out of scope.
9. **GitHub token permission.** Archiving needs "Administration: read and write" on the fine-grained token; deleting a repo needs the same. If the token lacks it, the step fails `provider_forbidden` with a plain message, and a card asks KK to add the permission (step-by-step, setup wizard). This is checked once by the live probe (AT10) before G2.
10. **Size split** (rules: > ~800 lines or more than one concern → task sub-issues, one PR each, in order):
    - **M2.5-a** `packages/teardown` core: provider delete/stop/archive ops (`teardown-ops.ts`), ownership check, Archive + Restore + Purge runners over the inventory, `provision_step` reset, the leftover scanner and its report. Fake providers + Postgres tests (AT1–AT8). Needs M2.4-a; the Coolify half needs M2.4-c's client.
    - **M2.5-b** wiring: `POST /projects/{id}/archive`, `POST /projects/{id}/restore` (CSRF), the purge card through M2.3 and the run-engine purge job, the daily purge-due job, `GET /projects/{id}/teardown` (state + last scan report), the dashboard panel (AT9). Needs M2.3-b and M2.4-d.
    - **Live probe** (AT10) after both merge and M2.4's AT13 probe has run: it purges `devos-probe-m24`.

## Out of scope
Pause/resume as a product feature (DV-FR-061, M6.1), off-site backup copies (M4.5; the final backup stays on the server until R2 exists), deleting a project's requirements, specs, run logs or cost history, the S4 network and limits teardown beyond deleting the Coolify resources (S4 adds its own cleanup hook and its own scan check).

## M2.5-a split (builder decision, 12 Nov 2026, ADR-0013)
M2.5-a as planned covers four concerns (provider ops, runners, Postgres store, Coolify app/volume teardown that needs M2.4-c). Per the size rule it is built in three PRs, in order:
- **M2.5-a1 (DEVOS-111, this PR):** `packages/provision/src/teardown-ops.ts` (GitHub repo inspect/archive/unarchive/delete, Coolify project inspect/delete, GitHub and Coolify leftover scanners; M2.4's existing functions untouched), `packages/teardown` (Archive, Restore, Purge, `scanLeftovers`, inventory scanner, `TeardownStore` interface, `MemoryTeardownStore` over M2.4's `MemoryStore`). Tests on fake providers: AT1, AT2, AT3 (policy half), AT4, AT5, AT6, AT7, AT8.
- **M2.5-a2:** `PrismaTeardownStore` under the provisioning advisory lock, a backward-compatible migration for `project.previous_stage` (ADR-0011 §10), `teardown.scan` audit rows, the inventory upsert reviving a slug after purge (a deleted row must not block a fresh create, AT7 on Postgres), vault/backup/port scanners, `.github/workflows/teardown-db.yml` with AT1, AT4 and AT7 on Postgres.
- **M2.5-a3 (DEVOS-118):** Coolify environments and host ports, the two kinds M2.4-c1 (DEVOS-109) provisions. Without ops for them, every purge of a provisioned project stops with `unsupported_resource`.
- **M2.5-a3b (follow-up, after M2.4-c2 / DEVOS-120):** Coolify applications and volumes (stop on Archive, delete on Purge, scan) and the final backup on Archive. Split out because applications and volumes are not provisioned until M2.4-c2 (see "M2.5-a3 build notes").

Decisions made in a1:
- **Order:** Coolify → vault → backups → R2 → Cloudflare → GitHub repo last; newest first within a provider. Project vault secrets (not inventory rows) go after all of these (DEVOS-131).
- **No half purges on unknown kinds:** before any delete, every active row must have ops; otherwise `unsupported_resource` and zero deletes.
- **Ownership on Archive and Restore too:** a resource that lost the marker is not archived or un-archived (`ownership_mismatch`).
- **A failed scanner is never "clean":** its error is in the report and the stage stays `archived`.
- **The GitHub scan is bounded** (20 pages × 100 repos); a full last page adds a `scan-incomplete` hit rather than reporting 0.
- **401/403 on any write → `provider_forbidden`** (decision 9), non-retryable; other non-transient HTTP errors → `provider_error`, non-retryable; transient lookup failures → `provider_error`, retryable.
- **One policy check per purge.** `teardown.purge` is checked once, before any provider call; KK's approved purge card covers the whole purge of that project (one decision, one grant). Archive and Restore likewise check `teardown.archive` / `teardown.restore` once.
- **The step journal is reset before the first delete** (pre-review finding 1), so a purge that stops half way and is then Restored never leaves a stale `done` step; the next provision re-creates what was deleted.
- **Archive and Restore prove ownership of every resource before their first write** (pre-review finding 3).
- **GitHub token scope (pre-review finding 2).** GitHub answers 404 for a private repo the token cannot see, so a narrowed token could make a repo look gone. The token must cover all repositories of the owner; the AT10 live probe checks this (it lists the owner's repos and requires `devos-probe-m24` to be visible before the purge), and M2.5-a2 adds the same check to the purge preflight.

## Codex PR48-r1 (12 Nov 2026; 1 high, 1 medium, both accepted)
- **(high) The scan must be complete.** `purgeProject` now refuses with `scan_incomplete` (non-retryable) before any provider call unless its scanners include `inventory` plus one scanner named after every provider that has teardown ops or inventory rows. An empty or partial scanner list can therefore never lead to `purged`. Scanners are wired in code (M2.5-b), never from input.
- **(medium) Only a 404 proves absence.** GitHub and Coolify `inspect` treat only a 404 as gone. A 200 must carry the repo or project object; a 204, an empty 200, JSON `null` or the wrong shape is an inconclusive `bad-response`. The purge then stops with `provider_error`, and the row stays active.
- Tests: the scanner check is refused with 0 calls for three incomplete lists; four inconclusive lookup shapes each leave the repo and its row in place. Result: 13/13.

## Codex PR48-r4 (12 Nov 2026; 1 medium, accepted)
- **The GitHub scan validates every field it matches on.** Each entry needs a string `full_name` and a string `name`, and that name must equal the repo part of `full_name`; `description` must be a string or null. Anything else makes the scan inconclusive (`bad-response`). The report then has an error, and the stage stays `archived`. The Coolify scan checks `description` the same way.
- Test: four malformed shapes (no name, a name that does not match `full_name`, a non-string description, a Coolify object description). None of them can produce a clean scan. Result: 14/14.

## Codex PR48-r5 (12 Nov 2026; 1 medium, accepted)
- **`description` must be present.** It has to be a string or an explicit null. An entry that omits it is inconclusive in both the GitHub and the Coolify scan, because only the marker in the description could identify a leftover with another name. Test: an omitted description is refused for both providers. Result: 14/14.

## M2.5-a2 build notes (DEVOS-117, 12 Nov 2026)
- **`PrismaTeardownStore`** (`packages/teardown/src/prisma-store.ts`) extends M2.4's `PrismaStore`. It takes the same session advisory lock and uses the same inventory and step journal. Every DB call has a 10 s bound.

There is no `project.previous_stage` column and no migration (ADR-0011 §10). This replaces the column proposed in the a1 split note.

The cross-project "revive a slug" case from the a1 note therefore cannot happen. AT7 is the same project provisioning again after its purge. M2.4's `recordResource` already reactivates the project's own deleted rows.
- **Tests:** `test-db/teardown.test.mjs` covers AT1, AT2, AT4, AT6 (vault) and AT7 on Postgres. It runs in the new `.github/workflows/teardown-db.yml`, in CI only, because Prisma's engines cannot be downloaded in the runner sandbox.

Ports are inventory rows (`coolify/port`, M2.4-c1), so the inventory scanner covers them. Backup dumps live on the server disk and are scanned by the M2.5-b job on the server.
- **GitHub token-scope preflight** (`githubTokenScopeCheck`, passed in `purgeProject`'s new `preflight` list): the token must list at least `public_repos + owned_private_repos` (from `GET /user`) owned repos, on one pinned token snapshot. Otherwise the purge stops with `provider_forbidden` before any delete, because a narrowed token would answer 404 for repos it cannot see (a1 pre-review finding 2). M2.5-b wires it in for every purge.

## Codex PR55-r1 (12 Nov 2026; 1 high, accepted)
- **The preflight checks the account as well as the scope.** `githubTokenScopeCheck(gh, { owner })` now requires the token's `GET /user` login to equal the repository owner, case-insensitive, on the same pinned snapshot. `owner` is required and validated.
- **Why it matters.** A token for another account sees its own counts and listing match. Without the owner check, the project's private repo would answer 404, look gone, and the scan would search the wrong account.
- **Test.** A replacement account with matching counts fails the preflight with `provider_forbidden`, with nothing reset and nothing deleted. A missing owner throws. Teardown tests: 18/18.

## M2.5-a3 build notes (DEVOS-118, 12 Nov 2026)
- **Split (runner decision, ADR-0013).** a3 as planned covered environments, applications, volumes and the final backup. Only environments and ports exist today (M2.4-c1); applications and volumes come with M2.4-c2 (DEVOS-120). Building ops for resources that are not yet provisioned would mean guessing their inventory shape. So a3 ships the environment and port ops now (they unblock purge for every provisioned project, a G2 blocker), and a3b takes applications, volumes and the final backup after DEVOS-120.
- **`coolifyEnvironmentOps`** (`packages/provision/src/stack-teardown-ops.ts`). External id `<project uuid>/<env>`, `env` ∈ {`preview`, `production`} and equal to the row's name; anything else is refused before any call. Ownership is the parent Coolify project's marker, the same rule M2.4-c1 used to create them (environments have no description). `inspect`: parent 404 → gone; a 200 must carry the same project uuid; the environment list must be a 200 array of named entries (M2.4-c1's `listEnvironments`, now exported unchanged), otherwise the lookup is inconclusive (`provider_error`, row stays active). Delete: one `DELETE /api/v1/projects/{uuid}/environments/{name}`; 404/410 is "already gone". No archive op: an environment holds applications, which a3b stops.
- **Coolify endpoint to confirm live.** M0.4 recorded environment list and create, not delete. The delete path follows Coolify v4's API (`/projects/{uuid}/environments/{environment_name_or_uuid}`). Coolify answers an unknown route with 404 too, so a 404 on this DELETE counts as "already gone" only when a fresh environment list no longer shows it; otherwise the purge stops with `provider_error` before the project delete and nothing is marked deleted (pre-review finding 1). A wrong path therefore shows up on the first live purge (M2.5-b AT10 on `devos-probe-m24`) as a stopped purge, not as a silent pass; the fix would be one line in this file.
- **`coolifyPortOps`.** A port is an inventory row only (nothing exists at a provider). `inspect` validates the port number (1000–65535) and reports nothing to delete, so the purge marks the row `deleted` without a provider call. The row is kept, so a purged project's port is never handed to another project or reused on re-provision (M2.4-c1's no-reuse rule).
- **Order.** Newest first within Coolify: environments, then the project; the repo last, as decision "Order" requires. Host ports are released after everything else (pre-review finding 2): a port is a reservation, so a purge that stops half way and is then Restored keeps its stable ports.
- **Pre-review (1 medium, 1 low; both fixed):** (1) a 404 on the environment DELETE is confirmed by a fresh list; (2) ports are released last. Tests: a DELETE answering 404 while the environment is still listed stops the purge with no row marked deleted; the ownership-mismatch and inconclusive-list tests also assert the port rows stay active.
- **Scan.** No new scanner: an environment cannot outlive its Coolify project, which `coolifyScanner` already finds by name and marker, and ports are covered by the inventory scanner.
- **Tests** (`packages/teardown/test/stack-teardown.test.mjs`, 7): AT1 with environments and ports (purged, 4 deletes in the right order, every row deleted); purged ports are not reused on re-provision; an environment under a project that lost its marker is not deleted (`ownership_mismatch`); an environment or its project already gone is marked deleted with no delete call; an inconclusive environment list stops the purge with the row active; malformed environment and port ids are refused with 0 calls. teardown 25/25, provision 34/34.


## DEVOS-131 build notes (12 Nov 2026, runner B, ADR-0013)
**Vault secrets in the purge.**
- Vault app secrets are not inventory rows, so before this nothing deleted them and `vault` was not a required scanner. Now:
  - `TeardownStore.deleteProjectSecrets(projectId)` deletes every `vault_secret` row with this `project_id`. It is a **hard delete**: `vault_secret` has no soft-delete column, keeping the ciphertext of a purged project is a liability, and the purge itself is KK's decision on a purge card (decision 1, M2.3). No schema change.
  - It runs **after every inventory resource is confirmed deleted** and before the scan, under the lock (re-checked first). So a purge that stops half way, then Restore, keeps the secrets its remaining apps still need.
  - `vault` is always in the required scanner set (`scan_incomplete` otherwise, before any provider call). The scanner stays independent of the delete (decision 6): a secret that survives, for example one written by a racing writer, is a hit and the stage stays `archived`.
  - The delete and a `teardown.secrets_deleted` audit event (count and names, never values) commit in one transaction, as every vault mutation does (pre-review r1, medium). `PurgeResult.secretsDeleted` reports the count. `MemoryTeardownStore` has `secrets` and a matching `vaultScanner()` for tests.
- **One pinned GitHub token per purge** (the issue's second bullet) was already delivered in the M2.5-a2 pre-review (`pinnedGitHub`, "One token snapshot per purge" above). M2.5-b must build the purge's GitHub ops, scanner and preflight from that one client. Nothing more is needed here.
- **M2.5-b** must pass `vaultScanner(db)` in every purge's scanner list.

**Tests:**
- `test/teardown.test.mjs`:
  - secrets are deleted after every provider delete, and only this project's;
  - a purge that stops on a provider delete keeps the secrets;
  - a purge without the vault scanner is refused with 0 calls;
  - a surviving secret keeps the project archived.
  - Result: 28/28.
- `test-db/teardown.test.mjs` (CI, `teardown-db`):
  - on Postgres, the purge deletes 2 secrets of the project and leaves another project's, and ends `purged`;
  - the AT6 leftover test now simulates a secret that survives the delete.
