## Design

### R2-a In-image helper (`packages/run-engine/dist/g1-cli.js`)
Runs inside the deployed **worker** container, started by the checks with
`docker exec <worker> node deploy/with-db-url.mjs node packages/run-engine/dist/g1-cli.js <cmd>` (R1's `with-db-url.mjs` builds `DATABASE_URL` in the container; nothing secret crosses `docker exec`). It prints **one JSON line** and exits 0 pass, 1 fail, 2 usage, 3 skipped. An error is reduced to a code (`config-*`, `prisma-P####`, `error-<errno>`, `error`); a message, URL or value is never printed.

| Command | Reads / writes | Pass | Skipped (3) | Fail (1) |
|---|---|---|---|---|
| `caps` | reads `app_settings` | `caps_confirmed_at` set and the Anthropic, OpenAI and default-project caps all > 0 | no row, or caps never confirmed (before H9) | a cap ≤ 0 or not a number |
| `receipts` | reads `policy_decision`; `PolicyEngine.verify(chain)` with the worker's `DEVOS_POLICY_HMAC_KEY` for every distinct chain | every chain valid (gapless seq from 1, prev hash, hash, HMAC) | no receipt yet | the first invalid chain, with its M1.7 error code and seq |
| `probe-start` | writes rows of the `g1-probe` project only (R2-e); enqueues one job | a probe run is created and queued; prints its run id | any run of another project is `queued` or `running` (`worker-busy`) | the probe project is paused; a probe run younger than 15 min is unfinished; or the enqueue failed — then the new run is closed `failed` (`probe-enqueue-failed`) at once, and an unfinished probe run older than 15 min (`PROBE_STALE_MS`, a lost job) is closed `failed` (`probe-stale`) before the check, so a lost job never blocks later checks (PR21-r1) |
| `probe-guard <runId>` | reads the run, the queue's active jobs, the worker's `DEVOS_WORKER_CONCURRENCY` | the last gate before the kill (PR21-r1): the worker runs one job at a time, the queue's **only** active job is the probe, no other project's run is `running`, and the probe is `running` at turn 1–2 of 4 (a turn left, so its single slot stays taken until the kill a moment later) | any of these does not hold: `run-resume` exits 3 and kills nothing; the probe finishes on its own | bad run id |
| `probe-status <runId>` | reads the run, its events, last checkpoint, reservations, cost entries | see R2-b | the run is still `queued`/`running` | see R2-b |

### R2-b `run-resume.sh` and the probe adapter
- **Probe adapter** (`ProbeAdapter`): deterministic, in-image, calls no provider. It answers only to the reserved model name `devos-g1-probe` (`PROBE_MODEL`); 4 turns, 3 s apart, each a `usage` event (1 input + 1 output token). It resumes after the checkpoint's turn (never repeats a turn) and its result always settles, also when the engine stops reading. Its reported cost is a ledger-only 1 µUSD per turn (not an estimate): enough to exercise reconcile and `cost_entry`, and nothing is billed.
- **Probe gate** (`ProbeGateAdapter`, `probeGated()` in the worker): each run's adapter is chosen at `start` from the run's own `model` (the database row): `devos-g1-probe` → the probe; anything else → the adapter the worker had in R1 (today `UnconfiguredAdapter`, failing non-retryable). Nothing an outside party writes can select the probe.
- **The probe run:** project `g1-probe`, task `g1-probe run-resume` (kind `test`), role `tester`, `max_turns` 10, `max_seconds` 300, `max_cost_usd` 0.01, queued with `reserveUsd` 0.001 and `reserveTokens` 1,000. The reservation is a tenth of the ceiling because a hard-killed attempt is charged its **whole** reservation on recovery (M1.5 rule 9, fail-closed); the resumed attempt still fits.
- **The check** (≤ 105 s, under the agent's 120 s): find the running container labelled `io.devos.service=worker` (skipped if none, or no `docker`) → `probe-start` → poll `probe-status` every 2 s until the run has checkpointed ≥ 1 turn (fail after 30 s, or if it ends before the kill) → `probe-guard` (skipped, no kill, unless the worker can be holding only the probe) → `docker kill --signal KILL` (no drain) → `docker start` (fail with a plain message if the worker does not come back) → poll until the run ends. BullMQ moves the stalled job back once its lock expires and a stalled check sees it; the engine recovers the open attempt and resumes from the checkpoint. With BullMQ's defaults (lock 30 s, check 30 s) this took about 90 s in CI, too long for the 120 s check limit, so the worker sets **lock 15 s and stalled check 5 s** (`LOCK_DURATION_MS`, `STALLED_INTERVAL_MS`): a killed worker's run resumes in about 20 s. This also shortens recovery after a real crash (OOM, host restart).
- **Pass** (`probe-status`): the run `succeeded` with all 4 turns; a `status: resumed` event exists; the event `seq` is gapless from 1; **no reservation is left `reserved`**; there is at least one `cost_entry`; the sum of `cost_entry.usd` equals the sum of `actual_usd` over the reconciled reservations, compared **exactly in integer microdollars** parsed from the decimal strings (PR21-r1; one probe turn is 1 µUSD, so a tolerance would hide a duplicate turn charge) (each reservation charged exactly once, no double charge); and the total is ≤ `max_cost_usd`.
- **Note on the issue's wording "one cost_entry":** after a hard kill, M1.5's fail-closed recovery writes one `cost_entry` for the killed attempt (its whole reservation) and one for the resumed attempt. The check therefore proves *one charge per reservation*, which is what "no double charge" means under ADR-0006; a graceful stop (R1 drain) leaves one entry.

### R2-c `caps-saved.sh`, R2-d `receipt-chain.sh`
Each finds the worker container the same way (skipped without it), runs its helper command under `timeout 60`, prints the JSON line, and returns the helper's 0 or 3 unchanged; every other exit (fail, usage, timeout, docker error) is 1. `caps-saved` stays skipped until KK confirms caps in the wizard (H9, DEVOS-36). The check scripts are self-contained (the server agent runs every `checks/*.sh`, so a shared library file would itself run as a check).

### R2-e Data written on the server
Only `run-resume` writes, and only rows of the dedicated `g1-probe` project: the project and its task once, then one `run` per check with its events, checkpoints, telemetry, one or two receipts, reservations and cost entries (a few µUSD of ledger-only cost, plus the killed attempt's 0.001 fail-closed charge, all on `g1-probe`). This is the evidence the G1 gate asks for; no other project's rows are read for writing, and no row is updated or deleted outside `g1-probe`. The provider caps count these ledger entries, at most about USD 0.001 per deploy.

## Not in R2
Cert renewal and API TLS (DEVOS-81, R3) · real provider runtimes in the worker (M3.x) · a dashboard view of check results (M2.x) · an outside probe of the cloud firewall (G1 note on `dashboard-tailnet-only`).
